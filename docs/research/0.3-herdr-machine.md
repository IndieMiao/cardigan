## 0. 结论

### 0.1 D9 建议：运行时基线改用 `herdr-core`（`hc`）0.1.x，Herdr 0.9.x 降为过渡备选

理由（按对 Cardigan 的影响排序）：

1. **状态来源从"看画面"变成"程序自报"。** `herdr-core` 只认 OSC 7501（Program Status Protocol），不做画面识别、也不维护"已知 Agent 名单"。而 §6.8 列出的最大风险（`done`/`blocked` 靠画面检测可能误判）正是 0.9.x 的实现方式。实测 0.9.3 对本次使用的主力 Harness **Pi** 只能落到兜底规则（`agent explain` → `rule: none`、`fallback_reason: default_known_agent_idle_fallback`，且 `herdr integration status` 里 `pi: not installed`）；而 Pi 1.5.0 自带 `program-status-reporter`，**原生上报 OSC 7501**（`working`/`blocked`/`done`/`error`/`idle`）。换成 core 后 Pi 的状态是程序上报，不需要装 Herdr 扩展。
2. **有推送事件，不用轮询。** core 的 `events.subscribe` 给快照 + 增量事件 + 每 15 s 心跳 + 落后时 `missed` 快照，`seq` 单调；0.9.x **没有事件订阅**（§11.3 已核实），只能轮询 `api snapshot`。这直接决定 §13.9 心跳超时判定和 §6 门铃去重的实现难度。
3. **API 有兼容承诺。** core 的 API 是 OpenRPC + JSON Schema（`hc schema`，32 个方法），"API only grows"，破坏性改动要换 protocol generation；状态为 preview（protocol generation 1, 0.x）。0.9.x 只有 CLI/socket API 与 protocol 22，没有面向第三方客户端的兼容承诺，而且它是 TUI 产品，我们只用它的一小部分。
4. **who owns worktree：** core 完全不碰 Git（没有 worktree 命令）。这反而与 §12 一致——worktree 由主机的 Git 服务创建，运行时只负责"在某个目录里开一个终端"。0.9.x 的 `worktree create` 会顺带创建 workspace、把 worktree 放到 Herdr 自己的基目录，等于把 §12 的职责分给了运行时。
5. **多机模型更整齐。** core 用一个本地 core 聚合所有机器，地址是 `machine/t7`，`run`/`exec`/`send`/`read`/`wait`/`file` 都能 `--on`，远程终端的事件也进同一条事件流；0.9.x 的 `--machine` 只覆盖一部分命令，而且不能和 `--session` 叠加。

代价与前提（这些必须写进 §11，也是回退的触发条件）：

- **不支持的 Agent 就没有状态。** Claude Code 2.1.318、Codex 0.161.0 都不上报 OSC 7501（0.9.x 靠 22 个内置清单 + 画面/hook 识别）。要么在 Launch Profile（§10.2）里加一个极薄的状态 shim（读 Agent 的 hook/事件，转成 OSC 7501），要么先接受 `status=null` 并完全依赖 Agent 侧 `finish_run` 自报（§6.3 本来就要求这个）。
- **core 还在 preview（0.1.x，2026-10-16 首建仓，2026-11-02 0.1.17）。** 需要锁版本（`hc update --version`）并接受升级节奏快。
- **core 没有 worktree / 没有"Agent 名单" / 没有 agent session 追踪。** `resume_or_replace` 只能做到 `--keep`（进程丢了换一个 shell，绝不重跑命令）+ 用 Agent CLI 自己的 resume 参数重建，Session 身份要由控制面自己记。

**回退触发条件**：如果 0.6 决策时要求"Codex / Claude Code 的自动状态识别零改造"，或 core 在 M1 期间出现影响 `run`/`send`/`events` 的破坏性变更，则 Phase 1 基线退回 Herdr 0.9.x（0.9.5，锁版本），并把 Runtime Adapter 的 status 端口实现换成"画面检测 + 兜底规则"。

不管选哪代，隔离方式相同：Runtime Adapter 只暴露 §11.1 的 7 个接口 + `RuntimeRef{machine_id, runtime_machine, terminal_ref, agent_name, worktree_path?, branch?}`，不把 Herdr 的 workspace/tab/pane 概念漏进 domain。

### 0.2 换代关系（一句话）

`herdr-core`（`hc`，无界面的运行时）+ `herdr-app`（桌面客户端）是官方新的两条仓；它们与 Herdr 0.9.x（TUI，单二进制自带 server + 客户端）是**并行的两条产品线，不共享状态**：0.9.x 不会被下架，但两者的 config、session、Agent 都不互通，也没有迁移指南。

### 0.3 B 部分要点（Herdr 0.9.x 实测）

- 可用。`local` 与 `worker-a` 上 §11.1 的全部动作都能跑通；`worker-a` 的 Herdr server 是 **0.9.2**，与 `local` 的 0.9.3 客户端 protocol 22 兼容，命令全部正常。
- 隔离：`--session <名字>` 能给 `local` 一个完全独立的 server + socket + state（本次用 `p0spike`，用完已删除）；**但 `--machine` 不能与 `--session` 叠加**（`error: --machine cannot be combined with other launch options; it uses the saved machine's session`），所以远程只能在用户的默认 session 里操作"自己创建的 workspace / worktree / pane"，结束时全部清理（远程 workspace 数 24 → 24）。
- 关键风险（比 §6.8 写的更严重）：**门铃送达无法从调用方判断**。实测 "杀掉 ssh 桥" 和 "SIGTERM 杀掉 herdr 客户端" 两种中断下，prompt 都已经送达并被执行了一次，而调用方只看到 `exit 1` / `ConnectionAborted`。另外**Agent 忙碌时再发一条 prompt 不会排队成独立回合**，两条文本落进同一回合，模型只听了后一条（实测只回了 `TWO_R`，`SLOW_R` 没有出现）。这两点说明 §6 的"门铃只是提示 + Run 幂等"是必须的，而且 prompt 正文里要带可判重的信息（例如 `seq`），不能假设"发一次 = 一次回合"。
- `interrupt` 在 0.9.x 没有独立命令，要自己用 `agent send-keys <target> esc`；§11.2 的映射表缺这一行。
- `pane run` 会把命令行**写进当前 pane 里的 Agent TUI**（不是 shell）。预研中因此误给远程 Pi 送进了一条命令文本；要在 pane 里跑 shell 命令，必须用 shell pane，或用 `--machine` 之外的独立连接。此坑需写进文档。

| 项 | 状态 | 原因 |

## 2. A 部分：换代评估

### 2.1 `herdr-core`、`herdr-app` 是什么

| | 仓库/安装 | 形态 | 一句话 |
|---|---|---|---|
| Herdr 0.9.x | `herdrdev/herdr`，`herdr` | 单二进制 TUI：自带 server + TUI 客户端 | "给 Agent 用的 tmux"：workspace/tab/pane、内置 22 种 Agent 识别、`--machine` 多机、插件 |
| herdr-core | `herdrdev/herdr-core`，`hc` | 无界面运行时（core + holder 进程） | 只跑终端：`hc run/send/read/wait/interrupt`、OSC 7501 状态、`events.subscribe`、OpenRPC API、`--on <machine>` 多机 |
| herdr-app | `herdrdev/herdr-app`，`herdr-app` | 桌面客户端（Linux/macOS/Windows） | core 的一个客户端：spaces、agents 侧栏、peek、layout/mod（JavaScript 面板）、`herdr-app --skill` |

关系：**并行的两条产品线，同一个组织，状态不互通**。

- `herdr-app` 自己不起终端，所有终端都在 `herdr-core` 里；`herdr-app` 拒绝低于其源码 `distribution/core-version` 的 core。
- 0.9.x 的 server 与 core 是两个不同的 server：0.9.x 的 session/config/Agent 不会出现在 app 或 core 里，反之亦然。社区记录（`herdr-app#96`、第三方迁移文章）与官方两套文档（`herdr.dev/tui/` vs `herdr.dev/`）都印证这一点。
- **没有迁移指南。** 官方文档索引（`https://herdr.dev/llms.txt`）里只有 0.9.5 的 TUI 文档；core/app 的文档在各自仓库的 `docs/` 与 `schema/`。两代之间没有"导入 0.9.x session"的路径。
- **0.9.x 没有宣布停止维护。** 0.9.5 仍是当前 stable（2026-10-14 发布），仓库最后一个提交 2026-10-29；`herdr.dev/tui/` 仍是独立产品页。措辞上应写"官方同时维护两代，0.9.x 定位为 TUI 产品，core/app 定位为新的 app+runtime 组合"，不要写"0.9.x 已弃用"（无证据）。

### 2.3 §11.1 接口在两代上的对照

图例：✅ 直接支持；🟡 需要控制面配合或组合命令；❌ 不支持。

| §11.1 接口 | Herdr 0.9.x（实测 0.9.3） | herdr-core 0.1.17（文档 + 本机试用） |
|---|---|---|
| `provision(assignment, role, machine)` | ✅ `herdr [--machine M] worktree create --cwd <base> --branch <branch> [--base <ref>] [--path <dir>] [--label <text>]` → 返回 `workspace`/`tab`/`root_pane`；再 `agent start <name> --kind <kind> --pane <id>`（名字全局唯一，支持 `-- [AGENT_ARG]...` 透传 resume 参数） | 🟡 core 不建 worktree：控制面（§12 Git 服务）自己 `git worktree add`，再 `hc run --bg --name <全局唯一名> --cwd <wt> --on <machine> --label assignment=<id> <template> "<task>"`；`templates` 提供角色提示词 + 启动命令 |
| `wake(ref, doorbell)` | ✅ `agent prompt <target> <text>`；`target` 可以是唯一 Agent 名或 pane id。**blocked 时直接拒绝**（`agent_blocked`），提交后 5 s 内没出现 `working`/`blocked` 则 `agent_prompt_stalled`；`--wait` 不区分回合 | ✅ `hc send <t> <text> [--wait] [--if idle\|working] [--force]`；`--wait` 等"本次 send 开启的那个回合"，返回 `{started, status, turn}` |
| `status(ref)` | 🟡 `agent list` / `agent get <target>`（必须给 target，**不接受 `--json`**）/ `api snapshot`（一次给全 workspaces+tabs+panes+agents+layouts+version+protocol）。字段：`agent_status ∈ {idle, working, blocked, done, unknown}`、`state_change_seq`（server 级）、`completion_seq`、`revision`（pane 级）、`interactive_ready`。**没有事件订阅，只能轮询** | ✅ 三档：`hc get <t>`（单终端快照）、`hc ls`、`hc events`（`events.subscribe`：快照 + `created/lost/restarted/status/turn/title/labels/size/foreground/finished/removed/doc` 事件，15 s 心跳，落后给 `missed`）。字段：`state ∈ {live, finished}`、`status ∈ {idle, working, done, blocked, error}`（OSC 7501 原样）、`turn`、`keep`、`labels`、`reason`（`exited/killed/server_stop/host_shutdown/holder_lost/stopped_by_restart/signaled`）、`foreground{cwd,argv}` |
| `interrupt(ref)` | ❌ 无独立命令；🟡 用 `agent send-keys <target> esc`（或 `ctrl+c`）自己组合 | ✅ `hc interrupt <t> [--timeout s]` → `{"key":"esc","outcome":"stopped"}` |
| `resume_or_replace(ref)` | 🟡 在同一 worktree 里 `agent start` 一个新 Agent，resume 靠 `-- [AGENT_ARG]...` 透传给 Agent CLI；Herdr 记录 `agent_session`（`pane report-agent-session`） | 🟡 `hc run --keep`（进程丢了原地换一个新 shell，**绝不重跑原命令**，恢复目录取最后一次观测到的 cwd）+ Agent CLI 自己的 resume 参数；core **不追踪 agent session 身份**，交接摘要由控制面生成（§13.9） |
| `human_entry(ref)` | ✅ Herdr 客户端里的机器名 + workspace；`--machine M workspace focus <id>`（未实测） | ✅ `hc attach <machine>/t7`（`attach` 支持 `--observe` 只看不动），或 `herdr-app` 里点该终端；地址形如 `t7` / `machine/t7` |
| `release(ref, {force})` | ✅ `worktree remove --workspace <id> [--force]`：干净时成功；脏时 `dirty_worktree_requires_force`（exit 1）；`--force` 强制删除（详见 §3.2） | ❌ 没有 worktree 命令。运行时侧只有 `hc kill <t>`（结束程序）与 `hc rm <t>`（移除已结束终端）；**worktree 清理归 §12** |

补充（两代都有、但 §11 没写的）：

- 0.9.x：`pane send-text/send-keys/wait-output/run`、`agent rename/focus/read`、`integration status`、`pane report-agent`（Agent 可以自己上报生命周期）。
- core：`machine.exec`（远程一次性命令，拿精确 stdout + exit code）、`file.read/write/edit`（远程读写）、`doc.get/doc.set`（带版本的乐观并发 KV，属于 API 层，可放控制面元数据）、`put`（把文件放到终端所在机器）。

### 2.4 0.9.3 → 0.9.5 里影响 §11 的改动

只读 CHANGELOG（计划禁止 `herdr update`）：

- **0.9.4**
  - Agent 状态识别：Antigravity / Grok "回到提示符即 idle，即使它自己的后台任务还在跑"（说明画面识别的判定规则仍在细化，误判是常态面）。
  - `Ctrl+Z` 挂起再 `fg` 后保持 Agent 名字与已保存会话（`agent` 身份跟着 pane，进程被挂起时名字不丢）。
  - 远程相关：SSH agent 转发不再每秒被调用（"could eventually break SSH and Git authentication"）；远程侧边栏状态/折叠/排序在重连后保留；切换机器时快速切 workspace 不再被取消。→ 与 §13.9 的"失联/重连"直接相关，**多机可靠性在 0.9.4 有实质修复**。
  - 会话保存改为先写盘再替换（崩溃/断电不会留下坏存档）；Mac 重启、Windows 关机时保存 Agent 会话。
  - `--machine`/API 表面本身没有新增或删除命令。
- **0.9.5**
  - **Codex 不再安装 turn hooks，状态改回画面检测**（`herdr integration install codex` 需重装到 v8）。→ 这条正好踩在 §6.8 的风险上：Codex 的状态在 0.9.5 又变成画面判断。
  - Claude Code 在具名 session 里的提问能显示为 `blocked`。
  - 输入法/前缀键修复。

结论：0.9.3 → 0.9.5 没有删除 §11 用到的任何命令；有两处直接相关的语义变化（Codex 状态来源、多机重连可靠性），若继续用 0.9.x 应升到 0.9.5 并把"Codex 状态来自画面检测"写进 §11.3。

### 2.5 herdr-core 隔离试用（实测）

隔离方式：不装进 `PATH`，不碰用户配置与用户 server。

```sh
mkdir -p /tmp/hc-spike/bin && cd /tmp/hc-spike
curl -fsSL https://releases.herdr.dev/core/latest.json -o latest.json   # version 0.1.17
curl -fsSL https://releases.herdr.dev/core/0.1.17/herdr-core-linux-x86_64.tar.gz -o hc.tar.gz
sha256sum hc.tar.gz   # 与 manifest 中 linux-x86_64 的 sha256 一致
tar -xzf hc.tar.gz && ln -sf /tmp/hc-spike/herdr-core /tmp/hc-spike/bin/hc

export PATH=/tmp/hc-spike/bin:$PATH \
       XDG_STATE_HOME=/tmp/hc-spike/state \
       XDG_CONFIG_HOME=/tmp/hc-spike/config \
       HC_SESSION=spike          # 独立 session，独立 socket 与 state
```

试用记录（结论用，全部在隔离目录内）：

```sh
hc server status
# {"core":{...,"version":"0.1.17"},"live":0,"finished":0}

hc run --bg --name demo bash
# {"address":"t1","agent":"bash","cwd":"/tmp/hc-spike","name":"demo","state":"live","turn":0}

hc get demo
# {"address":"t1","state":"live","status":null,"reported":false,"turn":0,
#  "labels":{},"keep":false,"parent":null,"foreground":{...},"cols":200,"rows":120,...}

hc label demo assignment=C-0/W-0      # 标签是 core 的一等公民，ls/events 都支持 --label 过滤
hc send demo "echo hello-cardigan"    # {"started":null,"status":null,"turn":0}
hc read demo --lines 5                # 输出里能看到 hello-cardigan

# OSC 7501 自报状态（假 Agent，只 printf 转义序列）
hc run --bg --name fake ./fake-agent.sh
hc get fake | jq '.status'            # {"app":"fake-agent","state":"working"}；之后 blocked → idle
hc events --json                      # 先给快照，再给 {"method":"event","params":{"type":"status",...}}

# 故障码是稳定枚举
hc send t99 hi         # {"error":{"kind":"not_found",...}}  exit 3
hc send fake hi        # {"error":{"kind":"finished",...}}   exit 11
hc send long x --if idle   # {"error":{"kind":"status_mismatch"},"t4 is working, not idle"} exit 10

hc interrupt long     # {"key":"esc","outcome":"stopped"}，之后 status 变 idle、turn=1
hc wait fake          # {"ended":true,"reason":"exit","exit_code":0,"turn":1}
hc schema --json | jq '.methods|length'   # 32
```

两条值得注意的观察：

- `hc` 的读命令会**自动拉起 core**：先 `hc server stop`，再 `hc ls` 或 `hc server status`，core 会以新 pid 起来（`uptime_ms` 只有 10 ms）。所以"探测存活"不能顺便产生进程，Adapter 探活要先看 socket 是否存在。
- 终端记录里 `agent` 字段是**程序名**（`bash`、`fake-agent.sh`），不是品牌识别；core 不做 Agent 名单匹配。这对我们是优点（Pi 自报就够），也意味着"只跑了个 shell"和"跑了个 Agent"在 core 看来只有 `status` 有无之分。

## 3. B 部分：Herdr 0.9.x 多机验证

### 3.1 隔离方式（计划第 1 步）

```sh
herdr --session p0spike --machine worker-a agent list
# error: --machine cannot be combined with other launch options; it uses the saved machine's session
```

- `local`：可行。`herdr --session p0spike status server` 给的是**另一个 socket**
  （`~/.config/herdr/sessions/p0spike/herdr.sock`），起法：`nohup herdr --session p0spike server &`。

### 3.3 故障表现

| 场景 | 做法 | 观察到的表现 | 恢复后 |
|---|---|---|---|
| 向不存在的 Agent 发 prompt | `agent prompt nosuch-agent "hi"`（`local` 与 `worker-a` 各一次） | `{"error":{"code":"agent_not_found","message":"agent target nosuch-agent not found"}}`，exit 1，耗时 ~0.2 s | 无需恢复 |
| 向不存在的 pane 发 prompt | `agent prompt w9:p9 "hi"` | 同上 `agent_not_found`（pane 不是 Agent 时也按 target 解析失败） | 无需恢复 |
| 调用中断（ssh 桥被杀） | 起 `herdr --machine worker-a agent wait …`，再 `kill -TERM <该调用的 ssh 子进程>` | `Error: Custom { kind: ConnectionAborted, error: "machine 'worker-a' (session default): ssh bridge exited with exit status: 255" }`，exit 1；客户端进程随即退出 | 下一次 `--machine` 调用正常（0.2 s），无残留 |
| 发送中途断链 | 起 `agent prompt coder-c0-w0 "只回复 DROP2_R"`，0.2 s 后杀 ssh 子进程 | 调用方拿到同一个 `ConnectionAborted`（exit 1）；**远程 Agent 实际收到并只回答了一次**（`agent read` 里只有一条 `DROP2_R`，`state_change_seq` 只前进一次） | 后续调用正常 |
| 客户端进程被杀 | 起同名 prompt，直接把 herdr 客户端 `SIGTERM` | 调用方 exit 143、无错误文本；**远程 Agent 同样收到并回答了一次**（`DROP_R` 只有一条） | 后续调用正常 |
| 断网期间查询 `agent list` | 与上面同一次断链窗口内 | CLI 路径**没有缓存**：调用直接失败（`ConnectionAborted`），不会返回旧状态。变灰的缓存只存在于 TUI 客户端（本次未动用户界面，未验证） | 后续调用正常 |
| Agent 忙碌时连发两条 prompt | 先发 `sleep 12 → 回复 SLOW_R`，不等待，立刻发 `只回复 TWO_R` | 两条都返回成功（第二条返回 `agent_status:"working"`）；**两条文本落进同一个回合**，模型只执行了最新的：`agent read` 里只有 `TWO_R`，`SLOW_R` 从未出现；`agent wait` 12.5 s 后返回 `done` | 无异常 |
| 长任务 + 长超时 | `agent wait --until idle --timeout 180000` 等一个跑 3 轮、其中一轮含 `sleep 20` 的 Pi 任务 | 180 s 用满后返回 `{"error":{"code":"timeout"}}`，exit 1；但紧接着 `agent read` 显示三轮回执**都已产出**，随后 `agent list` 是 `done`。→ 超时不能作为"失败/未完成"的证据 | Agent 正常，状态后续变 `done` |

补充：`worker-a` 的 Herdr server 停止与整机不可达两项未做（原因见 §0.4）。
