# 0.2 现有看板项目回溯

- 日期：2026-10-27
- 对应：[Phase 0 计划](../plans/phase-0.md) §3 · 0.2
- 执行：Claude（统计脚本与汇总）；两个 Claude 子 Agent（看板抽样标注）；Codex gpt-6.1-sol（门铃回复分类、单 Agent 对照分析）
- 脱敏：本文不含项目名、人名、机器名、卡号、路径和业务内容。原始数据和逐条标注放在仓库之外。

## 结论

1. **PM 的主对话确实被门铃淹没，§7 的前台、后台拆分有充分的数据支持。**
   - 14 天里 PM 收到门铃 3918 条，你自己的消息只有 464 条。
   - PM 处理门铃后，往你的对话里写了 3853 段汇报。
   - 随机抽 300 条逐条判断：82.7% 不需要你做任何事；需要立即提醒你的只有 6%。
2. **门铃本身几乎不带信息**：91% 是同一句"某卡有更新，请看卡"，PM 每处理一条平均要调用 4.9 次工具。这印证了 §7.2："能用规则处理的事件，不应该交给 PM 判断。"
3. **Needs You 要新增一类"待你执行的操作"。** 需要你介入的门铃里，一半是真正的拍板，另一半是只有你能做的操作，例如执行需要 root 的命令、点停止、回传截图。现在的模型只有 Decision，这一半会被漏掉。
4. **时间线条目之间需要引用关系。** 两个项目分别有 30 张以上的卡在用"评论 ID 前 8 位"互相引用，而且经常跨卡。
5. **交付和审核必须绑定到版本（commit SHA 或产物哈希）。** 实际起定位作用的是 SHA，写了分支的交付只有 18%–21%；有 29 张卡出现"批准在新推送后失效"。
6. **拍板几乎不保留你的原话**：记录决定的评论里，带原话的只有 8%–28%。常见的是"你在别的渠道回复 → PM 转述"，以及一次批准多条、PM 代批、事后撤回。
7. **大量运行状态被写成了评论。** 项目 B 的普通评论中，约 58% 是巡检、签收、ETA、等待说明这类运行状态，不应该进时间线。
8. **卡片状态和真实进度普遍对不上**：卡在待办状态下就已经做完，完成后还在继续派活，发版后再批量回填完成状态。
   - 中间状态（待办、进行中、审核中）由工作项推导出来。
   - **"完成"不由规则自动触发**：执行人发起完成申请，指定角色审核通过后才更新（2026-10-29 用户意见）。
9. 另有若干模型没覆盖的模式：分步放行、共享资源排队、规格版本、长期约束、发版、维护窗口等。**建议第一版不做**，只列入待办（见 §6）。
10. **用户补充（2026-10-29）**：
    - 拍板编号（例如 `q(280)`，通常写在文档里）、卡片号、PR 号要在卡片上一目了然，并且能直接跳转。
    - 上传附件时，必须带上它对应的拍板或确认编号。
    - 详见 §7 的 Decision、Attachment 和"卡片页"三项。

**对 0.1 的建议**：不再单独试行。数据已经回答了 0.1 要验证的问题。而且项目 B 已经暂停，眼下没有合适的试行对象。前台、后台拆分直接在 Phase 1 M3 实现，用附录 A 场景验收。

## 7. 对开发方案的修改建议

由 Claude 在 0.6 统一并入开发方案，本 PR 不改开发方案。

### §4.3 实体字段

- **TimelineEntry**
  - 新增 `short_id`（可读、可引用）、`reply_to`、`refs[]`（可以跨卡）、`supersedes`、`retracted`。
  - 允许一个条目携带多个结构化内容，或者由 MCP 拆成同一事件下的多个条目。
- **Delivery**
  - 新增必填的 `subject`：`{kind: git_head | artifact_sha256 | doc_version, value}`；`branch` 改为可选。
  - `requested_verifiers` 改为必填，由服务端校验。
  - 新增 `supersedes`、`evidence[]`、`known_gaps[]`。
  - 合并和部署作为事件记录：`merged`（含 merge SHA）、`deployed`（含环境）。
- **Review**
  - `target_sha` 必填；`stale` 是派生字段：目标交付有新版本时变为真。
  - `issues[].must_fix` 和 `blocking` 改为必填。
  - 新增 `kind`（`code | design | test | replay | product | user`）和 `recheck_required`。
- **Decision**
  - 新增 `kind: choose | approve`，批准型绑定到 Delivery 或 SHA。
  - `card_id` 可以为空（项目级决定）；`affected_cards[]` 可以跨卡。
  - 新增 `key`：人类可读的编号，例如 `q(280)`。项目内唯一，不复用（项目 B 出现过编号被重复使用）。
  - 新增 `doc_refs[]`：拍板记录在哪份文档的哪个位置（文档路径、commit、锚点）。
  - `decider` 必填，可以是任意角色。
  - 状态增加 `provisional`、`proxy_approved`（记录授权来源）、`revoked`、`superseded`。
  - `resolution` 增加：
    - `raw_quote`：decider 是你时必填。在 Needs You 里作答时自动记录原文。
    - `via_chain[]`：经过谁转述。
    - `external_ref`：外部消息的引用。
    - `batch`：一次批准了哪些条目。
- **Card**
  - 新增 `source`、`out_of_scope`、`deadline`、`related_cards[]`。
  - 新增 `resolution: done | superseded | duplicate | wontdo`。
  - 负责人和审核人不写进描述；验收标准由卡片模板强制。
  - 状态分两部分：
    - `backlog → todo → in_progress → review` 由工作项推导，规则自动更新。
    - **`done` 不由规则触发。** 执行人提交"完成申请"，由卡片模板指定的角色审核通过后才更新（对应 D4）。
    - 完成申请沿用 Delivery / Review 的机制：申请是一种针对卡片的交付（`kind=card_completion`），写明逐条验收标准的对照、证据和已知遗留；审核就是"PM 验收"这个验证型工作项。
    - 规则只负责两件事：所有必需工作项通过后提醒执行人可以申请；申请时由服务端校验前置条件（必需工作项、阻塞性拍板），并把结果展示给审核人。未满足的条件必须列为已知遗留，并关联后续卡片。
- **Attachment**（用户补充）
  - 绑定到具体的时间线条目或交付，不再只挂在卡上。
  - 新增 `basis`：这个附件依据哪个拍板，或者在等哪个拍板，值是 Decision 的 `key`。
    - 设计稿、规格、导出文档、构建产物等"产物类"附件必须填写，服务端拒绝没有 `basis` 的上传。
    - 测试截图、日志等"证据类"附件绑定到交付或审核即可。
  - 新增 `approval_status`：由所依据的拍板推导，取值为 `pending | approved | revoked`。
  - 新增 `supersedes`：取代旧附件时，旧附件标为"已取代"。
- **Assignment**
  - 运行状态增加 `blocked_on_prompt`（停在 CLI 的确认提示上）和 `delivery_failed`（门铃发送失败）。
  - 新增 `eta`。

### §5.2 时间线条目

- 新增 `handoff`（交接）和 `human_action`（你直接对 Agent 做了操作）两种类型。
- 巡检、签收、ETA、等待说明不进时间线，改为由 Assignment 的运行状态、游标和派生视图表达。

### §6 路由与门铃

- 门铃不再默认送给 PM。2.2 节的分类可以直接作为 Router 规则的验收用例：PM 内部调度和进展汇报都不升级。
- 门铃发送失败要标记 `delivery_failed`，转给 PM Ops，不要静默重试。
- 同一 Assignment 的门铃要合并，对应 §6.7（项目 B 有 41 处重复提醒）。

### §8.4 卡片页、§8.7 看板范围（用户补充）

- 卡片页顶部加一个"关联"区，列出这张卡关联的拍板、卡片和 PR。每一项都显示编号和当前状态，点击即可跳转：
  - 拍板：`q(280)` 待批 / 已批 / 已撤回；
  - 卡片：卡号和状态；
  - PR：编号，以及打开 / 已合并 / 已部署。中心合并由主机完成（§12.5），所以合并状态控制面自己就知道。
- 时间线和描述里出现的拍板编号、卡号、PR 号、条目短编号，由服务端识别后自动变成链接，并写入条目的 `refs[]`，不依赖 Agent 手工填写。
- 附件缩略图上显示所依据的拍板编号和状态，例如"q(280) 已批"；已取代的附件折叠显示。
- 这会让 §8.7 的"做"清单多出关联区和自动链接两项，需要在 0.6 一并确认。

### §8.2 Needs You

- 新增"待你执行的操作"：写清楚要执行什么命令或操作、回传什么、截止时间。和"待拍板"分开。
- 不紧急的拍板合并成批次呈现（72% 可以合并或延后），只有阻塞性的和风险立即提醒。

### §9.2 Card MCP

- `submit_delivery`：必填 `subject` 和 `requested_verifiers`。
- `submit_review`：必填 `target_sha`。
- `post_comment`：增加 `reply_to`、`refs[]`、`supersedes`。
- `request_decision`：增加 `kind`，返回 Decision 的 `key`。
- `upload_attachment`：增加 `basis`（Decision 的 `key`）和 `attach_to`（条目或交付）；产物类附件缺少 `basis` 时拒绝。
- 新增 `request_human_action`：Agent 请求你执行某个操作，进入 Needs You。

### §10 Role

- 验证型工作项可以声明能力要求（例如 `vision`），路由时检查。

## 9. 局限

- 每个项目只抽了约 40 张卡，而且评论高度集中：项目 A 评论最多的 5 张卡占了 53% 的评论，项目 B 的 6 张卡占了 75%。按条数算的比例主要反映这几张大卡。
- 标注由多个子 Agent 按同一份规格并行完成，对附件和 must_fix 的判断宽严不完全一致，字段出现率按 ±10 个百分点理解。项目 B 有一张超大卡按关键词规则分类，抽查约八成准确。
- 300 条门铃由 Codex 一次性逐条判断，没有交叉复核。
- "对话期间"用相邻消息间隔 ≤ 15 分钟来近似。
- 数据只来自同一个用户的两个项目，项目 B 的运维比重偏高。单 Agent 对照只有 3 个会话。
