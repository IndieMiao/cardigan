## 测量方法

复现脚本：[workbench-pagination.mjs](../../apps/server/test-support/workbench-pagination.mjs)。先安装锁定依赖，再在仓库根目录运行：

```sh
pnpm exec tsc -b apps/server
node apps/server/test-support/workbench-pagination.mjs /tmp/c243-baseline.json
```

- Node 24.22.1；独立临时文件 SQLite、真实 Workbench HTTP 监听。241 张卡、241 个工作项、241 个 Assignment（20 个活跃）、964 个已完成 Run、241 条拍板、28,920 条事件和同量时间线。正文固定生成，不使用生产数据，不启动 Dispatcher 或连接真实员工运行时。
- 基线每个接口重新打开 Store 和监听器，在登录后采一个首次请求，再顺序采 20 个暖请求。改后另外补齐每接口 20 次独立 Store 首次读取的 p50/p95，避免用暖缓存结果代替首屏目标；看板的实际多列首屏单列一行测量。没有并发请求、CPU 空转、网络或 CPU 降速；不做吞吐压测。操作系统文件缓存、JIT 和共享主机调度没有隔离，所以“首次”只表示该 Store 的业务快照缓存尚未由读接口填充。
- HTTP 时间包括回环传输、服务端处理和完整响应体接收；不含登录。暖请求 p50/p95 用排序后第 10/19 个样本，不将唯一一次首次请求称为 p95。每次响应均核对 HTTP 200 和有效 JSON；夹具断言卡片、事件、时间线、Run 数量。
- “SQL 返回行”由数据库语句的 `all/get` 返回值计数，含授权和元数据查询；原始 JSON 另列带 `doc` 的行数和逐条 SQL。它不是 SQLite 内部扫描行数：聚合可能扫描很多索引项只返回一行，缓存也可能不读 SQL 却在 JavaScript 中遍历整个项目。因此同时提供查询计划，不能将这项指标改名为数据库物理读行数。
- 同一接口暖请求间没有插入新事件。该组数据暴露首次加载和常驻缓存的差异，不代表持续写入时的生产性能；后续必须增加有新事件及并发插入的分页正确性验证。
- 临时数据库及监听器正常结束后关闭、清理。报告不保存密码、Cookie、主机名或响应正文。脚本不属于默认测试集，只在显式执行时测量。

## 索引与查询计划实测

脚本在同一合成库中执行 `EXPLAIN QUERY PLAN`。候选索引的创建、查询和回滚在单个事务中完成，并断言 `experiment_*` 索引全部撤销。下面“试验后”指候选 SQL 的计划变化，**不表示产品接口已经改用候选 SQL**。完整 SQL 与计划在原始 JSON 的 `query_plans` 字段。

| 查询 | 当前计划 | 试验后 |
|---|---|---|
| events 按卡聚合更新时间 | `SEARCH ... USING COVERING INDEX events_by_card_updated_at (project_id=? AND card_id>?)` | 不变；已有索引，但仍覆盖本项目全部卡片事件的索引范围 |
| 活动候选页，按创建时间和 id 倒序，limit 51 | `events_by_type (project_id=?)` 加临时排序树 | `(project_id, created_at表达式 DESC, id DESC)` 索引，无临时排序树 |
| 卡片候选页，项目加状态，limit 11 | 卡片主键只匹配项目 | `(project_id, status表达式, id)` 精确匹配项目及状态 |
| 当前卡片工作项 | 工作项主键只匹配项目 | `(project_id, card_id)` 精确匹配 |
| 时间线候选页，项目/卡片/seq上界，limit 21 | 既有 `timeline_by_card_seq` 精确匹配三项 | 不变，无需重复索引 |
| 活跃 Assignment | Assignment 主键只匹配项目 | `(project_id, status表达式, id)` 精确匹配 |
| 拍板历史候选页，按 resolution.at 和 id 倒序，limit 11 | 拍板主键只匹配项目，加临时排序树 | `(project_id, resolution.at表达式 DESC, id DESC)`，无临时排序树 |
| 通知按收件人和状态 | 既有 `notifications_by_recipient` 精确匹配项目、收件人种类、Assignment、状态 | 不变，无需重复索引 |

当前基线已经包含迁移 0013 的事件更新时间与类型索引；迁移 0001、0004 分别已有时间线、通知索引。因此不能直接沿用早期报告的“这些索引都不存在”结论，也不能仅以 EXPLAIN 出现 `SEARCH` 就声称工作量有界：它可能仅限定项目，仍遍历该项目所有记录。候选 activity、拍板历史查询还没有完整筛选条件和领域语义，仅证明对应排序索引的作用。

## 读取契约

已有依据为 M5 计划 §3.3/§4、开发方案 §4.4/§4.5、§8.2/§8.4/§8.5/§8.6，以及本卡验收标准。本节按 PM 的 C-243#10/#12 指令作为本卡计划依据；冲突时以本卡为准。

- **派生状态与筛选**：domain 在工作项变更后同步卡片状态，读取仍使用 `deriveCardStatus` 和 `deriveCardFields`。SQL 的状态候选选择可以利用已存状态，但“下一步谁做”“等我处理”、合并阶段、跨卡影响及全局计数还依赖工作项、交付、审核、拍板和人工操作。不能先截一页再做这些筛选，否则页大小、总数和下一游标都会错。若需要额外持久化派生投影，应在计划中明确一致性与失效边界，不能绕过领域规则。
- **Needs You**：不只是 `status=open AND decider=human`。还包括检查失败的已确认合并、已解决但无人接手的拍板、已完成人工操作的接手提醒、暂缓、等待检查汇总、未知运行时宽限期、代确认及未读知会。需明确每组独立游标和排序键，复用原有判断，避免截断后静默丢掉阻塞项。
- **时间线**：目前 `at=` 会把读取窗口扩至目标条目。游标版需保留历史锚点、跨卡编号引用、最新三条结论、附件上传日期、审核/交付时间及受影响卡片来源。锚点跳转应返回有界目标窗口，避免从最新一路取到目标。
- **执行视图**：最新 Run 的判断按编号创建顺序，不按 started_at；queued Run 的时间可能来自触发事件。只读取活跃 Assignment 后仍须明确暂停身份的查看入口、每个身份最新 Run 与全局最近 N 条的关系，历史抽屉继续可按身份读取。
- **SSE**：当前协议是每流序号和事件类型，前端合并失效通知后重读。新的增量读取需明确卡片进入/移出筛选集合、排序键变化、总数变更、删除/失效及跨卡依赖；断线补发保留现有 seq 语义，不推进 Agent ACK。只把全量重读改成重读首页仍不满足本卡“只发增量”的标准。
- **游标与隔离**：时间/序号必须带稳定唯一的第二排序键；游标与项目、筛选和排序绑定。非法、跨项目、跨筛选游标及超大 limit 应拒绝，不能因游标解码失败退回全量。并发新增事件不能导致历史页漏项或重复。

当前数值：看板渲染批次 10；列表默认 10、可选 20/50；活动默认 50、上限 200；时间线前端默认 20、可选 50/100，服务端默认 200 且调用可继续扩大；拍板历史默认 10、上限 100；执行历史抽屉 10。Needs You 和执行首屏暂无有界分页值。本报告没有新增最终数值，候选 SQL 的 `limit+1` 只用于探测是否有下一页；最终规则按卡片要求交人确认。

## 迁移兼容与验证

迁移 0023 只新增索引，复用 `migrate()` 的逐版本 `BEGIN IMMEDIATE` 事务、锁内重查及异常回滚，不新增冗余业务状态、不改原表和 JSON 字段。测试从已填充的版本 22 升级，验证重复迁移无效果、新写入被索引读取、失败后全部索引与版本回滚；另在文件库的 WAL 模式下按 C-201 使用 `VACUUM INTO` 保存升级前备份，并只读打开核对备份仍为旧版本且包含已写事件。旧服务先停、新服务迁移前备份的部署流程不变。

新增索引可能改变没有 ORDER BY 的旧查询遍历顺序，回归曾捕获这一点；最终时间线、Run 和相关表达式索引使用查询匹配的限定谓词，避免改变旧读取顺序。既有员工执行配置、取消/取代卡片、时间线顺序回归已复测。开发方案只更新 §8.2、§8.4、§8.5、§8.6、§8.7 和 §20.2 正文，没有改顶部版本或变更记录。

验证覆盖迁移、跨项目游标、筛选切换拒绝旧游标、超大页参数、并发插入事件后历史页不漏不重、SQL 先筛选再分页、派生状态与存储状态不一致时的泳道和计数、跨卡引用、同快照详情与原完整读取等价、前端同游标重试、按变化编号补拉、历史页保留与去重。测试范围限于 server 的 Web 读写层、web 包和 store 包；没有修改 domain，未运行 domain 类型测试或全仓端到端检查。最终命令与计数见下文交付结果。

## 实现边界

- Needs You 按 C-243#10 的例外不增加游标。SQL 只加载未关闭候选及其真实依赖，完整呈现待办和未读知会；不以页上限静默隐藏阻塞项。候选数和跨卡关联图仍影响派生计算成本，当前规模复测达标，未引入物化投影或缓存权限判断。
- 活动的事件正文按页读取；卡片筛选菜单仍读取项目内编号和标题这两列元数据，避免把正文、工作项和事件历史作为选项一起载入。列表默认兼容编号顺序，实际卡片页面显式请求更新时间排序。
- SSE 不新增带正文的事件：看板根据已见修订后的变化流补拉摘要并维护已加载卡片，单次变化集合超过 100 个或项目级失效时退回当前页。活动、拍板和时间线更新当前窗口；时间线与缓存重叠时按编号去重保留历史页，不重叠时重建连续窗口。历史锚点窗口有界，不再要求从最新记录一直加载到目标。
- 只列活跃身份是本卡明确要求；执行历史接口继续支持暂停和已释放身份，首屏每个活跃身份的最新 Run 独立于最近 50 条列表保留。没有改变调度、并发容量或上下文采样。
- 截图覆盖看板、列表、Needs You、项目动态、卡片详情，共 5 页面 × 1440/390 × 亮/暗 = 20 张。真实生产构建、独立合成数据库，脚本断言页面无横向溢出和浏览器无未捕获异常，并人工核对总览。合入基线后复测发现 390 宽的全列列表会溢出，已为表格加内部横向滚动，保留可读列宽与页码控件；页面自身无横向溢出，没有混入 C-242 的页面撑满改动。
- 数值仍为待定默认值：最终交人确认后才能申请完成；代码审核和同卡独立复核仍按当前交付进行。

合入新基线后，读取候选同时补齐 `ready_when` 指向的已关闭卡片、跨卡工作项依赖及项目级系统规则启用事件。新增回归对比窄快照与原完整快照的 Needs You 结果，防止就绪事项误入“稍后”或提醒丢失；未修改这些领域规则。
