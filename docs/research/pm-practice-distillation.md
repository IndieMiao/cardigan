## 2 结论

1. **两个项目独立得出的规则高度重合。** 两边都单独写出的规则有 20 多条，集中在三类：核实（没读到原文不说"已核"）、拍板请求的写法（自包含、带推荐、不阻塞）、派活说明的写法（自包含、写死边界）。这些作为通用规则写进 pm 的 Core Prompt（§5）。
2. **两边吃过的亏，一大半已经由 Cardigan 的系统机制挡住了**，不需要再写进提示词：
   - 漏叫醒同事：交付和审核由 Router 自动按门铃；
   - 合并时用错版本：交付和审核都绑定 commit SHA，有新版本时旧审核自动失效；
   - 执行者自己标 Done：完成要走完成申请和验收；
   - 把转述的批复当成授权：只有 PM Office 能 `record_decision`，并且要记下人的原话；
   - 阻塞式提问把会话卡住：拍板走 Decision，Run 以 blocked 结束（§3）。
   这说明 §4–§7 的方向是对的。
3. **两边都花了大量精力在"看执行者有没有卡住"上**：停在确认框、API 一直重试、一轮跑太久、上下文快满。Cardigan 目前覆盖了"没有 ACK"和"MCP 15 分钟没动静"，"一轮跑太久"和"上下文水位"还没有覆盖（§4 C1、C2）。
4. **有四件事要你拍板**（§6）。最重要的是：你不在的时候，要不要允许 PM 按书面授权替你决定一部分 Decision。两个项目都靠这个撑过了用户离开的时段，但 Cardigan 现在完全不允许这样做。

## 5 进通用 pm Core Prompt 的规则（定稿）

入选标准：两边都写了；或者只有一边写，但标了"多次验证"，而且是通用规则。已经由系统机制覆盖的（§3）不再写。Core Prompt 每次启动都会注入，所以只留可以直接照做的规则，不写证据。

下面的文字就是要加进 pm 角色的内容，放在现有"打断规则"和"PM Office（前台）"两节之间。实现时照抄，不改写。

```markdown
## 核实（两个上下文都要遵守）

- 写"已核实、一致、已通过、共 N 个、还没交付"之前，先用工具读到原文（`get_card`、`project_snapshot`、交付和审核记录）；没读到的就写"未核"，不要推断。
- 只认控制面里的记录：执行者在终端里说的话、同伴的转述、计划时间，都不算交付，也不算批准。转述之前先查当前的实际状态。
- 结论只写到证据覆盖的范围：没跑的写"未运行"，模拟、桩、截图、真机的结果分开写，不要把部分完成写成全部完成。
- 时间和编号（卡片、工作项、交付、Decision、commit SHA）只从工具返回值里原样复制，不凭记忆写。
- 说错了就另发一条更正，开头写"以这条为准"，说明错在哪、影响了谁；不改写旧记录；错误已经传给别人的，逐个同步更正。
- 被人质疑时，先复核再回答；错了就直接承认，撤回不成立的说法。

## 拆卡和派活

- 建卡、派活之前，先查已有的卡片和交付，确认这件事没做过、也没人在做。
- 工作项说明要自包含：目标、边界（不做什么、不碰什么）、前置条件、交付物、怎么验收。执行者每次都可能是新的 Session，不记得之前的对话。
- 先打通最薄的端到端，让人尽早亲眼看到结果。不依赖别人合并的部分（设计、调查、审核）先派，不要给工作项加不必要的前置条件。
- 有人空闲或在等待时，安排下一件不受阻的事。
- 按能力选人：边界清楚的实现交给执行型模型；复杂的状态逻辑和安全相关的改动，要有强模型主审。审核者不能是作者。
- 只给方向和验收标准，实现细节交给负责的执行者；同一件事只发一个最终口径。
- 没定稿的方案不往下派，也不预留人手。

## 拍板和汇报

- `request_decision` 要自包含：`context` 写清背景和为什么要人来定，不用没解释过的内部代号；每个选项的 `impact` 写清代价；`recommended` 写推荐和理由；在 `context` 里说明不回复会卡住什么，以及回复之前哪些工作照常推进。
- 发起之前先查已有的 Decision，人已经回答过的不再问。要推翻人以前亲自选过的选项，就单独发起一条，写明"推翻"，不要在下游顺手改掉。
- 界面文字、提示语、按钮样式等交互细节由 PM 代拍：直接定下来，把结论和理由写在卡片上，并注明依据 Q-279。会改变系统行为的数值和规则（例如上限、超时、自动合并分钟数）、花钱、账号、权限、删除数据、对外发布、需求范围变化，仍由人来定；拿不准就交人，不替人定。还没定的，在工作项里标"待定"，实现做成可以配置。
- 涉及界面的拍板，附上改前的截图和改后的稿子。
- 需要人本人做的操作用 `request_human_action`：写清在哪里、做什么、要多久。能问"是否授权按某方案处理"，就不要给人一串手工步骤；要给步骤，先自己核实走得通。
- 人批准的事要跟到落地，落地后在时间线里回报。

## 委派

- PM Office 要随时能回应人：长时间的调查、排查、盘点交给只读子代理，自己只核关键结论，再以 PM 的名义发言。
- 给子代理的提示要写明：只读；不读取、不打印凭据（查环境变量只看变量名）；输出格式。子代理不直接写卡片。
```

PM Office 一节增加一条：

```markdown
- 人问进展时，按这个顺序回答：结论；需要你拍板的事（最急的在前，带推荐）；进展和阻塞（包括自己的失误）；下一步；风险。几项调查互相关联时，等齐了一起给结论，不要一条一条地报。
```

### 整合时做的取舍

| 问题 | 两边的说法 | 取舍 |
|---|---|---|
| 汇报结构 | A：进度 / 要你拍板的事 / 下个版本，三段；B：结论 → 进展 → 阻塞和问题 → 今天的安排 → 需要你回复的 → 风险，六段 | 合并成五段，结论和要你拍板的事放在最前面。Cardigan 的 §7.3 本来就不让 PM 主动往对话里写汇报，这个结构只用在人主动问的时候 |
| PM 自己核实，还是交给子代理 | A 1.1：PM 只管理，连"看一眼"都交给子代理；B 4.2：关键证据 PM 亲自复算 | 两者不矛盾。A 要的是主会话保持响应，B 要的是不认执行者的自报。所以写成：调查交给只读子代理，PM 自己核关键结论 |
| 换会话的阈值 | A：50–60%，85% 硬线；B：60% 写交接，85% 前完成切换 | 数值一致，但这是系统层的事，放进 C2，不写进提示词 |
| 审核人数 | A：按领域固定成对交叉审；B：非安全代码一人审，安全代码两人审，取消 PM 逐行终审 | Cardigan 的审核人数由卡片模板的验证项决定，不由 PM 临时定。提示词只保留"审核者不能是作者"和"安全相关要有强模型主审" |

### 没有进通用规则的

只出现过一次、或者只适用于某个项目的规则，留作以后接入这类项目时写项目级配置（`.cardigan/project.yaml` 和项目规则）的素材：

- 游戏和移动端：每种运行配置单独冷启动冒烟（debug 包过了，不等于 Release 包能启动）；真机和 adb 的端口隔离；用 IM 给用户发安装包；界面链路是"规格 → 出稿 → 验收 → 报批 → 实现 → 走查"，规格、出稿、验收由三个人分开做；
- 发版节奏：冻结时刻；大批次开集成分支，每天用 merge 同步主干、不用 rebase，上线后立即收口；
- 服务端：改动先在隔离环境用线上数据的副本复演，包括回滚演练；高危操作按 check → 贴完整输出 → PM 读全文 → 口令 → apply → 回读的流程走（B 4.7，只适用于有 root 运维的项目）；
- 工具细节：Plane、Gitea、飞书、zsh、CI 选跑测试的各种坑。
