## 0. 结论

**D8 建议：不 fork；按第 9 节的清单借鉴设计。**

理由（按重要性）：

1. **上游的宿主平台已经不是我们钉住的那个 Herdr。** 我们 §2.1 记的 herdr-projects 是一个 Herdr 0.9.3 的终端插件（Rust，`herdr plugin install`）。上游在 2026-10-28 到 2026-11-04 这一周内改名 Shepherdr 并换了三次架构：2.0 仍是 Herdr 插件（Web UI）、2.1 是独立 Web 应用（TS/Bun + herdr-core 基线版本）、3.0 是 Herdr app 的 layout + 29 个 mod（Python/JS + herdr-app 基线版本 + herdr-core 基线版本）。本机钉住的 Herdr 0.9.3 里没有 `layout`、`mod`、`herdr-app`、`hc` 任何一项（第 1 节的实测），也就是说**当前 main 无法运行在我们的平台上**，而与我们平台兼容的 1.2.27 已经是上游的遗留分支。fork 一个自己被上游抛弃的架构，等于接手 8 万行级的 Rust 代码（1.2.27）或 4 万行的 Python + JS（3.0），加一个正在换代的平台适配层。
2. **它的领域模型和我们的差一层。** 它只有 Task 一个实体（3.0 是 `space` + `task`），没有 Card / WorkItem / Assignment / Run / Delivery / Review / Decision 的区分（第 3 节）。§4.4 的状态机、§4.5 的第 3、5、9、10、12 条不变量在它的模型里没有对应位置（第 6 节）。要 fork 就得把这些概念塞进一个把"任务"当一切的设计里，改动量大于自研骨架。
3. **它的 Git 模型和 §12 的方向相反。** 它的任务 agent 在自己的机器上 `git push` 到 origin 并开 PR（3.0 `github.py` 的 `git push --force-with-lease`），合并由人所在的机器用 `gh pr merge --squash` 完成（`commands.py:merge_now`）。§12 要求工作机不持有 Git 凭据、所有网络操作由主机发起。这不是补一个函数能改的，是信任边界不同（第 5 节）。
4. **它的 review 是"agent 自查"而非"独立验证工作项"。** 3.0 里 worker 自己起 subagent 或 headless CLI 审自己，然后把"这一轮审过了"记在 commit 上（`reviewed` + `review_gate`），`ready` 拒绝没有记录过 review 的最终 commit。没有 Review 实体的 verdict / issues / blocking，也没有 verify 型工作项、驳回后原卡返工的结构（第 3、5 节）。§4.3、§4.4 的 Review 语义要重写。
5. **可借鉴的点很多，但都是"设计"而非"代码"。** 第 9 节的 6 条（状态 + 一句话原因、review 门禁三条细则、轮次上限只能由外部放宽、按上次状态去重、proof/accept 卡、每会话 grant + 请求 journal）都能在我们的 TypeScript 代码里独立实现，成本远低于 fork 后的适配与同步。上游一周 96 个 PR 的节奏也说明 fork 后必须持续跟。

一句话：**它的产品判断（看板 + 每任务 worktree + 人工 accept + Needs you）和我们的方向高度一致，值得在 §2.1 里保留为"主要参照"；它的代码和平台假设不值得继承。**

## 2. 三代架构各是什么

### 2.1 v3.0（main）—— 当前形态

- 交付物是**一个 Herdr app 的 layout**（`layouts/shepherdr.json`）+ 29 个 mod（`mods/`）+ 4 个程序（`herdr-task`、`herdr-artifact`、`herdr-secret`、`herdr-browser`）+ 3 份角色说明（`templates/{assistant,worker,reviewer}.md`）+ 钩子。安装器 `./install.sh` / `shepherdr`（`bin/shepherdr`）把这些放进 `~/.config/herdr-app/` 与 `~/.config/herdr-core/templates/`。
- 状态：每个文件夹（git 仓库或其根）一个 JSON 文件 `~/.herdr/tasks/<slug>.json`，写入走 `fcntl` 文件锁 + 原子替换（`herdr_task/store.py` 的 `Store`）。worktree 在 `~/.herdr/worktrees/<repo>/<branch>`，分支 `task/<n>-<slug>`（`launch.py`）。
- 默认值（`settings.py:DEFAULTS`）：`merge: ask`、`review_rounds: 0`（**3.0 默认不审**）、`must_fix: major`、`max_running: 10`、`worktrees: true`。注意 `review_rounds: 0` 与 `assistant.md` 里写的"Review on by default / 默认 3 轮"不一致，属上游自己的文档漂移（2.1 的默认是 Review on、3 轮）。
- 编排：任务由人驱动。有空间的 Assistant（协调者）把人的话变成任务，`herdr-task` 负责 worktree、标签、启动、门铃。worker 不向协调者汇报，是 Herdr 自己把 news 推给协调者（`news.py`，`<herdr-news task="HAT-4" event="ready">`）。
- agent 支持：`settings.py` 只有 `AGENTS = {"claude": [...], "codex": [... "--no-daemon"]}`。**只支持 Claude Code 和 Codex**，没有 Pi / OpenCode 的启动路径（模板 `command: claude` 也一样）。
- 状态来源：Herdr 的 agent 状态（working / blocked / idle / done）+ `herdr-task status` 自报的进度（`--done`、`--left`）+ session 日志解析。明确写了"Process liveness never means Done"。
- 多机：靠 herdr-core 的 machine 链路（`hc exec --on <machine>`）与 SSH；每台机器的任务是自己的，看板汇总显示；"Work never moves between machines"。

### 2.2 v2.1 —— 独立 Web 应用（TS/Bun）

这一代离我们的形态最近：一个长期在线的服务端 + SPA，SQLite 落盘，WebSocket 推 UI。关键实现：

- 存储是通用 KV：`state.sqlite` 里 `records(kind,key,value)`、`commands(id,hash,result,error)`、`counters(key,value)`（`server/core/store.ts`）。`commands` 就是**幂等收据表**：同一个 command id 用不同入参再来一次会 conflict，中断过的再来一次报 `uncertain`。
- agent 与控制面之间的通道是 **mailbox**：`grants(id, chat, session, machine, actions, credential)` + `requests(grant_id, id, hash, response)`（`server/core/mailbox.ts`）。grant 是**每个 chat（≈每次会话）一张、带随机 key 的凭据**，绑定 machine 与 session，session 被替换即撤销，并带允许的动作清单。这就是我们 §9.1 想要的"每次 Assignment 一个 Token"的同构实现。
- 任务记录（`CoreTask`，`server/core/tasks.ts`）字段里值得注意的：`workflow`（todo/queued/working/ready/merging/merged/closed）、`mergePolicy`（ask/checks/auto）、`readyHead`/`pushedHead`/`approvedHead`（**审批钉的是 commit**）、`review { on, kind, rounds, mustFix }`、`reviewRound`/`reviewHead`/`reviewReport`/`reviewTurn`、`reviewRoundsAdded`、`providerTakeover`、`cleanupPending`。
- review 是"父 agent 请求一次 fresh review"，由服务端起一个 `role: reviewer` 的只读会话（`reviewNow`），审完把报告以 `<review round="2" head="…">` 回灌给父 agent；`ready` 要求 report 的 head 等于 ready commit。
- 决策卡片（`server/core/questions.ts`）是**一次性**的：`{id, chat, grant, question, answered}`，`answer` 校验 grant 未被替换，卡片随 CLI 的等待结束而关闭（`Question.closed` 带原因）。

### 2.3 v1.2.27 —— Rust 插件（Herdr 0.9.3 时代的形态）

- 5 个 crate 栈（core / flow / board / web / cli），全部领域逻辑在 `crates/core/src/store/` 下：一个任务一个目录 `<data>/tasks/<repo>/<n>/`，含 `task.json`、`inbox.jsonl`、`artifacts/`。
- `task.json` 是"看板拥有的全部事实"，Herdr 的状态是实时读的。`STAGES` 有 22 个（`todo/progress/queued/starting/setup/working/stopped/nosummary/asks/checking/pushing/reviewing/reviewneeds/plan/approval/merging/failed/done/attempts/pick/tried/after`），界面上派生为 5 个状态。
- 这是三代里**领域模型最完整**的一代：`reviews.rs` 有 review 轮次、每轮 findings（severity / subject / where / proof / preexisting）、gate 规则（`review.mustFix` 以下不阻塞、preexisting 永不返工、critical 无 proof 降级为 major）；`gate.md` 明确写"reviewer describes, the board decides"。`asks` + `plan` + `approval` 三个阶段对应"等你说"与"计划待批"。
- 多机：每台机器自己的任务，`Alt+M` 轮换看板，动作通过插件自己的 SSH 连接在对端执行（"Herdr has no command that runs a plugin's commands there"），"Work never moves between machines"。

## 3. 实体对照表

覆盖 §4.1 全部 12 个概念（计划第 2 步只列了 7 个，验收要求覆盖 §4.1 全部，故按 12 个写）。"1.2.27"列给的是同一概念在该代的最近似物，便于判断"是本来就缺，还是 3.0 才丢的"。

| §4.1 概念 | 3.0（main） | 1.2.27 | 判定 |
|---|---|---|---|
| **Card（目标卡）** | 无。`space`（一个文件夹 + 名字）是项目；`task` 是唯一的工作单位，标题 + brief（prompt）。任务是扁平的，没有子卡、没有验收标准字段（验收标准只能写在 brief 的自然语言里） | 无。`repo` + `task`，`task.json` 有 `description`、`plan[]` | **缺失**。我们的 Card 承载"目标 + 验收标准 + 必需工作项"，它把三件事塞进 brief 文本。§4.3 Card 的 `acceptance_criteria`、`template`、`required` 无对应物 |
| **WorkItem（工作项）** | 无。有 `--after`（任务间排队）与 `--base`（分支目标），但那是**任务之间的关系**，不是一张卡里拆出的工作项；也没有 produce / verify 之分 | 无独立实体；`plan[]` 是计划步骤；`attempts`（最多 5 个）是**同一任务的多路尝试**，各有自己的 agent / worktree / 分支，最后人选一个 | **缺失**。它的 `attempts` 是我们没有的概念（并行竞速取优），值得在 §4 讨论但不在第一版范围 |
| **Assignment（责任上下文）** | 部分对应：任务记录里的 `agents[]`（address / agent / session / log / at）、`herdr.task=<slug>#<id>` 标签、`space`/`tab`、`worktree`/`branch`/`base`。一个任务同时只有一个活动 agent；`resume`/`fix` 复用，换 agent 即"重启" | 任务上的 `worktree`/`branch`/`agent`/`since` 等字段；无独立实体 | **形态缺失，语义近似**。核心差异：它的 Assignment **不绑定角色**（角色只是启动时读的模板），也没有 `role_version`、`mcp_token_id`、`machine_id`（机器在任务上）。§4.3 Assignment 的 `scope`、`role_id/role_version`、`mcp_token_id` 无对应 |
| **Run（执行）** | 无实体。有"一次启动"的痕迹（`agents[]` 里一条、`started`/`ready_at`/`accepted_at`），有 `herdr-task status --done/--left` 的进度上报（`progress{text,done,left,at,paused_at}`），但没有 trigger、没有 kind、没有 queued→acked→running 的迁移，也没有 `UNIQUE(assignment, trigger_event)` 的幂等约束 | `runs.rs`：run 是**从阶段和时间戳推导**出来的（`run_role` 由 stage 决定 agent 还是 reviewer，`run_began` 取 `reviewAt`/`since`/`workAt`），不是记录 | **缺失**。§4.3 Run 的 `trigger_event_id`、`kind`、`outcome`、幂等约束全部无对应；§4.5 第 10 条（不是每条评论都是 Run）在它那里没有意义，因为没有 Run |
| **Agent Session** | 有：`sessions.py` 从 pid 找 Claude Code / Codex 的 session 与日志；`handoff` 传上一任的会话日志与屏幕；`resume` 用 `--resume`/`--continue`。Session 可换（`hc` 的 terminal 换掉） | 有：`handovers.rs`、session id 自选 | **基本对应**。差异：我们要求 Session 显式挂在 Assignment 上并有 `runtime_ref`/`session_ref`，它是从进程与日志反推 |
| **Timeline Entry** | 无统一时间线。评论在**每个 agent 会话的 chat** 里（Herdr 的 pane chat），不在卡片上；另有 `summary`（≤160 字）、`details`、`progress`、`attention`、`proof` 这些结构化碎片；news 是推给协调者的临时行 | `inbox.jsonl`（给 agent 的待投递文本）+ `task.json` 里的 `report`/`details`/`lastLine`；没有"卡片评论流" | **冲突**。§5.2 的七类条目（评论/指令/交付/审核/待拍板/决定/状态变化）在这里既没有统一载体，也没有类型字段；chat 归属"会话"而非"卡片"，与我们"评论寄给工单负责人"（§4.1 口诀）相反 |
| **Delivery（交付）** | 部分对应：`ready` 带 `--summary`（≤160 字，拒绝更长）、`--details`、`--proof <artifact id>`；worktree 任务的分支与 commit；`proof.py:evidence()` 从 git / GitHub / artifact 拼"证据"（commit、numstat、检查结果、proof 链接）。没有 `kind`、没有 `status`（submitted/accepted/rejected/superseded）、没有 `requested_verifiers[]` | `finish line`：check、catch up、push、PR、review、approve、merge，全流程有中间记录；无 Delivery 实体 | **实体缺失，字段大半可借**。§4.3 Delivery 的 `test_results?`、`attachments[]`、`requested_verifiers[]`、`status` 无对应；但 `summary`/`details`/`proof` 的长度与内容约束、以及"证据由系统拼、不用 agent 自述"的做法值得照搬 |
| **Review（审核结论）** | 名义有、结构无：worker 自己起 subagent 或 headless CLI 审，`herdr-task reviewed <id> --report "<findings, a line>"` 记一轮（`reviews[]` 里 `{round, result: report/pass/changes, text, at, head}`），`ready` 拒绝没有轮次记录的最终 commit；`review.rounds`（0–10，3.0 默认 0 即不审，2.1 默认 3）、`review.mustFix`（blocker/major/minor，默认 major）、`review-more` 只给协调者加一轮。**没有** verdict 三态、issues 结构化、blocking、kind（design/code/test/product），也不存在独立 reviewer 的会话记录在控制面（reviewer 是 worker 的 subagent 或一次性 headless 进程） | **最完整**：`review` + `reviews[]` + `reviewRound`，findings 带 severity/subject/where/proof/preexisting；gate 规则写在 `gate.md`；`reviewneeds` 阶段=等你的判定 | **冲突**。我们要求"审核是 verify 型工作项的产物、由另一个 Assignment 提交、有阻塞语义"（§4.4、§4.5 第 8 条）。它的 review 是产出者自查 + 门禁。1.2.27 的 gate 细节值得借鉴（见 9.2） |
| **Decision（待拍板/决定）** | 卡片在，记录薄：`attention`（一句话原因，≤40 字）、question/permission/plan 三类卡（`lib/asks.js` 从 Claude Code hook 取请求，Codex 同理），答案经 chat 回给 agent；plan 卡有"Approve / Send it back with a note"。没有 options[]/impact、没有 affected_work_items[]、没有 decider、没有 resolution（原话、来源、时间） | `asks`（question/permission/auth）+ `plan`（等你的 yes）+ `approval` 阶段；`report --state blocked --kind … --msg …` 是"我在等你"的唯一表达 | **缺失**。§4.3 Decision 的 `options[]`、`blocking`、`decider`、`resolution.via/human_quote` 全无；§4.5 的"没有 open 且 blocking 的 Decision"这条 Done 条件无从表达（它只有"这个任务在等我"） |
| **Event（事件）** | 近似物：`~/.herdr/tasks/.news.json` 记住"每个任务上次告诉过的状态"，状态变化才推一次（跨重启）；`news.py` 里的 `seen` 也是去重游标。**没有**按卡单调递增的 `seq`、没有 payload、没有 ACK | `inbox.jsonl` + `inbox.offset`（至少一次投递 + 偏移即 ack）、`dispatch/*.json`、`seq:dispatch` 计数器 | **缺失但可借**。按"上次状态"去重的思路可直接用于 §6 的门铃幂等；`offset` 语义对应我们的 Cursor。缺的是每卡 seq + 可重放事件流 |
| **Role（角色）** | 3 份模板文件（`assistant.md`、`worker.md`、`reviewer.md`），front matter 里 `command: claude`，靠 `herdr-task` 拼 brief + Settings 块（Review/Reviewer/Must fix/Rounds/Merge/Proof/Agent）注入。角色**不是数据**，没有版本、没有能力清单、没有权限 | `roles-and-commands.md` 四角色（Agent / Reviewer / Watcher / Coordinator）+ 每角色的 settings（`worker.access`、`reviewer.access`、`coordinator.agent`…） | **冲突**。§4.3 Role 的 `role_version`、能力、Harness、模型、权限是配置实体；这里是"文件 + 拼接"。另外它多一个我们没有的角色：**Watcher**（小模型读屏幕猜进度），我们第一版不需要 |
| **Machine（机器）** | 有：`machines.py`、herdr-core 的 machine 链路、每机启动上限、健康（CPU/内存/磁盘）、home space 的 Assistant、跨机汇总 news | 有：`herdr machine add` 来的机器、每机自己的任务、动作走 SSH、`board.machines` 覆盖 | **基本对应**，且它的"任务固定在某台机器上、从不迁移"与 §4.5 第 6 条一致。差异：它没有 `max_assignments`、`tags[]`、`status`（online/degraded/offline/draining）这套显式调度字段，靠 Herdr 的连接状态推断 |

补充（§4.3 有、§4.1 没列的）：**Attachment** —— 3.0 有 `herdr-artifact`（HTML 制品，带版本、标记）与 chat 附件，1.2.27 有 `artifacts/`。这部分它比我们方案里的一行 `Attachment` 更成熟，见 9.5。

## 4. 缺失与冲突汇总（按对我们的影响排序）

1. **没有 Card / WorkItem 分层**，一张卡里无法表达"设计走查 + 测试验收 + 实现"这种多岗位结构（§4.2 的核心）。它的替代物是"再开一个任务" + `--after`，等于把依赖关系放进文件系统式的任务队列。
2. **没有 Run / Event / Cursor 三件套**，"先持久化事件再按门铃"（§4.5 第 7 条）、"Run 与 trigger 唯一"（§4.3 Run）、"ACK 与重放"（§6.1）无处落地。它用"上次状态 + 直接给终端打字"替代，重启后靠 session 日志与 `hc read` 补。
3. **Review 不是独立工作项**，驳回无法产生"给原 Coding Assignment 的返工 Run"，也没有 blocking 判定（§4.4 WorkItem 状态机里的 `delivered --any reject--> changes_requested`）。
4. **Decision 不是持久实体**，拍板散落在 chat 里，事后无法审计；Done 条件里的"没有 open 且 blocking 的 Decision"无从判断（§4.4 Card Done）。
5. **Git 方向相反**（第 5 节）。
6. **角色没有版本与权限**，无法做到"Run 记录所用的 Role 版本"（§4.5 第 12 条）和"状态迁移与权限由服务端校验"（第 11 条；3.0 连控制面都没有，2.1 有 grant 但不覆盖 review/merge 语义）。
7. **只支持 Claude Code + Codex**（3.0 `AGENTS`），与我们"可插拔 Harness（含 Pi / OpenCode）"的目标不符。

## 5. worktree、review、合并 vs §12

| 环节 | 它怎么做（3.0 main，附 1.2.27 差异） | §12 要求 | 差异性质 |
|---|---|---|---|
| 建 worktree | `git worktree add ~/.herdr/worktrees/<repo>/<branch>`，分支 `task/<id>-<slug>`，从"文件夹当前检出的分支"或 `--base` 起（`launch.py:404-417`）；无 git 时就在文件夹里干活 | 每机每项目一个基础 clone `/srv/agent/repos/<project>`，worktree 在 `/srv/agent/worktrees/<assignment_id>`，分支 `agent/<card>/<work_item>`，provision 时记 `base_sha` | 布局不同但可换；**关键差异**是它没有"主机推基线"这一步，任务一次起分支后就不再同步基线（1.2.27 有"catch up with main"，但也是任务自己 rebase） |
| 交付 | worker 自己 `git push --force-with-lease -u origin <branch>`（`github.py:40`），在 GitHub 上开 PR；非 GitHub 仓库则由本机合并 | Agent **不 push**；主机从工作机拉该 SHA 进 `refs/cardigan/deliveries/<id>`，拉成功才算校验通过 | **冲突**：信任边界不同。它要求工作机有 origin 的写权限（或 `gh` 登录态）；我们的模型里工作机无凭据，主机单向拉取 |
| 验证 | 无独立验证工作项。review 由 worker 自己发起（subagent / `codex exec --sandbox read-only` / `claude -p --permission-mode plan`），报告回灌给 worker | 设计走查、测试验收各是 verify 型 WorkItem，主机把 SHA 推到验证机，在 detached worktree 里只读检查 | **冲突**：它的 reviewer 与 worker 同机、同目录（只读约束靠 CLI 参数与提示词），我们要跨 Assignment、跨机器也可 |
| 合并 | 人在 Accept 卡上点，或 `herdr-task accept/merge`；GitHub 上 `gh pr merge --squash --delete-branch`（`commands.py:merge_now`），非 GitHub 上在**主检出**里 fast-forward（`commands.py:ff_merge`），都不 force | 只在主机的集成 clone 合并，更新中心仓库 main，再按需推外部托管；冲突时为原 Coding Assignment 创建修复 Run | 方向一致（"人都要点一下"），落点不同：它直接改主检出/main，我们没有"在人的检出里 merge"这一步。冲突处理它交给 agent（rebase），我们对应用修复 Run |
| 清理 | 合并/收尾后删 worktree 与分支；有未提交或有 main 没有的工作就保留并说明，**从不 force**；每小时扫一次遗留 | release + 未提交修改在 Needs You 里给"查看 Diff / 保留 / 强制清理"；定期对账 `herdr worktree list` 与库 | 高度一致。它的"从不 force、只留不删"更保守，可以借鉴到 §12.6 的文案 |
| 写锁 | 一个任务同时只有一个 agent；另有**全局**并发上限（3.0 `max_running` 默认 10，设置可改；`assistant.md` 写默认 3，与代码常量不一致） | 同一 worktree 同时最多一个写入型 Run；后来的事件进 Inbox 排队 | 语义等价（一任务一 agent 天然满足），但它没有"排队事件"的概念，被限流的任务只是"还没启动" |
| 对账 | 每小时扫遗留 worktree/分支，用"main 是否已有该 tree"判断已合并 | 定期对账 + 通过 SSH 读未提交/ahead-behind（Herdr 没这个 API） | 一致；它的"按 tree 相等判断已合并"比"按 SHA 祖先判断"更抗 squash merge，值得借鉴 |

## 7. 扩展接口

- **3.0**：一切皆 add-on。`lib/addons.json` 列每个 add-on 的 mods / layout blocks / keys / helpers / templates / needs，带开关的在 Shepherdr settings 里可关。mod 是 Herdr app 的 JS 模块（`mods/<name>/main.js` + `mod.json`），共享代码在 `lib/` 由 `bin/sync-shared` 复制进各 mod。扩展点是"写一个 mod"或"改一份模板"，**没有稳定的服务端 API**；第三方 mod 与内置 mod 平级放在 `~/.config/herdr-app/mods/`，安装器"不覆盖别人的同名 mod"。
- **2.1**：插件有 `api: 2` 声明，客户端用 `definePlugin` + 具名 slot（bar / menu / side panel / settings / key）替换或追加；服务端插件 `setup(context)` 拿到 `snapshot()`、`state.get/set`（每插件命名空间，值 ≤1 MiB）、`onChange`、`handle(method, fn)`。这是三代里**唯一有明确插件契约**的一代。
- **1.2.27**：无插件 API，是一个自包含的 Rust 程序 + Herdr 的 `plugin link`。

对我们的意义：它的"扩展"都发生在**它自己的 UI/进程内部**，不是"给外部控制面用的接口"。我们 §9 的 Card MCP 是给 Agent 用的接口，二者不在一个层面，无法复用。

## 9. D8 建议与借鉴清单

**建议：不 fork，不引入为依赖；在 §2.1 保留为参照项目，并借鉴下列 6 点设计。**

不 fork 的理由已在第 0 节。补充两条工程判断：

- 规模与语言（实测行数）：3.0 是 8.6k 行 Python（`herdr_task` 包）+ 3.2 万行 JS（`mods/`，含 `lib/` 的共享副本）；2.1 的 `server/` + `shared/` 约 19k 行 TS；1.2.27 是 8.5 万行 Rust（853 个 `.rs` 文件，含测试）。任何一代都不是"小底板"。而我们的 §20.1 已经定好 11 个包的 TypeScript 骨架，语言与依赖方向都和它不同。
- 平台漂移：一周内换三次架构，说明上游仍在快速试错；§2.4 已提醒 fork 要跟上游，代价会落在每次 Herdr 换代上。

### 9.1 借鉴：卡片 = "状态 + 一句原因"，原因硬性 ≤40 字

它的 `status`（7 个：To do / Queued / Working / Needs you / Ready / Merging / Done）由记录 + agent 原生状态**派生**，从不存储；`why` 永远是标准原因（Plan to approve / Asks permission / Question for you / Waits for your reply / Signed out）或 agent 自己的问题裁到 40 字，**禁止粘贴整段消息**。任务列表、卡片行、通知、协调者 news 用的都是同一句话。

对应我们 §8.2 Needs You 与 §5.2：建议把"一句话原因 ≤40 字 + 标准原因枚举"写进 §4.3 的派生字段与 §8 的展示规则，避免 Needs You 变成第二份聊天记录。

### 9.2 借鉴：review 门禁的三条细则（来自 1.2.27 的 `gate.md`）

1. **reviewer 只描述，判断由系统按固定规则做**：没有 finding 在 `review.mustFix` 及以上就算通过；reviewer 不打分、不建议合并。
2. **critical 没有 proof 降为 major**；**preexisting 的 finding 永不触发返工**，只列出。
3. **第二轮起只复查上一轮的 finding 是否修好、修复有没有引入新问题**；要新开 finding 必须是 critical 且带 proof。

这三条能直接写进我们的 Review 字段语义（§4.3 的 `issues[].severity/must_fix`）与 §6.4 路由（驳回后返工 Run 的输入），并且可测。

### 9.3 借鉴：review 轮次上限 + 只有协调者能加轮

3.0 里 worker 用完 `review.rounds` 还想过，必须由协调者 `review-more`；`ready` 会拒绝并说明还剩几轮。防止"自己给自己放行"的循环，同时留一条人工开口。

对应 §6.4 与 §4.5 第 11 条：建议明确"轮次上限是控制面字段，只有 PM Ops（或你）能放宽，且记在 Run 上"。

### 9.4 借鉴：按"上次说过的状态"去重 + 需要时才唤醒

`news.py` 在 `~/.herdr/tasks/.news.json` 里记"每个任务上次告诉协调者的状态"，只有变化才推一次，跨重启有效；状态抖动（变了又变回来）不发。协调者拿到 news 后，若无可补充则回 `<no-reply>`，chat 里不出现任何东西。

对应 §6.1、§6.2：建议把"门铃去重键 = (assignment, 该卡片已 ACK 的 seq) + 状态未变则不敲"写成显式规则，并给 PM Ops 一个"无事可做就不发言"的默认。

### 9.5 借鉴：proof / Accept 卡（交付证据由系统拼，不用 agent 自述）

3.0 的 `ready` 要求 ≤160 字、面向人的 summary（拒绝更长），技术细节放 `--details`，可见效果要有 proof artifact；Accept 卡上显示的是 `evidence()` **自己算出来的** commit、diff numstat、检查结果、proof 链接。规则里还写了"a mocked test is no proof"。

对应 §4.3 Delivery 的 `test_results?`/`attachments[]` 与 §8.4 卡片页：建议在方案里点明"交付摘要限长、证据由控制面从 Git 与测试结果生成"，这比让 agent 自由写交付文本更可审计。

### 9.6 借鉴：每会话 grant + 请求 journal（来自 2.1）

`grants(chat, session, machine, actions[], credential)`，session 被替换即撤销；`requests(grant_id, id, hash, response)` 对同一请求 id 重发返回上次结果、不同入参报 conflict。
对应 §9.1（每次 Assignment 一个 Token）、§9.3（服务端校验）、以及 §4.3 Run 的 `UNIQUE(assignment, trigger_event)` 幂等：建议 Token 直接编码"assignment + 版本 + 允许的动作"，并把"同 id 不同体"判为错误而不是覆盖。

再补一条**不要借鉴**的：它的 reviewer 与 worker 同机、同 worktree（只读靠 CLI 参数与提示词）。我们 §12.4 的"主机把 SHA 推到验证机、在 detached worktree 里只读检查"更严格，保留我们的。
