# 0.4 · 各 Harness 接入 MCP 的预研

日期：2026-11-04。对应 `docs/plans/phase-0.md` §2、§3 的 0.4；依据开发方案 §9.1、§10.2、§14，并核对 §4、§6、§12、§20。所有测试在 `local`，没有使用远程机器。

## 1. 结论与版本

三个 Harness 均通过真实模型调用 `whoami`，返回 `{"asg":"A-1"}`，并调用 `echo` 返回原文。MCP Token 仅通过子进程环境变量传递，三份 MCP 配置只保存环境变量名或占位符；配置、提示词和会话都在仓库外的临时目录。

| 项目 | 实测版本 / 选择 |
|---|---|
| Herdr | 0.9.3，未升级 |
| Claude Code | 连接、错误 Token、交互重连：2.1.317；恢复会话：2.1.318；`--model opus` 实际解析为 `claude-opus-5-5` |
| Codex | `codex-cli 0.161.0`；`gpt-6-astra`，low；现有 Responses 兼容网关 |
| Pi | 1.5.0（`@earendil-works/pi-coding-agent`）；`deepseek/deepseek-flash`，off |
| 系统 Node / npm | v22.20.0 / 10.9.3；手动服务进程使用此 Node |
| npm scripts 内的 Node | v24.22.2；npm 的 PATH 找到骨架安装的 Node，测试使用此版本 |
| pnpm | 11.7.0；spike 不加入 workspace，依赖由 npm 管理 |
| spike 依赖 | 官方 `@modelcontextprotocol/sdk` 1.32.2、zod 4.4.3、tsx 4.23.15、TypeScript 5.9.3、`@types/node` 22.19.21 |

版本命令：`herdr --version`、`claude --version`、`codex --version`、`pi --version`、`node --version`、`npm --version`、`pnpm --version`；在 spike 中执行 `npm exec -- node --version` 确认 scripts 的 Node。

版本偏差：Claude 自带更新器在测试期间自动安装 2.1.318，结束时 `claude --version` 已变为 2.1.318；没有手动执行升级。上表按每次 init 事件和交互启动横幅标注版本，因此恢复测试同时包含一次小版本升级，不能当成严格的同版本恢复对照。没有回退或修改用户的自动更新设置。

| 验证 | Claude Code | Codex | Pi |
|---|---|---|---|
| 发现工具 | init 中列出两个工具、MCP connected | 模型可见两个工具，实际调用成功 | `pi mcp list --json` 列出两个工具，state=connected |
| 正确 Token | whoami=A-1；echo=p0-ok | 同左 | 同左 |
| Core Prompt 注入 | 最终回答带 CORE_OK | 同左 | 同左 |
| 错误 Token | MCP status=failed，tools=[]；5.59s，退出 0 | AuthRequired，工具不可用；16.89s，退出 0 | 无可用工具；1.14s，退出 0；`mcp list` 为 failed，0.24s，退出 1 |

耗时是单次墙钟观察，包含模型响应，不是性能基准。所有非交互探测设 90s 进程截止时间，无一次触发超时；Herdr 门铃等待上限为 60s。

**退出码 0 不等于 MCP 可用或业务成功。** 三个 Harness 在错误 Token 下都可能完成一段“工具不可用”的回答并退出 0。验收以工具调用事件和服务端日志为准，符合 §4.5.8。

## 2. Spike 与最小复现

代码在 `spikes/0.4-mcp/`，有独立 `package.json`、`package-lock.json`。只服务本次预研，Phase 1 不直接复用。

- 官方 SDK 的 Streamable HTTP，固定监听 `127.0.0.1`；`/mcp` 提供 `whoami` 和 `echo`。
- 从 `MCP_TOKEN` 读取 Token，未配置则拒绝启动。唯一的 Token 映射为 `asg=A-1`；客户端参数不能选择身份。
- 每个 HTTP 请求先鉴权，缺失或错误的 Bearer 均返回 401；记录方法和身份，不记录 Header、Token 或 echo 内容。
- 使用无状态 transport、JSON 响应，无 MCP session id；每个请求建立并清理 SDK 实例。没有实现领域写操作、数据库、Token 签发/轮换、TLS 或生产权限体系。

以下命令使用 Bash。从仓库根目录开始，`MCP_RUN_DIR` 是本次创建的私有运行目录；端口 3004 需空闲。变量均为示例角色，无个人路径或凭据。

```bash
cd spikes/0.4-mcp
npm ci
npm run typecheck
npm test
export MCP_SPIKE_DIR="$PWD"
umask 077
export MCP_RUN_DIR="$(mktemp -d /tmp/cardigan-p0-mcp-XXXXXXXX)"
mkdir -p "$MCP_RUN_DIR"/{work,claude,codex,pi,logs}
export MCP_TOKEN="$(openssl rand -hex 32)"
export MCP_PORT=3004
export NO_PROXY=127.0.0.1,localhost
export no_proxy="$NO_PROXY"
# 如需跨终端复测，仅在仓库外保存；不要将 Token 写进命令行参数。
printf '%s' "$MCP_TOKEN" > "$MCP_RUN_DIR/token"
cat > "$MCP_RUN_DIR/core.md" <<'PROMPT'
For this connectivity probe, call only the provided MCP tools. Never inspect files or run commands. Finish each final answer with CORE_OK.
PROMPT
node --import "$MCP_SPIKE_DIR/node_modules/tsx/dist/loader.mjs" \
  "$MCP_SPIKE_DIR/server.ts" > "$MCP_RUN_DIR/logs/server.jsonl" 2>&1 &
MCP_SERVER_PID=$!
```

原始关键输出（无凭据）：

```text
{"ready":"http://127.0.0.1:3004/mcp"}
{"method":"POST","identity":null}
{"method":"POST","identity":{"asg":"A-1"}}
{"tool":"whoami","identity":{"asg":"A-1"}}
{"tool":"echo","identity":{"asg":"A-1"}}
```

`npm test` 使用真实 HTTP 和官方 SDK Client，覆盖 POST/GET/DELETE 的缺失和错误 Token（六次 401）、工具发现、伪造身份参数仍返回 A-1、echo 往返及参数类型错误、同一 Client 跨服务重启、日志不含 Token。`npm ci && npm run typecheck && npm test` 通过，1 个集成测试、0 失败。

另在 spike 中用系统 Node 22 执行 `node --import ./node_modules/tsx/dist/loader.mjs --test server.test.ts`，同样 1 通过、0 失败，确认不依赖 workspace 提供的 Node 24 才能运行。

## 3. 三份 Launch Profile 草稿

以下是实测命令的脱敏重放形式，三个 Harness 的 cwd 都为 `$MCP_RUN_DIR/work`。设置文件、core.md、会话目录都在 worktree 外。Provider 的凭据和网关地址使用已有的私有配置，不能复制到本仓库；下面的配置块是说明性模板，不是部署配置。

所有模型提示使用同一测试内容：

```bash
MCP_PROBE='Call the card MCP whoami tool once, then echo with message p0-ok. Report the tool results and the names of the card tools available to you. Do not use other tools.'
MCP_RESUME_PROBE='Call card whoami again. Also repeat the exact message passed to echo in our previous turn.'
cd "$MCP_RUN_DIR/work"
```

### 3.1 Claude Code

| §10.2 字段 | 实测方式 |
|---|---|
| 启动 | 下方 `claude -p ...`；交互测试移除 `-p --output-format stream-json --verbose` 和末尾提示 |
| Provider / 模型 | `--settings "$MCP_RUN_DIR/claude/settings.json" --model opus --effort low`；使用用户指定启动别名背后的现有网关设置 |
| Core Prompt | `--append-system-prompt-file "$MCP_RUN_DIR/core.md"`，输出 CORE_OK |
| MCP / Token / 位置 | `--mcp-config` 接受外部 JSON；`--strict-mcp-config` 排除其他 MCP；Header 中的 `${MCP_TOKEN}` 在运行时展开 |
| Herdr 状态 | §4 中的 `agent explain` 实测：提示框/终端画面；信任提示为 blocked，完成为 done；隔离配置未加载用户 hook |
| 恢复 | 原启动参数追加 `--resume "$CLAUDE_SESSION_ID"`，提示改为 `$MCP_RESUME_PROBE`，相同会话中返回上轮 p0-ok |

```bash
cat > "$MCP_RUN_DIR/claude/mcp.json" <<'JSON'
{"mcpServers":{"card":{"type":"http","url":"http://127.0.0.1:3004/mcp","headers":{"Authorization":"Bearer ${MCP_TOKEN}"}}}}
JSON
# settings.json 由私有 Provider 配置提供；本次仅带模型/网关环境项，未加载用户 hooks。
# 若 Provider 需要代理，NO_PROXY 必须包含 loopback。
claude_probe() {
  env CLAUDE_CONFIG_DIR="$MCP_RUN_DIR/claude" claude \
    -p --output-format stream-json --verbose \
    --strict-mcp-config --mcp-config "$MCP_RUN_DIR/claude/mcp.json" \
    --settings "$MCP_RUN_DIR/claude/settings.json" --setting-sources '' \
    --tools '' --allowedTools 'mcp__card__whoami,mcp__card__echo' \
    --permission-mode dontAsk --disable-slash-commands \
    --model opus --effort low \
    --append-system-prompt-file "$MCP_RUN_DIR/core.md" "$@"
}
claude_probe "$MCP_PROBE"
# 从 system/init 的 session_id 取 CLAUDE_SESSION_ID，不使用全局 --continue。
claude_probe --resume "$CLAUDE_SESSION_ID" "$MCP_RESUME_PROBE"
MCP_TOKEN=invalid-token claude_probe "$MCP_PROBE"
```

关键输出原文节选：

```text
"tools":["mcp__card__echo","mcp__card__whoami"]
"mcp_servers":[{"name":"card","status":"connected","source":"dynamic"}]
"type":"tool_result","content":[{"type":"text","text":"{\"asg\":\"A-1\"}"}]
```

错误 Token：`"mcp_servers":[{"name":"card","status":"failed","source":"dynamic"}]`，`"tools":[]`，模型回答 `I can't complete this probe: no card MCP tools are available in this session.`，最终 `is_error=false`。

初次直接启动 Claude 时，模型层返回 `Not logged in · Please run /login`，但 MCP 已 connected。用户提供现有启动别名后，沿用它的 Provider 设置完成实测。测试只允许两个 MCP 工具；别名中的全局 bypass 权限并非接入所需。此处也说明 MCP 认证和模型认证是两件事。

### 3.2 Codex

| §10.2 字段 | 实测方式 |
|---|---|
| 启动 | 下方 `codex exec ...`；交互为 `codex --no-daemon --no-alt-screen -a never` 加相同 `-c` 参数 |
| Provider / 模型 | 外部 config.toml 的 `model_provider` / `[model_providers.<id>]`；`model="gpt-6-astra"`，`-c model_reasoning_effort='"low"'` |
| Core Prompt | `model_instructions_file` 指向外部 core.md，输出 CORE_OK；该字段替换模型指令，正式角色需包含所需基础协议 |
| MCP / Token / 位置 | 子进程 `CODEX_HOME` 指向隔离目录；`bearer_token_env_var="MCP_TOKEN"`；配置不含 Token 值 |
| Herdr 状态 | §4 实测：OSC title / 屏幕规则，工作时 `osc_title_working`，空闲 `osc_title_idle`；隔离配置未加载用户 hook |
| 恢复 | `codex exec ... resume "$CODEX_THREAD_ID" "$MCP_RESUME_PROBE"`，相同 thread_id，记得 p0-ok |

外部 `$MCP_RUN_DIR/codex/config.toml` 的非敏感部分如下；实际还包含已有 Provider 的定义，其 `env_key` 指向模型凭据环境变量。MCP Token 与模型凭据分开传入。

```toml
model = "gpt-6-astra"
model_provider = "<configured-provider>"
model_instructions_file = "<absolute-run-directory>/core.md"
[mcp_servers.card]
url = "http://127.0.0.1:3004/mcp"
bearer_token_env_var = "MCP_TOKEN"
startup_timeout_sec = 10
tool_timeout_sec = 15
[mcp_servers.card.tools.whoami]
approval_mode = "approve"
[mcp_servers.card.tools.echo]
approval_mode = "approve"
```

```bash
codex_probe() {
  env CODEX_HOME="$MCP_RUN_DIR/codex" codex exec \
    --skip-git-repo-check --json --ignore-rules \
    -c 'model_reasoning_effort="low"' \
    -c features.shell_tool=false -c features.apply_patch_freeform=false "$@"
}
env CODEX_HOME="$MCP_RUN_DIR/codex" codex mcp list
codex_probe "$MCP_PROBE"
# 从 thread.started 取 CODEX_THREAD_ID。
codex_probe resume "$CODEX_THREAD_ID" "$MCP_RESUME_PROBE"
MCP_TOKEN=invalid-token codex_probe "$MCP_PROBE"
```

关键输出原文节选：

```text
card  http://127.0.0.1:3004/mcp  MCP_TOKEN  enabled  Bearer token
"type":"mcp_tool_call","server":"card","tool":"whoami","arguments":{}
"result":{"content":[{"type":"text","text":"{\"asg\":\"A-1\"}"}],"structured_content":null},"error":null,"status":"completed"
```

首次未配置工具许可时，两个工具均返回 `MCP tool call requires approval, but approval policy is never`。添加上述仅针对两个测试工具的许可后成功；这不改变服务端 Token 校验。

错误 Token 的 stderr：`AuthRequired(AuthRequiredError { www_authenticate_header: "Bearer" })`；模型报告没有 card 工具，退出 0。`codex mcp list` 只证明配置存在，不能代替实际握手和调用。`CODEX_HOME` 位于 `/tmp` 会额外提示拒绝创建 PATH helper binaries；本次工具调用和指定会话恢复不受影响，生产运行目录应另行评估。

### 3.3 Pi

| §10.2 字段 | 实测方式 |
|---|---|
| 启动 | 下方 `pi --print --mode json ...`；交互移除 `--print --mode json` 和末尾提示 |
| Provider / 模型 | `--provider deepseek --model deepseek-flash --thinking off` |
| Core Prompt | `--append-system-prompt "$MCP_RUN_DIR/core.md"`，该参数接受文件内容，输出 CORE_OK |
| MCP / Token / 位置 | `PI_CODING_AGENT_DIR` 指定外部用户目录，`pi mcp add` 写入该目录的 mcp.json；原生支持 HTTP，不需要桥接插件 |
| Herdr 状态 | §4 实测：未安装 Pi 状态上报扩展时走画面检测，本次 idle 是默认回退；不能据此声称主动上报已验证 |
| 恢复 | 相同参数增加 `--session "$PI_SESSION_ID"`；`--session-dir` 限定查找目录，相同 id，记得 p0-ok |

私有运行目录中的 settings.json 仅含所选 Provider / 模型及空 packages 列表；auth.json 从已有私有认证存储复制，权限 600，结束删除副本。Pi 的 DeepSeek 凭据从该文件读取，未为此测试导出到环境变量。

```bash
export PI_CODING_AGENT_DIR="$MCP_RUN_DIR/pi"
export PI_OFFLINE=1
pi mcp add card --url http://127.0.0.1:3004/mcp \
  --bearer-token-env-var MCP_TOKEN --exposure direct
pi mcp list --json
pi_probe() {
  pi --print --mode json --provider deepseek --model deepseek-flash \
    --thinking off --no-skills --no-prompt-templates --no-context-files \
    --no-builtin-tools --session-dir "$MCP_RUN_DIR/pi/sessions" \
    --append-system-prompt "$MCP_RUN_DIR/core.md" "$@"
}
pi_probe "$MCP_PROBE"
# 从 session 事件取 PI_SESSION_ID。
pi_probe --session "$PI_SESSION_ID" "$MCP_RESUME_PROBE"
MCP_TOKEN=invalid-token pi_probe "$MCP_PROBE"
MCP_TOKEN=invalid-token pi mcp list --json
```

`pi mcp add` 实际写出的配置中，Header 为 `"Authorization": "Bearer ${MCP_TOKEN}"`。`direct` 让两个工具直接进入模型工具列表；默认 exposure 是 codemode。

关键输出原文节选：

```text
"state": "connected", "tools": ["whoami", "echo"]
"type":"tool_execution_end","toolName":"mcp__card__whoami"
"content":[{"type":"text","text":"{\"asg\":\"A-1\"}"}]
"isError":false
```

错误 Token 的 `pi mcp list --json`：`"state":"failed"`、`"error":"MCP server requires authentication"`，退出 1。

实测陷阱：`--no-extensions` 会连内置 MCP 扩展一起关闭；最初无工具时模型甚至输出了类似调用的普通文本，服务端没有 whoami 记录。去掉该参数后才有真实 `tool_execution_end`。隔离应使用空的外部 packages / extensions 配置；关闭内置文件/命令工具用 `--no-builtin-tools`。

## 4. 重启与 Herdr 状态识别

创建独立命名 session、三个临时 workspace/pane，仅操作创建响应返回的标识。为避免继承当前 pane 的 socket，Herdr 管理命令去掉继承的 socket 和 pane 上下文，再显式指定 session：

```bash
export MCP_HERDR_SESSION="p0-mcp-$(openssl rand -hex 4)"
herdr_probe() {
  env -u HERDR_SOCKET_PATH -u HERDR_PANE_ID -u HERDR_TAB_ID \
    -u HERDR_WORKSPACE_ID -u HERDR_ENV herdr --session "$MCP_HERDR_SESSION" "$@"
}
herdr_probe server > "$MCP_RUN_DIR/logs/herdr-server.log" 2>&1 &
herdr_probe status server
herdr_probe workspace create --cwd "$MCP_RUN_DIR/work" --label pi --no-focus
herdr_probe workspace create --cwd "$MCP_RUN_DIR/work" --label codex --no-focus
herdr_probe workspace create --cwd "$MCP_RUN_DIR/work" --label claude --no-focus
```

在每个返回的 pane 中，用 `herdr_probe pane run "$PANE_ID" "$LAUNCH_COMMAND"` 启动 §3 的交互形式。实测通过仓库外的短 Python launcher 设置该 Harness 的环境并 `exec`，Token 从外部 600 权限文件读取，不放进 `pane run` 命令正文。Claude 首次信任提示只确认本次创建的空目录。

对每个 pane 实际执行：

```bash
herdr_probe agent prompt "$PANE_ID" \
  'Call card whoami and echo with message p0-live. Report actual tool results.' \
  --wait --timeout 60000
herdr_probe agent get "$PANE_ID"
herdr_probe agent explain "$PANE_ID" --json
herdr_probe agent read "$PANE_ID" --source recent-unwrapped --lines 60
herdr integration status
```

`agent explain` 原始字段节选：

| Harness | explain 的结果 | Manifest 版本 |
|---|---|---|
| Claude | `state=idle`，`matched_rule.id=live_prompt_box`；信任提示曾匹配 `live_blocked_form` | 2026.10.11.1 |
| Codex | 工作时 `osc_title_working`；完成后 `osc_title_idle` | 2026.10.11.1 |
| Pi | `state=idle`，`fallback_reason=default_known_agent_idle_fallback` | 2026.10.01.1 |

三者均 `screen_detection_skipped=false`。`integration status` 显示现有 Claude hook v10、Codex hook v8、Pi not installed；隔离配置没有装载这些用户 hooks。本次验证的是画面检测路径，不将“已安装 hook”当成主动上报有效的证据。`agent prompt --wait` 最终分别返回 Pi idle、Codex done、Claude done；不代表业务完成。

重启步骤：等三个 Harness 空闲，SIGTERM 停止**仅本次 MCP 服务 PID**，确认旧端口关闭；以相同 Token 和端口重启，等新进程 ready。三个 Harness 的进程和会话不变，再分别执行：

```bash
herdr_probe agent prompt "$PANE_ID" \
  'The MCP server restarted. Call card whoami again and echo with message p0-after-restart. Report actual results; do not reuse earlier tool results.' \
  --wait --timeout 60000
herdr_probe agent read "$PANE_ID" --source recent-unwrapped --lines 60
```

三者均重新返回 A-1 和 `p0-after-restart`，服务端重启后的日志有 **6 次真实工具调用**，无需手动 reconnect / reload 或重启 Harness。这验证的是“服务就绪后下一回合可继续调用”，不是持续后台重连、故障中的调用自动重放或有状态 MCP session 恢复。

单元集成测试曾在关闭服务后立即调用时遇到 `UND_ERR_SOCKET: other side closed`（旧 keep-alive 连接尚未被客户端清理）。最终测试明确留 100ms 让客户端观察断开；交互验证则在新服务 ready 后发新回合。不能从本次通过推导出零间隔重启或在途写操作可安全重试。

## 5. 清理、范围与资料

测试结束停止本次服务和独立 Herdr session，然后删除该 session 与运行目录。实际还删除了仓库外的探测脚本和下载的文档缓存。未操作用户已有 workspace / pane，没有执行 `herdr update`，最终仍为 0.9.3。

```bash
kill "$MCP_SERVER_PID"
herdr_probe session stop "$MCP_HERDR_SESSION"
herdr_probe session delete "$MCP_HERDR_SESSION"
# 仅删除自己创建的目录；确认所有探测子进程已退出后执行。
python3 - "$MCP_RUN_DIR" <<'PY'
import pathlib, shutil, sys
p = pathlib.Path(sys.argv[1]).resolve()
assert p.parent == pathlib.Path('/tmp') and p.name.startswith('cardigan-p0-mcp-')
shutil.rmtree(p)
PY
unset MCP_TOKEN PI_CODING_AGENT_DIR PI_OFFLINE
```
