# 0.5b · 主机发起的 Git 模型预研

日期：2026-11-04。对应 `docs/plans/phase-0.md` v3 的 §2、§3 任务 0.5b；对照开发方案 §12、§13.2、§13.9，并核对 §4、§6、§14、§20。

## 1. 结论

本地路径和 SSH 两套流程均通过：hub 将基线推入 worker 的 `refs/remotes/origin/main`，不改变 worker 当前检出的分支、HEAD、文件或干净状态；worker 只在 worktree 中提交；hub 拉取交付、校验 SHA、批量备份，并在接管后拉取新提交、中心合并。

| 验证 | 本地路径 | SSH |
|---|---|---|
| 基线不影响 worker 当前 checkout | parked 分支、HEAD、parked.txt、status 均不变 | 同左 |
| 指定 SHA 在交付分支上 | 接受；故意选择第一个提交，D-1 固定到它，而非第二个提交的分支 tip | 同左 |
| SHA 不存在 | 拒绝，已接受的 D-1 不变 | 同左 |
| SHA 存在但不在交付分支历史中 | 拒绝，已接受的 D-1 不变 | 同左 |
| 一条 refspec 拉取所有 agent/* | 两个分支均进入 worker-a 的备份命名空间 | 同左 |
| 拉取失败后的备份 | 不变 | 连接拒绝、握手超时后均不变 |
| 接管 | 新仓库的 worktree 从最后备份 SHA 开始，提交后被 hub 拉回 | 同左，替代工作机仍用第三个本地目录模拟 |
| 中心合并 | main 的两个父提交分别为原基线和接管交付 | 同左 |
| 清理 | 本次临时根目录全部删除 | 本地及专用用户下的临时目录全部删除 |

SSH 只连接用户预先配置的 **`cardigan-agent@localhost`**，身份文件固定为 **`~/.ssh/cardigan_spike_ed25519`**。文中将这个逻辑 worker 称为 `worker-a`；它实际与 hub 同机、不同系统用户。没有连接其他机器，没有使用 sudo，没有修改 SSH 配置、创建/删除用户或密钥。

**计划差异**：计划举例用外部保留地址观察 TCP 连接超时；本次用户明确要求不连接其他机器，因此用 loopback 上“不发 SSH banner 的临时 TCP listener”验证 `ConnectTimeout`，另用关闭的临时端口验证拒绝连接。没有验证真实网络丢包或 TCP SYN 超时。这一差异不隐藏为完整多机断网验证。

版本命令：`git --version`、`ssh -V`、`node --version`、`npm --version`、`herdr --version`、`codex --version`、`claude --version`、`pi --version`；在 spike 中用 `npm exec -- node --version` 确认 npm 的执行版本。SSH 脚本还在 worker 运行 `git --version`。

`spikes/0.5-git/` 是独立 npm 项目，不加入 pnpm workspace，使用 Node 内置模块，没有第三方依赖。计划没有指定 0.5b 的脚本语言，本次用 `.mjs`，无需编译或改动产品包；Phase 1 不直接复用。

从仓库根目录执行：

```bash
cd spikes/0.5-git
npm ci
npm test                 # 本地路径，先通过再执行 SSH
npm run test:ssh         # 仅连接上述专用用户，自动执行并断言步骤 1–7
# 不通过测试框架、直接运行同一流程：
npm run spike -- local
npm run spike -- ssh
# 使用系统 Node，不依赖 workspace 的 Node：
node --test git-model.test.mjs
```

每次运行自己创建空目录，全部完成或遇到异常后进入 `finally` 清理，不需要已有仓库或保留上次结果。运行目录是 `/tmp/cardigan-p0-git-*`；SSH worker 使用自己创建的 `/tmp/cardigan-p0-git-worker-*`，目录归专用用户。脚本拒绝其他 mode，没有目标主机配置入口。

脚本显式调用的 Git 命令均指定 cwd，并禁用全局/系统 Git 配置、签名、hooks 和凭据助手；只给本次命令传入测试作者 `Cardigan Spike <spike@example.invalid>`，不修改用户 Git 配置。SSH transport 自动启动的服务端 git-upload-pack/git-receive-pack 使用专用账户的正常环境，凭据前置检查见 §4。本地场景只验证 Git 行为；不同用户的权限隔离由 SSH 场景覆盖。

SSH 的实际参数等价于：

```bash
ssh -F /dev/null -4 -i ~/.ssh/cardigan_spike_ed25519 \
  -o IdentitiesOnly=yes -o IdentityAgent=none -o BatchMode=yes \
  -o ForwardAgent=no -o ClearAllForwardings=yes \
  -o StrictHostKeyChecking=yes -o UpdateHostKeys=no \
  -o ConnectTimeout=3 -o ConnectionAttempts=1 \
  -o ControlMaster=no -o ControlPath=none \
  cardigan-agent@localhost 'git --version'
```

Git 的 SSH transport 通过 `GIT_SSH_COMMAND` 使用同一组参数，并设置 `GIT_SSH_VARIANT=ssh`。`-F /dev/null` 不读取用户路由/转发配置；不使用控制连接复用，保证故障测试确实建立本次连接；保持 host key 校验，不更新 known_hosts。每条子进程命令另有 15s 上限，整体验收测试上限 90s。

## 3. 各步骤的 Git 命令与观察

完整、可直接执行的命令序列在 `git-model.mjs`，上述 npm 命令即为复现入口。以下展示关键原生命令，变量表示该次运行创建的路径：`HUB` 为 hub 临时根目录，`CENTRAL=$HUB/central.git`，`INTEGRATION=$HUB/integration`；`WORKER` 为 worker 基础仓库，`WT` 为它的 worktree，`SOURCE` 为本地 `$WORKER` 或 `ssh://cardigan-agent@localhost$WORKER`。SSH 场景中的 worker 命令均由 hub 发起 SSH 后执行。

### 3.1 中心与基线

```bash
git -C "$HUB" init --bare --initial-branch=main "$CENTRAL"
git -C "$HUB" clone --no-local "$CENTRAL" "$INTEGRATION"
# 在 integration 写 README.md，add、commit 后：
git -C "$INTEGRATION" push origin main
# worker 初始化为已有提交的 parked 分支，保留 parked.txt：
git -C "$WORKER" init --initial-branch=parked
# hub 推送到远程跟踪引用，而非 worker 当前检出的分支：
git -C "$CENTRAL" push "$SOURCE" refs/heads/main:refs/remotes/origin/main
```

worker 基础仓库用 `git init` 后由 hub 注入基线，没有从 worker 向 hub clone/fetch 的反向连接。它没有配置 origin URL，但 `refs/remotes/origin/main` 是有效的基线引用。没有设置 `receive.denyCurrentBranch=ignore` 或 `updateInstead`。

脚本比较推送前后的 `git rev-parse HEAD`，并断言 `git symbolic-ref HEAD` 为 `refs/heads/parked`、`git status --porcelain` 为空、parked.txt 内容不变、origin/main 等于中心 main。原始输出：

```text
{"mode":"ssh","event":"baseline","checkoutUnchanged":true,"workerRemotes":0}
```

### 3.2 工作项与交付校验

```bash
git -C "$WORKER" worktree add -b agent/C-1/W-1 "$WT" refs/remotes/origin/main
# 分别写 first.txt、second.txt，各执行 git add 和 git commit，共两个提交。
git -C "$WORKER" branch agent/C-2/W-1 refs/remotes/origin/main
# hub 先拉取命名分支的快照，不直接把未校验内容发布为 Delivery：
git -C "$CENTRAL" fetch --no-tags --no-write-fetch-head "$SOURCE" \
  +refs/heads/agent/C-1/W-1:refs/cardigan/incoming/D-1
git -C "$CENTRAL" cat-file -e "$SHA^{commit}"
git -C "$CENTRAL" merge-base --is-ancestor "$SHA" refs/cardigan/incoming/D-1
# 只有上述两个检查通过才发布指定 SHA：
git -C "$CENTRAL" update-ref refs/cardigan/deliveries/D-1 "$SHA"
git -C "$CENTRAL" update-ref -d refs/cardigan/incoming/D-1
```

三个输入是：该分支的第一个提交、40 个 `f` 组成的不存在 SHA、hub 用 `git commit-tree "$BASE^{tree}" -p "$BASE" -m 'Unrelated sibling'` 创建的兄弟提交。第三个对象确实存在且为 commit，但不是交付分支的祖先，不能仅靠 `cat-file` 或 fetch 成功就接受。

“在分支上”在本 spike 中明确为“是本次拉取分支 tip 的祖先或 tip 本身”。第一个提交被接受后，D-1 始终指向第一个提交；第二个提交用于后续备份和接管。两次拒绝都额外检查 D-1 没有被覆盖。

```text
{"mode":"ssh","event":"delivery","decisions":["accepted","missing-object","not-in-branch"],"pinnedToRequestedAncestor":true,"rejectedAttemptsPreservedRef":true}
```

### 3.3 批量备份

```bash
git -C "$CENTRAL" fetch --no-tags --no-write-fetch-head "$SOURCE" \
  '+refs/heads/agent/*:refs/cardigan/backups/worker-a/agent/*'
```

一个 refspec 拉取 `agent/C-1/W-1` 和 `agent/C-2/W-1`。脚本分别验证其值为第二个提交和原基线。使用 machine 命名空间避免不同 worker 的同名分支冲突；前导 `+` 允许备份跟踪分支改写，但这不是不可变的审计历史。

### 3.4 故障、接管与合并

本地场景只把本次 worker 仓库重命名为 `repo.offline`，随后 hub 对原路径 fetch。SSH 场景不停止 sshd、不改防火墙，也不改变账户配置：用 Node 在 loopback 取得临时端口，关闭 listener 后测试连接拒绝；另开一个接受 TCP 但不发送 SSH banner 的 listener 测试握手超时。两次都只对这条 fetch 的 `GIT_SSH_COMMAND` 追加 `-p "$PORT"`，主机仍为 localhost。

| 故障 | 实测退出码 | 单次耗时 | 关键原始错误（临时端口省略） |
|---|---|---|---|
| 本地路径不可达 | Git 128 | 3ms | `fatal: '<worker>/repo' does not appear to be a git repository` |
| SSH 无服务端口 | Git 128 | 6ms | `ssh: connect to host localhost port …: Connection refused` |
| SSH 不发 banner | Git 128 | 3008ms | `Connection timed out during banner exchange` |

每个失败都有 `killed=false`；超时来自 SSH 的 `ConnectTimeout=3`，不是外层 15s 强杀。OpenSSH 随系统安装的文档 `ssh_config(5)` 明确说明 ConnectTimeout 覆盖连接建立、初始握手和密钥交换。耗时仅是单次观察，脚本要求超时在 2.5–10s 内。无监听端口存在被其他进程抢占的微小竞态；脚本会核对 `Connection refused`，不把其他错误当成通过。

失败后先验证备份引用仍等于最后成功拉取的第二个提交，再在第三个本地目录模拟替代 worker：

```bash
git -C "$HUB" init --initial-branch=parked "$REPLACEMENT"
git -C "$CENTRAL" push "$REPLACEMENT" \
  refs/cardigan/backups/worker-a/agent/C-1/W-1:refs/remotes/origin/checkpoint
git -C "$REPLACEMENT" worktree add -b agent/C-1/W-1 "$RESUMED" refs/remotes/origin/checkpoint
# RESUMED 的初始 HEAD 必须等于最后备份 SHA；写 takeover.txt、add、commit。
git -C "$CENTRAL" fetch --no-tags --no-write-fetch-head "$REPLACEMENT" \
  +refs/heads/agent/C-1/W-1:refs/cardigan/deliveries/D-2
git -C "$INTEGRATION" fetch origin refs/cardigan/deliveries/D-2
git -C "$INTEGRATION" merge --no-ff --no-edit FETCH_HEAD
git -C "$INTEGRATION" push origin main
```

最后检查接管提交的父提交等于备份 SHA、D-2 等于接管提交、中心 main 的两个父提交正确、最终树包含 README.md、first.txt、second.txt、takeover.txt，且 takeover.txt 内容正确。

```text
{"mode":"ssh","event":"takeover","continued":true,"fetchedByHub":true}
{"mode":"ssh","event":"merged","files":["README.md","first.txt","second.txt","takeover.txt"]}
```

这里仅合并自己创建的临时仓库 main，不涉及 Cardigan 的 main。接管是本次测试中已授权的模拟步骤；没有实现自动接管、业务状态机或 SSH 故障恢复调度。

## 4. worker 凭据与清理

SSH 前置检查通过：没有转发来的 `SSH_AUTH_SOCK`，没有配置 credential helper，`.ssh` 中只有 `authorized_keys`；常见 Git/GitHub/GitLab 凭据文件和 `.netrc` 不存在。只检查名称/存在性，没有读取密钥或凭据内容。执行 worker Git 命令时还用 `env -i` 清空环境，并禁用全局/系统配置和凭据助手。

```text
{"mode":"ssh","event":"worker-preflight","git":"git version 2.53.0","privateKeys":false,"forwardedAgent":false,"credentialFiles":false}
```

worker 的 Git remote 列表为空；实现中没有从 worker 发起 fetch/push，只有 hub 发起的 SSH/git-upload-pack/git-receive-pack。hub 私钥只由 hub 的 SSH 客户端使用，不复制到 worker，也不通过 agent forwarding 暴露。上述检查证明本次流程无需 worker Git 凭据，不是对任意位置的凭据泄露或所有 OS 权限的完整审计；没有用 sudo 探测账户权限，也没有做反向 SSH 登录尝试。

清理由脚本 `finally` 执行：销毁测试 socket，关闭临时 listener；SSH 删除自己通过 mktemp 创建的 worker 根目录，并远端 `test ! -e` 确认；本地删除自己创建的 hub 根目录，测试再断言路径不存在。SSH 路径先匹配 `/tmp/cardigan-p0-git-worker-<随机后缀>`，不接受用户传入的删除目标。本次各运行均输出：

```text
{"mode":"ssh","event":"cleaned","local":true,"worker":true}
```

如清理时 SSH 本身不可用，脚本报失败，需只针对该次创建的临时目录补清理，不扩大到用户 home。专用用户、authorized_keys 以及 hub 的预置测试密钥全部保留，由用户决定后续删除。

## 5. 验证结果与未覆盖项

- `npm ci && npm test && npm run test:ssh`：本地和 SSH 各 1 个真实 Git 集成测试，全部通过；每个场景都执行步骤 1–7 及上述断言。开发过程中两套流程重复从空目录运行，无需上次结果。
- `node --test git-model.test.mjs`：系统 Node 22 的本地流程通过，确认 spike 可独立运行。
- `git diff --cached --check` 通过；只提交研究报告、spike 脚本/测试及 npm 清单/lockfile，无环境配置、私钥、Token、个人路径或原始日志。
- 未覆盖：跨机器链路、TCP SYN 黑洞、断网期间仍运行的旧 Agent、未 commit/未备份修改、分支并发改写、多个 hub 写入、合并冲突、不可变备份保留策略和生产级权限隔离。脚本只使用固定测试 SHA，尚未实现不可信输入校验、完整错误分类或业务幂等接口。
- D-2 是脚本创建并核对父提交的接管提交；没有把 D-1 的负例校验包装成生产 Delivery API。所有故障都在受控夹具内触发，不能据此绕过 §13.9 的等待、人工确认或旧 Assignment 的隔离。

## 6. 对开发方案的修改建议

按计划留给 Claude 在 0.6 汇总，本 PR 不修改 `docs/development-plan.md`。

1. **§12.2**：写明 hub 可向非 bare worker 仓库的 `refs/remotes/origin/main` 推基线；worker 当前 checkout 保持不变，工作项显式从所记录的基线创建 worktree。不要通过关闭 `receive.denyCurrentBranch` 来同步工作目录。
2. **§12.3**：把“拉取成功即完成校验”细化为“先拉取 Assignment 指定分支快照，再检查 SHA 为 commit 且是该快照 tip 的祖先，最后发布精确 SHA”。Delivery ref 不应直接等同于分支最新 tip；拒绝输入不能覆盖已接受的 Delivery。
3. **§12.3 / §12.6**：批量备份 refspec 可使用 `+refs/heads/agent/*:refs/cardigan/backups/<machine_id>/agent/*`，避免同名分支跨机器碰撞；需另决定分支强制改写、备份历史保留与清理规则。
4. **§13.2 / §13.4 / §14**：记录 localhost 专用用户也是可用的 SSH transport 验证方式；明确 hub 独占私钥、不转发 agent，worker 不配置 hub remote 或凭据。真实部署仍需独立权限/网络验证。
5. **§13.9**：记录 SSH 连接/握手超时、外层命令截止时间及失败前最后成功备份 SHA；传输失败不得推进备份游标或认定业务失败/完成。接管只从已拉取的检查点继续，旧 worker 的隔离与未备份修改处置仍由控制面和人决定。
