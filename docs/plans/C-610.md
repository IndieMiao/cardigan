# C-610 审核收敛

宗旨：打通阻塞，不新增人工确认、拍板、守卫或停摆条件。只对流程版本 ≥5 的卡生效（当前项目新卡和在途卡都是 5）；≤4 的旧卡保持原行为。

## 1. 必改项必须有依据（`issues[].basis`）

`submit_review` 的每条 `must_fix=true` 填 `basis`，取值：

| 写法 | 含义 |
|---|---|
| `AC1`…`ACn` | 本卡第 n 条验收标准 |
| `INV1`…`INVn` | 本卡 `card.invariants` 第 n 条（由对齐回合写入） |
| `PC1`…`PCn` | 当前通过条件清单第 n 条（见 §2） |
| `lost_work` | 会丢工作或数据 |
| `dual_executor` | 会出现两个执行者 |
| `security` | 凭据泄露、越权、注入（§14） |
| `check_failed` | 必跑测试或检查实际失败 |
| `ui_copy` | 界面新增了未要求的说明小字（AGENTS.md 界面规则） |

- 缺 `basis` 的必改项由系统改记为后续跟进：`must_fix=false`，`follow_up.reason=no_basis`，不挡合并。
- `basis` 写了但格式不对或超出范围时直接报参数错误，让审核员当场改正（不是流程停摆）。
- 后续跟进不挡合并；卡片合并时系统把全部跟进汇总成后续卡草稿（标题、目标、逐条来源）发给 PM Ops，PM 决定是否开卡。`get_card.follow_up_draft` 随时可看。

后五个是项目级常驻不变量，对应原代码审核“四类必改”里验收以外的三类（丢数据、安全、检查失败）、本卡宗旨里的两类停止条件和既有界面规则，保证安全、权限、数值边界问题只要对应到依据就仍是必改（卡片范围外条款）。

## 2. 第 2 次驳回给通过条件清单（`pass_conditions`）

- 同一验证项连续第 2 次驳回（当前连续驳回中还没有清单）时，`submit_review` 必须带 `pass_conditions`：1～10 条，每条写可验证的条件和依据（AC/INV/常驻不变量）。缺失时报参数错误。第 1 次驳回附带的清单不保存、不生效。
- 清单从下一轮起生效，直到通过或 conditional 打断连续驳回。之后的审核只核对清单：必改项依据须为 `PCn`、`INVn` 或 `lost_work`/`dual_executor`/`security`/`check_failed`，或 impact 为 `data_or_permission`（数据、权限、数值上限错误，卡片范围外条款要求不降低标准）；其余（包括新发现的边角）改记为跟进（`outside_checklist`），新发现的举证门槛只对仍阻塞的必改项生效。
- 审核只剩跟进项时，驳回类别、`recheck_required` 和 `followup_card_id` 不再适用，跟进照常保存，交付继续。

## 3. 第 3 次驳回开对齐回合

- 连续第 3 次驳回时不再开 PM 拍板，系统在验证项上记 `review_alignment`（open），验证项进入等待，并通知作者用 `post_comment.review_alignment={step:"propose",invariants:[...]}` 提出不变量清单（1～10 条）；作者可同时继续修改、交付。
- 另一方（通常是审核员）回复该条：`step:"confirm"` 同意，或 `step:"dispute"` 说明分歧。任一方都可提案，提案人可在对方回复前重新提案。
- 同意：清单追加到 `card.invariants`（之后可用 `INVn` 引用），连续驳回视为已对齐，系统按现有规则自动加轮并恢复审核；新交付已到则直接审，没到则唤醒作者返工。同一段连续驳回之后的驳回继续自动加轮，不再开对齐或拍板。
- 分歧：走原有的连续驳回拍板交 PM，上下文附提案和分歧回帖；PM 处理方式不变。
- 卡片在部署前已有待处理的连续驳回拍板时沿用该拍板，不另开对齐。

## 4. 守卫类意见降级

必改项描述命中守卫特征（新增人工确认/拍板、停摆或停住、核不清就停、fail closed 等）时改记为跟进（`guard`），除非依据是 `lost_work`、`dual_executor` 或 `security`（安全按卡片范围外条款不降低标准；引用 `PCn` 时按该条件的依据判断）。要求移除多余确认或停摆的意见不算守卫。

对齐分歧时带上触发本轮的驳回，并行审核对同一组共享必改项的分歧沿用同一个 PM 拍板。

## 5. 角色说明

reviewer、independent_reviewer 和 design_director 共用同一组审核收敛规则（design_director 也会提交必改项，一并更新）；pm 改为只处理对齐分歧和部署前遗留的长连续驳回，合并后按草稿决定是否开后续卡；AGENTS.md 的 Flow Lite 默认值同步。

## 6. 指标

`project_snapshot.review_convergence.rejection_streak_episodes` 每次有验证项达到连续 3 次驳回就记一条（卡号、验证项、本次最长连续次数、达到时间）；`rejectionStreakCards(state, {from, to})` 按时间窗口对卡去重，同一张卡在部署前后各自复发时两边都会计入。上线前基线已回填到卡上，上线后的对比作为合并后跟进。
