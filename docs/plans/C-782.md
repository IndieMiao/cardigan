# C-782：交付后提前发现合并冲突，并让冲突修复能沿用审核

孙悟空按卡片目标实现三件事：main 前进后对在途卡试合并并提前通知作者；让 ADR 0011 的审核沿用在常见冲突修复上真正生效；把一类高频冲突文件改成不再互相冲突的结构。

## 1. 试合并不占锁（验收 1）

- 试合并只调用 `git merge-tree --write-tree`（经 `CentralRepositoryService.trialMerge`），在中心裸库里写树和 blob 对象，不建提交、不写 ref、不碰索引和工作区。之前的路径比较用 `merge-base` 和 `diff-tree`，同样只读。
- 这些调用不经过 `RepositoryLock`、`hostRepositoryLock`（Linux flock）、`MergeMutex`／`tryPublication` 或 `MergeChecks.serial`。在本仓库里，这几把锁只包在工作区、构建检出、交付发布、候选推送、镜像和备份外面；中心库上的合并准备本来就靠 CAS 写 ref，不加锁。
- 试合并在调度 tick 里于事务外执行（与 `MergeShadowObserver` 相同），不在发布锁内。所有 Git 读取结束后重读一次基线，变了就丢弃本轮结果，下一轮重试。
- 测试 `apps/server/src/early-conflicts.test.ts` 用真实 Git 验证：`ServerGit` 自己的项目锁被占住时，`trialMerge` 照常返回冲突文件；锁采样里只有测试自己那次占锁；前后 ref 列表完全相同。

## 2. main 前进后提前通知（验收 2）

- 主机：`EarlyConflictObserver.tick` 挂在调度 tick 上，紧跟合并影子观察。候选是审核中或待合并卡片的当前产出交付（git_head，产出项为 delivered 或 accepted），且同一基线分支、卡片未暂停。只有双方自分叉以来改过的路径有重叠（同一路径，或一方是另一方的目录）才试合并；分叉点不唯一时直接试合并。结果按“交付、HEAD、基线”缓存。Git 出错不记事件，下一轮重试，也不把原始诊断写进事件。
- 领域：内部命令 `notify_early_merge_conflicts`（仅 system）。它在新快照里重新核对候选，写 `early_merge_conflict_detected` 事件和系统时间线，内容包括交付、HEAD、基线、排序去重后的冲突文件。卡片、工作项和审核状态都不改；合并闸门照常准备和检查真实候选。
- 防抖：
  - 同一交付只提醒一次。之后 main 再怎么前进都并进这一条，作者重新交付后，新交付另算一条。
  - 作者有未结束的 Run（含排队中）、被人工停止、负责人失效或卡片暂停时不发，也不做 Git 读取；条件恢复后的下一轮再发。所以在途审核不会因为反复提醒而频繁作废。
  - 一轮里同一交付的重复探测只发一条。
- 路由：只通知当前产出负责人，类型为 instruction，按普通 followup 唤醒。负责人失效、作者已经重交，或事件不是本项目系统写的，就不通知，也不转给 PM。通知正文会提示：只合入基线和解冲突的重交，已知遗漏和附件沿用上一版原文（见第 3 节）。

## 3. 审核沿用为什么几乎不命中，怎么改（验收 3）

查到两个原因：

1. **证明太窄**。原规则只承认一种冲突解决：每个冲突块都只留作者一侧，等于丢掉 main 的改动。真实的冲突大多是两边在同一处插入行（比如 barrel 导出、导入列表、选项字段、文档段落），作者会把两边都留下，这种解决原规则证明不了。
2. **内容门槛**。原来要求前后两次交付的 `test_results` 完全相同。可冲突修复后重新提交时，测试结果必然写着新的预检编号、新 SHA 和新基线，所以跨 SHA 的沿用实际上一次都过不了。C-701 和 C-501 的真实交付都是这样；它们的已知遗漏也被作者改写过。

改法（不放宽审核）：

- `review-equivalence`：原规则不通过时，用 diff3 格式（带合并基）重新渲染已审交付在可信 main 上的合并结果，再逐块比对。合并基为空、两边只在同一处插入行的块，可以原样保留两边插入的行，顺序不限；其它块仍只认作者一侧；块外的内容必须与自动合并结果逐字节相同。
  - 这样作者的已审行和 main 的已合入行都一字不差。内容和两处插入隔开一行时 Git 自动合并出来的结果相同，而自动合并的内容本来就可以沿用。
  - 两边改的是同一行、手工改写、多出或少了一行，都证明不了，仍然完整审核。证明里记下 `union_paths`。
- `review-reuse`：跨 SHA 时（只靠主机证明），不再比较作者自报的 `test_results`。新 SHA 另有同 SHA 预检和最终合并检查。同 SHA 重交、完成申请、附件和已知遗漏仍按原规则比较，原来的 “materials” 用例不变。
- ADR 0011 补了一句说明这条规则。

复测（同一批场景，旧规则与新规则对照）：从本仓库历史中找出所有实际发生过冲突的作者同步合并（父一为作者旧 HEAD，父二为 main，合并提交为解决后的新 HEAD），分别用旧版和新版 `reviewEquivalence` 计算：

| 范围 | 冲突合并数 | 旧规则可证明 | 新规则可证明 |
|---|---|---|---|
| 11-17 以后 | 180 | 0 | 39（22%） |
| 11-01 以后全部 | 394 | 2 | 100（25%） |

新增的命中来自两边插入都保留的解决，涉及 `docs/development-plan.md`、`apps/server/src/dispatch.ts`、`packages/domain/src/index.ts`、`CardDetailLayout.tsx`、`role-pack.test.ts` 等。上表只统计代码树这一层。在此之前，真实交付还被 `test_results` 门槛拦在 0；这道门槛这次已经去掉。已知遗漏和附件仍须原样，所以冲突通知里加了提示。实际命中率取决于作者是否照做，合并后跟踪。

## 4. 高频冲突文件的结构性消除（验收 4）

先复测报告点名的热点（重放 11-01 以来全部合并，看哪些文件冲突）：

| 文件 | 修复前 | 修复当天追平 | 之后 |
|---|---|---|---|
| `packages/store/src/migrate.test.ts`（C-525 迁移编号） | 15 | 6 | 0（11-21～11-26） |
| `apps/web/test-support/page-skeleton-snapshots/manifest.json`（C-469 截图清单） | 8 | 4 | 0（11-20～11-26） |

报告里的 `migrate.test.ts`、`manifest.json` 两类冲突已被 C-525、C-469 消除。按 11-21 以后的数据，仍在冲突的“多卡同处追加”文件是两个 barrel：`packages/host/src/index.ts` 和 `packages/domain/src/index.ts`，各冲突 9 次。其中近一半是两张卡往同一个具名导出块里加名字，块被格式化成多行以后必然冲突。

本卡仿照 C-525 的思路处理：

- 两个 barrel 改成每个模块一行 `export * from "./x.js";`。往已有模块里加导出不再需要改 barrel；只有新增或删除模块才改一行。编译器会拒绝有歧义的同名导出，本次转换编译通过，没有同名冲突。
- `packages/domain/src/barrel.contract.test.ts` 和 `packages/host/src/barrel.test.ts` 规定 barrel 只能有这种行，且不重复，防止有人把具名块加回来。
- 复测：把历史上 18 次 barrel 冲突的三方版本（合并基、ours、theirs）都转成新格式后重新合并，host 9→5、domain 9→6。剩下的都是两张卡在同一处新增相邻模块，属于纯插入，解决办法就是两行都留，而第 3 节的新规则能证明这种解决、沿用审核。
- 代价：在途卡如果也改了这两个 barrel，会和本卡冲突一次；解决办法是保留本卡的整模块行，再补上自己新增的模块行。
