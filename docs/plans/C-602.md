# C-602：mac-mini 空闲会话回收在探测阶段失败

作者：关羽。承接 C-597 验收 4（C-597#80）。只处理空闲回收，不涉及 C-573 的有待办会话接续，不改阈值或重试次数。开发方案正文由里程碑收尾统一同步。

## 现场证据（脱敏，来自 C-597#80）

- A-54（部署 C-597 后才起的会话，Harness 为 Codex）：`idle_session_retirement_started` → 2 秒后 `withdrawn`，evidence `{stage: probe, reason: probe_invalid}`，`retry=true`；三次后 `handed_off reason=probe_invalid`。
- A-37（C-597 部署前已存在的旧会话）：`handed_off reason=hc_failed`。
- 部署后没有一例 `session_replaced reason=idle_session_retired`。

## A-54 在哪一步被判无效

macOS 路径（`retire_idle` → `stopDarwinOwner`）里，`stage=probe, reason=probe_invalid` 且证据中没有 `exit_code`、`runtime_code`，只可能来自 `stopDarwinOwner` 的 `lost()`：relay 已连上 owner，但 owner 没有发出挑战就关闭连接。owner 只有在自身资格检查不通过时才会这样做（`handle()` 中的 `eligible()` 为假）。

资格检查里有一项是 `inspect-worker.py` 中 `darwin_retirement(..., require_idle=True)` 的 `live()`，要求 hc 记录的 `status.state` 为 `idle` 或 `done`。hc 0.1.21 的 `status` 只来自程序自己发出的 OSC 7501。Claude Code 和 Codex 不发这个序列（见 `docs/research/0.3-herdr-machine.md`、开发方案“状态来源因运行时而异”），因此整段会话的 `status` 始终是 `null`。结果是：任何 Claude Code 或 Codex 会话，owner 都判为“不空闲”，并静默拒绝。

隔离复现（本机 Linux，私有 hc 0.1.21 会话，不连生产 socket）：

1. 用与生产相同的形状启动终端：根进程是包装进程，下面是 `Popen` 出来的 CLI 子进程。`hc get` 显示 `status: null`、`agent: python3`；`foreground.pid` 等于终端 `pid`（即包装进程）；`cwd` 与传入的 `--cwd` 原样一致；`rm=false`、`keep=false`；终端环境中 `HC_TERMINAL_ID=t1`。只有程序自报 OSC 7501 后，`status` 才不为 `null`。
2. 新增的真实 hc 用例（见“测试”）在修复前的 `inspect-worker.py` 上失败，返回结果与现场一致：`{outcome: withdrawn, evidence: {stage: probe, reason: probe_invalid}}`。修复后同一用例通过。

健康的同代空闲会话怎样通过：控制器先做只读观察（绑定同一代次、同一终端、原 CLI 出生身份）；之后 owner 依次核对请求进程就是自己的直接子进程、`HC_TERMINAL_ID` 一致、工作区干净且仍登记在同一仓库；`terminal.get` 中名称、cwd、`rm`、终端 pid、前台进程、标签、代次都一致，原 CLI 出生身份未变，hc 也没有报告忙碌。全部通过后才发出带公钥摘要的随机挑战。控制器跑最终业务守卫后签名，owner 验签并再次核对资格，然后只向自己的直接子进程发一次 TERM。

## 修复

`deploy/inspect-worker.py` 的 `live()`：`status` 缺失（`null`）、没有 `state` 或为 `unknown` 时也视为空闲；`idle`、`done` 照旧放行；`working`、`blocked`、`error` 及其它上报值仍然拒绝。

- 这条规则与 Linux 路径（`system_finished_turn` 只接受 `unknown`/`idle`/`done`）和 bound prompt 的现有规则一致，没有放宽归属、代次、独占或工作区守卫。
- 空闲的证明本来就在主机侧最终业务守卫 `before_signal` 中：阶段仍为 stopping；runtime_ref 未变；自开始回收以来没有 MCP 活动；没有在途通知；没有同终端或同工作区的其它活跃 Assignment；`sessionMaintenanceCandidate` 仍成立（无排队或运行中的 Run，并已超过空闲阈值）。对 Claude Code 和 Codex，hc 的 `null` 不包含任何信息；以前强制要求它，等于让这条路径永远走不通，并没有增加安全性。
- 其它调用方不受影响：控制器只读观察在普通空闲回收中 `require_idle=false`；`system_finished_turn` 在 macOS 上由 `stopDarwinOwner` 直接拒绝，`stopSystemTurn` 的确认也只看 `exited`。

## A-37（hc_failed）核对

结论：与 A-54 不同源。

- owner 拒绝只会表现为 `probe_invalid`，不会产生 `hc_failed`。macOS 路径的 `hc_failed` 只来自控制器侧异常，且都发生在与 owner 通信之前：`stage=target` 的引用校验，或 `stage=probe` 的只读 worker 探测（`workerTerminalProbe` 会把一切失败都归为 `runtime_unavailable`）、relay 传输异常。
- A-37 是 C-597 部署前登记的会话：它的 owner 不报公钥摘要（或者根本没有 owner）。即使探测成功，也只会得到 `conditional_close_unavailable`，并按 C-597/Q-1166 有界移交，不发送任何输入或信号。本卡不改变这一点。
- 缺口：`workerTerminalProbe` 不保留具体失败原因，现场摘要也没有回填 A-37 的 `stage`、`runtime_code`、`hc_kind`。可能的原因包括终端已移除、标签或代次不符、core RPC 超时、SSH 失败，目前无法区分。建议：主机运维回填 A-37 那条 `withdrawn` 事件的完整 evidence；如需细分 worker 探测失败原因，另开卡处理（需在领域层新增原因枚举）。

## 测试

- `test-support/darwin-retirement.py`（由 `darwin-retirement.test.ts` 调用）：`require_idle` 时，`null`、`{}`、`unknown`、`done` 返回 `alive`，`working`、`blocked`、`error` 及其它值返回 `unknown`；`require_idle=false` 时不看状态。
- `darwin-idle-owner.test.ts`，模拟 core：自报 `working`、`blocked`、`error` 时，owner 拒绝，进程保留；`null` 状态下，模拟控制器重启后签名停止成功。原有的脏工作区、登记被替换、代次换代、派送前转忙、种子缺失或更换等用例不变。
- `darwin-idle-owner.test.ts`，真实 hc（仅 Linux；员工本地默认跳过，远程检查执行）：owner 运行在私有 hc 会话的真实终端里，读取的是该 core 自己的终端记录，只替换 Darwin 平台与账号检查和出生身份适配。不自报状态的会话被签名停止，终端以 143 结束，工作区保留；自报 `working` 的会话被拒绝，进程仍然存活。

## 已知缺口

1. owner 和检查器源码在启动时随参数下发。本修复部署前启动的会话仍沿用旧规则，会继续 `probe_invalid` 三次后有界移交（与现状相同，没有不安全动作）。只有部署后新起的会话受益。
2. 本机没有 macOS，真实 hc 记录只在 Linux 上验证；hc 0.1.21 的终端记录结构与平台无关，macOS 上的前台进程和 cwd 字段要靠现场确认。
3. owner 的其它拒绝（工作区不干净、身份不符）仍统一报为 `probe_invalid`。如需区分，建议另开卡，并在领域层增加原因枚举。
4. 现场验证（验收 4）在部署后由主机运维执行：至少一例部署后才起、并经历过一次服务重启的 mac-mini 会话，由空闲回收完成 `session_replaced reason=idle_session_retired`。看门狗兜底不计。
