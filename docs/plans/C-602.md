# C-602：mac-mini 空闲会话回收在探测阶段失败

作者：关羽。承接 C-597 验收 4（C-597#80），按审核 V-2990、V-2993 返工。只处理空闲回收，不涉及 C-573 的有待办会话接续，不改阈值或重试次数。开发方案正文由里程碑收尾统一同步。

## 现场证据（脱敏，来自 C-597#80）

- A-54（部署 C-597 后才起的会话，Harness 为 Codex）：`idle_session_retirement_started` → 2 秒后 `withdrawn`，evidence 摘要为 `{stage: probe, reason: probe_invalid}`，`retry=true`；三次后 `handed_off reason=probe_invalid`。
- A-37（C-597 部署前已存在的旧会话）：`handed_off reason=hc_failed`，未提供 stage 和其它字段。
- 部署后没有一例 `session_replaced reason=idle_session_retired`。

## A-54：已定位的阶段、隔离可复现的原因、仍缺的现场证据

**现场证据能证明的范围。** 摘要只说明失败发生在 macOS 回收的 `probe` 阶段，没有签名，结果是撤回（`withdrawn`），并且可以重试。macOS 路径里，以下几种情况都会得到相同的 `{stage: probe, reason: probe_invalid}`：

1. `stopDarwinOwner` 的 `lost()`：relay 子进程启动出错、在签名前以 3 以外的码退出（包括 owner 不发挑战就关闭连接），或挑战格式无效；
2. 外层 catch：helper 以退出码 2 结束（这种情况下证据会带 `exit_code`，摘要没有提到，但不能排除摘要省略了它）。

现场没有挑战收发记录，也没有更细的 evidence 字段，所以**不能证明现场 relay 已经连上 owner，也不能断定是 owner 的哪一项检查拒绝了请求**。

**隔离环境可复现的原因。** owner 只要有一项资格检查不通过，就会不发挑战、直接关闭连接（上面第 1 种情况）。其中 `inspect-worker.py` 的 `live()` 在 `require_idle` 时要求 hc 状态为 `idle` 或 `done`。hc 0.1.21 的状态只来自程序自己发出的 OSC 7501，Claude Code 和 Codex 不发（`docs/research/0.3-herdr-machine.md`），所以 Codex 会话的状态整段都是 `null`。在私有 hc 会话的真实终端里，用基线版检查器对一个同代、干净、停在空输入框的 `null` 会话发起停止，得到的结果与现场摘要完全一致（`withdrawn`，`probe`，`probe_invalid`），并且每次都会如此。这是一个能稳定解释 A-54 的原因，但现场没有证据排除其它情况（例如 relay 连接失败、工作区不干净）。

**仍缺的现场证据。** 当时 relay 是否连上、挑战是否发出、owner 拒绝的是哪一项。本卡不改生产协议去补这些字段（审核意见同意）；部署后若仍失败，需要另行取证。

## 修复

第一版把 `null` 直接当作空闲。审核 V-2990 指出：对不发状态的 CLI，等待输入和还在处理旧回合时状态都是 `null`；而主机守卫只核对业务状态（Run 已结束、没有新的 MCP 活动或通知），不知道 CLI 的回合是否真正结束。第二版改为：

- **状态有上报**：只有 `{"state": "idle"}` 或 `{"state": "done"}` 放行；`working`、`blocked`、`error`、`unknown`、没有 state 的对象，以及 `false`、`[]`、字符串等类型不对的值，一律拒绝。
- **状态为 `null`**（Claude Code、Codex）：必须另外取得同一终端代次的空闲证据，否则拒绝。具体做法：
  1. 读取该终端的屏幕（`terminal.read lines=0`），套用控制器 bound prompt 已在使用的规则：最后一行是该客户端的空闲页脚（Codex：`? for shortcuts` 或 `N% context left`；Claude Code：`? for shortcuts` 或 `shift+tab to cycle`）；页脚正上方是空输入框（Codex `›`，Claude Code `❯`，中间可以隔一条分隔线）；最后 8 行里没有 `esc to interrupt`、`esc to cancel`、`press enter to confirm`。屏幕超过 64 KiB、读取结果类型不对、提示符和页脚不属于同一客户端时都拒绝。屏幕文本不外传。
  2. 等待 `SETTLE_SECONDS`（1.5 秒）后再取一次 `terminal.get`：地址、创建时刻、进程号、状态、keep、标签、回合数（`turn`）和前台进程都必须与第一次一致。
  3. 再读一次屏幕：仍须是空闲画面，并且与第一次读到的内容逐字节相同。正在运行的回合每秒至少重绘一次计时（例如 Claude Code 的 `Working… (3s`、Codex 的 `Working (5s`），所以不可能两次都读到同一个空闲画面。最后这次读屏是发出 TERM 前的最后一次观察；审核 V-2993 指出的情形——读到空闲快照后、第二次 `terminal.get` 前画面刷新为忙碌，而元数据不变——会在这一步被拒绝。
  4. 第二次读屏到 owner 发出 TERM 之间，只剩 `child.poll()` 这一步。这段窗口无法消除，任何“先检查、后动作”的做法都有；如果空闲客户端要在这段时间里开始新回合，必须先收到输入，而回收期间主机的停止围栏不会派送新任务。
- owner 在发挑战前和验签后各做一次完整的资格检查（原有流程），所以这项空闲证据在发出 TERM 前会被重新核实。主机的最终业务守卫（`before_signal`）保持不变，仍然必须通过。
- 归属、代次、独占、工作区和签名核对都没有改动。
- **放弃的挑战不再占住 owner**（C-604 隔离 macOS 实跑发现）：控制器收到挑战后不签名就结束（主机守卫不通过 `guard_changed`，或公钥摘要对不上），以前 relay 仍在等 owner 回第二行，owner 单线程要等满 3 秒读超时才能接下一个请求。现在 relay 读到控制器 stdin 结束（没有签名行）就立即退出并关闭连接，owner 马上读到空签名、验签失败、回 `withdrawn`，不发信号。只改了随调用下发的 relay，owner 协议不变；部署前启动的 owner 收到的也只是更早的连接关闭，原有处理不变。
- **owner 遇到格式不对的 core 回复不再退出**（V-3000 非必改建议，C-602#57 约定随下次改码处理）：`supervise` 的单次请求异常里补上 `AttributeError`（例如 `terminal.read` 返回的不是对象），本次请求拒绝，owner 继续监听。只对修复部署后启动的会话生效。

Python 版 `prompt_idle` 与控制器的 TypeScript `editor()`（`bound-prompt.ts`）做了差分对照：在 3780 组生成的屏幕上（Claude Code 和 Codex 各算一遍，其中 360 组判为空闲），两者结果完全一致。

其它调用方：普通空闲回收里，控制器的只读观察不要求空闲（`require_idle=false`），不会读屏；在 macOS 上，`system_finished_turn` 由 `stopDarwinOwner` 直接拒绝，`stopSystemTurn` 的确认也只看是否已退出。

## A-37（hc_failed）

单列记录，暂不判定根因。

- **已知**：A-37 是 C-597 部署前登记的会话，owner 不会报告公钥摘要（或者根本没有 owner）。按 C-597 / Q-1166，即使后续步骤都成功，也只能得到 `conditional_close_unavailable` 并有界移交，不会发出任何输入或信号。本卡不改变这一点。
- **不能确定**：在 macOS 路径里，`hc_failed` 是 catch 的默认原因，可能出在引用校验（`target`）、只读 worker 探测或 relay 传输（`probe`），也可能出在与 owner 通信之后的确认观察（`confirm`）。现场只给了移交原因，没有 stage、`runtime_code`、`hc_kind`，所以无法确定发生在哪一步，也无法确定与 A-54 是否同源。
- **建议**：主机运维回填 A-37 那条 `withdrawn` 或 `uncertain` 事件的完整 evidence。如需细分 worker 探测失败原因，另开卡处理（需在领域层新增原因枚举）。

## 测试

- `test-support/darwin-retirement.py`（由 `darwin-retirement.test.ts` 调用）：`null` 状态下，Claude Code 和 Codex 的空输入框都放行；以下情况都拒绝：旧回合仍在运行（`esc to interrupt`）、输入框里有草稿、提示符和页脚不属于同一客户端、等待确认、屏幕为空、屏幕超长、读屏结果无效、两次读屏之间回合数、状态、进程号、前台进程或创建时刻发生变化、两次空闲画面不一致，以及 V-2993 的顺序（先读到空闲快照，在下一次 `terminal.get` 前画面变为忙碌）。另外在 owner 路径上固定调用顺序为 get → read → 等待 → get → read。`require_idle=false` 时不读屏。已上报的状态只认 `idle` 和 `done`。
- `darwin-idle-owner.test.ts`，模拟 core：`null` 状态加运行中的屏幕被拒绝，进程保留；回到空输入框后，模拟控制器重启，签名停止成功。原有的脏工作区、登记被替换、代次换代、派送前转忙、种子缺失或更换等用例不变。`guard_changed` 之后的下一次请求须在 2.5 秒内得到回复（旧 relay 下约 3 秒，测试失败）；该用例 Linux 本地从约 11.8 秒降到约 5.8 秒，超时上限从 20 秒放宽到 30 秒，给托管 macOS 留余量。core 对 `terminal.read` 回复非对象时，本次请求得到 `probe_invalid`，下一次请求仍由同一 owner 应答（旧 owner 会退出，下一次得到 `conditional_close_unavailable`，测试失败）。
- `darwin-idle-owner.test.ts`，真实 hc（Linux 和 macOS；员工本地默认跳过，远程检查在 Linux 上必须执行）：在私有 hc 会话里同时起几个同代、干净、状态为 `null` 的会话。仍在处理旧回合的、在空闲样子的提示符上方持续重绘的、停在输入框但自报 `working` 的，都被拒绝且一直存活；画面稳定停在空输入框的被签名停止，终端以 143 结束，工作区保留。
  - 用基线版检查器运行：失败在空闲样本上（被拒绝，结果与现场一致）。
  - 用第一版（D-2301）检查器运行：失败在运行中样本上（被发了 TERM）。
  - 用第二版（D-2303）检查器运行：失败在持续重绘样本上（被发了 TERM）。
  - 用本版运行：本地连续 4 次通过。

## 已知缺口

1. **隔离 macOS 验证**（审核 V-2990 第 2 项、V-2993 第 2 项）：C-604 在 D-2309 候选上跑过一次（GitHub run 45099889018，macOS 15.8.2 arm64，hc 0.1.21）。真实 hc 用例在 macOS 上执行并通过；`darwin-retirement.test.ts` 2/2 通过；模拟 core 的签名停止用例超过 20 秒超时（无断言差异），原因是上面放弃的挑战占住 owner 约 3 秒（两次）加两次空闲核对。本版修复后需在新候选上再跑一次 C-604。
2. owner 和检查器源码在会话启动时随参数下发。本修复部署前启动的会话仍沿用旧规则，会继续 `probe_invalid` 三次后有界移交（与现状相同，没有不安全的动作）。只有部署后新起的会话受益。
3. 空闲证据依赖 Claude Code 和 Codex 当前的输入框与页脚样式，并假定运行中的回合至少每秒重绘一次。如果客户端改了样式，结果是认不出空闲、保留会话（与 bound prompt 一样），不会误停。每次空闲核对增加约 1.5 秒（发挑战前和验签后各一次），都在现有超时范围内。
4. owner 的其它拒绝仍统一报为 `probe_invalid`。如需区分，另开卡处理。
5. 现场验证（验收 4）在部署后由主机运维执行，不作为合并前门禁。
