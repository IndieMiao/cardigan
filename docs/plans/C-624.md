# C-624：人工停止后排队的启动不再僵死在队头

宗旨：优化的目标是打通阻塞，不制造新的阻塞。

## 第一步结论（只读取证）

R-715 的“启动占用”**既不是启动预留（bell attempt），也不是资源租约**。它是人工停止标记还在生效：A-62 先被 `assignment stop`，随后人工 `assignment start` 因为模拟器被占只排了队，停止标记没有被解除，调度器因此一直跳过 R-715，而它又以“可派发的前序”占着队头。

## 修复

1. **排队的人工启动也算启动**（`stop.ts`、`launch.ts`）：人工 `queueRun` 遇到停止中的工作项指派时，在同一事务里记 `assignment_start_requested`（human，载荷含 `assignment_id`、`run_id`）。`stoppedByHuman` 把它当作解除停止，只认 human 发起的这类事件。复用已排队的 Run 时同样记录，这样旧数据里留下的排队项也能用一次 `assignment start` 接上。之后由调度器在名额允许时自动派发，不需要再手工 start。之后再 stop 仍以最后一条为准，并取消排队的 Run。系统或助手发起的排队不解除人工停止。
2. **人工停止的指派不占队列位置**（`packages/host/src/run-capacity.ts`）：`waitingRuns` 跳过停止中的指派，因此 `hasEarlierCapacityWait` 和“前面还有 N 个”都不再计入它。人工 start 后它按原触发时间回到原位置，同一资源仍按先来后到。
3. **没有终端也能停止排队的 Run**（`apps/cli/src/assignment.ts`）：`assignment stop` 遇到没有终端、但有排队 Run 的工作项指派时，走停止第 1 步：记录停止并取消排队的 Run，然后可以 `release`。两样都没有时，提示“没有在运行的终端，也没有排队的 Run”。
4. **`--cancel-queued-run` 说明具体原因和下一步**（`release.ts`）：逐项判断，分别提示：不是在岗的工作项指派；不是该指派的排队 Run（附当前状态）；已有会话、工作区或派发记录，这时给出 `assignment stop` 再 `release`（放弃）或 `assignment start`（继续）；正在启动（未结束的启动记录或资源租约），等这次启动结束后重试。允许取消的条件不变。

### 为什么不设 5 分钟阈值

卡上设想的“超时补起”是为了应对来源不明的占用。取证确认来源是停止标记后，修复 1 直接消除了这种状态：名额一到就派发，不必等阈值，也不会凭超时去清理可能真实存在的启动预留或资源租约，避免制造新的竞态。真实的启动预留和资源租约原有到期与释放核验流程，本卡不改。

## 测试

- `apps/server/src/dispatch-human-start-queue.test.ts`：完整回放 R-715。停止并释放终端，人工 start 在模拟器被占时排队；只需要 godot 的后续项照常派发；模拟器释放后，排队的启动由调度器自动派发。另有两个用例：旧数据里停止中的排队项不挡后面的项，人工 start 后原地复用并派发；系统排队不解除人工停止。改动前前两个用例失败。
- `packages/domain/src/commands/stop.contract.test.ts`：排队的人工启动解除停止且只记录一次；之后再 stop 仍生效；非 human 的排队或伪造事件不解除停止；未停止的指派不记录。
- `packages/domain/src/commands/release-cancel-queued.contract.test.ts`：允许取消的路径不变，各拒绝原因分别给出对应提示。
- `apps/cli/src/assignment.test.ts`：没有终端时 stop 取消排队的 Run 并保持停止，没有可停止的内容时给出明确提示。
