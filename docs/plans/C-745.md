# C-745 上游诊断分类失败可查、子原因透传、closed 后诊断恢复再试一次

## 改动

1. **分类失败与恢复记录**（`packages/host/src/upstream-health.ts`）
   - 项目级分类失败（`reconcile` 抛错或后台观测失败）从内存 `Set` 改为带记录的 `Map`：来源（`reconcile`/`observation`）、异常类型（错误类名加 code，如 `SqliteError:SQLITE_BUSY`）、开始时间、连续次数。
   - 首次失败写事件 `upstream_classification_failed`（项目流，system 发起）和一行主机日志；同一项目连续失败合并计数，只在异常类型变化、距上次记录满 10 分钟或上次事件没写成时再记一条；恢复时写 `upstream_classification_recovered`（含开始、恢复时间、总次数、持续时长）。
   - 事件只含异常类型，不含错误正文；经脱敏截断的错误摘要只进主机日志。写事件失败时改用监控器自己的 store，再失败只留日志，不影响 fail-closed。
2. **子原因透传**
   - `upstreamHoldDetail()` 给 `upstream_diagnosis_unavailable` 算出子原因：`classification_failed`（附项目级失败的开始时间、次数、异常类型；线路组发布失败没有项目级开始时间）、`provider_not_resolved`、`no_diagnosis`。
   - 自动换会话的暂缓／失败结果、派发积压恢复的撤回（`blocked_by`）、普通恢复的推迟事件都在 payload 带 `upstream_detail`；domain 只保留已知字段。
3. **closed 后诊断恢复再试一次**（domain）
   - `contextRestartRetryState` 新增 `recoverable`：该会话最后一次尝试因 `upstream_diagnosis_unavailable`／`upstream_observation_failed` 终态失败、停止尚未开始，且还没用过这次额外尝试。
   - 主机在上下文巡检时，只有当前诊断可用且停止闸门放行（非分类失败、非线路故障／事件）才传 `diagnosis_recovered`，系统以 `diagnosis_recovery_retry` 发起一次换会话，并接管该会话原失败的围栏和待办（待办由系统结项并写明原因）。这次尝试再失败就照常开新待办，会话保持 closed；被暂缓则沿用 C-741 退避。上游真实故障时不发起。

## 11-25 两次分类失败的原因（从代码推断，未在现场日志核实）

后台线路轮询 `pollUpstream` 先 `observeUpstream` 再 `reconcile`。`observeUpstream` 在采样（逐个 `runtime.status`、读取会话上下文）期间，只要项目内任一被采样的 Assignment 的终端、会话或最新 Run 变了，就抛 `stale_target`。原代码把这个异常也当成观测失败，调用 `observationFailed(project)`，把整个项目标成分类失败，直到下一轮轮询成功 `reconcile` 才清除。sensen-godot 会话多、Run 切换频繁，这个竞态很容易命中。A-61 在 04:55Z 换会话失败（当时 C-741 未部署，记为终态失败）、A-48 在 06:47Z 被推迟后约 64 秒（下一轮轮询）自愈，都符合这个模式，但没有现场日志能证明就是这一条。

修复：采样期间会话变化属于竞态，不再把整个项目标成分类失败（后台轮询和单次恢复的采样都一样）；单次恢复仍以 `upstream_observation_failed` 暂缓，按 C-741 退避重试。`reconcile` 本身抛错的其它可能（如 SQLite 忙）无法从代码排除；现在每次都会留下异常类型、开始时间和次数，下次可以直接定位。
