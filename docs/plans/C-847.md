# C-847：大仓库的 submit_delivery 校验超时与结果丢失

## 现象

SEN-C-243 的完成申请连提 5 次，服务端每次都在 `prepare_verify` 花 88～125 秒；客户端早已超时，Agent 随即 `report_blocker`、`finish_run`。服务端算完时 Run 已结束或工作项已阻塞，分别判 `stale_target`（校验绑定的 Run 已变）和 `illegal_transition`（工作项仍有阻塞），事务回滚，没有登记。

## ① 耗时从哪来

### 复现方法

`packages/git-transport/src/delivery-large-repo.bench.test.ts`，默认跳过；设 `CARDIGAN_LARGE_REPO_BENCH=<空目录>` 后运行：

```sh
CARDIGAN_LARGE_REPO_BENCH=$TMPDIR/large-repo CARDIGAN_LARGE_REPO_LABEL=after \
  pnpm exec vitest run packages/git-transport/src/delivery-large-repo.bench.test.ts
```

合成仓库全部现场生成，不用生产数据：

- 8000 个提交，3000 个文本文件，1100 个不可压缩二进制资源（每个 860 KiB，四分之一是对旧资源的改版）；
- 打包后 939.7 MiB；中心库另有 3000 个主机引用（candidates、prechecks、incoming）；
- Agent 分支从 `main~600` 起步，自己改 `AGENTS.md`、一个脚本和一个资源，再合入最新基线后提交。这正是“后期完成申请”的形状：从 Assignment 基线到交付共 1489 个文件有变化。

测量方式：给中心库 Git 端口的每个方法包一层计时（只计最外层调用），并按子命令统计 Git 进程数。环境：i7-13700KF、ext4、git 2.43.0，每种交付各跑 3 次。

### 优化前（基线 fc64b2e5）

| 交付 | 总耗时 | 其中 `fileDiffs` | 取分支 `fetchBranchTip` | Git 进程数 |
|---|---|---|---|---|
| 完成申请（无上一版） | 24.2 / 24.7 / 23.5 s | 23.8 / 24.5 / 23.3 s | 0.27 / 0.12 / 0.11 s | 4485（cat-file 2963，diff 1495） |
| 产出交付（有上一版） | 24.0 / 24.4 / 34.9 s | 23.8 / 24.2 / 34.7 s | 0.12 / 0.12 / 0.11 s | 4484 |

其余步骤（`ensureBare`、`objectType`、`isAncestor`、`countCommits`、`readRef`、`treeOfCommit`、`mergeTree`、发布 incoming／candidate 引用）合计不到 0.1 秒。

原因：角色规则清单 `collectRoleRuleInventory` 调 `fileDiffs`，对**每个**变化文件起 3 个 Git 进程（`git diff` 取补丁，两次 `cat-file blob` 取前后全文，二进制资源也整块读进内存），而只有角色／提示词路径（`AGENTS.md`、`CLAUDE.md`、`SKILL.md`、`roles/`、`prompts/`、`agents/` 等）才用到这些内容；其他文件只按路径判为 `ordinary`。从 Assignment 基线算一遍，从“本作者自己的起点”再算一遍。这台机器上每个进程约 5 ms；生产主机 88～125 秒折合每进程 20～28 ms，与更慢的磁盘、并发负载和更多 pack 文件相符。仓库越大、基线走得越远，进程数越多。

没有发现重复 fetch：取分支只有一次远端传输和一次本地导入，0.1～0.3 秒；提交遍历（`rev-list --count`、`merge-base`）都在 10 ms 以内，不需要限制遍历范围。

### 优化

- 端口 `fileDiffs` 增加可选的 `content` 过滤（`GitFileDiffOptions`）：每个变化路径照常列出模式、对象号和状态，只有被选中的路径才读补丁和全文。
- 角色规则清单只对 `roleRuleNeedsContent` 选中的路径读内容（与分类规则同一判断：非测试文件且是角色路径），分类结果逐项不变。
- 交付校验复用清单里已算好的树号，基线引用只读一次。
- 检查项一个不少：绑定、完整 SHA、对象类型、分支包含、角色规则清单、作者自己的变更路径、复核等价判断全部照旧。

### 优化后

| 交付 | 总耗时 | 其中 `fileDiffs` | Git 进程数 |
|---|---|---|---|
| 完成申请 | 0.21 / 0.18 / 0.19 s | 0.04 s | 39（cat-file 12，diff 2） |
| 产出交付 | 0.20 / 0.20 / 0.21 s | 0.04 s | 39 |

约快 120 倍；剩下的时间主要是取分支（约 0.1 秒）。

### 生产侧分解

服务端每次交付校验输出一行 `{"event":"delivery_verify_steps","project_id":…,"assignment_id":…,"steps_ms":{…}}`，阶段为 `ensure_central`、`fetch_tip`、`commit_checks`、`role_inventory`、`commit_count`、`own_inventory`、`review_equivalence`（只有阶段名和毫秒数）。发布引用的锁等待和持有时间仍看既有的 `delivery_source_lock`。部署后可以直接核对 sensen 的实际分解。

## ② 客户端超时不再丢结果

`submit_delivery` 改为“先受理、后取结果”：

- 服务端最多等 20 秒（`deliveryReplyWithinMs`，默认 `DELIVERY_REPLY_WITHIN_MS = 20000`）。超过时立即返回 `status=processing`、`delivered=false`，同时附 `idempotency_key`、`retry_after_seconds=15` 和一句做法说明；校验、登记、固定提交在服务端继续完成。
- 同一调用方（同项目、同 Assignment、同工具、同幂等键、完全相同的参数）在进行中重提时，接上正在进行的那一次，不重复校验；完成后由幂等记录直接返回已登记的交付。
- 参数不同的同键请求不会接上别人的结果。
- 进行中的失败（例如期间调用方结束了 Run 或报了阻塞）不缓存：下一次重提按当前状态重新校验，不会把旧失败原样回放。后台完成时记一行 `method=background` 的工具日志，写明结果码和总耗时。
- 进程重启时进行中的校验随之丢失，重提会重新校验，结果仍由幂等记录保证只登记一次。

领域层不放宽任何状态转换：校验结果晚到时，Run 已变按 `stale_target` 拒绝（提示语改为说明“校验期间本 Run 已变化，请在当前 Run 重新提交”），工作项阻塞按 `illegal_transition` 拒绝。契约测试见 `packages/domain/src/commands/delivery-late-settlement.contract.test.ts`。

## ③ 工具说明与角色规则

- `submit_delivery` 的工具说明写明：可能返回 `processing`；收到它或客户端超时后先等约 15 秒，用同一幂等键和完全相同的参数重提，也可用 `get_card` / `get_updates` 查看；等待期间不要 `report_blocker`、`finish_run` 或改动工作项。
- 开发角色规则在“用 `submit_delivery` 提交交付”之后加一句同样的做法。

## ④ 客户端工具超时来自哪里

| 来源 | 值 | 作用范围 |
|---|---|---|
| `runtime-workers.yaml` 的 `mcp_timeout_ms` | 10 秒 | 只用于工作机启动前的 MCP 鉴权探测（`probeWorkerMcp`），不限制工具调用 |
| Codex 原生 MCP 工具调用 `tool_timeout_sec` | 默认 60 秒（本仓库未配置，见 C-598） | 每次工具调用 |
| Codex 的 stdio 转接（`mcp-bridge.ts` 的 `BRIDGE_TIMEOUT`） | 300 秒 | 转接到 Card MCP 的单次 HTTP 请求 |
| Claude Code `MCP_TOOL_TIMEOUT` | 未设置，采用 Claude Code 自带的默认值（远长于 60 秒） | 每次工具调用 |
| Pi 的 MCP 适配器 | 本机未安装，未核 | — |
| 服务端 Git 查询 / 传输 | 每条命令 30 秒 / 30 分钟（`CARDIGAN_GIT_QUERY_TIMEOUT_MS` / `CARDIGAN_GIT_TRANSFER_TIMEOUT_MS`） | 单个 Git 进程 |

最短的是 Codex 的 60 秒。服务端的应答预算 20 秒，不到它的一半；即使校验本身更慢（远端传输很慢、主机繁忙），客户端也会在超时前收到 `processing`。现场的报错原文 “The operation timed out” 具体出自哪个客户端，本卡没有拿到 A-713 的会话记录，未核。

## 已知未覆盖

- 复核等价判断（`reviewEquivalence`）仍会读两版交付之间每个差异文件的全文；它只比较作者两次交付之间的变化，基准测试里不到 0.02 秒，本卡未改。
- 进行中的校验只在单个服务进程内合并；写请求都在主进程处理。
