# C-402：空闲活会话安全退役的能力评估与实施计划

作者：赵云。评估日期：2026-11-17；源码基线：`cbd0c094d69499a4e077c4aa1b80226862546baa`。本卡固定 flow 5 / dev@2。按新增 C-402#9，目标已明确为直接实现自动回收、消除静默跳过和发布期角色误报，评估不单独作为完成交付。本文是实现第一步的检查点：已确认安全退役所需上游能力缺口，尚未修改运行时代码；新接口、状态和默认值均为待实施合同，不是已支持能力。完整实现不能以此检查点宣称完成，需 PM 协调上游前置或收敛可先交付的范围。

## 1. 结论和目标策略

当前不能安全自动回收活进程。Cardigan 缺少可信的原生 attach 和终端输入输出活动观测；hc 0.1.18 的释放接口也不提供按观测条件原子退役或禁止升级强杀的合同。加长静默时间、普通主机锁、重复读取状态，都不能补齐执行端竞态。保持 C-398 的保护：自动角色维护仅处理已退出、不存在或空引用的会话，不恢复曾被驳回的 live + unknown 释放路径。

按 C-402#5 的目标，未来仅考虑内部、非常驻的工作项 Assignment：没有未结束 Run、没有人 attach，最近一次 Run 结束及最后一次 MCP 活动均已超过可配置阈值，默认 60 分钟。回收的对象只是终端会话；Assignment、员工、工作项、工作区、分支和未提交文件都保留，下次合法唤醒创建新会话。已经是最新角色版本的 Assignment 也应能回收，不能把候选集限制成“有角色版本可升”。

60 分钟是候选条件，不是安全证明。还必须有执行端对同一进程代次的完整活动证据和非强制退出能力。建议采用更保守的首版：输入、输出、最后一次 attach 变化也连续静默超过同一阈值；任一信息缺失、事件丢失、时钟异常或 busy 状态均等待。支持范围和启用仍走原审核流程，本卡不启用回收、不升级 hc、不操作生产会话或权限。

### 2.3 本次直接核验的 hc 帮助和静态 schema

只执行以下无目标查询，没有 get/list/attach/kill/rm 或生产核心连接：

```sh
hc --version
hc kill --help
hc attach --help
hc schema --help
hc schema --json
```

本机二进制返回 `hc 0.1.18`。schema 为 herdr-core 0.1.18、协议代号 1；原始 `hc schema --json` stdout SHA-256 为 `769dd0cf6ddf39200d53a15f6eaccf1f2c6469f30c2ce25e3cc6f08dfbe6004b`。复查时可对 stdout 重新取哈希，再检查下列方法和字段，无需连接核心。

| schema / 帮助内容 | 结论 |
|---|---|
| `terminal.kill` 参数仅 caller、terminal；描述为 “hangup, then terminate, then kill” | 没有 expected-generation、expected-activity、no-attach、no-escalation 参数；现有 `force:false` 只是适配器前置判断，不等于执行端非强制 |
| `terminal.rm` 描述 “Remove a finished terminal”，live 返回错误 | 不能拿它回收活进程；保留历史终端即可，不必将 rm 纳入新回收协议 |
| `terminal.attach` 支持 observe、framed 原始流；`hc attach --observe` 不输入、不 resize | 有原生入口；没有给出排他退役互锁或全局 attach 计数合同 |
| `terminal.send` 的 `if` 只检查 idle/working；人工输入有缓冲语义 | 不是按完整终端活动水位的条件发送；必须考虑已排队但尚未注入的输入 |
| `events.subscribe` 列出 created/lost/restarted/keep/finished/removed/status/turn/title/labels/size/doc 和 heartbeat/missed | 没有承诺逐次输入、输出、attach/detach 都更新可比较水位 |
| Terminal.address 称在同 core 永久；CoreInfo.id 仅清空状态时重置；Terminal.keep 可原地换 shell | 地址/core ID 仍不足以表示进程代次；`created_ms`、`pid`、`turn`、`status_ms` 不能替代重启、PID 复用及未自报活动的证据 |

这是已安装版本的公开接口合同，不是上游实现源码审计。未取得上游新能力的发布记录、源码提交或承诺；不能断言所有未来版本都不支持，也不能声称 0.1.21 已补齐。没有运行新的真实终端隔离实验；本卡交付真实实验的可执行计划。当前确认可用的仅是 0.1.18 的已有观测/退出后维护，新活进程退役能力的可用版本为“未确认”。

## 3. 最小安全合同：在终端所有者处核验并关闭入口

以下 `observe_retirement`、`retire_if_unchanged`、`retirement_result` 是接口占位名，不是可运行 hc 命令。优先向上游提出合同；若不用新增 hc 能力，替代实现必须在真正持有 PTY/进程句柄的执行端完整拦截原生 CLI、桌面客户端、SSH 转发及缓冲输入，并提供同等证据。仅改 Cardigan wrapper 或加文件锁不合格。

### 3.1 观测凭证

只返回元数据，不收集终端正文。一次一致快照至少包含：

- 身份：可信目标绑定、core 实例及启动代次、终端不可复用 ID、进程 incarnation、Cardigan 的 project/assignment/run/launch generation。标签可变时也必须检测变化。旧引用缺代次不补猜值，等自然退出后重建。
- 活动：所有输入来源和 PTY 输出的单调计数/最后活动单调时刻，attach/detach revision，所有观察/交互连接数，未送达输入数，关闭/启动/恢复状态。静默时长由执行端计算，不跨机器比较墙钟。
- 完整性：观测 revision、有效期限、已覆盖的连续观测区间、是否断线/丢事件/重启及能力版本。`missed` 后若执行端仍保存可信连续水位可重新取证，否则从零累计；不知道就返回不可用。
- 非强制退出能力：目标程序是否支持安全结束的协作合同、当前是否确认无在途工作。不能仅信 OSC idle；完全静默但仍在计算或有脱离子进程的会话不能自动终止。核心必须能证明并保护其管理的整个会话进程集合；无法覆盖时报告不支持。

主机用最近一次已结束 Run 的 `finished_at`、最后一次 MCP 工具活动和当前时间判断候选，两者都须有效且严格超过阈值；同时检查任意 queued/dispatched/acked/running/unknown Run 和未收尾 launch/stop 操作。缺失时间、未来时间、时钟回拨或重启后无法证明连续静默时重新等待，不能用零/创建时间补出已空闲。终端侧用自己的单调时钟再次判断 IO/attach 静默，不接受主机声称的“早已空闲”。

### 3.2 原子条件退役

`retire_if_unchanged` 接收完整身份、观测 revision、阈值、主机操作 ID 和明确的“禁止升级强杀”策略。由 PTY 所有者在一个串行临界区完成以下动作：

1. 核身份、进程代次、活动 revision、attach 数为零、输入队列为空、连续静默时长及协作退出资格；任何差异返回未执行的明确原因。
2. 在同一临界区关闭这一代次的新 attach、send/keys/put、resize/自动输入、进程重启和恢复入口，并建立持久操作记录。已到达但尚未处理的输入/输出也要纳入判断；不能只锁 RPC 入口而漏掉 PTY reader 或远端 holder。
3. 将“条件检查成功且入口已关闭”作为线性化点。先发生的 attach/输入/输出使本次失效；退役先发生时，新 attach/输入收到明确的正在退役响应，不写入即将退出的进程，也不吞掉已确认接收的输入。
4. 通过经验证的协作机制正常退出，等待准确进程代次及其受管工作结束；不把 `kill` 的默认升级路径包装成 `force:false`。SIGTERM 也必须有程序/子进程语义证据，不能只因历史 16 个退出就视为无损。退出握手期间新工作或输出不能被静默丢弃：上游须证明已进入不可再接业务的收尾阶段，否则取消或返回结果不确定，不能继续强制结束。
5. 返回可重查的 `exited` 回执；已收请求、连接关闭、超时、终端名字不存在、PID 不可见均不直接代表成功。保留终端历史，不自动 rm。若协议做不到这一合同，能力标记必须为不支持。

上游应给出拒绝（确定无副作用）、已接受待退出、已退出、结果不确定四类结果；相同操作 ID 只能指向同一代次，重试不能再次发停止信号或误伤新会话。取消必须与执行端接受退役互斥：只能返回“确定未执行并已解围栏”或“已接受，继续查询”，不能超时后默认取消成功。

### 3.3 主机与并发工作串联

建议独立于角色升级新增持久回收围栏，不直接复用会撤凭据的 `beginIdleAssignmentRoleUpgrade`。状态最少区分 `prepared`、`committing`、`exit_pending`、`exited`、`cancelled`、`uncertain`，绑定完整旧引用、操作 ID、控制面活动代次和执行端回执。

1. 主机先核所有资格和能力，不支持则记录原因，不设会阻塞正常工作的围栏。对候选建立 `prepared`，取得执行端新观测；旧凭据此时保持有效。
2. 在同一持久事务内重核引用、所有未结束 Run、共享工作区操作、人工 stop、MCP 活动及新工作；若有变化，取消准备。本地锁仅防 Cardigan 自身竞争，不宣称保护原生 attach。
3. 所有能产生 Run、wake、恢复、Token 签发或业务 MCP 写入的入口，都须通过同一持久围栏并校验活动代次；不能只给定时维护加锁。事务将状态转为 `committing` 后才能发执行端请求。先到的新工作使准备失效；后到的新工作持久排队，尚不创建/派发 Run，也不向旧终端发送。晚到业务 MCP 写入明确返回可重试的会话退役状态，不执行副作用，不假装成功；读请求的处理与活动计数规则必须在消费者测试中固定。
4. 执行端仍独立核验原生 attach/IO 并原子关闭入口。不能把“主机已提交围栏”当执行端已经安全。确定未执行时解除主机围栏，旧身份/凭据可继续使用；不确定时阻止新会话和重复停止，按操作 ID 查明结果。
5. 精确退出回执核验后，同事务清旧 runtime/session 引用、撤旧凭据、记录仅会话回收的审计，保留工作区和身份。若有符合 C-398 条件的新默认角色，再走原有精确版本审计；单纯回收不伪造 `default_role_upgraded` 来放宽工具范围。同版本新会话仍沿用原权限上限。
6. 结算后按既有 Dispatcher 处理排队通知并创建新会话；人工 stop、暂停/人工分配决定继续生效，不因回收或升级自动开工。重放回执/通知不能重复新建 Run。

这需要主机入口围栏和执行端排他两者。只做主机原子事务无法保护原生 attach；只做执行端条件关闭则可能让已创建的 Run 被终止。若直接消费者中有任何入口未接围栏，不允许启用。

## 4. 失败恢复、可见原因与相关问题

| 情况 | 保守处理与恢复 |
|---|---|
| 能力缺失、旧引用无代次、unsupported 平台 | 不执行停止、不撤凭据。按 Assignment/代次/原因保存等待状态；能力或代次变化后再评估 |
| busy、attach、IO、新工作、MCP 活动改变 | 确定未执行时取消准备，保留会话；从最新活动重新计时。繁忙是正常等待，不持续告警 |
| 请求超时、SSH/核心断线、回包丢失 | 记录 uncertain，不把超时当退出；重连后只用同操作 ID/代次查询。无法证明时继续保留围栏并通知 PM |
| 主机崩溃或多控制器同时维护 | 从持久操作阶段恢复；唯一操作约束保证一代只有一个退役动作。围栏不能因租期到期就当作退出；明确未执行的准备才可安全取消 |
| 执行端崩溃/重启、keep 换 shell、PID/名字复用 | 旧凭证失效；查询持久回执和精确代次。未知不是 absent；不得向新进程重复发信号 |
| 退出后主机落库失败 | 旧围栏仍在；再次查询同操作结果并幂等结算，身份/角色只切换一次，工作区不删 |
| 人工 stop 先发生 | 使用原 stop 流程，取消未执行准备；精确核旧代次退出后收尾。保留 stopped 标记，不自启动；已接受的退役与 stop 共用操作仲裁，不能并发重复停止 |
| 非强制退出超时/拒绝 | 不升级 SIGKILL、不借通用 release 补杀。明确仍活且已安全撤销关闭状态才解围栏；否则按不确定处理 |

建议延用现有维护的 60 秒节流、每批/跨控制器最多 2 个在途、1/2/4/5 分钟封顶退避，不改变现有并发偏好；新回收与升级共用预算，不能各取 2 个。60 分钟目标阈值另配为正整数分钟，非法配置拒绝启用；初始开关关闭。

建议原因码区分 `unsupported_capability`、`identity_unproven`、`control_activity`、`terminal_activity`、`attached`、`observation_gap`、`exit_unconfirmed`、`publication_in_progress`。执行视图/卡片使用现有事实与事件入口显示原因、最后评估时间、下一次重试，不增加说明小字或写终端内容。持续缺能力/故障超过 15 分钟只向 PM 去重通知一次；原因恢复后记录解除，再次故障可开新一轮。未开始退役的等待也必须可查询，避免重演首次 live 直接 continue 后无诊断的情况。此为后续可观测性切片，不是本次已实现。

**C-402#4 的部署角色误报。** 源码中空闲升级将当前数据库角色与运行进程加载的默认包直接比 hash；`upgradeDeployedRoles` 则在事务中发布新角色和 `host_role_upgraded`。不同发布阶段/不同进程包版本可能产生暂时不一致，现有空闲维护没有发布代次校验；与报告相容，但没有生产事件/进程快照，不能宣称根因已实测。建议后续在同事务核对已完成的部署代次、包指纹及数据库角色快照，发布进行中或读到不同代次时仅推迟冲突判定；稳定快照下仍不匹配才走原手改冲突流程。不能简单要求一定存在 `host_role_upgraded`：角色本来一致时该函数可无变化返回。需覆盖无需升级、发布中崩溃、旧进程残留和真实手改四种情况；本卡不改角色规则或历史人工事项。

**C-402#6 的 A-973 未升级。** 当前候选筛选和领域资格没有读取 `manual_assign`，也没有单独排除“暂停”字样；它们核 active 内部工作项、新默认版本、卡未 done/cancelled、未结束 Run、stop/host-ops/启动发布、共享工作区、退出证据及默认包指纹。因此不能把该个例直接解释成“暂停卡按设计不升级”。只读 C-313 确认其正文要求暂停和人工分配；本次不读取生产 DB，无法确定 A-973 当时命中哪个条件。后续由已有权限的操作员只提供资格原因/审计元数据；不要为调查解除暂停。新回收的诊断应能直接说明这些原因，角色维护与派发资格仍分开。
