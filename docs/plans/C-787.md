# C-787 监督器升级并入服务部署的同一次停起

## 现场与基线

- 监督器自升级（C-767）重启 systemd 单元时，server 是监督器的子进程，会一起停；健康判定也要求 server 换代。所以“先部署服务、再升级监督器”的现行顺序，一次发布会停起两遍。
- 11-26 13:54 第一次成功的自动升级就是这样：13:54:38 部署 af7fbe90 启动一次，13:55:32 监督器升级又启动一次，前后只隔 54 秒。
- 基线数据从项目事件里取：`host_server_log_recorded`（每次 server 启动一条，文件名里带版本）、`host_deployment_recorded`、`host_supervisor_upgrade`。数字见交付附件。

## 方案

监督器落后、且 main 的差异命中监督器监视范围时，监督器升级不再单独停起一次，而是作为同一 main 那次部署的“启动”一步：

1. 准备提前：开关打开、比较出需要升级后，升级器在 server 空闲（ready、无切换、无维护窗口）时就在 `release-watch-<main>` 准备新监督器（clone、安装、构建、读现有配置），不再等服务先部署到 main。准备不占检查容量。
2. 部署等一步：部署控制器发现待部署的就是这个 main、新监督器还没准备好时，本轮不部署（不取容量、不构建），等升级器这一步准备完。每个 main 在一个监督器进程里最多只等这一次；准备失败、抛错、或残留旧计划文件时照常部署，监督器再按原路径单独升级。人工固定版本从不合并。
3. 交接：部署照常取容量、核对发布证据、构建、等长操作并封住、写停服快照、停旧 server、需要时备份数据库。到“启动新构建”这一步时，把重启交给升级器：备份并改写启动配置、`daemon-reload`、写升级计划文件（新增 `deploy` 字段：停服快照的 attempt、新构建的 SHA 与目录、旧 SHA、停服时间、备份文件名），用 systemd-run 启动重启助手。容量和长操作围栏保持由旧监督器持有，直到它被替换。健康窗口在 `health_timeout_ms` 之上加 `2×ready_timeout_ms + stop_timeout_ms`（新构建启动加一次回滚），上限仍是 10 分钟。
4. 新监督器启动：没有存活的 server、没有未完成的启动（state.json 没有 `running`）、最近一条部署记录是本次的停服快照、计划的 `new_root` 就是本目录、`deploy` 的 attempt / SHA / 旧 SHA 都对得上、新构建目录在部署目录里且 HEAD 是该 SHA 时，才接手：启动阶段不启动旧构建，保留容量，由部署控制器在第一轮先启动新构建。ready 就提升并记 `deployed`（“与监督器升级合并为一次停起”），否则停掉它、恢复旧构建，沿用 C-650 的重试计数。任何一条对不上，都走原来的“恢复未完成的切换”：启动旧构建并记 `rolled_back`。
5. 交接不成：改写或启动助手失败时，升级照旧记 `failed`、恢复启动配置，部署由旧监督器自己启动新构建（仍是一次停起）。助手没有在时限内重启监督器（或助手已结束但没重启）时，旧监督器的升级器放弃等待，部署控制器接着启动新构建。

## 恢复路径（最后一环）

- state.json 的 `current` 在新构建 ready 之前一直是旧构建，任何时刻被打断，下一个启动的监督器（新的、或回滚后的旧的）都按“未完成的切换”恢复旧构建。
- 新监督器起不来时，重启助手照旧回滚启动配置、重启旧监督器；旧监督器看到计划不是给自己的，按原路径恢复旧构建，之后照常部署新 main（这一次是两遍停起，但服务不会停在半路）。
- 演练发现的一处恢复盲区（与合并停起无关，单独升级时同样存在）：新监督器启动即崩溃、单元按 `Restart=` 快速重启时，会触发 systemd 的启动频率限制（start-limit-hit）。这时重启助手回滚后的 `restart` 被拒绝，旧监督器起不来，服务一直停着。本卡在回滚重启前加了一步 `systemctl --user reset-failed <unit>`，只改这一处。
- 重启助手、回滚、`ExecStopPost` 兜底（C-770）和失败原因、启用前自检（C-772）的其余逻辑本卡不改。

## 与 C-770、C-772 的分工

- C-770：放弃等待时恢复启动配置、助手异常退出的兜底、失败只留一条待办。
- C-772：启动配置读取失败的原因、启用前自检命令、launch_file 说明。
- 本卡只改“什么时候重启监督器”：准备提前、部署在启动一步交接、新监督器启动时接手。助手、回滚、待办与自检的代码不动。

## 已知边界

- 带监督器改动的 main，部署要多等一次准备（生产上约 40 秒）。
- 助手没有发出重启时，旧监督器最多等 `2×health_timeout_ms + 120s`（默认 4 分钟）才放弃并自己启动新构建，期间服务是停着的；助手被杀或崩溃时由 C-770 的兜底更早结束等待。
- 合并后重启次数的复测要等本卡上线并运行一段时间，作为合并后跟进。
