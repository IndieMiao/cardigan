# C-661 GitHub 检查步骤合同支持多基线与可选步骤

## 背景

sensen-godot 有两条基线：`integration/dynamicfarm` 的 `cardigan-check.yml` 在 lint 和 deps 之间新增了 `dynamic_farm`，`farm-dev` 还没有。C-592 的 `step_contract` 一个执行器只有一份合同、主步骤必须完全一致，所以两条基线只能有一条通过，另一条全部步骤成功也被判“GitHub 检查步骤合同不符”。合同不符时日志只显示 `job_unavailable`，看不到差在哪一步。

## 改动

- `step_contract` 新增 `branches`：键是基线分支名，值是该基线完整的 `steps`/`post_steps`，**整体替换**执行器默认合同（不是合并）。没有列出的基线仍用顶层 `steps`/`post_steps`。选哪份合同看 GitHub run 的 `head_branch`，它就是派发工作流的基线，派发和轮询时都已与绑定身份核对。
- 主步骤条目支持对象写法 `{ name: 步骤名 }` / `{ uses: owner/repo }`，可加 `optional: true`：该步骤可以不出现；出现时必须在声明的位置。六个检查步骤不能设为可选；`post_steps` 本身每项可缺省，不接受 `optional`。可选的 `uses` 步骤缺席时，对应的 `Post Run` 收尾步骤也不能出现。
- 合同不符时，检查结论原因写出：使用的是哪份合同（基线专用 / 执行器默认 / Cardigan 默认）、第一处不同的步骤序号（与 GitHub 页面步骤编号一致）、期望的步骤、实际的步骤，例如：

  ```
  GitHub 检查步骤合同不符，拒绝通过：基线 farm-dev 的步骤合同第 10 步期望 deps，实际 dynamic_farm
  期望步骤：Set up job（可缺省）、Initialize containers、Run actions/checkout@<ref>、…、lint、deps、e2e
  期望收尾（按序，均可缺省）：Post Run actions/setup-node@<ref>、…、Stop containers、Complete job
  实际步骤：Set up job、Initialize containers、Run actions/checkout@v4、…、lint、dynamic_farm、deps、e2e、…
  ```

  job 全部成功因而没有可下载日志时，这段诊断作为失败日志写入，不再报 `job_unavailable`。job 不符、步骤编号不连续或未结束、请求检查不是六项等其它拒绝原因也写明。步骤名来自基线工作流，显示时替换控制字符、单个截到 120 字符。
- 判定严格度不变：未声明的步骤、顺序错误、缺检查、重复步骤名仍然拒绝；`step_contract` 仍不进入 dispatch 身份。

## 配置示例（sensen）

```yaml
executors:
  github-actions-sensen:
    type: github
    # ……原有字段不变……
    step_contract:
      # 默认（integration/dynamicfarm 及未列出的基线）
      steps:
        - Initialize containers
        - uses: actions/checkout
        - uses: pnpm/action-setup
        - uses: actions/setup-node
        - install
        - build
        - test
        - lint
        - dynamic_farm
        - deps
        - e2e
      post_steps: [...]
      branches:
        farm-dev:          # 该基线完整的一份合同
          steps:
            - Initialize containers
            - uses: actions/checkout
            - uses: pnpm/action-setup
            - uses: actions/setup-node
            - install
            - build
            - test
            - lint
            - deps
            - e2e
          post_steps: [...]
```

只差一个步骤时也可以不分基线，改成一份带可选步骤的合同：

```yaml
    step_contract:
      steps:
        - ……
        - lint
        - name: dynamic_farm
          optional: true
        - deps
        - e2e
```

可选写法更省事，但它允许 `integration/dynamicfarm` 去掉 `dynamic_farm` 仍通过；要求每条基线精确一致时用 `branches`。

## 校验规则（在 C-592 基础上新增）

- `step_contract` 只能含 `steps`、`post_steps`、`branches`；顶层 `steps` 仍必填。
- `branches` 为 1–16 项的映射；键须为有效分支名，不能以 `ci/` 开头；每项只能含 `steps`、`post_steps`，按与顶层相同的规则校验（不能再嵌套 `branches`）。
- 对象条目只能含 `name` 或 `uses` 之一，外加可选的 `optional: true`；`optional` 只能写 `true`，只允许出现在 `steps`，不能用于六个检查步骤。
- 错误信息不回显配置值。

## 运维约定：工作流加减步骤时同步改合同

外部仓库的检查工作流（例如 sensen 的 `.github/workflows/cardigan-check.yml`）**新增、删除、改名或调整步骤顺序**时，必须在同一时间修改主机 `merge-gate.yaml` 中对应执行器的 `step_contract`，否则该基线上所有卡的合并检查都会被判“步骤合同不符”：

1. 只改了一条基线的工作流：在 `branches` 下为它（或为尚未改的基线）写一份完整合同；或者把新步骤声明为 `optional: true`。
2. 所有基线都改完后，把顶层合同更新为新形状，删掉不再需要的 `branches` 项或 `optional`。
3. 修改前备份 `merge-gate.yaml`；改完后看主机加载结果，执行器无效时引用它的项目合并检查会整体变为无效。
4. 不确定实际步骤时，看最近一次被拒绝检查的原因或日志：其中“实际步骤”一行就是 GitHub 返回的步骤列表。

部署配置不在本仓库，以上修改在主机私有配置中完成。

## 测试

`packages/host/src/github-step-contract.test.ts`（C-661 一组）：

- 同一执行器下 `integration/dynamicfarm`（带 `dynamic_farm`）与 `farm-dev`（不带）各自通过；未列出的基线用默认合同；每条基线仍拒绝另一条基线的形状。
- 可选步骤缺席、出现均通过，出现时失败会作为失败步骤命名；位置错误、出现在检查之后、出现两次、检查顺序互换、缺检查、未声明步骤仍拒绝；可选 `uses` 缺席时其收尾步骤不能出现。
- 拒绝原因中的合同名、步骤序号、期望/实际列表，收尾多出、步骤缺失；编号不连续、job 名不符；控制字符替换与截断。
- 轮询器对合同拒绝不再报 `job_unavailable`，把诊断写成失败日志且不请求 GitHub 日志。
- 字段校验：`branches` 为空/非对象/null/非法键/`ci/` 键/嵌套/超 16 项、缺顶层 `steps`、检查步骤可选、`optional` 非 true、对象同时含 name 与 uses、`post_steps` 用 optional、可选名与精确名重复；错误不回显配置值。

`packages/host/src/merge-gate-executors.test.ts`：YAML 中 `branches` 与 `optional` 能解析进执行器配置，非法值使执行器无效。
