# C-848 Run 结束后槽位上的模拟器由系统兜底收掉

## 原因（R-6670 推断）

C-679 的槽位释放只做两件事：向模拟器控制台发 `kill`（读账号主目录下的控制台令牌认证），向 adb 端口发 `host:kill`，再用 127.0.0.1 连接判断端口是否还开着。两类情况会让模拟器留下：

- 控制台没应答或认证失败（mac-mini 负载 13～15 时控制台 1 秒内没回横幅，或令牌不在账号主目录）：端口一直开着，释放永远“待确认”，槽位一直占着。free-slot 巡检只查空闲槽位，C-844 的未登记模拟器检查又把仍占着的槽位端口当作“已覆盖”，所以两边都不会收它；
- 端口探测没看到监听（模拟器正在启动、只绑在别的回环地址上等）：释放直接判“已关”，槽位放出。之后巡检同样只看端口，C-844 也只在超额或被预约时才停进程。

两种情况都只依赖 Agent 自觉收尾，系统没有按进程兜底。没有读取 sensen-godot 当时的事件，以上是按代码推断的结论。

## 做法

- 槽位的 `check` / `release`（主机下发、在实际 worker 上以项目账号运行的脚本）除了端口，也找这个槽位的进程：`-port`/`-ports` 等于槽位控制台端口的 qemu／emulator、环境变量 `CARDIGAN_RESOURCE_SESSION` 指向这个 Run 的模拟器（Linux），以及监听槽位端口、名字是模拟器或 `adb` 的进程。
- `release` 先走控制台和 adb 协议；约 3 秒后仍在的，核对进程启动时间后按 PID 先 SIGTERM（2.5 秒）再 SIGKILL。整次释放约 6 秒，在 10 秒调用上限内；超时也不误判，下一次重试会看到进程已经没了。
- 主机传 `keep_sessions`：本项目在这台机器上仍在跑（或正在启动）的 Run。环境里写着这些 Run 的进程和它们占用的端口一律不碰。只查本账号的进程；被别的项目占用的槽位不算空闲，不会被巡检。
- 进程列表取不到（macOS `ps` 失败）时脚本不回答，主机按“未确认”重试，不当作已释放。
- 事件：`machine_adb_slot_released`（Run 结束）和 `machine_adb_orphan_closed`（空闲槽位巡检）在发现有东西在跑时，附 `reason`（`run_ended`／`slot_free`）、`run_status`、槽位的 `adb_port`／`emulator_port`、`pids`、`processes`（类型:PID:端口:父进程[:signalled]）、`signalled`、`orphaned`（父进程为 1）。只写入本项目事件流；这些端口本来就在该 Run 的启动环境里。按验收标准要求写端口和 PID，这是对 C-497“事件不写端口”的有意例外，跨项目容量视图不变。

## 时限

Run 结束后的下一个派发周期就会触发释放；worker 不可达时槽位保持占用，按 30 秒起、翻倍、最长 10 分钟的间隔重试，重连后的第一次重试就收掉。空闲槽位巡检间隔仍是 `sweep_minutes`（默认 10 分钟）。
