# C-620 空闲会话不占名额，系统回收或受管停止后自动续办

来源：Q-1194 / C-608#17。与 C-608 并行；不改 C-602 的回收探测、C-573 的安全接续。

## 名额口径

- 新增 `runEndedByBusiness(run)`（completed / failed，即 finish_run 或系统按阻塞拍板、审核轮数用尽结束的轮次）和 `runHoldsCapacity(run)`（`runOccupiesSlot` 且不是业务结束）。`packages/domain/src/run-capacity.ts`。
- `runCapacitySnapshot` 计数：
  - Run：`runHoldsCapacity` 或“排队且有进行中启动预留”。业务结束的轮次即使还带停止围栏，也不再占名额。
  - 待处理的主机运维停止意图：回收交接（`retirement_handoff`）和系统代结束空闲轮次（`system_finished_run_id`）一律不计；其它意图只在该指派最近一次真正派发过的 Run 不是业务结束时才计（例如被取消但进程可能还在跑），没有派发过的会话也不计。
- 结果：轮次已结束的空闲会话，即使回收或停止尚未确认退出，也不占全机准入、项目额度和 `android.emulator` 等资源名额；被外部取消、可能仍在执行的会话在确认退出前继续占名额。后继 Run 照常排队，通过同一计数准入，正常并发仍受上限约束。
- 不变的物理守卫：`runOccupiesSlot` 仍用于资源租约释放核验、清场核验、helper 升级和本指派的启动互斥（Dispatcher `busy`、`queueRun`），所以同一指派在退出确认前不会另起会话，绑定实体的资源在释放核验前也不会交给别人。

## 队头阻塞（C-620#9）

- `hasEarlierCapacityWait` 按各资源最小剩余比例判断：前面的项缺某个资源（剩余为 0）时本来就不挡后面只需要其它资源的项，同一资源仍按先来后到。补了回归测试（模拟器被占时只要 godot 的项先派；模拟器释放后队头先于后来的模拟器项）。
- 另补一条：前面的排队项如果其指派此刻根本不能起会话（主机运维操作待处理、回收未确认、人工停止或受管停止未确认释放、角色升级中、自己还有另一个 Run 在跑），不再当作“可派发的前序”挡住同机后面的项；这些条件解除后立即恢复原排队位置。

## 停止的两种语义

- `cardigan assignment stop <A-n>`（受管停止，默认）：在 `assignment_stopped` 里记 `hold: false`。终端释放确认前和人工暂停一样挡住派发；`assignment_stop_released` 之后不再算停止，新的通知、指派或工作项状态变化会自动起新会话。未开始的排队 Run 保留为待办；worktree 保留。
- `cardigan assignment stop <A-n> --hold`（人工暂停）：记 `hold: true`，行为与 C-211 相同：取消排队 Run，门铃排队，只有 `assignment start` 恢复。
- 历史上没有 `hold` 字段的停止一律按人工暂停处理，不放宽已有暂停。对已暂停的指派再执行不带 `--hold` 的 stop，仍保持暂停。
- 受管停止只在确认“本会话自己”已退出后才结算。释放前先按会话身份观测：会话正在运行、且本次释放成功（适配器核对身份后结束了它）即为证据。终端行已是“已结束”或已找不到时，删行或读行都不算进程组已退出，只认本机按启动回执由内核确认进程及整组已不存在（`stoppedSessionExited`）。证明不了时停止状态和终端引用保留，不会另起会话；可重试，或用 `--hold` 按人工暂停结算（不自动续办）。
- 退出一旦证实就记 `assignment_stop_exit_confirmed`（绑定该会话），再做清理和结算。清理失败后重试直接沿用这条证据，不再去找已删的终端行。Token 在尝试释放后立即作废，不等退出证实。
- 每次停止调用只作用于它被要求停止的那个会话：调用开始时记下会话引用，在 launch 锁内核对；期间原会话已结算或已换成后继会话时，直接返回“没有改动”，不释放、不清理、不记停止。整个工作项停止都在该指派的 launch 锁内完成，所有新会话都经 `launchRun` 取同一把锁。
- 受管停止期间工作项被恢复：恢复不再因“停止”本身而推迟，排队 Run 保留到释放后派发；若因被停的 Run 尚未结束而推迟，释放结算时在同一事务里重放一次（`replayStopDeferredResume`）。重放从本次停止期的第一条停止记录算起（`openStopEpisodeStart`），重试停止不会丢掉之前推迟的续办；只排一个 Run。暂停仍只记推迟、不自动启动。
- 停止状态的判断函数移到 `commands/stop-state.ts`，避免 `stop.ts` 与 `resumption.ts` 循环依赖。
- 域函数：`stoppedByHuman`（暂停，或受管停止尚未确认释放）、`pausedByHuman`（仅暂停）、`humanStopRecorded`（最近一次派发后有过任意停止，供回收结算判断“终端已被人释放”）。

## 系统回收

回收确认退出后 `runtime_ref` 清空、`idle_retirement` 移除，Dispatcher 对新工作直接起新会话；回收未确认（`idle_retirement.phase=stopping` 或交接中）时不另起。本卡只补回放测试，不改回收流程。

## 与 C-624 合流（基线 61b2e6e9）

- C-624 让排队中的人工 `assignment start` 记录 `assignment_start_requested`（仅 human），解除人工停止。在本卡的停止状态索引（`stop-state.ts`）里，这条事件与 `run_dispatched` 等同：清除暂停或受管停止状态，并结束当前停止回合。`recordHumanStart` 放进 `stop-state.ts`，避免 `launch → stop → resumption → launch` 循环依赖。
- C-624 新增的无终端 `assignment stop`（取消排队 Run）固定按人工暂停（`hold: true`）处理：受管停止要等终端释放才解除，没有终端就永远等不到释放。CLI 提示相应写“已暂停”。
- C-624 在容量队列里跳过 `stoppedByHuman` 的指派。本卡的 `stoppedByHuman` 只在人工暂停和尚未确认释放的受管停止时成立，两者方向一致。
