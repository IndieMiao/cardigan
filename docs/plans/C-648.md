# C-648 project_snapshot 按卡索引并移到读 worker

负责人：孙悟空。基线：`abd7945903c13a4c3f8af31d726cf8161da51823`。对应 C-633 attachment-9130 第 1.3、1.5、1.6 节（P0-1）。

## 根因

合成复现（630 卡、19.3 万事件、卡片依赖、6.3 万条系统流事件）下，原实现的整项目投影在 Web 主线程同步执行，工作项指派一次约 14 s，常驻 PM 约 1.5 s。剖析的主要来源：

1. `cardView` 每张卡都重新过滤一次全部可读卡；对工作项指派，每次得到的新数组让 `cardCriticalPathLengths` 的缓存失效，于是每张卡都重算一遍全项目关键路径。
2. `mergeStage` 每张卡扫描“交付 × 工作项”来找最新完成申请。
3. `cardView` 每张卡过滤全部工作项和交付；`referenceReadState` 对每个附件扫描全部时间线。
4. 主线程上的跨卡审计对每张卡在全部工作项里做 find、some、filter。

## 改动

- domain（语义不变）：快照内只建一次与卡无关的来源（按卡分组的工作项与交付、可读卡、依赖状态），每张卡只取自己那一份，分组保持原列表顺序；`mergeStage` 的“每卡最新未作废完成申请”按集合身份缓存（同 event-index 的不可变快照约定），并列时取原排序的最后一条；附件可见性改为键查找，重复交付编号仍以第一条为准；关键路径构建改为追加，不再复制数组；`deriveNextOwners` 的指派表按数组身份复用；排序比较函数里的全量查找移到循环外。
- mcp-server：拆出 `readProjectSnapshot`（只读事务：快照、读取审计查询、去掉 repo 与 log_ref），新增可选 `readProjectSnapshot` 端口。未配置端口时仍走原同步路径。配置端口后，令牌复核、运行容量、跨卡审计写入及其重新校验都留在调用方。审计读取器每个事务只收窄一次本指派的工作项，并按卡分组。
- server：新增 `McpReader`，用一个 worker 线程和私有只读连接（`PRAGMA query_only`）执行读半部分。只传服务端推导出的 actor，不传 Token。请求按顺序处理。worker 故障时拒绝挂起的请求，下一次请求重新启动 worker；关闭时拒绝挂起的请求。Web/server 角色在有数据库文件时启用，background 角色不创建。

返回字段、排序、授权和审计语义不变：契约测试在基线代码上同样通过，合成数据上基线、内联和 worker 三种方式的卡片响应摘要逐字节相同。

## 合成量测

复现命令（先 `pnpm exec tsc -b`；输出前缀必须是新文件）：

```sh
node apps/server/test-support/snapshot-worker-experiment.mjs worker /tmp/c648-worker 20
node apps/server/test-support/snapshot-worker-experiment.mjs inline /tmp/c648-inline 4
```

脚本在临时目录生成全合成数据，退出时删除，不读取生产数据。客户端在独立线程里发出 project_snapshot，10 ms 后再发一个轻量请求；服务端用 5 ms 定时器和事件循环直方图记录最大停顿。下表除第 0 轮冷读外取 p50 / p95，单位毫秒；响应约 1.8 MB。

| 方式 | 读者 | 快照 RTT | 主线程最大停顿 | 轻请求 RTT | worker 内耗时 |
|---|---|---:|---:|---:|---:|
| 基线（内联） | 常驻 PM | 1512 / 1554 | 1511 / 1552 | 1498 / 1541 | — |
| 基线（内联） | 工作项 | 13821 / 14133 | 13818 / 14130 | 13808 / 14120 | — |
| 本卡（内联） | 常驻 PM | 197 / 229 | 195 / 227 | 187 / 216 | — |
| 本卡（内联） | 工作项 | 245 / 282 | 243 / 278 | 232 / 268 | — |
| 本卡（worker） | 常驻 PM | 184 / 226 | 15 / 18 | 2.5 / 3.2 | 167 / 208 |
| 本卡（worker） | 工作项 | 224 / 277 | 15 / 18 | 2.5 / 3.1 | 207 / 260 |

worker 冷启动（建线程并首次装载命令状态）一次快照 RTT 约 0.7 s，主线程最大停顿 28 ms。每 5 轮由另一连接提交一次改动，使缓存失效，耗时与暖读同一量级。

## 残余与边界

- 合成数据不代表生产的全部事件类型。验收中的 24 小时 event_loop_delay 和 mcp_gateway_error 指标，要在部署后用生产日志观察。
- worker 维护自己的一份命令状态缓存，内存会随之增加。热数据集（P1-1）落地前，这部分内存与 Web 进程现有缓存同一量级。
- 请求在 worker 内按顺序排队，没有另设并发上限或超时；排队只影响 project_snapshot，不阻塞 Web 主线程。
- 只把 project_snapshot 移到了 worker；Workbench 的重读路径属于 P1-6。
