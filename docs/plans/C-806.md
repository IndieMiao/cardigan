# C-806 启动失败的一手证据

## 背景

sensen-godot 的 A-522 连续 4 次启动失败，事件里只有 `mcp_session_failed` / `run_dispatch_stalled`（`mcp_unavailable`），没有退出码、stderr，也看不出哪个 MCP 没连上，只能翻 journalctl 反推。本卡让主机在回收一个未开工的 Run 之前留下可读的一手证据。

## 做法

1. **采集时机**：派发恢复路径（`apps/server/src/dispatch-retry.ts` 的 `stopRun`）在停止一个从未开工（`started_at` 为空）的 Run 之前、`release` 之前采集一次，覆盖 `mcp_unavailable`、`dispatch_timeout`、`runtime_exited`、`provider_unavailable` 等所有停止原因。每个 Run 只记一次；采集失败不影响停止和恢复的结果。握手超时时长不变。
2. **采集方式**：复用 `host_ops_inspect_worker` 的固定只读采集器 `deploy/inspect-worker.py`，以 worker 账号运行（本机走受管回环 agent-ssh，远程 worker 走 agent-ssh），新增 `launch` 一节：
   - **终端**：hc 终端状态；已结束时的退出码和结束原因（`exit_code` / `exit_reason`）；终端尾部（CLI 的 stdout 和 stderr 都写到这里）最多 20 行、每行 200 字符、合计 2 KiB，**在 worker 上先脱敏再截断**。
   - **资源**：CLI 进程的 CPU、常驻内存、已运行时长（`ps`）；Linux 上若 CLI 在 `cardigan-session-*.scope` 里，改用该 scope 的 cgroup 记账（`cpu.stat` 的 `usage_usec`、`memory.current`、`memory.peak`，含 MCP 子进程）。
   - **各 MCP 服务器连接结果**：读 Claude Code 自己写的连接日志 `<缓存目录>/claude-cli-nodejs/<cwd 转写>/mcp-logs-<服务器名>/<时间>.jsonl`（Linux 为 `~/.cache`，macOS 为 `~/Library/Caches`），只取本次派发之后创建的那一份，每个服务器给出 `connected`（含传输方式和耗时）/ `failed`（含脱敏后的首条错误，≤160 字符）/ `pending`（开始连接但没有结果）。cwd 候选是该 Assignment 的 worktree、运行目录和远程发布代次目录。其它 harness 记 `harness_unsupported`。
3. **主机侧事实**：停止原因（回收原因）、派发后已等待时长、Card MCP 握手状态（C-600 的 `pending` / `listed` / `missing`）、机器和 harness。
4. **脱敏**：worker（Python）和主机（`packages/host/src/launch-redaction.ts`）用同一套规则各做一次：私钥块、`Authorization` / `Cookie` / `Bearer` 值、`*token*=`/`*secret*:` 等键值、已知 token 前缀（`gh*_`、`sk-`、`xox*-`、`AKIA`）、JWT、URL 里的用户名密码和查询串、含 `token|secret|credential|.ssh|id_*|.pem|.key|.netrc|auth` 的路径（如运行目录下的 `token`、`secrets.env`）、字母数字混合的 24 位以上不透明串和 40 位以上 base64 串，然后去控制字符、截断。domain 再校验条数、长度和原因码格式，超限拒绝写入。远程 worker 只回传上述有界摘要，原始屏幕和日志不出 worker。
5. **写入**：system 命令 `recordLaunchEvidence` 发出事件 `run_launch_evidence`（完整有界证据），并在 Run 所在卡片时间线追加一行系统摘要（不含终端尾部）。

## 证据存放位置、保留期限和读取方式

| 内容 | 存放位置 | 保留期限 | 读取方式 |
|---|---|---|---|
| 完整有界证据（回收原因、退出码、终端尾部、各 MCP 结果、CPU/内存/时长、缺失原因码） | 控制主机项目库的事件 `run_launch_evidence`（`payload.run_id` 指向失败的 Run） | 与项目事件流相同，长期保留（事件不清理） | `get_updates(card_id)` 读卡片事件；常驻任务（无卡）用不带 `card_id` 的 `get_updates` 读项目流 |
| 一行摘要 | 同一事件对应的卡片时间线系统条目 | 同上 | `get_card` 的 timeline，Web 卡片时间线 |
| 原始 MCP 连接日志 | worker 本机 agent 账号缓存目录（见上） | 由 Claude Code 自己清理（默认约 30 天） | `host_ops_inspect_worker(machine_id, assignment_id, run_id)`：Run 未开工时返回同样有界、脱敏的 `launch` 一节，Run 结束后也能拉到 MCP 结果 |
| 终端屏幕、进程 | worker 本机，随终端结束消失 | 不保留 | 只在停止前采集一次进事件 |

## 测试

- `packages/host/test-support/worker-inspection.py`（由 `worker-inspection.test.ts` 运行）：脱敏（token、凭据路径、URL、私钥、控制字符、长度与字节上限）、MCP 日志分类（失败 / 连上 / 无结果 / 本次之前的旧日志忽略 / 符号链接目录忽略 / macOS 缓存目录）、scope 与 ps 资源、模拟启动失败时采集器输出 `launch` 一节、hc 协议下的终端尾部。
- `packages/host/src/launch-evidence.test.ts`：本机与远程 worker 两种情况下证据完整进入且 token、凭据路径不出现；worker 不可达时仍记录主机事实并给出原因码；已开工或已记录的 Run 不重复采集；`host_ops_inspect_worker` 只在问到失败启动时带 `launch`。
- `packages/domain/src/commands/launch-evidence.contract.test.ts`：只 system 可写、每 Run 一次、时间线摘要、超限拒绝。
- `apps/server/src/dispatch-mcp-session.test.ts`：两次握手超时的失败启动，每次都先记证据再 `release`，事件落在卡片上。

## 已知未覆盖

- Codex / Pi 没有等价的 MCP 连接日志，记 `harness_unsupported`；终端尾部和资源照常采集。
- 原生 local 模式（控制账号直接跑 Agent，开发用）不以控制账号运行采集器，证据只有主机事实，记 `local_runtime_only`。
- 采集在停止前同步进行，最长受采集器 15 秒超时限制；只发生在启动失败的 Run 上。
