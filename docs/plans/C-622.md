# C-622 工作项阻塞条件满足后自动恢复

## 问题

作者用 `report_blocker` 登记了解除条件（`resume_when`），条件满足后：

- 若作者此时已有进行中的 Run（例如新会话补证据），后台只把恢复延后交 PM（“已有未结束的 Run”），阻塞状态不变；
- 交付入口只认“当前作者等待的同一提交预检通过”这一种情况，其它已满足的条件一律以 `illegal_transition` 拒绝，只能请 PM 手工恢复。

## 改动

1. 交付时内联解除（`resumeDeliveryWait`，`packages/domain/src/commands/work-waits.ts`）：
   - 适用条件：`card_merged`、`deployment_ready`、`decision_resolved`、`merge_check_finished`、`github_run_completed`，用与后台恢复相同的 `satisfied()` 判定，证据只取本项目系统记录；`deployment_ready` 只认目标 SHA 的 `deployed` 且 `ready` 记录，合并或失败部署都不算。
   - `precheck_finished` 沿用原“同一提交预检通过”规则；`baseline_updated` 仍由系统基线同步恢复。
   - 不放宽其它校验：仍需当前负责人、卡片未暂停/未关闭、指派未被人工停止、Run 未在停止、无其它待拍板或合并前置操作；版本、预检、归属等交付校验照常执行。
   - 同一条件已被自动恢复用过（`auto_resume_disabled` 或已消费）时不内联解除，仍交 PM。
   - 在同一事务内写 `blocker_wait_delivered` 事件与时间线，载明条件、证据、原阻塞事件编号、上报人和时间，再写交付。
2. 可追溯：后台自动恢复的 `work_item_resume_requested` 也带上原阻塞事件编号、上报人和时间。
3. 一次性：内联解除计入同一条件的已用额度，后续同条件阻塞不会再被自动唤醒；交付后的后台扫描不再产生恢复或新 Run。
4. 拒绝时报具体原因（“工作项仍有阻塞：…”），便于作者判断。

## 已知未覆盖

- 跨项目前置（例如 sensen 工作项等待 cardigan 平台卡部署）仍无法登记：`card_merged` 只接受本项目卡片，平台部署记录只写在平台项目里。需要跨项目读取平台卡合并与部署记录，另开卡处理。
