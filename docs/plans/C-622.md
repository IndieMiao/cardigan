# C-622 工作项阻塞条件满足后自动恢复

## 问题

作者用 `report_blocker` 登记了解除条件（`resume_when`），条件满足后：

- 若作者此时已有进行中的 Run（例如新会话补证据），后台只把恢复延后交 PM（“已有未结束的 Run”），阻塞状态不变，也不通知作者；
- 交付入口只认“当前作者等待的同一提交预检通过”这一种情况，其它已满足的条件一律以 `illegal_transition` 拒绝，只能请 PM 手工恢复；
- 业务项目（如 sensen）等待平台（cardigan）修复上线时，平台的部署记录只写在平台项目里，业务项目的后台与交付都看不到。

## 改动

1. 平台部署凭据（`deploymentEvidence`，`packages/domain/src/commands/work-waits.ts`）：
   - `deployment_ready` 先看本项目的主机部署记录，再通过主机提供的只读端口 `platform_deployments` 查控制面其它项目（平台）中同一 SHA 的主机部署记录。
   - 只认系统写入、项目级（无卡片）的 `host_deployment_recorded`，按项目取该 SHA 的最新一条，`deployed` 且 `ready` 才算满足；合并、开始部署、失败、其后回滚、其它 SHA 都不算。证据写成 `平台项目/事件编号`。
   - 端口只放在命令端口（`CommandPorts`）里：MCP 命令事务（`executeCommand`）与系统规则从存储事务取得，不进命令状态缓存，不接受工具参数，不给 Agent 开跨项目读权限。存储端按 `(project_id, type)` 索引逐项目查询，只在评估部署等待时调用。
2. 进行中的 Run 原地继续（`resumeWorkWaits`）：作者登记的阻塞条件满足、负责人已有未停止的 Run 时，系统解除阻塞并写 `work_item_resume_requested`（带 `active_run_id`），由路由通知这个 Run 继续，不另起 Run；重复扫描只恢复一次。暂停、人工停止、Run 正在停止、另有拍板或合并前置未完成时仍不解除；基线冲突等待仍等新会话同步。
3. 交付时内联解除（`resumeDeliveryWait`）：
   - 适用条件：`card_merged`、`deployment_ready`（含平台）、`decision_resolved`、`merge_check_finished`、`github_run_completed`，以及等待其它工作项的 `precheck_finished`（上游预检结束即满足），与后台恢复用同一判定。
   - 等待本工作项自己的预检时沿用原“同一提交预检通过”规则；`baseline_updated` 仍由系统基线同步恢复。
   - 不放宽其它校验：仍需当前负责人、卡片未暂停/未关闭、指派未被人工停止、Run 未在停止、无其它待拍板或合并前置操作；版本、预检、归属等交付校验照常执行。同一条件已被自动恢复用过时仍交 PM。
   - 同一事务内写 `blocker_wait_delivered` 事件与时间线，载明条件、证据、原阻塞事件编号、上报人和时间，再写交付；该事件计入同一条件的已用额度。
4. 可追溯：后台自动恢复的 `work_item_resume_requested` 也带上原阻塞事件编号、上报人和时间。
5. 拒绝时报具体原因（“工作项仍有阻塞：…”）。

## 验证要点

- domain 合成用例：平台部署（仅合并、开始、失败、他 SHA、非系统写入、卡片流、本项目编号、回滚均不算）、其它前置、上游预检、本项预检同提交规则、进行中 Run 原地恢复及其守卫、各类异常、重放与并发。
- server SQLite 两项目用例：业务项目等待平台项目部署，作者 Run 进行中由 Dispatcher 原地通知且不另起 Run；后台未刷新前作者交付同事务解除。
- MCP 用例：命令事务的端口能读到其它项目的主机部署记录，不含本项目。
