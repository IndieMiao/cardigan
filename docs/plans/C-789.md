# C-789：Run 结束必有下一步；卡住的会话走受管换代

依据：11-26 架构调研 3-autonomous-flow.md #5、#6。本卡按卡片目标与验收标准实现，不改开发方案正文。

## 1. 诊断：SEN-C-107（SEN-A-454）为什么没被 C-752 自动停

时间线（UTC，来自调研报告）：17:59 最后活动 → 18:28 `run_inactive` → 19:49 人 stop。C-752 在 11-25 15:26 随 MB-89 合入 main。

本卡在 cardigan 的 worker 上开发，读不到 sensen 的事件和主机部署记录，以下是**代码层诊断，未用现场数据核实**。60 分钟失活回收对 claude-code 远程会话会静默不触发的路径有四条，均会让 `lastInactiveStopActivity` 返回“未知”，派发器预筛直接跳过，且不留任何记录：

1. **部署时点**：C-752 只有在控制机部署了 MB-89 之后才生效。若部署晚于 18:59（本应到期的时刻），这次不会触发。核对：控制机 `host_deployment_recorded` 中 MB-89 合并提交的 `ready` 时间。
2. **预筛读不到缓存证据**：`HostOps.harnessFileActivity` / `harnessActivity` 在该项目有后台会话轮询进行中（`sessionPolls.has(project)`）或缓存超过 10 分钟时返回空。sensen 的远程会话逐个经 SSH 读取（每个读取上限 10 秒），轮询本身耗时较长；告警巡检调用 `inspectHarnessActivity` 时不复用缓存会再起一次轮询。轮询几乎连续时，派发器每轮预筛都拿到“未知”，回收永不进入停止前复读。核对：该时段 sensen 有无任何 `run_inactivity_stop_requested`；若无，再看后台轮询耗时。
3. **上游错误规则**：会话元信息带错误（限流、服务端错误）而没有可核实的最后进展时，按 C-752 §2 不停（设计如此）。核对：18:28 那条 `run_inactive` 的 `activity_error`。
4. **Run 归属**：`readSessionContexts` 用该 Assignment 最新一条 Run（`own.runs.at(-1)`）绑定活动的 `run_id`；若卡住期间该 Assignment 已有排在后面的 Run，证据的 `run_id` 与正在运行的 Run 不一致，回收不采用。核对：SEN-A-454 在 17:59–19:49 是否有 queued Run。

**结论与取舍**：四条都不能在本卡用现场数据确认。它们共同的问题是“核不清时静默跳过、不交人”。本卡的统一换代流程（§4）只在主机证明终端退出后才自动续派，不放宽 C-752 的证据规则；第 2、4 条的定点修复和“未知持续超过阈值时知会主机运维”列为后续项（见 §7），需要先按上面的核对项取得 sensen 现场数据，避免误停合法静默的会话。

## 2. `finish_run(blocked)` 没登记阻塞时由系统代登记

- `finish_run` 照常接受，不拒绝（延迟结束路径也一样：主机确认会话重连后结算时才代登记）。
- 判定“已登记下一步”：工作项已是 blocked / waiting_decision；已有不改状态的等待（§3）；有未决拍板影响该工作项；本 Assignment 在本卡有未关闭的人工待办；系统已接管的等待（未处理的预检候选冲突、本作者在途的预检）。
- 已交付（delivered）的产出项在等审核，系统已跟踪，也算已登记。
- 未登记时：
  - 产出项 in_progress：系统代登记阻塞（`needs=role`，`auto_registered=true`，无解除条件），发出系统身份的 `blocker_reported`，按既有路由进入 PM Ops 队列（`needs=pm` 在现有模型中即“无解除条件的 role 阻塞交 PM Ops”）。
  - 产出项已验收：登记一条不改状态、无条件的等待，交 PM。
  - 验证项及其它状态：只记 `run_next_step_missing` 交 PM，不改状态（V-3498：验证项若被置为 blocked，作者重新交付时无法回到 ready）。
- `run_finished` 事件内容不变（C-255）。

## 3. 已交付/已验收工作项的“等待资源名额或等待基线”

- 新增解除条件 `resource_available`（目标为该工作项要求的资源键：工作项能力要求 + 所属角色版本的 `required_capabilities`）。
- 入口：`finish_run.wait_for`（`baseline_updated` / `resource_available`）和 `report_blocker.resume_when`。产出项为 delivered / accepted 时，只登记 `WorkItem.standby_wait`，**不做任何状态迁移**；只接受基线或资源两类条件，不带条件则交 PM。
- 恢复：`resumeWorkWaits` 每轮检查；本 Assignment 仍有未结束的 Run 时不唤起（不被自己的 Run 叫醒），卡片暂停、人工停止、主机操作在途、角色升级时等待。条件满足后发系统 `work_item_resume_requested`（`automatic_wait`、`standby`），工作项状态保持不变。该事件按既有规则是“满重量”唤起，新 Run 在准入时占用工作项要求的全部资源，名额空出前在派发队列等待——这就是“带名额重派”。
- 每个条件只自动恢复一次（与阻塞等待共用 `autoResumeUsed`）；再次登记同一条件记 `auto_resume_disabled` 交 PM。
- 工作项离开 delivered/accepted、卡片结束或登记后又有新交付时，等待自动清除。
- 进行中的工作项也可等资源：沿用阻塞→恢复，但不在原 Run 上就地继续（原 Run 没有该资源）。
- 本次 Run 已持有该资源、或资源不是该工作项要求的，拒绝登记。

## 4. 受管会话换代（统一规则）

`session-rotation.ts` 是四类信号共用的结算规则：

| 信号 | 进入点 | 退出证明 |
| --- | --- | --- |
| 失活 | 60 分钟失活回收确认终端退出（`finishInactiveRunStop`） | 主机确认该终端引用退出 |
| 空闲占名额 | 主机运维停止空闲会话、空闲会话上排队 Run 久等（`releaseUnresponsiveSession`：`host_ops_stop_assignment`、`turn_done`） | 同上 |
| 门铃推迟超时 | 系统代结束回合后旧回合久久确认不了（`system_turn`） | 同上 |
| 回收失败 | 空闲回收反复被撤回、进程身份失效（`retirement_withdrawn`、`probe_invalid`） | 同上；确认不了退出的回收仍按既有交接通知交人 |

结算条件（全部满足才请求新会话）：

1. 有主机退出证明，且该 Assignment 当前没有绑定会话（不变量 5、6：未确认退出不建任何后继执行资源）。
2. 每个 Assignment 终身一次（`session_rotation_requested`）。
3. 工作项 in_progress、无阻塞、无不改状态的等待；卡片未结束未暂停；未被人工停止；无在途主机操作；没有未结束或正在停止的 Run（排队工作由既有派发继续，不重复）。
4. **有未读**：该卡上游标之后，有其他参与者写的事件，或系统的“请行动”事件（续派、指令、检查结果、合并冲突、补证）。Run／会话／指派生命周期记录和本人写的不算。

`releaseUnresponsiveSession` 的 `turn_done`、`system_turn`、`retirement_withdrawn`、`probe_invalid` 和主机运维停止，前置条件要求会话上没有已开始的 Run，释放后保留排队的 Run，由既有派发在新会话中投递——这就是这几类信号的“自动 start 并重投积压通知”。换代结算只在释放确实取消了已开始的 Run 时才会续派，否则不调用（避免与保留的排队 Run 重复启动）。

“有未读”中，带 `assignment_id` 或 `work_item_id` 的系统事件只算发给本负责人和本工作项的（V-3497）。

满足时发 `session_rotation_requested` 和系统 `work_item_resume_requested`（`rotation=true`，不消耗等待额度）；不满足时记 `session_rotation_skipped`（带原因），仅“额度已用完”交 PM Ops。因此“叫醒→空闲→再等 60 分钟→叫醒”最多发生一次：第二次失活只记录并交 PM；没有未读时根本不叫醒。

不变量 10：续派由系统在主机证明退出后发出，不是 Agent 自己的 Run 唤起自己；“无产出时自动续派一次”未做（已撤回）。
