# C-766 合并检查失败摘要定位与四分类

## 摘要兜底（host）

- `CheckFailureSummary` 仍按原正则识别失败用例、错误行和 lint 行；都没识别到时（例如用例计数全部 passed、进程退出码 1），追加“未识别到失败用例，相关输出：”，再列出最多 5 行：含 error/failed/panic 等关键词的行，以及输出的最后 3 行。包装器噪声（ELIFECYCLE、ERR_PNPM_、Duration、`Process completed with exit code` 等）不计入。所有行与原有发现一样，先脱敏再截断。
- vitest 的 `Errors  N error` 统计行保留到摘要。
- 新增 `points()`：从已识别的失败行（FAIL、×、错误行、`❯ file:line:col`、lint 文件）提取仓库相对文件，pnpm 递归前缀 `packages/x test:` 会被补回包路径，最多 10 个；`finish()` 返回 `failure_points`，只交主机分类使用，不写进摘要。

## 分类（server + domain）

- server 在单卡／卡级检查失败后读取 Git（全部只读，任一 Git 错误都视为没有证据）：
  - 本卡改动：各交付与检查基线的 merge-base 到交付提交（沿用 `deliveryChangedPaths`）；
  - 期间合入：从检查基线沿 `card_merged` 记录的 `merge_sha → previous_sha` 往回走，最多 20 步；遇到交付已包含的合并（`isAncestor`）或“相同交付通过过的旧基线”时停止，每张卡取其合并提交的改动文件。
  - 调用 domain 纯函数 `classifyCheckFailure` 得到 `baseline_drift` / `genuine` / `unknown`，作为 `failure_class` 交给 `recordMergeCheck`。
- 判定顺序：相同交付在旧基线通过（预检或本完成申请的检查），且期间有合入 → `baseline_drift`；日志没定位到文件 → `unknown`；按模块（`packages/x`、`apps/x`，其余取顶层目录）比较：只有期间合入的卡改过 → `baseline_drift`，只有本卡改过 → `genuine`；两边都改过时以精确文件决定，仍分不清为 `unknown` 并列出两边；都没改过 → `unknown`。
- domain 校验主机分类：标签只能是三者之一（主机不能报 `flaky`），依据不超过 600 字、无控制字符、通过摘录脱敏规则；`baseline_drift` 必须带卡号，且所列提交必须是所列卡已记录的合并提交。
- `flaky` 只由 domain 根据结构化记录判定：失败步骤全是测试前步骤（checkout/setup/bootstrap/install，后续步骤未运行或跳过），或同一代码树此前合并检查或作者预检已通过。命中时并入现有“每个完成申请只自动重跑一次”的额度（`flaky_auto_rerun`，与超时、基础设施重跑共用），流程版本 ≥2 生效。重跑后再失败不再重跑，改用主机分类（缺省 `unknown`），依据写明“已按偶发自动重跑一次（首次 attempt），重跑仍失败”，并带 `rerun.result`。
- 分类写入 `merge_check_finished` 和 `merge_changes_requested` 的 `failure_class`，退回理由最后一行为“失败分类：label（中文）：依据”，路由给作者的 fix 通知原样带上这一行。分类不改变任何检查结果或合并门禁。

## 批次

- 批次退回写明“批次 B 定位到本卡 C 的失败步骤：…”和日志入口；批次日志可能涉及同批其它卡，仍按 C-391 不复制摘要。二分有已通过前缀时标 `genuine`（依据为前缀通过、加入本卡后失败），只剩本卡时标 `unknown`。受限读取视图同时去掉 `failure_class`。

## 不做

- 不改动 GitHub 执行器、轮询和执行器配置；不改超时／基础设施偶发规则本身。
