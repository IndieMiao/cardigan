# C-767 部署监督器最小自升级（默认关闭）

## 目标

监督器发现自身版本落后、且 `supervisorChanges()` 的差异命中它依赖的包时，在开关打开的前提下自己完成升级：新目录 clone 与构建、用新代码读取现有配置、备份并改写启动配置、等空闲、通过 systemd 重启；60 秒内健康检查不过就用备份回滚。开关关闭（默认）时行为与现状一致，仍只开人工待办。

## 开关与兼容方案

- 开关不放进 `self-deploy.yaml`：它的解析对未知字段严格拒绝，旧监督器（包括回滚恢复的那个版本）读到新字段会拒绝启动。
- 开关放在同目录的独立文件 `supervisor-upgrade.yaml`，只有认识它的监督器才读；文件不存在等于关闭。这个文件忽略未知字段，以便回滚后的较旧版本还能读较新版本写的文件。
- 文件读取规则与 `self-deploy.yaml` 相同（属主、0600、不跟随符号链接、大小上限）。文件无法安全读取时自动升级保持关闭，并开一条待办，不影响常规部署。

```yaml
enabled: true
unit: cardigan-selfdeploy.service          # systemd user 单元
launch_file: /home/<user>/cardigan-selfdeploy/selfdeploy-watch.sh
health_timeout_ms: 60000                    # 可选，10 秒到 10 分钟，默认 60 秒
```

`launch_file` 的要求（C-772）：
- 指向**实际决定启动哪个版本**的那个文件，即含当前监督器目录完整路径 `…/release-watch-<sha>` 的文件。单元若通过包装脚本启动（例如 `ExecStart=…/selfdeploy-watch.sh`，脚本里用 `RELEASE=…/release-watch-<sha>` 选版本），就指向包装脚本，而不是 systemd 单元；单元本身写了版本目录路径时才指向单元。升级只替换这个文件里的版本目录路径。
- 是普通文件，不是符号链接；属主是运行监督器的用户或 root；组和其他人不可写（例如 0644 或 0600，0664 会被拒绝）；不超过 64 KiB。它所在目录及各级上级目录同样不能是符号链接、属主须为该用户或 root、组和其他人不可写（带粘滞位的除外）。

启用顺序：
1. 先按 README 人工把监督器升级到包含本卡的版本（这一步开关不存在，行为不变）。
2. 写入 `supervisor-upgrade.yaml`（`enabled: true`）。
3. 用当前运行的监督器目录跑只读自检：`node <当前监督器目录>/apps/cli/dist/bin.js self-deploy check-upgrade`（与监督器相同的用户和 `CARDIGAN_CONFIG_DIR`）。它按开关文件对 `launch_file` 做与正式升级相同的检查（属主、权限、符号链接、能否找到当前监督器目录路径），并检查监督器目录的上级目录能否安全准备新版本；逐条给出原因和改法，不改任何文件、不重启、不打开数据库。未通过时先修正再重跑，直到“自检通过”。
4. 重启一次监督器（开关只在启动时读取）。
5. 之后监督器落后时走自动路径；`enabled: false` 或删除文件即恢复人工路径。

自动升级因启动配置失败时，事件与 Needs You 待办写明具体原因和改法（组或其他人可写及当前权限、属主不符、符号链接、文件不存在、目录不安全、找不到当前监督器目录路径），不含主机路径和文件内容；问题目录的完整路径只在本机自检输出里显示。

## 流程

1. 比较：`main()` 照旧算差异。开关打开、且这个监督器版本没有失败或回滚记录时，`reconcileSupervisorNotice` 以 automatic 方式只写一条 `host_deployment_supervisor_change`（`automatic: true`），不开待办；旧版本的过期提醒照旧自动取消。
2. 前置：先等常规部署把服务部署到同一个 main（`state.current == main`，ready、进程在、无维护窗口），监督器再跟进到同一版本。
3. 准备（不挡检查）：在当前监督器目录的同级新建 `release-watch-<sha>`（已存在则不覆盖，记失败），clone、`pnpm install --frozen-lockfile`、`pnpm build`；在新目录里运行新代码的 `loadDeploymentConfig` 与 `loadSupervisorUpgradeConfig`；确认启动配置确实引用当前监督器目录。
4. 等空闲：要求没有受管长操作，并取得部署容量。取得容量需要 `merge_check_capacity` 里没有任何项目的活检查（单卡和批次合并检查、作者预检都占同一张表），也没有其它部署持有者；等待期间与部署一样关闭新检查准入，放弃等待时立即撤掉。取得后再封住长操作并复核部署状态。
5. 重启：把启动配置备份到部署目录（0600），用新目录路径整体替换旧目录路径（只替换完整路径分量），`daemon-reload`，写升级计划文件，记 `restarting`，用 `systemd-run --user` 在独立临时单元里启动重启助手（旧目录的 `self-deploy finish-upgrade`），重启监督器不会连带停掉助手。
6. 助手：`systemctl --user restart --no-block`，在 `health_timeout_ms` 内轮询：单元 active、主进程来自新目录、`state.json` 显示比重启前更新的就绪服务进程、所有固定端口可连。单元连续两次显示 failed/auto-restart，或主进程不是新目录，视为显式失败、立即回滚；超时也回滚。回滚前核对启动配置仍是本次改写的内容（被人改过就不覆盖），恢复备份、`daemon-reload`、重启并复查旧版本健康。
7. 结果：成功记 `completed`，只在项目动态出现；失败或回滚记 `failed` / `rolled_back` 并开一条 Needs You 待办。这个监督器版本此后不再自动尝试，回到人工提醒，避免坏版本造成反复重启。新监督器起来后照旧用 `supervisor_rechecked` 取消旧提醒。

## 已知边界

- 失败后留下的 `release-watch-<sha>` 目录不自动清理（同一目标不会再自动尝试）。
- 健康窗口包括旧监督器停服、新监督器启动服务到 ready；`stop_timeout_ms`、`ready_timeout_ms` 很大的主机需要相应调大 `health_timeout_ms`。
- 已绑定的 GitHub 远程检查在本机重启后照常继续（C-609 既有结论），不计入本机空闲判断。
- 隔离演练用真实 systemd user 管理器和真实重启助手，监督器本身用桩程序代替；真实主机上的首次演练作为合并后跟进项。
