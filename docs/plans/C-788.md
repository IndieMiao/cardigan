# C-788 派发每轮成本随通知积压增长，慢尾巴全局串行

依据：11-26 架构调研 1-performance.md P6、2-multi-project.md P3。

## 1. 每轮扫描按收件人和前置条件收窄

没人在循环里消化的通知（外接 Office 的未读、owner 的 needs_you、PM Office 角色行）不再每轮逐条解码、逐条判断。各步骤只在 SQL 里排除“按它自己的判断永远不会动”的行，留下的行仍走原来的判断，不改任何状态语义：

| 步骤 | 原来 | 现在 |
|---|---|---|
| `ack_inbox` 里的 `retireReconcileNotifications` | 每条活跃通知一次按主键查事件 | 一条 SQL 联结 `reconcile_finding` 事件 |
| `ack_inbox` | 全部可确认状态的行 | `listAckCandidates`：被铃声占用的行、绑定 Run 的角色行，以及“其主人的游标已覆盖到 seq”的行；needs_you 没有主人，不再参与 |
| `unreadable` | 全部未结行 | 只看发给非常驻 Assignment 的行（常驻 Assignment 能读所有卡） |
| `maintenance.obsolete` | 全部未结行 | `listAttentionCandidates`：投递异常状态、绑定 Run、诊断类来源事件、来源事件带人工待办的 needs_you；两个领域谓词的前置条件写在其注释里，契约测试固定 |
| `resolveObsoletePmNotifications` | 全部待处理行 | 只看主人可能是 PM Ops 的行 |
| 外接 Office 候选 | 每个候选一次读事务（deliver）+ 一次写事务（`checkStandingInbox`） | `external` 不可变：开事务前就返回；写事务内的复核保留 |

不做“到期自动确认”：needs_you、外接 Office 的未读保持 pending，测试固定。

## 2. 认领后的投递按机器并发，角色升级移出派发主路径

- 认领（`deliver.claim`，名额仲裁的同步事务）仍按原 FIFO 顺序逐个进行；认领之后的唤醒或起会话交给 `LaunchLanes`：每台机器同时只有一个，总数不超过 `launchConcurrency`（默认取 hc 调用队列与准备队列宽度的较小值，现为 2）。同一 Assignment 的下一个候选等上一个投递结束；只有在本机器车道空闲时才认领，认领后的铃声尝试立即投递。一轮结束前等所有车道收尾，再换掉本轮的状态加载器。
- 空闲退役和默认角色升级（`upgradeIdleAssignmentRoles`，有运行时 IO）不再在每个项目的路由里内联等待：每项目每 60 秒最多一次，在派发旁边单独跑（tick profile 里是独立的 `dispatch_role_upgrade` 循环）。为保持“先升级再投递”，某项目的这一趟排上到跑完之间，该项目的工作项候选本轮跳过（`role_upgrade_pass`），下一轮投递；其它项目和常驻角色不受影响。`close()` 等这一趟结束。
- 运行位置由 `DispatcherOptions.roleUpgradePass` 决定：控制平面（`assembly.ts`）用 `beside`（上述旁路）；不传时为 `inline`，仍在各项目路由里、投递之前等这一趟跑完，与改动前一致。旁路这一趟要拿主机操作锁（真实文件 IO），用假时钟背靠背连续 tick 的测试若跑在旁路模式，结果会取决于这一趟的真实耗时（首次合并检查里 `dispatch-superseded-retirement.test.ts` 的不稳定失败即此原因），所以既有测试保持 `inline`，只有专门覆盖旁路的测试显式用 `beside`，并在需要时等 `roleUpgradesSettled()`。
