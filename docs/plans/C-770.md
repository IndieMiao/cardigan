# C-770 监督器自升级的回滚盲区

C-767 的监督器自升级（默认关闭）留下三处回滚链路盲区，本卡补齐。开关、`self-deploy.yaml` 字段和常规部署流程都不变；开关关闭时没有升级器、不写升级记录，下列改动都不会触发。

## 1. 放弃等待时恢复启动配置

`SupervisorUpgrader.awaitRestart()` 超过 `2 × health_timeout_ms + 120 秒` 仍有计划文件、本进程也没被重启时：

- 启动配置仍等于计划里的改写摘要（`launch_sha256`）：用备份恢复，`daemon-reload`。之后监督器无论因为什么重启，运行的都是旧目录。
- 启动配置已经等于备份：视为已恢复（助手或兜底先做了），只补 `daemon-reload`。
- 启动配置被人改过或备份不可读：不覆盖、不重新加载。
- 三种情况都把这次尝试记为 `failed`（说明写清恢复结果和备份路径），由它开出唯一一条 Needs You。这个版本从此不再自动尝试，计划文件删除。
- 审计写不进去时保留计划文件，退回 C-767 的“重启助手超时”提醒。

恢复函数 `restoreLaunch` 改为幂等，返回 `restored | already | changed`。监督器、助手、兜底三方可能都会尝试恢复，谁先谁后结果都一样。

## 2. 重启助手异常退出的兜底

方案：助手临时单元加 `ExecStopPost=`。没有用 `OnFailure=`，因为它要求事先安装一个常驻单元。

- `systemd-run` 额外传 `--property=ExecStopPost=<node> <旧目录 bin.js> self-deploy recover-upgrade` 和 `--property=TimeoutStopSec=<2×健康窗口+120 秒>`。不管助手是正常结束、报错退出还是被 SIGKILL，systemd 都会在助手退出后运行这条命令。本机 systemd 255 已实测：SIGKILL 之后 ExecStopPost 照常执行。
- 助手发出 `restart` 之前，先在计划文件里写 `restart_requested_at`。兜底据此判断旧监督器有没有被要求停下。
- `recover-upgrade`，即 `finishSupervisorUpgrade({ resume: true })`：
  - 没有计划文件（助手已正常结束）：什么都不做，退出码 0。
  - 计划里带 `result`（助手的结果没能写进审计）：重放这条审计，再删除计划。
  - 没有 `restart_requested_at`（助手在重启前就退出了）：恢复启动配置并 `daemon-reload`，不重启，记 `failed`。
  - 有 `restart_requested_at`：在剩余的健康窗口里继续核对新监督器，至少观察一次。健康就记 `completed`；否则按原流程回滚（恢复、重新加载、重启旧版本、复查健康），记 `rolled_back` 或 `failed`。如果启动配置已是备份、旧版本也已健康（助手在回滚中途退出），就不再重启一次。
- 助手和兜底写终态审计时最多尝试 3 次。仍失败时，把结果写回计划文件（`result`）交给兜底重放，不再只打印到控制台。
- 计划文件新增的两个字段都是可选的。C-767 版本的读取方忽略未知字段，旧版本照样能读。

## 3. 一次失败只有一件 Needs You

`reconcileSupervisorNotice` 处理人工提醒时，如果当前监督器版本有 `failed` 或 `rolled_back` 的自升级尝试，并且该尝试已开出待办：

- 不再新开“请按 README 升级”的提醒，在失败待办的说明末尾补上这次到 main 的差异。`host_deployment_supervisor_change` 事件改为引用这条失败待办（`human_action_id`），并带上 `upgrade_attempt`。
- 开关打开前已经开着的同版本人工提醒会被取消，原因写“已并入监督器自动升级失败待办 H-n”。
- 每次失败尝试只合并一次，之后 main 再前进也不再新增。

## 已知边界

- 用户 systemd 管理器本身停止，或主机在助手运行中重启时，`ExecStopPost=` 不会运行。临时单元不会跨重启保留，这种情况仍需人工按 README 核对。
- 监督器放弃等待时如果助手其实仍在运行，助手之后的重启会落到已恢复的旧配置上，再按回滚路径收尾，结果一致。代价是旧监督器可能多重启一次。
