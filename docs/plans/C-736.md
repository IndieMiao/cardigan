# C-736 点名或 PM 派活的评论 Run 按工作项占资源，并记下原因

来源：SEN-C-131、SEN-C-105。C-721 把所有 `comment_posted` 唤起的产出项跟进 Run 视为“只提交/回帖”，不占资源；PM 用评论派活时 Agent 拿不到 godot，只能报 blocked。

## 选择的做法

采用卡片要求中的方式 1（准入时按评论判定），不新增 Run 内申请资源的入口：只改 `runResourceKeys` 的判定，派发、排队、前序等待者、巡检诊断都已共用这一个函数，改动面最小。

## 判定（`packages/host/src/run-resources.ts`）

`comment_posted` 作为触发事件或同铃待读通知时，满足以下两条即按工作项占资源（没名额就按 `concurrency_limit` 排队）：

- 是“派活评论”：
  - 作者是 PM 指派（`role_id=pm`，含 Ops 与 Office）；或
  - 点名了本指派 `@A-n` 或本工作项 `@W-n`。点名从评论对应的时间线条目 `mentions`（包含 `post_comment.mentions` 显式点名）和正文里的 `@A-n`/`@W-n` 两处合并读取。
- 工作项处于可执行状态：`in_progress`、`ready`、`changes_requested`。

其它评论（普通讨论、点名别人、工作项已交付等）维持 C-721 的轻量判定，不占资源。

## 诊断

- 新增 `runResourceClaim` 返回 `{ keys, reason }`；`runResourceKeys` 只取 `keys`，原调用方不变。
- 派发准入写 `resource_keys` 时同时写 `Run.resource_reason`（JSON 字段，不加列、不迁移），例如“普通讨论评论”“评论点名 @A-3，工作项处于 in_progress”“PM 评论，但工作项处于 delivered，不可开工”“待读通知：instruction_issued 需要按工作项开工”“rework Run”“验证项跟进”。工作项和角色不要求资源时不写。
- 主机 `cardigan launch` 路径写“主机启动按工作项占用”。
- 少占资源 Run 的铃声提示改为“本次 Run 未占用 X 名额（原因：…）”。
- 执行页 Run 状态的悬停详情加一行：“已预留 godot：原因”或“未占用资源：原因”。

## 不做

不改资源名额配置、不加门禁、不加 Run 内申请资源入口。

## 测试

- `packages/host/src/run-resources.test.ts`：正文点名、`@W-n`、仅时间线显式点名、PM 评论、同铃 PM 评论均按工作项占用并给出原因；普通讨论、点名他人、相似文本、工作项已交付不占；其它判定的原因文字。
- `apps/server/src/dispatch.test.ts`：godot/模拟器名额占满时 `@A-n` 评论排队，名额释放后按工作项占用派发并记下原因；普通评论照常直接派发，铃声写明未占原因。
- `apps/web/src/views/ExecutionPriority.test.tsx`：Run 悬停详情显示预留与原因。
