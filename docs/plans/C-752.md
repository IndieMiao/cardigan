# C-752：远程 claude-code 会话的 60 分钟失活回收

## 现状核对（修复前）

- `run_inactive` 告警的 `activity_source` 先取会话元信息（`claude-code:session_metadata`，状态 fresh/stale 时），没有才取文件写入时间。A-399 / R-3420 的告警记为 `claude-code:transcript_mtime`，说明那次读取**确实没有可关联的会话元信息**，只有同一 transcript 的写入证据。
- 失活回收（`InactiveRunReaper`）对 claude-code 和非本机 Run 只认同 Run 的会话元信息（`lastInactiveStopActivity`）。没有时返回“未知”，派发循环的预筛就判为未到期，连停止前的定向复读都不会发起，60 分钟回收永远不触发。sensen 的 Agent 基本是 mac-mini、cardigan-ci 上的 claude-code，所以一次 `inactive_stop_confirmed` 都没有。
- 修复前 sensen 远程会话的活动来源：告警侧为 `claude-code:transcript_mtime`（会话元信息缺失），回收侧无可用来源。

### 为什么远程读不到会话元信息（未能用现场数据确认）

本卡不读生产文件和 sensen 的 worker 目录（属另一项目账户）。按代码与本机 transcript 的格式对照，元信息为空而文件证据仍在的路径有三条，均只影响会话元信息、不影响文件证据：

1. 末 256 行内任一主线程记录时间戳回退，读取器整段丢弃会话元信息（文件证据不做此检查）。排队后补写的用户消息、门铃注入等都可能造成。
2. 最新主线程记录的 cwd 不在登记工作树内（会话 `cd` 到工作树外的允许目录），会话元信息不能关联；文件证据取目录内最后一条。
3. 末 256 行全是非对话记录（长时间前台命令的进度记录，以及新版 Claude Code 每轮写入的 api-request、mode 等记录）。

这三条都是为防误判而设的既有规则，放宽它们会让告警与上游聚类一并变化，本卡不改，改走验收第 2 条的替代证据。

## 修复后的判据

1. **可归属的 transcript 写入**：读取器对已核实会话、目录与 Run 代次的文件证据，另带同一文件的原始写入时间 `written_at`。回收只在以下条件同时满足时采用：harness 为 claude-code；来源为 `claude-code:transcript_mtime`；`run_id` 为当前 Run；会话号、终端引用（`runtime_key`）、会话代次与 Run 开始时间都通过既有关联检查；没有错误标记。计时取记录时间与原始写入时间的较晚者，同一会话之后的任何写入（错误、旁支、工作树外记录）都只会推迟回收。
2. **不退回只看 MCP**：既无会话元信息也无上述文件证据时仍为“未知”，不回收。会话元信息带错误且无可核实进展时（上游故障），旧的写入时间不能替代进展，仍不回收。
3. **终端进程身份**：停止只针对领取围栏时记下的终端引用；领取、停止前复查、结算三处都核对引用未变，结算仍须确认该终端退出。停止前复查定向重读同一会话，读到新的写入就撤回。
4. **现有例外**：受管主机操作在途（`hostOpsPending`）不领取；人通过 `cardigan assignment attach` 接入时，回收先取同一把主机操作锁，取不到就本轮跳过，从领取到结算全程持锁。修复前回收没有取这把锁，本卡补上。
5. **留痕**：领取事件 `run_inactivity_stop_requested` 记 `evidence`（`session_metadata` / `transcript_write`）；确认退出后照旧在卡片时间线写一句“失活回收：已确认终端退出，自动取消 Run（失败），保留工作项与工作树。”

## 启动失败与空闲回收（C-140 A-355）

- `mcp_unavailable`（会话没连上 Card 工具）与 `recovery_startup_failed`、`runtime_exited` 一样按启动失败处理：Run 取消不算处理完，只有同一 Assignment 之后有 Run 真正开工（会话恢复）或 Assignment 已释放，PM Ops 等收件人的 `run_attention` 和系统待办才自动关闭。读过、确认收到都不算处理。
- 空闲会话回收遇到未处理的启动失败，记为 `startup_failure_pending` 不接手，由启动失败的通知交 PM 或人重启，两套机制不再同时处理同一会话。

## 稀缺名额的更短阈值（默认关闭）

`run-capacity.yaml` 新增可选项：

```yaml
scarce_inactive_cancel_after_minutes: 30   # 不配置即关闭；须短于 inactive_cancel_after_minutes
scarce_resources: [android.emulator, ios.simulator, godot]  # 可选，默认即此三项
```

只对 `resource_keys` 含其中任一项的 Run 生效，判据与普通回收相同，只换阈值。默认 60 分钟不变。按卡片要求，先观察一周第 1～2 条的误判再决定是否启用。

## 受管 stop 后待处理通知不起新会话（sensen A-388，所有者补充）

现场：A-388（mac-mini）被 `cardigan assignment stop` 受管停止后，待处理通知报 `notification_backlog`（`restart_blocked=session_maintenance`）和交接超时，一直没有新会话，人手动 start 后才恢复；同时停的 A-399 能自己起来。

原因：空闲回收在 macOS worker 上多次确认不了退出时，会把回收记录标为交接（`idle_retirement.handoff`）并保留会话。受管 stop 的释放步骤清空了会话绑定，却没清这条记录。C-690 只在新会话已绑定时才把旧记录判为被取代，没有绑定时记录一直留着，派发器就一直把它当作 `idle_retirement` 挡住。所以只有带这条记录的会话会出现这个问题，A-399 没有这条记录，不受影响。

修复：受管 stop 或暂停的释放步骤（主机已确认释放该终端）一并结束属于被释放会话的空闲回收记录，等待中和停止中的都清，与 C-667 已退出确认、C-730 无响应释放的处理一致，并记录 `idle_session_retirement_superseded` 事件。属于别的会话的记录不动；暂停照旧等人 start。之后有待处理通知或新工作时，按正常派发起新会话。

已部署前就卡在这种状态的 Assignment（释放早于本修复）不会被自动清理，仍需人 start 一次。

## 已知限制

- 会话主线程等待一个超过 60 分钟的子代理时，主 transcript 不写入；与修复前只认会话元信息的情况相同，本卡不改变。
- worker 时钟超前于控制机时，刚写入的证据被视为来自未来而不采用（只会推迟回收）。
