# C-520 · 控制主机磁盘回收

1. 空间知会与删除无关：自举监督器检查数据目录所在文件系统，按普通账号可用块数除以总块数比较，严格低于阈值时在 Needs You 知会。`self-deploy.yaml` 可设 `disk_low_percent`（1–100 的整数，默认 15）。一次持续低空间只知会一次，包括监督器重启、知会已读；恢复后再次跌破才再知会。不创建待办、不阻塞部署，也不因低空间越过删除门禁。
2. 计划器只接收受信根的直接子项：部署器生成的 release、快照文件和数据库中对应的本地 `A-n`。release 保留 state 引用、监督器及初始 release 和最近 5 个；快照保留最近 5 份和含当天在内最近 7 个自然日各最后一份。手动备份、worktree 和 Git 分支不进入候选集合。
3. 运行目录需同时核对 released 时间严格超过 3 天、所有 Run 已终结、没有运维围栏或开放待办引用。不得给 Agent 增加父目录写权限。release 查不到占用证据不能视为无人使用；需要在执行端方案确定后实现排他核查。
4. 首次对真实存量只出 dry-run：清单包含相对名称、大小、合计、保留策略与无法核实的对象。运维将清单附卡，PM 核对；按项目的真实数据删除授权确认后，才可启动实际执行。执行前重验状态和文件身份；跳过与清单不符的对象。删除及跳过原因留审计。测试只用临时文件和合成状态，不能代替现场清单。

## 上线与回退

- Q-970：沿用本机已配置的隔离 SSH 账号清内容，不用 sudo。原主机账号跨两步持有原目录描述符，在新的写事务内复核释放时间、Run 和运维引用，只对保护父目录内同一、非挂载、已空的外壳 `rmdir`。非空、实例变化、凭据或权限不匹配时保留，绝不递归兜底。本卡只处理共享在控制主机的 `local` 运行目录，不把远程机器的路径当本地路径。
- 升级**监督器本身**，不仅是 Web 服务。新监督器确认部署成功、两个角色按实际模式 ready 且仍存活后，默认只在主机私有的 `self-deploy/retention-preview-1.json` 原子生成一次清单；没有批准不回收。清单含相对名称、大小、总字节、跳过项、策略及实例标识。目录按实际分配块统计（硬链接共享时总量不是净释放量）；数据库快照按文件长度统计。低空间知会不代替确认。
- 运维把**原文件字节**作为证据附到本卡或专用运维卡，核对 SHA-256、总量及 `skipped`。完整进程视图不可读、检测到正在使用、出现挂载或嵌套 Git 仓库等，都不把对象列为可删。若占用无法核实，不提权、不以空输出代替空闲证明。若清单不完整，先排查，不确认；重出清单只递增 `retention.revision`，不用手改旧报告。
- PM 核对清单与持续启用范围后作出批准。真实数据删除还需同卡 `data_deletion` 批准，由人或已有该类别有效授权的 PM 作出。两者均须为已解决的 `approve`，选项键 `enable_retention`，目标 `artifact_sha256` 和引用附件均绑定这份原清单；拒绝、撤销、摘要不符或委托失效都不会执行。若有有效类别授权，PM 的同一份删除决定可以同时满足两项。Q-970 不满足此条件。
- **取得批准之后**，管理员才在私有 `self-deploy.yaml` 填入下列配置并重启监督器。移除 `approval` 并重启即回到只预览。改变保留策略或执行目标需新版本清单和新批准。示例键值不是授权：

```yaml
retention:
  revision: 1
  releases: 5
  snapshots: 5
  daily_days: 7
  released_days: 3
  # approval:
  #   sha256: <清单的完整 SHA-256>
  #   pm_review: <同意该清单的 PM 拍板编号>
  #   data_deletion: <同意实际删除的拍板编号>
```

- 第一次执行只处理批准清单里仍匹配的对象；在之后的成功部署才滚动处理新增和退出保留窗口的对象。每轮最多处理一个对象，成功、尝试和未完成均写入 `host_retention_recorded` 项目审计。不可读或有残余时先核对现场，不因清理失败回滚服务。release 脱离原名后会再次检查全机进程引用；进程或文件系统异常中断留下的 `.retiring-release-*` 不自动重删。运行目录若部分清理后发生中断或变更，需要重新预览，原清单不放宽匹配。
