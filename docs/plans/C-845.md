# C-845：部署后角色同步遇写锁时在同步内退避重试

## 现象

部署后的 `self-deploy roles` 三次报 `database is locked`（退出码 1），都发生在“停旧 server、新 server 和后台刚起来、立即同步角色”的窗口里，靠 C-801 的外层整体重试才完成。CLI 的 Store 用 `BEGIN IMMEDIATE` 加 `busy_timeout = 5000`：新后台启动时的恢复写入、派发和其它 CLI 写命令连续占着写锁超过 5 秒，同步就直接失败。

## 做法

1. **同步内退避重试**（`packages/host/src/deployment-node.ts` 的 `refreshRoles`）：只对 `sync` 一步、且命令输出里认出“数据库被锁”（沿用 C-650 的固定原因识别）时，等待后重跑 `self-deploy roles`。其它退出原因、快照失败照旧立即失败。
   - 默认重试 5 次，首次等 2 秒，之后翻倍，单次最多 8 倍：2、4、8、16、16 秒，共 46 秒退避；加上每次运行自身最多 5 秒的 busy 等待，最坏约 76 秒。
   - 两个值都在主机 `self-deploy.yaml` 里可配：`role_sync_lock_retries`（0–20，0 即回到 C-801 原样）、`role_sync_lock_backoff_ms`（1 毫秒–10 分钟）。
   - 重跑是安全的：C-801 的外层重试本来就整体重跑同一命令；角色升级按受信记录判断，重跑同一版本得出同样结论。
2. **最终仍失败时写明等待和持锁方**：错误文字写“同步内已退避重试 N 次、共等约 S 秒仍被锁；打开数据库的进程：……”，同时在该次尝试上记结构化的 `lock_wait`（`retries`、`waited_ms`、`holders`），部署诊断原样带出。
   - SQLite 不告诉谁持着写锁，所以列的是失败那一刻**打开了数据库（含 -wal/-shm）的其它进程**：监督器自己的 server 子进程标成“web 服务”“后台服务”；Cardigan CLI 标成 `cardigan CLI` 加最多两个小写命令词（如 `card comment`），不带参数值；其余只写“其它进程”。每项附 pid，最多 10 项，不含路径、参数值、环境变量；只读 `/proc`，从不发信号。非 Linux 或读不到时写“未能识别”。
   - 处理口径不变（C-801）：外层仍重试 1 次；最终失败交主机操作员，不推所有者；角色包无变化且常驻 PM 在岗时只知会。
3. **不拖长上线**：ready 判定、停服时长和“已部署”记录都在角色同步之前完成并落库，同步的等待不影响它们。另外把长操作闸门（C-609 的 fence）提前到角色同步之前释放：server 已起来，受管长操作（合并步骤、送签等）不必陪着同步退避。部署锁仍持到同步结束，避免下一次部署与同步并发。

## 测试

- `deployment-post-deploy.test.ts`：真实 SQLite 写锁由另一个进程持有——中途释放时同步在自身退避内完成；一直持有时报出重试次数、等待时长和持锁进程（命令词有、参数值和路径没有）；持锁方标注；最终失败交主机操作员、不进所有者消息。
- `deployment.test.ts`：同步等待期间 ready/停服时长已记录、闸门已释放；`lock_wait` 只随 sync 失败进入部署记录。
- `deployment-config.test.ts`：两个配置项的默认值和边界。
- `deployment.contract.test.ts`（domain）：`lock_wait` 的字段边界，只允许出现在 sync 尝试上。
- `deployment-recovery.test.ts`：C-801 的“新 server 恢复期间持锁”场景以 `role_sync_lock_retries: 0` 运行，外层重试与交人口径不变，失败记录多出 `lock_wait`。

## 未覆盖的风险

- 默认 76 秒的最坏等待之后仍可能失败（例如后台启动持锁更久），这时口径同 C-801。合并后由主机运维在后续几次部署里观察 `post_deploy_failure` 是否消失，再决定是否调大配置。
- “打开数据库的进程”不等于“持锁的进程”，只是排查线索。
