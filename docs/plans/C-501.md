# C-501 需求卡与子卡

- 使用非 Git 的内置 story 模板。拆解项由常驻 PM Office 通过需求卡处理，不派发独立工作会话；总结作为有身份的时间线记录，人仍是唯一完成者。
- 创建时记录同项目、未结束的需求卡为父卡。父子不是依赖，不获得额外读写权限；子卡按原跨卡规则读父卡及其附件。
- MCP 与 Web 详情返回子卡编号、标题、状态、各状态计数和结束进度。最后一张子卡结束时，在同一事务内记父卡事件，路由给 Office。新子卡使旧总结失效。
- 取消需求卡仅由人发起。存在未结束子卡时提交明确的取消或脱离选择，并校验确认时所见的子卡集合。取消复用原有工作项、排队执行和人工待办收尾逻辑。
- Web 提供单张创建与取消选择；讨论、整份拆解方案确认和节点图分别属于 C-502、C-503。

## 后续卡可复用的接口

- `create_card(parent_card_id)`、CLI `card create --parent-card C-…`、Web `POST /cards` 均走 `createCard`。父子关系不隐含 `depends_on_cards`。
- 详情的 `card.story_progress` 含 `children`（仅 id、title、status）、`counts`、`finished`、`total`。MCP 子卡的 `parent_reference` 只列可读父附件编号；读取内容仍需 `read_attachment`。
- 常驻 Office 用 `post_comment({card_id,body,story_summary:true})` 写对照总结；当前总结定位在 `card.story.summary_entry_id`。确认走既有人标完成接口；新增子卡后旧总结只保留在时间线。
- 取消需求卡复用 `/cards/:id/cancel`，`story_children:{action:'cancel'|'detach',ids:[…]}` 是人确认时看到的全部未结束子卡，清单过期则整笔拒绝。
- Web 入口：空项目可直接新建；已有卡片从详情「更多 → 新建卡片」进入。未结束需求卡的同一入口为「新建子卡」，默认带入该需求卡编号，不改变看板工具栏。
