# C-613 项目定制角色：默认包 + 项目附加规则

宗旨：打通阻塞，不新增人工确认、拍板或停摆条件。发现问题保留当前版本并知会 PM，继续推进。

## 结构

- 角色版本新增可选字段 `default_overlay`：
  - `base_role_id`：作为底的默认角色（通常就是本角色；非默认编号的角色如 `release_ops` 需显式指定）；
  - `append_instructions`：追加在默认说明之后的说明段；
  - `extra_tools`：额外工具；`removed_tools`：显式移除的工具（优先于默认包，默认包以后新增的同名工具也不装）；
  - `base_hash`：作为底的默认角色的策略指纹，即“默认包版本引用”；
  - `composed_hash`：组合结果的策略指纹。之后有人在附加规则之外手改，指纹就对不上，系统不会悄悄重组覆盖。
- 两个指纹都由 `deploymentRolePolicyHash` 计算。这是部署监督器、发布回执和 C-603 共用的同一套指纹，不另造来源判定。
- 组合是纯函数 `composeRoleOverlay`（domain），只替换默认包管理的策略字段。harness、启动配置、显示名、abilities、机器标签沿用项目自己的值。
- `packages/host/src/role-overlay.ts` 的 `expectedRolePolicy` 是“这个版本应当等于什么”的唯一出处，发布回执、空闲会话升级和 CLI 都用它：带附加规则时取“当前默认包 + 附加规则”，否则取默认包。

## 部署时（`self-deploy roles`）

所有项目都执行同一套部署处理（`syncOverlayRoles`）。cardigan 原有的默认包路径保留，只负责普通默认角色。

### 可信默认记录（与 C-603 共用，Q-1197）

来源判定只读一份只追加的系统记录 `host_role_defaults_recorded`：
- 只认本项目流里 `actor.kind=system`、`actor.project_id` 为本项目、不挂卡片的条目，不同项目互不串用。
- 每条是一个角色的完整策略哈希（`deploymentRolePolicyHash`），可带内容指纹（段落哈希、工具、策略字段，不存正文）。
- 写入时机：每次部署记下当前默认包；CLI `role upgrade --from-default` 记下当时的默认；第 2 步精确命中的种子、第 3 步证明出的旧默认，都连内容一起写回。
- 首次上线的种子：本项目第一条记录之前已有的 `host_role_pack_published` 回执里 `matched` 条目的完整哈希（那时回执只覆盖普通默认角色）。
- 不再用监督器的弱指纹或 changedRoles 判定。判定时“更早的默认”不含本发行版自己的默认，同一发行版重跑结论不变。
- C-603 的“等于任一条记录就自动升级”直接读这份记录（`knownDefaults` / `recordDefault`）。两卡谁后合并谁对齐接口。

### 带附加规则的角色

每次部署都按新默认包重组。内容有变时追加新版本，写 `host_role_upgraded`，路由给 PM Ops，并轮换空闲的常驻会话。

以下情况保留当前版本、通知 PM，不生成人工待办：
- 附加规则之外有手改；
- 重组后校验不通过；
- 底角色已不在默认包；
- 启动配置缺失。

### 默认编号、未登记附加规则的角色（所有项目，包括 cardigan）

1. 等于当前默认：不处理。
2. 等于任一条更早的记录：没手改过的旧默认，直接升级到新默认。cardigan 也在这一步完成，不再交回原路径重判。命中的若是只有哈希的记录（种子），当场把这一版的内容写回记录，延期后项目再追加也能认出旧默认的内容（V-3073:2）。
3. 先证明所有只有哈希的记录（种子）：在说明末尾的段落边界切分，并尝试少量工具组合，用完整哈希证明；证明出的旧默认连内容写回记录。再对每条带内容或已证明的更早记录 K，读成“K + 追加段落 + 额外工具 − 移除工具”：
   - 当前默认包本来就有的工具和段落不算项目规则；
   - 其余额外的工具和段落不能出现在该角色任何一条带内容或已证明的更早记录里，否则可能是被后来的默认包收回的内容；
   - 多个候选时取额外、追加、移除项总数最少的；数目相同取较新的记录。
4. 其余情况保留当前版本：cardigan 交原默认包路径；其它项目知会 PM。

缺启动配置时保留版本并知会 PM；来源已在记录里，下次部署直接复用。

cardigan 原默认包路径只处理本轮没判定过的角色。指纹与上一默认不一致时：有本发行版以外的记录，才按手工改动交人核对（C-603 原规则）；没有记录（例如旧监督器的弱指纹）只知会 PM，不建人工待办。

迁移后内容有变，写 `host_role_upgraded`，带 `migrated` 前后指纹。内容不变时见下节。

### 常驻会话轮换（V-3037:1）

domain 的 `rotateStandingAfterDeployment` 和主机巡检都用 `deploymentAuditedVersion`：只轮换到有系统升级审计（`host_role_upgraded` 正好指向该版本）的版本。

- 系统写出的新版本若生效策略与上一版相同、启动配置和 harness 未变、启动配置在本次部署有效，且上一版本身有审计，就为它续写一条 `host_role_upgraded`，标 `metadata_only`，照常送 PM。domain 再核对两版的工具、能力、机器要求、启动配置和 worktree 相同。
- 人手改出来的版本、改了启动配置的版本都没有审计：不轮换，保留会话。
- 部署时轮换会核对目标版本的启动配置在本次部署有效，无效就保留会话并告警。会话忙碌也照样核对，结论按角色、版本、启动配置写进项目流的系统事件 `host_role_launch_checked`（不挂卡，结论变化时才写）。
- 部署之外（服务巡检）先看这条结论：最近一次为无效就保留会话，不重复告警（V-3073:1）；为有效或没有结论时，只在启动配置与在岗版本相同时轮换，否则告警，等下次部署核对。配置恢复后由下一次部署写入“有效”，空闲会话当场轮换，忙碌的等巡检轮换；其它角色不受影响。

## CLI（仅人可用）

`cardigan role overlay <角色> [--base <默认角色>] [--keep-instructions] [--append-file f] [--add-tools a,b] [--remove-tools a,b] [--dry-run]`

- 已登记的规则原样保留，重跑不会撤销显式移除。
- 未登记时，从当前版本读出规则，说明和权限保持不变：当前缺少的默认工具登记为显式移除；`withdraw_review` 只在角色也没有 `submit_review` 时一起移除（V-3028:3）。
- `--append-file` 替换追加说明。
- `--add-tools` / `--remove-tools` 在现有规则上增减。即使某个工具今天不在默认包里，显式移除也会记下，以后默认包加入它时不会授予（V-3028:2）。
- `--keep-instructions` 用于非默认角色：保留本角色说明，只跟随底角色的工具和策略字段。
- 角色的 kind、worktree、能力或机器要求与底角色不同时，直接拒绝，不改动角色。
- 仅常驻 PM 可用的工具（如 `send_owner_message`）仍按原规则拒绝。

`role upgrade <角色> --from-default`：带附加规则的角色按“当前默认包 + 附加规则”升级。

## 存量迁移（sensen）

由人操作，Agent 权限不变。sensen 没有旧回执可作种子，上线后的第一次部署只记下当前默认包，定制角色知会 PM；之后默认包有变化时，能对上已记录默认的角色自动迁移，事件里带前后指纹。H-215 按 PM 的安排，用下面的命令处理仍需人工登记的角色。

```sh
cardigan role overlay <角色> --project sensen --dry-run   # 先看对比，确认后去掉 --dry-run
# release_ops 不是默认角色：选 kind、worktree、能力都一致的默认角色作为底
# （例如 produce 型对应 coder），保留本角色说明。
# 发布工具 publish_artifact 作为额外工具保留；send_owner_message 只给常驻 PM，不授予 release_ops。
cardigan role overlay release_ops --project sensen --base <同类默认角色> --keep-instructions --dry-run
```

## 已知边界

- 附加规则只表达“追加说明段（或整段替换）+ 增减工具”，不能改 kind、worktree、能力。
- 用哈希证明旧默认时，只覆盖追加在末尾的段落（最后 12 个段落边界），新包没有的额外工具最多 14 个，新包已有的额外工具最多两个；超出范围不猜，只通知。
- 建立在本发行版默认上的定制角色，本发行版不迁移（本发行版的默认不算更早的证据）；下一次默认包变化时按第 3 步迁移。
- 项目若要加回一个曾被默认包收回的工具，不会自动读成附加规则，只知会 PM，由人用 `role overlay` 登记。
- `role apply` / `role update` 手改带附加规则的角色后，部署只通知，需要人用 `role overlay` 重新登记。
