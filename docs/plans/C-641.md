# C-641 写事务里不做计算：系统命令和 dispatcher 命令改为乐观提交

## 背景

写事务一律 `BEGIN IMMEDIATE`，系统命令把建状态、跑 reducer、落盘整段放在写锁里。后台约四成时间持有写锁，web 写入等锁最长 4.67 s（调研见 C-633 attachment-9130 第 1.7、3.4 节）。

## 做法

### Store 原语 `uow.optimistic(project, plan, { attempts })`

1. **快照计算**：`BEGIN DEFERRED`，先读出本项目的命令状态版本（`CommandSnapshots.version(project)`，也就是命令状态缓存用的键：本项目各集合、全局身份、全部 Assignment），再调用 `plan`。`plan` 拿到的是只读仓库，外加一个缓冲 ID 分配器（每个计数器只读一次，在内存里编号，不写库）。
2. **没有要写的**：`plan` 不返回 `write` 时，读事务结束就直接返回，不拿写锁。系统规则多数轮次属于这种情况。
3. **短写事务**：`BEGIN IMMEDIATE` 后重新核对版本，以及本次用过的每个 ID 计数器。两者都没变才执行 `write`，并把缓冲的 ID 写回计数器；写锁只覆盖落盘。
4. **冲突**：版本或计数器变了就丢弃计划、重新计算，最多 `attempts` 次（默认 3，上限 20）。用完后退回悲观锁：`plan` 和 `write` 在同一个 `BEGIN IMMEDIATE` 里执行，和原来的 `uow.run` 相同。
5. **读集之外的端口**：机器放置（`read_machine_placement`）会跨项目读取，还会读文件，版本覆盖不到。`plan` 一旦读它，本次直接走悲观路径；即使调用方吞掉了这个信号，也照样走悲观路径。
6. **观测**：快照阶段向 observer 报 `read`，短写阶段报 `run`，所以 tick profiler 里的 `run` 时长就是持锁时长。`store.optimisticStats` 累计 committed / unchanged / conflicts / fallbacks 四项。

计算过程不跨 await，同一进程内不会有交错写入。跨进程的并发写由版本加计数器核对来发现。

### 接入点

| 位置 | 改动 |
|---|---|
| `apps/server/src/merge-loop.ts` `runSystemCommand` | 改走 optimistic，覆盖 merge loop 和 cleanup loop 的全部系统命令；效果为空时不拿写锁 |
| `apps/server/src/system-rules.ts` `runSystemRules` | 原来一个大写事务里串着十几条规则，每写一次就重建一次状态。现在拆成依次执行的步骤：连续没有效果的步骤共用一个快照；每个非空效果单独提交一次短写事务，下一步读已提交的状态。循环的候选顺序仍取自循环开始时的状态 |
| `packages/host/src/deployment-roles.ts` `rotateIdleDeployedRoles` | 每轮先在快照里判断有没有待轮换或待处理的角色冲突，没有就直接返回；有才进入原来的加锁流程（锁内全部重新判断） |
| `apps/server/src/dispatch.ts` decision_followups、suggestion_progress | 改走 optimistic，只有到期提醒才拿写锁 |

### 行为变化

`runSystemRules` 中某条规则报错时，之前已经提交的规则效果会保留，和逐条执行的系统命令一样，不再整轮回滚。报错的那条规则本身仍然不落盘（见 B3a 测试的更新）。

## 未覆盖

- dispatcher 的 deliver 阶段（bell attempt、runtime_status、start_run）、路由收件箱、`runSystemReviewLimits`、host-ops 巡检等其它 `uow.run` 仍走悲观锁。这些位置读写 notifications、bell_attempts、tokens 等不在命令状态版本里的表，需要另行扩展读集，留作后续。
- 验收里的“后台写锁占用 < 5%”和“单个写事务 p99 < 100 ms”要在生产剖析里复测：tick profiler 的 `run` 时长，以及 CPU 剖析中 `#writeAndCommit` 的包含时间。本地只证明了计算阶段不持锁、无效果时不拿锁、冲突有上限。
