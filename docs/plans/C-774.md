# C-774 读池 lane 撞车、冷启动超时与详情读计时

作者：关羽。基线 `ee0f3d15186e67643503723e20af2b97653d1e07`。按 C-774#15 的最新验收标准：lane 不撞车、单次详情读热点、冷启动不集中超时、三段计时。前端退避在 C-775，本卡不改前端。

## 改动

0. **详情读主因：建议进展 SQL 的连接顺序**（`apps/server/src/web/sql-state.ts` 的 `withSuggestionProgress`，C-774#25 张良调研 P1）。带“建议拍板”基线（`evidence_baseline`）的卡，详情读要按基线取后续事件和对应时间线。库里没有 ANALYZE 统计信息，SQLite 把 `events` / `timeline` 放在外层、`json_each` 放在内层，每一行项目事件或时间线都把 json 数组扫一遍，耗时约为“进展条目数 × 项目时间线行数”（生产快照 0.2–16 s）。两条语句都改成 `CROSS JOIN`，固定 `json_each` 在外层，每个 json 条目走一次索引查找（`timeline_by_card_seq`、`check_recovery_history`）。结果行顺序变化不影响下游（`read.ts` 自行按 `event_seq` 排序，进展按唯一键查找）。这一步计入 `suggestion_sql` 分段。已结案拍板是否继续参与进展计算按 PM 在 C-774#30 的决定保持不变。
   - C-688 的查询计划守卫（`card-detail-load.test.ts`）补了两个漏洞：EXPLAIN 显示别名（`SEARCH t USING INDEX ... (project_id=?)`），守卫现在把语句里文档表的别名也算作表名；夹具补一条带基线的已结案拍板，并断言两条进展语句确实执行过。用旧写法跑守卫会报 48 条整表扫描。
1. **读池按首次出现固定分配 worker**（`apps/server/src/web/read-pool.ts`）。原来 `sha256(project) % workers` 固定分配，workers=2 时 cardigan 与 sensen-godot 恰好同 lane。现在：
   - 读池第一次见到一个项目（启动时的预热清单，或它的第一次读）时，把它放到已分配项目最少的 worker；平手取原哈希 lane，再取最小编号。
   - 之后这个项目在读池存续期间不再换 worker：同一项目的读始终在同一个 worker、按序执行、共用一份缓存和同一个每连接版本 epoch（`cards-cache.ts`），不会因换 worker 让版本号来回变，也不会在新 worker 上重新冷构建（C-774#25 的建议；第一版“闲置 10 分钟后可迁移”已撤掉）。
   - 项目数不超过 worker 数时每个项目独占一个 worker；超过时按首次出现顺序轮流分摊。worker 数默认仍为 2，主机设的 `CARDIGAN_WORKBENCH_READ_WORKERS` 照旧生效（解析未改）。`stats().projects` 列出每个 worker 上的项目，`laneOf()` 给出项目的 worker（未见过的项目只预测，不占位）。
2. **冷启动预热**（`read-pool.ts`、`read-worker.ts`、`web/server.ts`）。
   - Web 服务监听成功后把全部项目按卡片数从多到少交给读池（`warm()`；监听失败时关闭读池，不留读 worker 阻止进程退出）；读池先按上面的规则把它们分到各 worker（最忙的两个项目落在不同 worker），并立即启动这些 worker。
   - 每个新启动或崩溃/卡死后重启的 worker，都会收到分到本 worker 的项目的预热清单：按每片 5000 条解码项目事件历史，解完再建一次命令状态。每片之间让出事件循环，**有读请求时先处理读**，读完再继续下一片；预热失败只放弃预热，由第一次读自己建。
   - 预热只填缓存，不产生任何响应；读请求始终在自己的读事务里读数据库（包括预热之后、之间的写入），不会拿到预热时的旧版本。
3. **已完成卡详情不再触发整段事件历史冷加载**（`packages/store/src/command-events.ts`）。已完成或待合并卡的详情要读项目的合并批次事件；原来走内存事件日志的类型索引，读 worker 里该项目的历史还没解码时，这一步会先解码项目全部事件（sensen 规模约 5.5 万条）。现在历史尚未解码时改用 `events_by_type` 索引直接读这几行（与 C-652 之前的 SQL 相同，C-652 的等价测试仍覆盖），已解码时照旧用内存索引。
4. **计时字段**（`packages/mcp-server/src/read-timing.ts`、`commands/execute.ts`、`apps/server/src/web/read-ops.ts`、`timeline-state.ts`、`card-detail-cache.ts`、`read-pool.ts`）。每个 Workbench 读的 `web_http` 日志 `phases_ms` 新增：
   - `read_queue`：在读池排队的时间（原有）；**超时的读现在也记**：未开始的记整段等待，已开始的另记 `read_running`。原来 79% 超时请求在日志里没有任何分段。
   - `read_state`：本次读里 `loadCommandState` 的总耗时（只计最外层调用，含缓存命中检查和事件历史解码）；`read_state_rebuild`：其中因版本变化重建缓存状态的部分。用 AsyncLocalStorage 计量，内联读并发时互不串扰。
   - `read_query`：除状态以外的时间（SQL、组装、序列化）；`read_state + read_query` 等于读的总运行时间，`read_worker` 仍是 worker 内整体耗时。
   - 详情读原来没计时的步骤补齐：`timeline_sql`、`references_sql`、`suggestion_sql`、`events_sql`，以及缓存层的 `detail_version`、`detail_serialize`、`detail_gzip`。

## 测量

数据：`pnpm fixture:generate --profile diagnostics`（338 卡、55015 事件、18075 时间线、5556 Run、920 附件、590 拍板，即 sensen-godot 约 5.7 万事件的规模），开启合并队列；本机合成数据，Node v24.22.2，未读生产库，未人为制造负载，读取串行。机器同时跑着其他 Agent，同一条件前后背靠背跑，绝对值有波动。

### 冷启动（读池刚启动时一批读同时到达）

读池 2 个 worker，进程启动后同时发出已完成卡详情、进行中卡详情、Needs You、Needs You 版本、卡片列表 5 个读，记每个读的完成时间（含 worker 启动约 0.5 秒）：

| 情形 | 详情（已完成） | 详情（进行中） | Needs You | 版本 | 卡片列表 |
|---|---:|---:|---:|---:|---:|
| 不预热，启动即读 | 556 | 585 | 1018 | 1020 | 1089 |
| 不预热，启动 2 秒后读 | 526 | 556 | 953 | 954 | 1006 |
| 预热，启动即读 | 601 | 644 | 1162 | 1164 | 1225 |
| 预热，启动 2 秒后读 | 33 | 39 | 89 | 90 | 158 |

单位 ms。重启后浏览器通常要几秒才重连，预热在这段时间里把冷构建做完；启动即到的读与不预热相当（读在预热片之间先行）。

### 定位到但未改的热点

- 进行中卡详情的冷读约 100ms 花在 Store 快照集合首读（拍板、人工待办、Assignment、附件整表解码一次）。
- 写入后重建命令状态（待合并卡详情、Needs You）主要花在快照集合增量刷新：按 SQLite 原迭代顺序整表重扫 + 整表 Map 复制，与表行数成正比（`cards` 档位剖析中占待合并卡约 49%、Needs You 版本约 70%）。它要保持各表所用索引的迭代顺序（如 assignments 走 `assignments_by_activity`，更新会改变顺序），改成增量排序影响所有项目的状态一致性，需生产分段数据确认后再单独处理。
- 冷加载事件历史时 `NOT INDEXED` 按 rowid 扫全表（含其他项目的行）；合成双项目库上多约 150ms，未改。

## 测试

- `card-detail-load.test.ts`：C-688 守卫认别名、夹具带建议基线；旧写法下守卫失败（48 条 `SEARCH t USING INDEX timeline_by_card_seq (project_id=?)`），新写法通过。
- `dual-startup.test.ts`：预热改到 Web 监听成功之后、监听失败时关闭读池，Web 端口被占时 Web 角色照常退出（第一版提交在预检里因读 worker 不退出而失败）。

- `read-pool.test.ts`（慢读桩）：workers=2 时 cardigan 与 sensen-godot（原哈希同 lane）落在不同 worker，一个项目的慢读不挡另一个；三个项目交错读 6 轮，每个项目的读始终同一 worker 且按序；第三个项目分到项目更少的 worker，项目的 worker 忙时它的后续读仍在原 worker 排队、不迁移；超时读记录排队与运行时间；预热项目分到不同 worker、worker 立即启动并收到各自的预热清单，按读启动的 worker 预热发起读的项目。
- `read-pool.test.ts`（真实 worker）：两项目交错轮询时项目版本（含每个 worker 自己的 epoch）在无写入时不变、写入后变一次再稳定；详情日志含全部新字段，`read_state + read_query ≤ read_worker`；Needs You 首次读有重建、无写入重复读重建为 0；读池刚启动、预热进行中同时到达的详情、Needs You、卡片列表读与内联读结果一致，启动前的写入可见，之后的写入在下一次读可见。
- `command-events.test.ts`：历史未解码时 `projectMergeEvents` 与 SQL 读一致且不解码历史，之后提交的行可见，解码后内存索引结果相同。
