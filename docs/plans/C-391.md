# C-391 多卡批次合并实施记录

依据：P2a-13 第 3 节、ADR 0004，以及本卡第 7 条时间线记录的提前启动授权。固定流程版本为 5，不改变现行 Flow Lite 的授权与审核边界。

## 实现边界

- 队列默认关闭；开启后，当前完成申请的卡级通过记录只用于确认，批次最终树的全量通过记录才可授权发布。
- 批次及探测从项目事件重建，不另存第二份队列；成员保留原确认时间与优先级。每卡一个合并提交，整批一次比较更新。
- 发布前持久化发布意图，发布成功后在一个事务内写全部卡片的合并事件。重启先恢复发布，再判断基线过期和无需合并。
- 失败按前缀定位，至少两次失败证据；通过前缀直接发布，后续成员回队。中断、执行器不可达不作为代码失败。
- 复用现有执行器容量、GitHub 运行身份校验、重启续接、日志脱敏和检查目录清理；部署审计按批次最终提交验证整段证据。
- 合并窗口默认累计两次冲突打开，24 小时到期；按文件路径相交判断，重交更新范围和期限，相交窗口按开启顺序生效。这些值作为可信主机配置，不改变 Agent 权限。
- 批次上限默认 4，允许 1–8。敏感卡保留现行人工／类别授权边界；是否默认单独成批须在实际启用队列前确认。

## 验证范围

本地只跑相关单测和契约测试、domain 测试类型检查、lint 与依赖检查；全量及端到端测试由同提交的远程预检执行。真实 GitHub 冒烟由受限主机探针执行，并核对测试提交和清理结果，不把基线探针当作实现验收。

## 本轮审核修复

- 批次诊断统一按读取时的全部成员权限过滤，覆盖卡片检查副本、项目快照、增量事件、时间线和日志入口；受限检查仍保留失败状态，避免回退显示旧通过记录。
- 流程版本至少为 2 的失败定位复用系统退回迁移；健康前缀单独重核后继续发布。旧流程仍由原确认和重查路径处理。
- 合并窗口使用交付与当前基线的共同祖先计算作者改动，排除基线独有文件；范围不明时拒绝推断。
- 分页看板和详情读取共用完整队列状态，补齐阶段与单独批次字段。批次竖条移到右侧以保留左侧等待／阻塞含义；修复点击遮挡、44px 命中区、失败原因和已发布前缀标识及设置错误提示。
- 计划第 3.9 节和 ADR 0004 明确要求的检查范围说明及确认按钮文案保留；没有将它们当作未授权说明文字删除。
- 浏览器验证使用固定 5 卡的 App 合成夹具，覆盖 1440／390、亮／暗、鼠标点击、抽屉焦点与成员导航；另以 HTTP 测试验证真实分页接口，不把模拟界面视作生产队列演练。
