# C-672：mac-mini 上 Agent 已退出、终端仍在，新通知不自动续起

## 原因核查

1. **“外层 Python 受管入口进程”是什么**：mac-mini 上新起的会话由 C-602 的空闲回收 owner 包一层启动（`enrollDarwinOwner`）。终端的主程序是 `/usr/bin/python3 -IB -c <darwin-idle-owner.py>`，Agent CLI（交互模式的 claude，没有 `-p`）是它的直接子进程，启动登记（`launch_publication.process`）记的是 CLI 的 PID 和出生身份。所以“终端 live、Python 在、claude 不在”就是 owner 还在、CLI 已退出。
2. **CLI 为什么退出**：Run 正常结束（Agent 自己 `finish_run`）后，系统只有三条路径会结束作者 CLI：
   - 空闲回收：最近活动超过 60 分钟（`CARDIGAN_IDLE_SESSION_MINUTES`）才成为候选；
   - C-626 系统代结束轮次：只针对系统结束的 `blocked` 轮次（`finished_by=system`）；
   - 主机运维显式换会话。

   R-1641 开跑几十秒、02:48:51Z CLI 退出，不在任何回收窗口内；如果 R-1641 是 Agent 自己结束的，这次退出就不是设计上的空闲回收，而是 CLI 自己退出（异常退出）。退出码或信号在现有登记里没有记录，系统侧分不出是崩溃、被会话内命令结束，还是收到外部信号。如果 R-1641 是系统代结束的阻塞轮次，那就是 C-626 设计上的一次 TERM。两种情况后续表现一样，本卡的修复不依赖是哪一种。
3. **为什么系统把它当成活会话**：Linux 上用 hc 0.1.21 实测，owner 在子进程退出后 0.5 秒内退出，终端随即变成 `finished`，即使孙进程还占着终端也一样（`supervise` 每 0.5 秒 `poll` 一次）。所以卡上的状态说明 mac-mini 上 owner 当时没有退出，或者 hc 没有收割它。无论哪种，原有判定都没有“终端仍 live、登记的 CLI 已不在”这个结论：
   - worker 探针 `darwin_retirement` 只在终端 `finished` 且 CLI 已退出时给出 `exited`，其余情况一律 `unknown`；C-667 的 `shell` 只认 `--keep` 终端。
   - 运行时 `status` 只看终端，报 `alive`：派发器把门铃打进这个终端，或者在 `wake_guard` 上一直等待。
   - 空闲回收和派发都用 `unknown` 保留会话：等待中的回收报 `recent_activity`；连续失败后 handoff，报 `retained_for_dispatch`，派发器把它当作忙碌；发过 TERM 但没确认退出的报 `observation_incomplete`，`stopping` 状态只读观察，永远等不到。
   - 主机运维的证据里，远端会话只认“终端已不在”的退出证明，所以 `can_restart=false`；只要有 `idle_retirement`，`restart_blocked` 就是 `session_maintenance`。

## 改动

1. **worker 探针**（`deploy/inspect-worker.py`）：新增一个需要显式请求（`agent_exit: true`）的结论 `agent_exited`，条件全部满足才给出：终端是本代次、带登记标签的那个，`live`、不是 `--keep`、名字一致、不是 `rm` 终端、有正的主进程 PID，而且登记 CLI 的出生身份（boot 加 start）已不在（PID 不存在或已被复用）。身份读不到、权限不足、僵尸进程都不算。不请求的调用方（owner 自己的停止判定、回收、唤醒）结论不变。探针由控制主机每次内联下发，不涉及 worker helper 升级。
2. **运行时端口**：`observe_kept_shell` 改名为 `observe_agent_exit`，语义扩大为“这个终端仍 live，但已经不在运行登记的 CLI”，包括 C-667 的保留 shell 和本卡的 owner 终端。只有 macOS worker 实现，其它运行时返回 false。
3. **自动续起**（`packages/host` 维护，每 60 秒一次）：`releaseExitedAgents` 取代 `releaseKeptShells`：
   - 候选：macOS worker 上有待投递通知、排队 Run、待完成回收或角色落后的指派；
   - 排除：人工停止、主机运维操作、角色升级、在跑、在停、在启动、在投递的 Run；
   - 等待中、已 handoff、TERM 后未确认退出（`stopping`）的回收都不再挡；
   - 不看 `recent_activity` 窗口。

   流程：终端 `alive` 时持有两把主机运维锁，再核对一次指派，然后请求 `observe_agent_exit`。为真则 `release(force)` 关闭终端，由领域命令 `confirmKeptShellExit` 清空终端引用、结束回收，发 `session_replaced(reason=agent_exited)`，作废旧 Token；排队 Run 保留。下一轮派发按受管入口起新会话；角色落后的先升级。从通知到达到新 Run 派发最多约 60 秒加一次派发间隔，测试按 2 分钟上限断言。
4. **派发不再打进去**（`apps/server`）：macOS worker 上非续轮的唤醒，先问 `observe_agent_exit`；为真时门铃保持待投递（`dispatch_skipped reason=agent_exited`），等维护关闭终端。
5. **领域命令**：`confirmKeptShellExit` 放开 `stopping` 阶段。这时内核已证实 CLI 退出，两把锁保证没有并发的回收在执行。
6. **主机运维**：
   - 证据：`stallEvidence` 对远端工作项会话新增 `agent_exited`，诊断里 `process_state` 显示 `agent_exited`，`can_restart=true`；
   - 积压行：被会话维护挡住（`session_maintenance`）的行，在 Agent 已退出时不再报阻塞；
   - 重启：`host_ops_restart_assignment` 先走与维护相同的守卫路径关闭终端、结算会话，返回 `result=agent_exited`，之后派发自动起新会话，不发任何信号；
   - 巡检：同一情况也走这条路径。
7. **诊断**：会话维护原因新增 `agent_exited`（“Agent 已退出，终端仍在”）。这个原因优先于 `recent_activity`、`retained_for_dispatch`、`retirement_pending`、`observation_incomplete` 这类窗口或围栏原因，不再显示成活会话；系统会自己续起，所以不产生 PM 关注。

## 不变量

- 只有 worker 用内核证实登记 CLI 的出生身份已不在、终端仍是本代次时，才关闭终端，不会出现两个执行者。CLI 仍在、身份读不到、worker 不可达时，一律保留会话，按原路径处理。
- 人工停止（含 `--hold`）、在跑的 Run、Run 的停止或启动、主机运维操作、角色升级都不续起，也不关闭终端。
- 工作区、分支、排队 Run 保留；领域命令只接受 system，只结算同一条终端引用。

## 已知未覆盖

- CLI 的退出码或信号没有记录，以后的事故仍分不清是崩溃还是被结束；需要的话另开卡，让 owner 记录子进程的退出状态。
- 本地和 Linux worker 的同类情况不在本卡范围（这些机器上没有 owner，CLI 退出后终端直接结束，走原有路径）。
