# C-598：移动签名大包在慢链路上的受理、时限与取回

## 背景

sensen C-14 第二次送签：334 MB 的 APK 从控制主机传到 mac-mini 签名端用了 9 分 13 秒，链路实测约 0.6 MB/s。服务端签名助手的 `timeout: 600_000` 加 SIGKILL 在第 600 秒把它强杀，账本里既没有 `signed`，也没有 `not_released`。签名端回执是 `signed`，但产出没有回到控制主机。

## 改动

1. **时限按输入大小计算**（`deploy/mobile-signing/host.py`）：`budget = base_seconds + ceil(2 × 输入字节 ÷ bytes_per_second)`。输入和回传两个方向都按同一保守速率估算，默认 600 秒加 512 KiB/s。334 MB 约为 600 + 1275 秒，比实测所需约 10 分钟多出近两倍余量。状态已是 `signed` 时只在本地复核，按 0 字节计算。控制账号私有的 `$CONTROL/limits.json` 可覆盖任意一项，有上下界；格式错误、权限不对或是符号链接时不签。主机用 `SIGALRM` 执行自己的时限，到期在账本记 `timed_out`；收到 SIGTERM、SIGHUP 或 SIGINT 时记 `interrupted`；其它失败仍记 `not_released`。记事件前先回滚未完成的写事务，确保事件能落盘。
2. **主机先报“已受理”**：`request` 在持久认领之后、联系签名端之前，向控制服务输出 `accepted <请求号> <时限秒> <sign|lookup|stored>`，然后再走原有的 `ready`／`commit` 栅栏。主机与签名端（`worker.py`）之间的消息不变，签名端不需要换版。
3. **控制服务受理即返回**（`apps/server/src/mobile-signing.ts`）：每个 Run 加平台对应一个内存中的在途任务。首次调用最多等 2 秒：期间完成就直接返回回执，否则返回 `status: pending`，附带请求号、阶段（`queued`／`transferring`／`signing`）、方式、时限、已用时间和 `poll_after_seconds: 30`。同一 Run 再次调用时，若任务在途，只返回进度；若已结束，返回 `status: signed` 回执或报“签名未放行”，并清除这条记录。之后再调用，会新起一个助手，只按账本现有语义处理：`pending` 或 `peer_signed` 时向签名端 lookup，`signed` 时本地复核。这条路径不会重新传输，也不会重新签名。服务端重启后内存记录丢失，也走这条路径。没收到 `accepted` 前的后备时限是 120 秒；收到后为主机报告的时限加 60 秒，先发 SIGTERM，30 秒后才强杀，主机因此能把终态记进账本。栅栏处仍调用 `current()`；Run 已不在场时关闭输入并终止助手，不发 `commit`。
4. **工具说明**：`request_mobile_signature` 的描述改为“受理后在本 Run 内轮询，不重送”。

## 授权边界（不变）

只收平台参数。Run、Assignment、机器和 UID 绑定，单次批准、撤销和有效期均不变。任务键包含完整的签名范围；每次调用仍由 MCP 层核验当前 Run，派发前由主机再核一次。不同 Run 共用不到同一个任务。

## release_ops 调用约 15 秒以退出码 125 结束的来源

- 本系统里只有 `$CARDIGAN_RUN_COMMAND` 的私用进程包装（`deploy/run-resources.py`）会产生退出码 125。原生 MCP 工具调用没有退出码，所以当时 release_ops 是用 shell 里的 HTTP 客户端（例如 `curl`）调用 MCP 端点，并且套了 `R-n --private --` 包装。
- 包装器启动时确认 Run 处于 `active`，之后由 `Confirmation`（`interval=15`）每 15 秒向 `/mcp?run_resource=` 重查一次。第一次重查正好在第 15 秒，这与“约 15 秒”吻合。重查结果为 `ended`（键里的 R 编号对应的 Run 已不在运行中），或监督子进程在这次刷新时异常退出、状态管道没有返回字节，包装器都会返回 125。前一种情况下 HTTP 客户端会被留在后台继续等待，所以调用方拿不到回执，但服务端照常继续。这与 18:09:45 仍然正常派发的记录一致。
- 服务端不是原因：MCP 传输是无状态的，每个请求独立处理，没有按会话串行的锁；签名助手是异步 `spawn`，不会阻塞状态查询。
- 另外，Codex 原生 MCP 调用默认的工具超时约 60 秒，原来同步阻塞 10 分钟以上的调用即使不包装也拿不到结果。
- 调整：工具改为 2 秒内受理返回，因此不再依赖客户端的长超时，也不需要给 Codex 增加 `tool_timeout_sec`。文档（README 第 3 步与工具说明）写明：直接作为 Card MCP 工具调用，不要经 shell、`curl` 或私用进程包装；受理后在本 Run 内轮询。要确认当时走的是哪条路径，可在 sensen 工作机的 syslog 查 18:00:47 前后的 `cardigan run_resource <键> ...` 记录：有 `private_release_unconfirmed_retained` 或 `missing_private_participant_retained` 是前一种，什么都没有是后一种。

## release_ops 角色说明（建议文本，需在 sensen 项目的角色版本中更新）

> 移动签名：直接调用 Card MCP 工具 `request_mobile_signature`（只传 `platform`），不要经 shell、curl 或 `$CARDIGAN_RUN_COMMAND` 包装。首次调用返回 `status: pending` 和请求号即表示已受理；保持本 Run，按 `poll_after_seconds`（约 30 秒）用同一平台再次调用查看进度，直到 `status: signed` 后按回执的 `download.query` 下载并复算 SHA-256。不要重送、不要新开请求；返回“签名未放行”时停止并报告请求号。

## 测试

- `apps/server/test-support/mobile-signing-test.py`：时限计算、`limits.json` 覆盖与越界拒绝；主机自定时限到期记 `timed_out` 并解除计时器；签名端已签而主机被 SIGTERM 中断后记 `interrupted`，`reconcile` 得到 `peer_signed`，同一 Run 再请求按 lookup 取回字节，再请求走本地 `stored`；真实 `host.py request` 输出 `accepted … stored`／`ready`／结果；在途进程被终止时记 `interrupted`。
- `apps/server/src/mobile-signing.test.ts`：用替身主机程序验证：首次调用立即得到 `pending` 和请求号，轮询依次看到 `transferring`、`signing`，最终得到回执，全程只起一个助手；任务结束后再调用只新起一次 lookup；超过主机报告的时限后先 SIGTERM，然后轮询失败；Run 在栅栏处不在场时不发 `commit`。
