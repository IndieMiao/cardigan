# C-594 worker 自动升级接入文档补齐

来源：C-548#147（H-183 回执：原步骤②的 `tar` 需加 `--no-same-owner`，否则报 `unsafe bootstrap permissions`）、C-548#146（H-184 缺少与 C-551 最终交付对应的双项目管理员步骤和失败处置）。本卡只改文档，不改运行代码、账号、凭据、机器或权限，也不执行 H-183、H-184。

## 1. Linux 解包步骤核对结论

- 当前主线已修正，不重复改：`docs/linux-worker.md` 第 2 步解包命令为 `sudo tar --no-same-owner -xf "$KIT/release.tar" -C "$KIT"`。该写法由 fa4ce7ec 引入，随 C-548 合并 57bd9c5b 上线，C-551（aa28e6c1）之后未变；`docs/macos-worker.md` 同步使用该写法。
- 出问题的是 H-183 待办正文（C-548#26 步骤②的 `sudo tar -xzf`），不是仓库文档。该包由 server 账号在发行目录打成，root 解包时沿用了 server 账号的所有者。`deploy/enroll-helper-worker.sh` 的 `guard` 要求每个引导文件及其祖先目录 `st_uid == 0`，并且不可被组或其它账号写入，所以在授权前退出。
- 核对中另发现同类缺口：文档只写了“打包”，没写怎么打包。`git archive` 默认 `tar.umask=0002`，成员组可写；root 解包时 tar 会沿用权限位，即使加了 `--no-same-owner` 也会报同一个错误。现已在两份平台文档的解包命令后补一段原因说明和打包要求，解包命令本身未改。
- 隔离夹具验证结果见第 4 节。

## 2. 同机两个项目的 Mac 接入与撤权草稿（供 PM 更新 H-184）

> 送审稿，不是执行授权。C-548#27 原步骤作废：它只覆盖单个项目，且解包会继承归档所有者。仓库稿只写参数名，不写现场取值；实际取值由 PM 在原待办里核齐并填写，不另开待办。H-183 不重做。

### 参数（由 PM 在原待办中填写）

| 参数 | 含义 |
|---|---|
| `MACHINE` | 目标 Mac 在控制端登记的机器编号；两个项目共用同一编号 |
| `PROJECT_OLD` | 使用旧路径 `/Library/Cardigan/worker.json` 的项目 |
| `PROJECT_NEW` | 使用命名配置 `/Library/Cardigan/worker-$PROJECT_NEW.json` 的项目 |
| `AUTO_OLD`、`AUTO_NEW` | 各绑定是否选择自动升级（`yes`/`no`）。只影响从未接入的绑定，已接入的绑定原样保留 |
| `TEMP_RULE` | 待撤的临时 sudoers 文件，绝对路径，必须直接位于 `/private/etc/sudoers.d/` 下 |
| `TEMP_USER` | `TEMP_RULE` 授权的账号，仅用于撤权前后对比 |

参数缺失或与现场不符就**停止**，不要自行猜测。待撤目标只认原待办写明的 `TEMP_RULE`，不在现场另找其它规则。

### 终端与登录方式

| 终端 | 机器 | 登录身份 | 用途 |
|---|---|---|---|
| S | 控制主机 | server 服务账号，已载入其私有环境（`CARDIGAN_DATA_DIR`、`CARDIGAN_CONFIG_DIR`） | 只读核对、打包、prepare/activate、正式检查 |
| A | 目标 Mac | 永久管理员本人账号，`sudo -i` 后保持到结束 | 只用于撤权子进程和恢复，不依赖再次 sudo |
| B | 目标 Mac | 同一永久管理员本人账号（本地或其既有 SSH） | 只读核对、解包、接入、撤权后复核 |

不使用 `TEMP_USER`、worker 账号、升级账号或 Agent 的身份。不在卡片上粘贴包、私钥、公钥正文、配置正文或 sudoers 正文。

每个终端先设置参数，S 和 B 另外计算命名绑定的 tag：

```sh
MACHINE=…; PROJECT_OLD=…; PROJECT_NEW=…; AUTO_OLD=…; AUTO_NEW=…; TEMP_RULE=…; TEMP_USER=…
tag=$(/usr/bin/python3 -IB -c 'import hashlib,sys; print(hashlib.sha256(sys.argv[1].encode()).hexdigest()[:20])' "$PROJECT_NEW")
```

### 绑定与升级身份的对应关系

| 绑定 | 控制端激活身份（`CARDIGAN_CONFIG_DIR` 下） | Mac 端升级账号 / 入口目录 / sudoers / HOME |
|---|---|---|
| 旧路径 `PROJECT_OLD` | `upgrade-<机器编号长度>-$MACHINE-$PROJECT_OLD.key` | `cardigan_updater`、`/opt/cardigan-helper-upgrade`、`/private/etc/sudoers.d/cardigan-helper-upgrade`、`/Users/cardigan_updater` |
| 命名 `PROJECT_NEW` | `upgrade-<机器编号长度>-$MACHINE-$PROJECT_NEW.key.bound` | `cgu_$tag`、`/opt/cardigan-helper-upgrade-$tag`、`/private/etc/sudoers.d/cardigan-helper-upgrade-$tag`、`/Users/cgu_$tag` |

两个绑定各用各的接入材料，不要把一个项目的 prepare 输出粘到另一个项目的接入命令里。worker 配置和账号原样复用，不重建、不覆盖，也不把两份配置合并。

### 第 0 步：控制端只读核对（S）

维护窗口内，先确认两个项目在该机器上都没有活跃 Run，也没有其他人或配置工具在改账号或 sudo 策略。按 H-183 的做法备份控制主机私有配置（不上传）。不改调度开关，不停旧会话。

下面两条命令只读取已记录的结果，不探测，不改变检查状态：

```sh
for P in "$PROJECT_OLD" "$PROJECT_NEW"; do
  cardigan worker status --project "$P" --machine "$MACHINE"
  cardigan machine show "$MACHINE" --project "$P"
done
```

某个项目报“本项目未登记该机器”或“没有接入记录”就**停止**，不新登记。这里不运行 `worker check` 或 `machine check`：这两条是正式检查，会建立新记录，满足条件时还会解除升级停派，所以只在第 7 步运行。

判定两个绑定在控制端的接入状态。是否存在只按一次成功的目录列表判断；列不出目录就报 `unknown`，不当作“没有”。另一种绑定方式下只要有任何材料（包括 prepare 最先写入的 `.signer.pem`），也报 `conflict`：

```sh
c_state() {
  names=$(ls -A "${CARDIGAN_CONFIG_DIR:-$HOME/.config/cardigan}") || { echo unknown; return; }
  k=upgrade-${#MACHINE}-$MACHINE-$1.key
  if [ "$2" = named ]; then act=$k.bound alt=$k; else act=$k alt=$k.bound; fi
  has() { printf '%s\n' "$names" | grep -qxF "$1"; }
  for s in '' .pending .pending.pub .signer.pem; do if has "$alt$s"; then echo conflict; return; fi; done
  if has "$act"; then if has "$act.pending"; then echo conflict; else echo active; fi
  elif has "$act.pending" || has "$act.pending.pub" || has "$act.signer.pem"; then echo pending
  else echo none; fi
}
echo "OLD $(c_state "$PROJECT_OLD" legacy)"; echo "NEW $(c_state "$PROJECT_NEW" named)"
```

可能的结果：`none`、`pending`、`active`、`conflict`、`unknown`。

### 第 1 步：Mac 建立两条管理通道

1. 在 B 运行 `id -un; sudo -k && sudo /usr/bin/id -u`：用户必须是预期的永久管理员（不是 `TEMP_USER`），输出 `0`，并且管理员确认这份授权不来自 `TEMP_RULE`。
2. 在 A 运行 `sudo -i`，再用 `/usr/bin/id -u` 确认输出 `0`。A 保持开启到全部结束。

两条通道有一条不成立就**停止**。

### 第 2 步：Mac 只读核对并判定每个绑定的分支（B）

```sh
sudo ls -lde /opt /Library/Cardigan /private/etc/sudoers.d
sudo ls -le /Library/Cardigan
sudo /usr/bin/python3 -IB -c 'import json,sys; [print(p, json.load(open(p)).get("project"), json.load(open(p)).get("account")) for p in sys.argv[1:]]' \
  /Library/Cardigan/worker.json "/Library/Cardigan/worker-$PROJECT_NEW.json"
probe() {
  out=$(sudo /usr/bin/env LC_ALL=C /bin/ls -lde "$1" 2>&1); rc=$?
  if [ "$rc" = 0 ]; then echo present
  elif [ "$(printf '%s\n' "$out" | wc -l)" -eq 1 ] && printf '%s\n' "$out" | grep -q 'No such file or directory$'; then echo absent
  else echo unknown; fi
}
uprobe() {
  out=$(LC_ALL=C id "$1" 2>&1); rc=$?
  if [ "$rc" = 0 ]; then echo present
  elif [ "$rc" = 1 ] && printf '%s\n' "$out" | grep -qi 'no such user'; then echo absent
  else echo unknown; fi
}
w_state() {
  r="$(uprobe "$1") $(probe "$2") $(probe "$3") $(probe "$4")"
  case " $r " in
    *" unknown "*) echo unknown;;
    " present present present present ") echo present;;
    " absent absent absent absent ") echo absent;;
    *) echo partial;;
  esac
}
echo "OLD $(w_state cardigan_updater /opt/cardigan-helper-upgrade /private/etc/sudoers.d/cardigan-helper-upgrade /Users/cardigan_updater)"
echo "NEW $(w_state "cgu_$tag" "/opt/cardigan-helper-upgrade-$tag" "/private/etc/sudoers.d/cardigan-helper-upgrade-$tag" "/Users/cgu_$tag")"
ls -l /usr/bin/python3 /usr/bin/openssl
```

预期：

- 三个目录都归 root，组和其它账号不可写，权限列没有 `+`。
- `/Library/Cardigan` 下与 worker 相关的只有 `worker.json` 和 `worker-$PROJECT_NEW.json`，两者均为 `-rw------- root`，没有 `worker-$PROJECT_OLD.json`。
- 第三条依次输出 `… $PROJECT_OLD <账号>` 和 `… $PROJECT_NEW <账号>`，两个账号不同。

以上任一项不符即**停止**，不覆盖、不修补、不删除。

`w_state` 只把明确报“No such file or directory”的路径、明确报“no such user”的账号算作不存在。sudo 失败、权限不足或其它报错都算 `unknown`。可能的结果：`absent`、`present`、`partial`、`unknown`。

把第 0 步的控制端状态（`c_state`）与这里的 Mac 端状态（`w_state`）合起来，**每个绑定单独**按下表判定：

| 控制端 | Mac 端 | 选择自动升级 | 分支 | 后续 |
|---|---|---|---|---|
| `none` | `absent` | `yes` | 首次接入 | 第 6 步做接入 |
| `pending` | `absent` | `yes` | 首次接入（上次 prepare 中断过） | 第 6 步做接入；prepare 会复用已有材料，不删除 |
| `none` | `absent` | `no` | 未选择 | 跳过第 6 步；该绑定继续收到人工升级命令 |
| `active` | `present` | 任意 | 已接入 | 第 6 步只做复用核对，不重新接入 |
| 其它任何组合，包括任一端为 `unknown` 或 `conflict`、Mac 端为 `partial`、`pending` 但未选择、只有一端存在 | | | 不一致或未查明 | **停止**该绑定，不接入，交管理员核对；整单不撤权 |

只有上表前四行列出的组合可以继续。

不能凭控制端存在某个文件就认定已接入：已接入的绑定必须在第 6 步通过两端复用核对。

### 第 3 步：控制主机打包（S）

整段一次粘贴运行。部署记录、发行目录、五份摘要、打包，任一环节失败，整段都返回非零并打印 `STOP`。只有打印了 `KIT-READY` 才算成功。不需要也不要在交互终端设置 `set -e`。

```sh
umask 077; R= SHA= OUT= S=
: "${CARDIGAN_DATA_DIR:?请先载入 server 的数据目录环境}" &&
S=$(python3 -IB -c 'import json,os,re; s=json.load(open(os.path.join(os.environ["CARDIGAN_DATA_DIR"],"self-deploy/state.json"))); c,r=s["current"],s["running"]; assert c["release"]==r["release"] and c["sha"]==r["sha"] and re.fullmatch("[0-9a-f]{40}",c["sha"]); print(c["release"]); print(c["sha"])') &&
R=$(printf '%s\n' "$S" | sed -n 1p) && SHA=$(printf '%s\n' "$S" | sed -n 2p) &&
cd "$R" &&
sha256sum -c --strict - <<'EOF' &&
2eaba49cf0f4a1c04bc8bf514edb5785f9b36376d3b92ea087ac5ea485fc021e  deploy/enroll-helper-worker.sh
```

打包要显式包含 `deploy` 目录条目并去掉组和其它账号的写权限，原因见 `docs/linux-worker.md` 第 2 步。管理员用获准的通道把 `enroll.tar` 交到 Mac。整包摘要由管理员本人从 S 终端读取，作为 `EXPECTED`；不信随包送来的摘要，也不经卡片传递。S 保持在 `$R` 目录，后续步骤要用。

### 第 4 步：Mac 解包（B）

`BUNDLE` 设为收到的包，`EXPECTED` 设为第 3 步的整包摘要。目录列表和摘要核对都在 root 的 shell 里执行，这样 0700 的 `KIT` 才能展开：

```sh
KIT=$(sudo mktemp -d /opt/cardigan-enroll.XXXXXXXX) &&
  sudo install -m 0400 "$BUNDLE" "$KIT/release.tar" &&
  got=$(sudo shasum -a 256 "$KIT/release.tar") && [ "${got%% *}" = "$EXPECTED" ] &&
  sudo tar --no-same-owner -xf "$KIT/release.tar" -C "$KIT" &&
  sudo /bin/sh -c 'cd "$1" && /bin/ls -lde . deploy deploy/* && /usr/bin/shasum -a 256 -c -' sh "$KIT" <<'EOF' &&
```

预期：`.`、`deploy` 和五个文件都归 root，组和其它账号不可写，没有 `+`；随后五行 `OK` 和一行 `KIT-OK`。出现 `STOP` 时不改归属或权限，不从其它目录挑脚本，回报失败位置。后续一律用同一个 `KIT`。

### 第 5 步：两个绑定的安装器只读检查（B）

```sh
sudo /usr/bin/python3 -IB "$KIT/deploy/install-macos-worker.py" --check
```

预期：退出码 0，输出两行 JSON，`"project"` 分别为 `PROJECT_OLD`、`PROJECT_NEW`，都是 `"installation": "checked"`。

处置：出现 `"installation": "failed"` 或 `worker_preflight_failed` 即**停止**并回报对应项目，不运行 `--apply`，也不接入。本检查会比对 libexec 里的 `worker-primitives.py`，以及账号、目录、标记和容量；不会改动任何文件。

### 第 6 步：按分支处理每个绑定

一次只处理一个绑定，处理完再处理下一个。两个绑定的命令参数个数不同，请按下表**原样**复制，不要把参数拼进一个变量里再展开：在 zsh 等不做分词的 shell 中，那样会变成一个参数，接入脚本会直接退出。

| | 旧路径绑定 `PROJECT_OLD` | 命名绑定 `PROJECT_NEW` |
|---|---|---|
| S：prepare | `sh deploy/enroll-helper-controller.sh prepare "$PROJECT_OLD" "$MACHINE"` | `sh deploy/enroll-helper-controller.sh prepare "$PROJECT_NEW" "$MACHINE" --project-config` |
| B：接入 | `sudo /bin/sh "${KIT:?}/deploy/enroll-helper-worker.sh"` | `sudo /bin/sh "${KIT:?}/deploy/enroll-helper-worker.sh" --project "$PROJECT_NEW"` |
| S：activate | `sh deploy/enroll-helper-controller.sh activate "$PROJECT_OLD" "$MACHINE"` | `sh deploy/enroll-helper-controller.sh activate "$PROJECT_NEW" "$MACHINE" --project-config` |
| S：激活身份 `A` | `A="${CARDIGAN_CONFIG_DIR:-$HOME/.config/cardigan}/upgrade-${#MACHINE}-$MACHINE-$PROJECT_OLD.key"` | `A="${CARDIGAN_CONFIG_DIR:-$HOME/.config/cardigan}/upgrade-${#MACHINE}-$MACHINE-$PROJECT_NEW.key.bound"` |
| B：`P`、`u`、`b`、`h` | `P=$PROJECT_OLD u=cardigan_updater b=/opt/cardigan-helper-upgrade h=/Users/cardigan_updater` | `P=$PROJECT_NEW u=cgu_$tag b=/opt/cardigan-helper-upgrade-$tag h=/Users/cgu_$tag` |

#### 6.1 首次接入

1. 在 S（`$R` 目录）运行该绑定的 prepare。标准错误输出两个指纹，标准输出给出 SSH 一行和 PEM 公钥。
2. 在 B 先设置该绑定的 `P`、`u`、`b`、`h`。然后运行该绑定的接入命令，粘贴**本绑定**上一步标准输出的两段公钥，按 Ctrl-D。最后检查账号和 sudo：

   ```sh
   id "$u"
   sudo -n -l -U "$u"
   ```

   预期：
   - 脚本打印的 SSH 指纹和 `openssl dgst` 摘要值，与 S 上 prepare 打印的两个指纹一致（worker 端那一行显示文件路径，控制端显示 `stdin`，只比较摘要值）。
   - 最后一行为 `项目 $P：$u 仅可执行 $b/upgrade（零参数）`。
   - `id` 只显示它自己的组，不在 admin、wheel 或任何 worker 组。
   - `sudo -l` 只列出 `$b/upgrade ""`。
   - SSH 只允许这把受限强制命令公钥，没有其它登录、转发或图形登录入口。
3. 两端都符合后，在 S 运行该绑定的 activate。

#### 6.2 已接入：复用核对（不重新接入）

这一步比对的是**实际生效**的两样东西：控制端连接时使用的激活私钥，和 Mac 上唯一生效的受限授权行。不使用 `.pending.pub`、`transport.pub` 这类登记副本。

在 S 设置该绑定的 `A`，然后运行：

```sh
pub=$(ssh-keygen -y -f "$A") && printf '%s\n' "$pub" | ssh-keygen -lf - &&
  openssl pkey -in "$A.signer.pem" -pubout | openssl dgst -sha256 || echo 'STOP: 读取激活身份失败'
```

在 B 设置该绑定的 `P`、`u`、`b`、`h`，然后运行：

```sh
[ "$(sudo grep -c . "$h/.ssh/authorized_keys")" = 1 ] &&
  [ "$(sudo grep -c "^restrict,command=\"/usr/bin/sudo -n -- $b/upgrade\" ssh-ed25519 " "$h/.ssh/authorized_keys")" = 1 ] &&
  sudo ssh-keygen -lf "$h/.ssh/authorized_keys" &&
  sudo openssl dgst -sha256 "$b/signer.pub" && sudo cat "$b/project" &&
  id "$u" && sudo -n -l -U "$u" || echo 'STOP: 授权行或入口不符'
```

预期：

- 没有打印 `STOP`。
- S 由激活私钥推出的 SSH 指纹，与 B 授权文件中唯一一行的指纹相同。
- 签名公钥的摘要值两端相同。
- `$b/project` 的内容等于 `P`。
- `id` 和 `sudo -l` 的要求同 6.1。

打印 `STOP`、指纹或摘要不一致、读取失败，都按“不一致”处理：**停止**该绑定，不重新接入，整单不撤权。

#### 6.3 未选择

不做任何操作。第 2 步已确认两端都不存在；第 8 步会再次确认该升级账号不存在。

#### 第 6 步失败时

| 情况 | 处置 |
|---|---|
| prepare 退出非 0 | 不在 B 接入。保留控制端已有的 `.pending` 和 `.signer.pem`，回报 |
| 接入脚本中途退出非 0（含 `unsafe bootstrap permissions`、`worker_binding_changed`） | 不 activate，不重跑，不删除或覆盖已建的账号、目录、规则，交管理员核对残留。整单不撤权 |
| 指纹不一致，或 `id` / `sudo -l` / SSH 不符合预期 | 不 activate，不通过改权限绕过，回报。整单不撤权 |
| activate 退出非 0 | 回报，不手工移动 key 文件 |

### 第 7 步：两个项目分别通过正式双检查（S）

```sh
for P in "$PROJECT_OLD" "$PROJECT_NEW"; do
  if cardigan worker check --project "$P" --machine "$MACHINE"; then echo "RESULT $P worker PASS"; else echo "RESULT $P worker FAIL"; fi
  if cardigan machine check "$MACHINE" --project "$P"; then echo "RESULT $P machine PASS"; else echo "RESULT $P machine FAIL"; fi
done
```

预期：四行 `RESULT` 都是 `PASS`。两条命令在未通过时都会以非零退出。同时核对输出：两个项目的 worker check 全部通过（H-183 回执为 9 项全过），machine check 为 `passed`。逐条核对这四行结果，不以整个循环的退出码为准。

- 这是正式检查，会建立新的检查记录。若某绑定处于升级停派且条件满足，成功的一对检查会解除停派，这是预期效果。
- 激活本身不会让检查变绿。报 helper 落后时（主线在 C-551 之后改过 `deploy/worker-git.py`），已接入的绑定等后台巡检（启动时和每 30 分钟）完成自动升级；未选择的绑定按该绑定的人工升级命令处理。然后重跑整个循环。新的 worker check 一开始，之前的通过结果就作废，所以每个项目都要先 worker check、再 machine check。
- 只认同一绑定、同一版本的最终一轮结果。
- 升级失败会保持停派：不重跑同版安装，不手动解除停派，按运维待办处理。

### 第 8 步：撤权

#### 8.1 闸门

只有以下条件**全部**满足，才继续：

- 两个项目各自的 worker check 和 machine check，共四项，在最终一轮均通过：四行 `RESULT … PASS` 齐全，输出与之一致；
- 两个绑定都不属于“不一致”分支，第 6 步实际做过的接入或复用核对全部符合预期；
- 两条管理通道仍然成立。

任一项未通过就**停止，不撤权**：保留 `TEMP_RULE`，回报未通过的项目和检查。

#### 8.2 撤权前记录（B）

```sh
before_list=$(sudo ls -1A /private/etc/sudoers.d) &&
before_old=$(sudo -n -l -U cardigan_updater 2>&1); before_new=$(sudo -n -l -U "cgu_$tag" 2>&1)
before_tmp=$(sudo -n -l -U "$TEMP_USER" 2>&1); printf '%s\n' "$before_tmp"
```

预期：`before_tmp` 的输出中能看到 `TEMP_RULE` 授予的权限。看不到就**停止**，交 PM 核对参数。

#### 8.3 在 A 执行撤权子进程

本子进程沿用 C-548#34 的已审脚本。唯一改动：目标路径从参数读取，并且只接受 `/private/etc/sudoers.d/` 下的非升级规则。

先在 A 设置 `TEMP_RULE`，并确认 `/private/etc`、`sudoers.d` 及其祖先的所有者、权限和 ACL 只允许管理员写入，无法确认即停。不要在 A 里设置 `set -e` 或执行 `exit`。规则正文只在 A 的本地终端核对，不回传到卡片。

```
/usr/bin/python3 -IB - "$TEMP_RULE" <<'PY'
import hashlib, os, stat, subprocess, sys, tempfile
from pathlib import Path
p = Path(sys.argv[1])
if p.parent != Path('/private/etc/sudoers.d') or not p.name or p.name.startswith('cardigan-helper-upgrade'): raise SystemExit('STOP: unexpected target')
assert os.geteuid() == 0
s = p.lstat()
if not (stat.S_ISREG(s.st_mode) and s.st_uid == 0 and s.st_nlink == 1 and not s.st_mode & 0o022): raise SystemExit('STOP: unexpected rule')
def ident(x): return (x.st_dev,x.st_ino,x.st_mode,x.st_uid,x.st_gid,x.st_nlink,x.st_size,x.st_mtime_ns)
def checked(path):
    fd = os.open(path, os.O_RDONLY | os.O_NOFOLLOW | os.O_NONBLOCK)
    with os.fdopen(fd,'rb') as f:
        if ident(os.fstat(f.fileno())) != ident(s): raise SystemExit('STOP: changed rule')
        return f.read()
data = checked(p)
subprocess.run(['/usr/sbin/visudo','-c'], check=True)
print(repr(data), flush=True)
with open('/dev/tty') as tty:
    print('核对仅为指定人员的临时授权、不是永久通道来源；确认才输入 REVOKE：',flush=True)
    if tty.readline().strip() != 'REVOKE': raise SystemExit('STOP: not confirmed')
    if checked(p) != data: raise SystemExit('STOP: changed rule')
    b = Path(tempfile.mkdtemp(prefix='cardigan-policy-',dir='/private/etc')) / p.name
    print('仅记在管理员终端的归档位置及原件 SHA256：', b, hashlib.sha256(data).hexdigest(), flush=True)
    if b.parent.stat().st_dev != s.st_dev: raise SystemExit('STOP: different filesystem')
    os.rename(p,b)
    try:
        subprocess.run(['/usr/sbin/visudo','-c'], check=True)
        print('在 B 用永久管理员重新 sudo -k && sudo /usr/bin/id -u；确认为 0 并核对指定临时授权已撤、无其它变更，才输入 PASS；否则回车回退：',flush=True)
        if tty.readline().strip() != 'PASS': raise ValueError('admin check failed')
    except BaseException:
        if checked(b) != data: raise SystemExit('STOP: archive changed; keep root session')
        os.link(b,p,follow_symlinks=False)  # 只在确切原路径不存在时恢复同一原件，保留归档
        subprocess.run(['/usr/sbin/visudo','-c'], check=True)
        raise SystemExit('已恢复原件；须在 B 重新核验永久管理员。此次撤权未完成。')
PY
```

#### 8.4 撤权后复核（B）

等 A 依次打印出归档位置、`visudo -c` 成功，并停在“……才输入 PASS”的提示上，再在 B 运行。在此之前取得的结果不算数。

```sh
sudo -k && sudo /usr/bin/id -u &&
sudo test ! -e "$TEMP_RULE" && sudo test ! -L "$TEMP_RULE" && echo RULE-GONE &&
after_list=$(sudo ls -1A /private/etc/sudoers.d) &&
[ "$(printf '%s\n' "$before_list" | grep -vxF "${TEMP_RULE##*/}")" = "$after_list" ] && echo LIST-OK &&
[ "$(sudo -n -l -U cardigan_updater 2>&1)" = "$before_old" ] && [ "$(sudo -n -l -U "cgu_$tag" 2>&1)" = "$before_new" ] && echo UPGRADE-RULES-UNCHANGED
sudo -n -l -U "$TEMP_USER"
```

预期：

- 第一条要求重新输入永久管理员的密码，输出 `0`。
- 依次打印 `RULE-GONE`、`LIST-OK`、`UPGRADE-RULES-UNCHANGED`。升级账号的授权与撤权前相同：已接入或首次接入的绑定只有自己的入口；未选择的绑定撤权前后都报该用户不存在。
- 最后一条的输出中不再有 `TEMP_RULE` 授予的权限；与 `before_tmp` 相比，没有其它变化。

全部符合才在 A 输入 `PASS`。任一不符就在 A 直接回车，脚本会自动恢复原件。

#### 8.5 失败或中断（同 C-548#34）

- A 必须保持开启。
- 自动回退完成后，仍要在 B 重新运行 `sudo -k && sudo /usr/bin/id -u` 并确认输出 `0`，结果报“已回退”，不报撤权成功。
- 子进程在归档后中断时，不要假定已恢复。先在 A 按记下的确切位置和摘要，核对归档仍是同一个 root 普通文件，并检查原路径（包括悬空链接）。
- 只有原路径确实空缺且归档无误时，才在 A 把 `BFILE` 设为该归档的绝对路径，运行 `/usr/bin/python3 -IB -c 'import os,sys; os.link(sys.argv[1], sys.argv[2], follow_symlinks=False)' "$BFILE" "$TEMP_RULE"`，再运行 `/usr/sbin/visudo -c`，然后在 B 复核永久管理员。
- 原路径已被占用、归档不符、无法恢复或恢复后复查失败：立即停止，由 A 通道交永久管理员处置。不覆盖文件，不改其它规则，不关闭最后一个管理通道。

## 4. 隔离验证（未做现场验证）

验证都在 Run 的 `$TMPDIR` 下进行，用 `fakeroot` 模拟 root：没有真实 root，没有生产数据，没有 macOS 实机。夹具脚本和输出作为交付附件。

1. **解包归属与权限位**：从 `deploy/enroll-helper-worker.sh` 原样抽出 `guard` 代码，对解出的五个引导文件和 `deploy` 目录运行。结果：
   - 非 root 账号打包（成员 uid 2000）后 `tar -xf` → `unsafe bootstrap permissions`（复现 H-183 现场报错）；
   - 同一包加 `--no-same-owner` → 通过；
   - `git archive` 用默认 `tar.umask=0002` 打包，即使加 `--no-same-owner` → 仍被拒；
   - `tar.umask=0022` 打包 → 通过；
   - 第 3 步打包命令：源文件组可写、解包 umask 为 0002 的最坏情况下 → 通过，解出的文件摘要与主线一致。
2. **同机双绑定选择**：只把 `CONFIG_DIR` 指向夹具目录，对真实文件调用 `install-macos-worker.py` 的 `binding_inventory` / `select_binding`。结果：
   - 两份有效配置时，旧路径项目选中 `worker.json`，命名项目选中 `worker-<项目>.json`；
   - 命名配置权限为 0644、内容损坏，或内容与文件名不符时，只拒绝命名项目，旧路径项目不受影响；
   - 额外出现 `worker-<旧路径项目>.json` 时拒绝旧路径项目（对应第 2 步的预期）。
3. **第 3 步失败即停**：用 dash 和 bash 两种 shell 原样运行。结果：

5. **第 0 步只读**：`worker status` 只读接入记录（apps/cli/src/worker-wizard.ts 的 status 分支）；`machine show` 只做存储读取（apps/cli/src/workflow.ts 的 list/show 分支）。正式检查只在第 7 步运行。
6. **第 6 步参数与复用核对**：
   - 首次接入的命令按绑定原样写出，不再把 `--project <项目>` 拼进一个变量展开（zsh 不分词时会变成一个参数）；

7. **第 0、2 步状态判定未查明即停**：从文档原文抽取 `c_state`、`w_state`，用 dash、bash 运行。
