# C-618 平台阻塞时将必需验收证据标为待补

承接 C-610#4。只对流程版本 ≥5 的卡生效；≤4 的卡传 `evidence_pending` 直接报参数错误，沿用原流程。

## 1. 审核员标证据待补（`submit_review.evidence_pending`）

```
evidence_pending: {
  items: [{ description, basis }],          // 1–10 条，basis 为 ACn / INVn / PCn
  blocker: { kind: "card_merged", target_id: "C-605" }
         | { kind: "deployment_ready", target_id: "<40 位 SHA>" }
}
```

- **可核查的平台阻塞**只认系统能自己判断是否解除的记录：本项目内未完成、未取消、不是本卡的平台卡（`card_merged`，以系统 `card_merged` 事件加卡片 done 为准），或平台修复提交的部署（`deployment_ready`，含控制面其它项目的部署记录）。目标不存在、是本卡、已取消、已完成或已部署时报参数错误，审核员按现有流程审。
- 待补项必须引用验收标准、卡上不变量或通过条件；常驻不变量（如 `check_failed`）不能用来标待补，普通测试失败不算平台阻塞。
- 不能与 `recheck_required`、`followup_card_id` 同用（后者会让结论变成通过）。

## 2. 结论与轮数

- 没有代码必改：结论为 `conditional`，`recheck_required=false`、`rework_allowed=false`，**不是通过**（`reviewPassed` 为假，交付保持 submitted，验证项保持 in_progress，系统完成申请不会汇总）。
- 不算驳回、不消耗轮数（轮数本来只数 reject），也**不重置连续驳回**：`rejectionStreak` 和 C-610 指标 `rejectionStreakEpisodes` 跳过这类审核，第 2 次驳回仍要通过条件清单，第 3 次驳回仍开对齐回合。
- 有代码或功能必改：照常 `reject`，计一轮、唤醒作者返工；待补项一并记录。
- 路由：纯待补不唤醒任何人，也不按“通过”走完成路由；验证项的活动标签显示“证据待补”，不再把同一交付当成待审目标。

## 3. 平台阻塞解除后

- 系统维护（`resumeWorkWaits`，每个系统规则周期都跑）检查每个验证项**尚未结清**的待补（该验证项最新的待补审核，之后没有通过；代码驳回会把待补带到下一版）。阻塞有系统记录证明已解除时，发 `review_evidence_unblocked`（时间线）并给原作者发一条 `instruction_issued`（`evidence_unblocked` 列出审核编号），写明待补项。
- 同一审核只通知一次；多个审核员等同一解除记录时合并为一条。已通知过的审核不再催办。
- 主机卡顿巡检：作者产出项处于 delivered 时，普通指令仍视为“等待工作项”不重启；补证指令的门铃丢失时照常显示为待唤醒。

## 4. 补证与核对

- 作者只补仍适用的证据，提交新交付，把证据附件绑定到新交付（附件 `attach_to` 为该交付，或挂在带该交付编号的时间线条目上）。
- 对应审核员核对：存在未结清的待补时，**通过**必须带 `evidence_attachments`（只接受绑定到当前被审交付的附件，旧版本附件报错）或 `evidence_not_applicable`（写明为何不再适用）。阻塞仍未解除可继续标待补；驳回不要求结清，待补继续保留。
- 没有待补时传这两个字段报参数错误。

## 5. 读口与角色

- `get_card.work_items[].pending_evidence`：验证项未结清的待补（审核编号、交付编号、待补项、阻塞）。
- reviewer、independent_reviewer、design_director 共用的审核收敛规则加一条证据待补说明；coder、frontend_engineer 加补证说明。

## 已知遗留

- 跨项目的平台卡（如其它项目引用 cardigan 的卡号）目前没有只读读口，只能用 `deployment_ready`（平台修复提交 SHA）登记；跨项目卡号读口作为后续。
- 平台卡被取消后不会自动通知；作者可随时提交新交付，审核员照常核对。
