# C-785 每个隔离区常驻全部历史：堆上限保险、读取审计移出常驻、后续拆分

依据：11-26 架构调研 2-multi-project.md P2、1-performance.md P7。范围按 Q-1433 收窄：本卡只把 `cross_card_read` 移出常驻；`github_check_dispatch` 由 C-796 承接（另配独立复核）。

## 1. 堆上限的生效路径（核实结论）

- 生产上两个 server 进程都由部署监督器（`cardigan self-deploy`，systemd user 单元 `cardigan-selfdeploy.service`）拉起：`packages/host/src/deployment-node.ts` 的 `spawnRole` 用 `process.execPath <release>/apps/server/dist/{bin,background-bin}.js` 启动，环境是监督器自己的环境展开后加 `CARDIGAN_DATA_DIR`、`CARDIGAN_SUPERVISED`。两个角色走同一个函数、同一份环境。
- 不能用命令行参数：监督器靠 `/proc/<pid>/cmdline` 的 `argv[1]` 等于 server 脚本来核对进程身份（`verifyProcess`），在脚本前插 `--max-old-space-size` 会让身份核对失败。只能走 `NODE_OPTIONS`。
- 以前要靠单元文件给监督器设 `NODE_OPTIONS`，再“碰巧”被展开传下去，这条路没有代码保证，也没有测试，监督器自升级（C-767）改写单元文件后也无人核对。
- 改法：监督器自己算出一个 `NODE_OPTIONS`（`packages/host/src/server-heap.ts` 的 `serverHeap`），构造时算一次存在 `driver.serverHeap`，两个角色的 `spawnRole` 都用这一个值。Web 进程里的读 worker、MCP 读 worker、诊断 worker 是 `worker_threads`，继承进程级 V8 标志，同一个上限（测试实测主线程与 worker 的 `heap_size_limit` 相同）。
- 测试：`deployment-pair.test.ts` 起真实的两个子进程，各自报告 `v8.getHeapStatistics().heap_size_limit`，断言 Web 和后台都不低于 8192 MiB；`server-heap.test.ts` 起真实 node 子进程验证主线程和 worker 都按该值生效。

## 2. 取值（作者选定，可配置）

- 默认 `--max-old-space-size=8192`（MiB），`heap_size_limit` 约 8.2 GiB，是原默认 4,345 MB 的约 1.9 倍。
- 覆盖：监督器环境里的 `CARDIGAN_SERVER_HEAP_MB`（1024～65536 的整数）。不放进 `self-deploy.yaml`：它对未知字段严格拒绝，回滚到旧监督器时会拒绝启动（C-767 的同一考虑）。
- 主机自己的 `NODE_OPTIONS` 里已有 `--max-old-space-size` 时原样沿用（最后一个生效），不叠加；其它 `NODE_OPTIONS` 保留。
- 值不合法时用默认值，并在监督器 stderr 写一行说明。
- 余量：后台堆现在 0.86～0.98 GB，按每天约 55 MB 增长，到 8.2 GiB 约 130 天，覆盖下一次复测周期。注意这是“每个隔离区”的上限，主机 23 GB 内存才是总约束（Web 进程 5～6 个隔离区合计 RSS 4.2 GB），真正的解法是第 5 节的结构性改动。
- 生效核对：部署后打开 Workbench「机器」设置页的进程健康，Web 与后台两行的堆上限应显示约 8.2 GB（来源是各自进程的 `heap_size_limit`）。这一步在生产上做，作为合并后跟进项交主机运维。

## 3. `cross_card_read` 移出常驻

- 做法：`packages/store/src/command-events.ts` 的 `NON_RESIDENT_EVENT_TYPES`（目前只有 `cross_card_read`）。命令状态装载事件时在 SQL 里就跳过这些行（`type NOT IN (...)`），不解析、不进内存日志，任何范围（full/hot/lean/slim）都一样。行仍在 `events` 表里。
- 读取方核对：
  - `project_snapshot` 的读取审计：原来经内存日志的类型索引，改为 `Store.streamEventsOfType`（走 `events_by_type` 索引直接查表）。
  - `get_updates`（`Store.getUpdates`）、路由（`routeStreamEvents`）、项目动态页（`activity-state.ts`）本来就查表，不受影响；路由对读取审计本来就不产生通知或 Run（`route.test.ts` 已有用例）。
  - PM Office 摘要的首个窗口：按项目流 ACK 的 seq 找事件取时间，这个 seq 常常就是一条读取审计。改为先用 `Store.eventAt` 查表，查不到再退回内存日志（新增用例，去掉修复会失败）。
  - 其余项目流整流读取方（角色来源、角色覆盖、部署钉、批次合并检查、运行容量、`get_card`、发布签名、批次读取范围）只找特定类型，与读取审计无关；`lean` 范围对它的保留规则本来就是“全部不留”。
  - 事件序号由 `event_counters` 表分配，不依赖内存日志的最后一条 seq。
- 测试：`command-events.test.ts` 两条（内存日志不含、表里都在、自己写入后在事务内也不出现、分片预热跨过被跳过的行不卡住）；改了原来经内存日志读审计行的 4 个测试文件，改为查表。

## 4. 复测数字

合成库对照（`apps/server/test-support/resident-event-bench.mjs`，同一批行，一份类型是 `cross_card_read`，一份换成仍会常驻的类型；各自在独立子进程里装载并 GC 后量堆）：

| | 常驻堆 |
|---|---|
| C-785 之前（36,000 条审计 + 120,000 条普通事件） | 249.0 MB |
| C-785 之后 | 196.3 MB |
| 节省 | 52.7 MB，每条审计约 1,535 字节 |

三次运行堆数字完全一致；装载耗时受机器负载影响较大，不作结论。

换算到生产（推算，不是两点实测）：

- 快照里 `cross_card_read` 35,943 行，功能 11-16 上线，到 11-26 约 10.3 天，约 3,500 行/天。
- 每份 cardigan 状态一次性少约 55 MB（35,943 × 1,535 B）；Web 进程主线程加 4 个读 worker、后台各一份，合计 RSS 少约 0.3 GB。
- 每份状态的堆日增：约 3,500 × 1,535 B ≈ 5.4 MB/天，从 50～80 MB/天降到约 45～75 MB/天（中值 60 → 约 55，约 −9%）。
- 两点实测要在生产上做：部署后记一次 Web、后台的堆用量，24 小时后再记一次，作为合并后跟进项交主机运维。

## 5. 长期：已关闭卡不常驻（后续阶段拆分，本卡不做）

按每份状态约 55 MB/天的增速排期，越靠前的收益越大、风险越小：

1. **C-796：`github_check_dispatch` 移出常驻**（已开卡，配独立复核）。派发日志 `allAt` / `unfinishedExecutorsAt` 改为每个 attempt 只解码最新一条，默认 hot 范围对已关闭卡裁掉派发记录（沿用 C-649 lean 的审计结论和 `githubRunCards` 例外）。约占事件字节 12%。
2. **事件里的 Assignment 身份去重**（建议新开卡，低风险）。每条 Assignment 发出的事件都带完整的 `actor.allowed_tools`（二三十个工具名）和 `capabilities`，解码后每条各一份。装载时把相同的数组换成同一个冻结的共享数组。实测一条 1 KB 的评论事件，堆从 1,872 B 降到 672 B（−64%）。它对所有 Assignment 事件都生效，可能是单项最大的收益；风险是有代码原地改事件里的数组（冻结后会直接报错，测试能发现）。
3. **运行队列按项目判断**（P7 短期方案）。`run-capacity.ts` 的 `waitingRuns` 先用 `runs_queue_candidates` 索引判断项目有没有排队 Run，没有就不装载该项目的状态。读 worker 约省 0.7 GB，sensen-godot 冷读从约 4.5 秒降到约 1 秒。要和 dispatcher 的队列口径一致。
4. **已关闭卡的实体不常驻**：`readCommandState` 只装未关闭卡和热卡的 deliveries、reviews、runs、timeline，已关闭卡的这些实体按卡从 SQL 读（`cardSources` 已有按卡读取）。先清点 `state.deliveries` / `state.reviews` / `state.runs` / `state.timeline` 的读取方并逐个迁到按卡读取，再切换。实体约占每份状态的一半（cardigan 实体约 294 MB），已关闭卡占 95% 以上。风险最大，要分批，每批配影子对照（沿用 C-639 的 `compareHotState`）。
5. **已关闭卡的事件不常驻成为默认**：在 C-671 slim 基础上，装载时先用 `type`、`card_id` 列判断是否休眠，再决定是否 `JSON.parse`（现在是先解析再判断，峰值和耗时都没省）；跑完生产副本影子回放后把默认范围从 hot 切到 slim。
6. **数据清理**（P14）：idempotency 按“指派已释放”删、已作废交付的 `role_rule_inventory`、`github_rest_budget` 不落事件表。不影响常驻堆，但影响冷建时间和备份体积。

## 已知未覆盖

- 生产的生效核对和两点堆增长实测只能在主机上做，作为合并后跟进项（交主机运维）。
- 推算的“每天约 3,500 条审计”按 10.3 天平均，接入项目增多后会变。
- 直接在命令行执行 `node apps/server/dist/bin.js`（非监督器启动，非生产方式）不会自动带上新上限。
