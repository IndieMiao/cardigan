# C-596 常驻 PM 门铃停滞自动恢复

本文件是 C-596 的任务计划与设计说明。按 PM 指令（C-596#26），本卡不改 `docs/development-plan.md` 正文；下方“开发方案拟稿”供里程碑收尾时统一同步到 §6.4 路由表和 §7.1 常驻 PM 小节。

## 根因（按证据口径）

### 现场证据（来自卡片描述与 C-596#8，未经本卡复核）

- sensen A-31（PM Ops）的轮次 R-388 于 15:53:20Z 结束后，通知全部被推迟：`bell_wake_deferred`（reason=`system_finished_turn`，activity_source=`alive/unknown`，run_id 一直是 R-388）。
- `bell_turn_recovery_due` 在 16:28、16:46、16:50 各出现一次，之后没有新 Run；16:56 人手动 `pm rotate --ops` + `pm start --ops` 后恢复。
- sensen 只读核对：A-31 终端 t3gh 标签为 run=R-387（创建该终端的 Run），实际已是 R-388。

### 回放结论（代码路径 + `apps/server/src/standing-pm-stall.test.ts`）

- 到期后的系统换会话先用 `observe_retirement` 证明原轮次的终端归属。终端是 keep（`resume_or_replace` 换会话后留下，herdr 对其只回答 unknown），或无 generation 的 loopback 终端标签与该引用上首个确认门铃的 Run 对不上时，证明拿不到，恢复以 `unsafe_evidence` 记一次 `bell_turn_recovery_failed` 后停住。回放测试复现了这一拒绝。
- 这些通知被 `checkStandingInbox` 排除，不会转成 `standing_inbox_stalled`；`recoverPmSession` 只处理进程已退出的 PM。因此没有其它路径恢复，只能等人发现。
- 终端标签记录创建 Run 属设计行为，投递时的标签核对与 runtime_ref 中的创建 Run 一致，标签本身不会让投递失败（C-596#10）。

### 未核事项

- **A-31 当时的终端是否为 keep 没有现场证据**；标签与首个确认门铃 Run 是否失配也未读取主机记录核对。上述根因是推断，两种情况均会导致同样结果，本卡的恢复对两者都生效。
- A-48 在 16:56:04 出现的 attempts=0 `delivery_failed`：需主机读取配对升级事件的 reason 才能定性（C-596#10），本卡未处理。

## 实现要点

- 规划函数 `planStandingPmStall`（`packages/domain/src/commands/standing-pm-stall.ts`）纯函数计算阶段；三个 system 命令在写事务内用同一函数重算，状态变化即拒绝。
- 主机巡检 `StandingPmRecovery`（`packages/host/src/standing-pm-recovery.ts`）挂在 `StallPatrol` 每 30 秒一轮。
- 重开走既有 `host_ops_restart_standing_pm` 执行路径：先独立确认旧终端退出，再清会话、作废 Token、排新 Run。意图带 `standing_pm_stall` 来源标记，执行时旧终端不归本机则挂起转运维，不走人工确认退出；人工 `pm restart` 的规则不变。
- 重开失败只记实际尝试（内存中按项目 + Assignment 和停滞轮次记首次失败时间，同一巡检遍历所有项目，编号按项目分配）；主机重启后丢失只会推迟升级，不会误判。
- 系统自己发的提醒、升级和移交通知照常投递，但不计入待处理工作：每一步都要求仍有未读的原通知，原通知在宽限期内被确认后不会只凭提醒重开或升级。
- 测试：`packages/domain/src/commands/standing-pm-stall.contract.test.ts`、`apps/server/src/standing-pm-stall.test.ts`。

## 开发方案拟稿（里程碑收尾同步，非本卡改动）

**常驻 PM 门铃停滞自动恢复（C-596）。** 起因：sensen A-31（PM Ops）的轮次 R-388 由系统代结束后，终端一直报 alive/unknown，门铃按 `system_finished_turn` 不停推迟；`bell_turn_recovery_due` 到期后，系统换会话要先用 `observe_retirement` 证明原轮次的终端归属。按代码路径和回放测试推断，这一证明在两种情况下拿不到：终端是 keep（`resume_or_replace` 换会话后留下，herdr 对它只回答 unknown），或无 generation 的 loopback 终端标签与该引用上首个确认门铃的 Run 对不上；A-31 当时属于哪一种未取得主机侧证据。证明拿不到时恢复以 `unsafe_evidence` 记一次 `bell_turn_recovery_failed` 后就停住，这些通知又被排除在 `standing_inbox_stalled` 之外，所以只能等人发现。现在主机巡检（每 30 秒，和派发停滞巡检同一轮）对每个托管的在岗常驻 PM（Office 和 Ops，不含外接、人停止的）单独计时：它自己的未投递通知（pending、delivery_failed，以及由它转出的 needs_attention；不算已 ACK、暂停卡、拍板跟进压住的和 Ops 已过期的请求）里，从“通知产生”和“该 PM 最近一次 Run 开始或结束”两者较晚的时间起算，最早一条超过阈值且期间没有 Run 在执行，就按三步处理，每一步都在写事务里用同一个 domain 规划函数重算，状态变了就不做：① 提醒：写 `standing_pm_stall_redelivered`（时间线），并给该 PM 记一条指向它的可投递通知，走原 Dispatcher 和原守卫；原通知、原事件和 ACK 游标不动，delivery_failed 的原通知同时改回 pending 立即重试。② 宽限期后仍没有新 Run 开始，写 `standing_pm_stall_restarted`（时间线 + Needs You 知会），并以 system 身份发起与 `pm restart` 相同的 `host_ops_restart_standing_pm`：意图上记自动来源标记（`standing_pm_stall`，只有系统可设）；执行时按普通重启独立确认旧终端退出，才清会话、作废旧 Token、排新 Run；若执行时旧终端已不归当前运行时（例如落库后主机切换运行时或重启后接续），保持操作挂起、不建人工确认待办，由下一步转主机运维，Assignment、ACK 游标、拍板和待执行事项都不动，旧通知留在游标后由新会话读取；运维动作挂起期间 Dispatcher 不向该 PM 按铃，所以不会同时有两个执行者。③ 以下情况写 `standing_pm_stall_escalated`（时间线 + Needs You 知会），不建 HumanAction、不交人，也不另发停止或启动：时间窗内已自动重开达到上限；该 PM 上任何主机操作（本卡的重开、较早的轮次恢复或运维手动重启）挂起超过宽限期仍未确认退出；重开已实际尝试但无法发起（取不到启动快照或意图被拒），自首次失败起满一个宽限期（巡检迟到或主机重启不算失败，先尝试重开）；正在会话维护（角色升级、空闲退役）；旧终端不在本机或不属于当前运行时（避免落入需要人确认退出的分支）。有在岗主机运维时事件记 `handoff=host_ops` 并通知它；没有时记 `handoff=waiting_host_ops`，只在另一 PM 上下文实际存在时知会它，等主机运维上岗后由巡检写 `standing_pm_stall_handoff_delivered`（引用原升级），可投递通知绑定这条新事件，运维此前读过等待事件也不影响按铃。同一原因在时间窗内只升级一次，期间不再自动重开。新 Run 真正开始即结束本轮。该 PM 已被这样重开后，原轮次的 `bell_turn_recovery_due` 不再另发恢复失败告警。默认阈值 15 分钟、宽限 5 分钟、时间窗 60 分钟、上限 2 次，可用 `CARDIGAN_STANDING_PM_STALL_MS`、`CARDIGAN_STANDING_PM_STALL_GRACE_MS`、`CARDIGAN_STANDING_PM_STALL_WINDOW_MS`、`CARDIGAN_STANDING_PM_STALL_MAX_RESTARTS`（正整数，毫秒或次数）调整，非法值启动失败。
