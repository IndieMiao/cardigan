# C-605：受管运行入口在 macOS 上约 15 秒退出 125

## 根因

`$CARDIGAN_RUN_COMMAND` 执行 `deploy/run-resources.py`。原来 `command()` 的顺序是：

1. 入口进程向控制服务做第一次生命周期查询 `Confirmation.state()`（`http.client` → 域名解析 → TLS → 调用 `/usr/bin/openssl` 验签）；
2. 创建私有临时目录，写系统日志审计 `shared_directory_retained`；
3. `os.fork()`，子进程不 exec，直接在 Python 里当监督进程：启动私用任务，每 0.12 秒检查会话和取消，每 15 秒（`interval=15`）再查一次生命周期。

在 macOS 上，第 1、2 步的域名解析和系统日志会启动 libdispatch／XPC（mDNSResponder、logd 连接和工作线程）。按 Apple 的 fork 规则，进程已经多线程或已经用过这些系统服务时，fork 出的子进程在 exec 之前不能再用它们。监督子进程在第 15 秒第一次复查时再次解析 `*.ts.net` 主机名，被系统直接终止。终止由 libdispatch 触发（trap），不是 Python 异常，所以：

- 子进程没写状态字节就消失，入口 `os.read(reader, 1)` 读到 EOF，按旧代码返回 `125`；
- 生命周期 socket 随子进程关闭，参与者只看到 EOF，没有 `cardigan-private-settled-v1` 结算记录；
- 监督进程的 stdio 已经重定向到 `/dev/null`，崩溃也写不进审计，所以什么痕迹都没留下；
- 私用任务用 `start_new_session=True` 启动，不受影响，继续运行，只能由 Agent 按自己记下的 PID 收尾。

三次现象（R-427 送签、R-515、张衡 W-62 模拟器）都在约 15 秒时出现，返回码都是 125，都有 EOF、没有结算。这与上面的路径完全一致。卡上列出的其它环节都已排除：

- 入口脚本的哈希校验和 `main()` 启动失败也返回 125，但会立即返回，不会等 15 秒；
- “Run 已结束、会话退出、取消”这条正常路径会先发结算记录，并写审计；
- hc／herdr-core 会话和 SSH 通道不参与这个进程树，入口和监督进程都在 worker 本地；
- 资源会话（控制服务的 `run_resource` 读取）只会返回 `active`、`ended` 等状态，查询失败只记为 `unknown`，不会让进程退出。

同一入口在 Linux 上跑 40 秒的命令能正常返回命令自己的退出码（本卡已在 local 机器实测）。Linux 没有这条 fork 限制。

### 证据等级

- 已证实：代码路径；Linux 上不复现；用替身测试确认旧代码在 fork 之前就做了生命周期查询和建目录，新代码只先 fork。
- 未取得：mac-mini 上的崩溃报告。worker 账号 `~/Library/Logs/DiagnosticReports/` 下应能找到 11-22 18:00 前后和 11-23 00:18 前后 `python3`／`Python` 的 `.ips`，内容带 `crashed on child side of fork pre-exec` 或 libdispatch 的 fork 相关信息。已请主机运维核对，不挡合并。

## 修复（`deploy/run-resources.py`）

1. **先 fork 再做任何联网或写日志的事**。入口只校验参数和会话身份（syscall），读取 Token 摘要，然后立刻 fork。生命周期首查、建临时目录、审计、启动私用任务和之后的复查都在监督进程里做。监督进程是这个进程树里第一个用到域名解析、TLS 和系统日志的进程，它的子进程（私用任务、openssl）都是 fork 后马上 exec。入口在 fork 之后只等状态。
2. **不再静默返回 125**。状态管道在状态字节后可以附一行不超过 200 字节的 ASCII 原因，单次写入，不超过 PIPE_BUF，入口读到 EOF 为止：
   - Run 已结束：`cardigan: run ended; …`。私用命令没有单独时限，以所属 Run 的生命周期为界，这就是“到达声明的时限”；
   - Agent 会话退出：`cardigan: agent session exited; …`；入口被取消：`entry cancelled; …`（入口已不在，只写审计）；
   - 后半句写明参与者是 `private participants released`（143）、`release unconfirmed, private task retained`，还是 `private participant missing, task retained`（125）；Vite 写 `Vite ingress unproven, Vite retained`；
   - 监督进程没给状态就消失：入口 `waitpid` 拿到信号或退出码，打印 `cardigan: supervisor lost (SIGKILL); lifetime connection closed without settlement, private task retained`，并审计 `supervisor_lost <信号>`；
   - 启动时 Run 已不在运行：`cardigan: run not active (ended)`，不启动命令；
   - 监督进程里其它异常：`supervisor failed (<代码或异常类型>)`，审计 `supervisor_failed`；入口启动失败：`run resource unavailable (<代码或异常类型>)`。只显示本文件固定的小写代码或异常类型名，不带路径和取值。
   - 每种停止原因都另写一条审计 `stop_run_ended`、`stop_agent_session_exited` 或 `stop_entry_cancelled`。
3. `Confirmation` 对读取时的任何异常都记为 `unknown`，原来只捕获几类，其它异常会让监督进程崩溃。
4. **慢链路启动**（张良 C-605#3 的线索）：每次生命周期读取的单步网络超时从 2 秒放宽到 10 秒，整次读取上限从 5 秒放宽到 15 秒（与复查间隔相同）；防重放靠每次请求的签名随机数，不靠这个上限。启动首查得到 unknown 时，每秒重试一次，最多 30 秒；得到 ended 等明确状态时不重试，直接报原因。监督期间读取失败本来就只记为 unknown、不退出，所以链路慢不会造成第 15 秒的 125。但旧代码在启动时只要一次读取失败，就立即返回 125，命令根本不会启动。这与“任务已在跑、15 秒后返回”的现象不符，作为加固一并处理。四个数值都是文件顶部的常量。
5. 退出码含义不变：命令自身退出码，143 已释放，125 保留或入口失败。授权、结算、参与者释放和 Vite 规则都不变。

## 测试（`test-support/run-resources.py`，由 `apps/server/src/run-resource-cleanup.test.ts` 调用）

- 长命令正常结束：命令运行期间经历 10 次以上生命周期复查，返回自己的退出码 9，stderr 为空。
- 时限（Run 结束）：原有已登记服务用例补充断言 stderr 为 `cardigan: run ended; release unconfirmed, private task retained`。原有 `test_runs` 中 Run 结束返回 143。
- 连接断开或监督进程丢失：用 SIGKILL 杀掉夹具自己的监督进程（从任务的父进程号找到），入口返回 125 并打印 `supervisor lost (SIGKILL)`；参与者读到 EOF、没有结算记录；审计中有 `supervisor_lost SIGKILL`。会话退出补充断言 stderr 为 `agent session exited; private participants released`。
- 慢链路启动：首查先返回两次 503，改为 active 后命令正常启动并返回自己的退出码；每次读取都延迟 3 秒（超过旧的 2 秒超时）时也能正常启动。
- Run 不在运行：返回 125，打印 `run not active (ended)`，命令没有启动。
- fork 顺序回归：用替身证明 fork 之前没有生命周期查询、建目录和审计。在旧代码上，同一替身记录到的是先查询、后建目录。
- `Confirmation` 遇到 `RuntimeError` 时记为 `unknown`。

- 已经在运行的旧会话要重新启动，才会拿到新的 `$CARDIGAN_RUN_COMMAND`。
