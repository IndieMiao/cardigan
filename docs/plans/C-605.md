# C-605：受管运行入口在 macOS 上约 15 秒退出 125

## 根因

`$CARDIGAN_RUN_COMMAND` 执行 `deploy/run-resources.py`。原来 `command()` 的顺序是：

1. 入口进程向控制服务做第一次生命周期查询 `Confirmation.state()`（`http.client` → 域名解析 → TLS → 调用 `/usr/bin/openssl` 验签）；
2. 创建私有临时目录，写系统日志审计 `shared_directory_retained`；
3. `os.fork()`，子进程不 exec，直接在 Python 里当监督进程：启动私用任务，每 0.12 秒检查会话和取消，每 15 秒（`interval=15`）再查一次生命周期。

在 macOS 上，第 1、2 步的域名解析和系统日志会启动 libdispatch／XPC（mDNSResponder、logd 连接和工作线程）。按 Apple 的 fork 规则，进程已经多线程或已经用过这些系统服务时，fork 出的子进程在 exec 之前不能再用它们。监督子进程在第 15 秒第一次复查时再次解析 `*.ts.net` 主机名，进程崩溃（mac-mini 上的报告为 SIGSEGV）。这是进程级崩溃，不是 Python 异常，所以：

- 子进程没写状态字节就消失，入口 `os.read(reader, 1)` 读到 EOF，按旧代码返回 `125`；
- 生命周期 socket 随子进程关闭，参与者只看到 EOF，没有 `cardigan-private-settled-v1` 结算记录；
- 监督进程的 stdio 已经重定向到 `/dev/null`，崩溃也写不进审计，所以什么痕迹都没留下；
- 私用任务用 `start_new_session=True` 启动，不受影响，继续运行，只能由 Agent 按自己记下的 PID 收尾。

三次现象（R-427 送签、R-515、张衡 W-62 模拟器）都在约 15 秒时出现，返回码都是 125，都有 EOF、没有结算。这与上面的路径完全一致。卡上列出的其它环节都已排除：

- 入口脚本的哈希校验和 `main()` 启动失败也返回 125，但会立即返回，不会等 15 秒；
- “Run 已结束、会话退出、取消”这条正常路径会先发结算记录，并写审计；
- hc／herdr-core 会话和 SSH 通道不参与这个进程树，入口和监督进程都在 worker 本地；
- 资源会话（控制服务的 `run_resource` 读取）只会返回 `active`、`ended` 等状态，查询失败只记为 `unknown`，不会让进程退出。

同一入口在 Linux 上跑 40 秒的命令能正常返回命令自己的退出码（本卡已在 local 机器实测）。Linux 没有这条 fork 限制。

### 证据等级

- 已证实：代码路径；Linux 上不复现；用替身测试确认旧代码在 fork 之前就做了生命周期查询和建目录，新代码只先 fork。
- 现场证据（只读核对 macOS worker，细节见 C-605#14）：系统级崩溃报告目录中有多份 Python 崩溃报告。抽查的 4 份内容一致：进程为系统自带的 Python 3.9（`/usr/bin/python3`），SIGSEGV，标记为 `crashed on child side of fork pre-exec`；涉及两个 worker 账号。
- 未逐一对上：报告时间与三次 125 的时间没有一一对应（可能是系统对同类报告限流）。所以 fork 后、exec 前崩溃已确认在 worker 上发生，但不能证明每一次 125 都来自它。慢链路导致启动失败的另一条路径也已一并加固（见下文第 4 条），两种情况现在都会打印原因。

## 修复（`deploy/run-resources.py`）

1. **先 fork 再做任何联网或写日志的事**。入口只校验参数和会话身份（syscall），读取 Token 摘要，然后立刻 fork。生命周期首查、建临时目录、审计、启动私用任务和之后的复查都在监督进程里做。监督进程是这个进程树里第一个用到域名解析、TLS 和系统日志的进程，它的子进程（私用任务、openssl）都是 fork 后马上 exec。入口在 fork 之后只等状态。
2. **不再静默返回 125**。状态管道在状态字节后可以附一行不超过 200 字节的 ASCII 原因，单次写入，不超过 PIPE_BUF，入口读到 EOF 为止：
   - Run 已结束：`cardigan: run ended; …`。私用命令没有单独时限，以所属 Run 的生命周期为界，这就是“到达声明的时限”；
   - Agent 会话退出：`cardigan: agent session exited; …`；入口被取消：`entry cancelled; …`（入口已不在，只写审计）；
   - 后半句写明参与者是 `private participants released`（143）、`release unconfirmed, private task retained`，还是 `private participant missing, task retained`（125）；Vite 写 `Vite ingress unproven, Vite retained`；
   - 监督进程没给状态就消失：入口 `waitpid` 拿到信号或退出码，打印 `cardigan: supervisor lost (SIGKILL); lifetime connection closed without settlement, task state unconfirmed`，并审计 `supervisor_lost <信号>`。入口不知道监督进程走到了哪一步，所以只说任务状态未确认；
   - 启动时 Run 已不在运行，或 30 秒内没有确认 active：`cardigan: run not active (…)`，不启动命令；
   - 启动等待期间入口被取消或 Agent 会话退出：不启动命令，审计 `start_refused_entry` 或 `start_refused_agent`；会话退出时入口打印 `agent session exited before start`；
   - 监督进程里其它异常：`supervisor failed (<代码或异常类型>)`，审计 `supervisor_failed`；入口启动失败：`run resource unavailable (<代码或异常类型>)`。只显示本文件固定的小写代码或异常类型名，不带路径和取值。
   - 每种停止原因都另写一条审计 `stop_run_ended`、`stop_agent_session_exited` 或 `stop_entry_cancelled`。
3. **正常结束有记录**：前台命令退出时审计 `foreground_exited <退出码>`。之后私用参与者全部关闭（生命周期 socket 收到 POLLHUP），说明命令和它交出生命周期连接的后代都已结束，这时审计 `private_task_finished <退出码>`。正常结束不发 SETTLED。Vite 正常结束审计 `vite_finished <退出码>`。
4. `Confirmation` 对读取时的任何异常都记为 `unknown`，原来只捕获几类，其它异常会让监督进程崩溃。
5. **慢链路启动**（张良 C-605#3 的线索）：每次生命周期读取的单步网络超时从 2 秒放宽到 10 秒，整次读取上限从 5 秒放宽到 15 秒（与复查间隔相同）；防重放靠每次请求的签名随机数，不靠这个上限。读取的每一步（连接、发请求、等响应、验签）只拿剩余预算作超时。socket 超时只限制单次等待，响应分段到达时多次等待会累加，所以整次读取另设一个一次性的实时定时信号（SIGALRM），到截止时刻直接中断读取，按失败（unknown）处理，而不是等结果回来再拒收（V-3016）。监督进程是单线程的；读取结束后恢复原信号处理并清零定时器；fork 和 exec 都不继承这个定时器。域名解析是一次 C 调用，信号处理要等它返回才执行，所以不受这个预算约束。启动首查用一个 30 秒的单调时钟总预算：每次读取最多用剩余预算，重试间隔也在预算内；预算用完不再发起读取，预算外才到的 active 也不启动命令。得到 ended 等明确状态时不重试，直接报原因。等待期间和启动命令或建立监听之前，都检查一次入口是否被取消、会话是否退出。监督期间的一次读取最多占用 15 秒（域名解析除外），这段时间里对取消、会话退出和命令退出的响应最多晚 15 秒。监督期间读取失败本来就只记为 unknown、不退出，所以链路慢不会造成第 15 秒的 125。但旧代码在启动时只要一次读取失败，就立即返回 125，命令根本不会启动。这与“任务已在跑、15 秒后返回”的现象不符，作为加固一并处理。四个数值都是文件顶部的常量。
6. 退出码含义不变：命令自身退出码，143 已释放，125 保留或入口失败。授权、结算、参与者释放和 Vite 规则都不变。

## 测试（`test-support/run-resources.py`，由 `apps/server/src/run-resource-cleanup.test.ts` 调用）

- 长命令正常结束：命令运行期间经历 10 次以上生命周期复查，返回自己的退出码 9，stderr 为空；审计有 `foreground_exited 9` 和 `private_task_finished 9`，没有 `stop_` 记录。
- 时限（Run 结束）：原有已登记服务用例补充断言 stderr 为 `cardigan: run ended; release unconfirmed, private task retained`。原有 `test_runs` 中 Run 结束返回 143。
- 连接断开或监督进程丢失：用 SIGKILL 杀掉夹具自己的监督进程（从任务的父进程号找到），入口返回 125 并打印 `supervisor lost (SIGKILL)`；参与者读到 EOF、没有结算记录；审计中有 `supervisor_lost SIGKILL`。会话退出补充断言 stderr 为 `agent session exited; private participants released`。
- 慢链路启动：首查先返回两次 503，改为 active 后命令正常启动并返回自己的退出码；每次读取都延迟 3 秒（超过旧的 2 秒超时）时也能正常启动。
- Run 不在运行：返回 125，打印 `run not active (ended)`，命令没有启动。
- 启动等待中取消或会话退出：首查一直失败时终止入口（或结束会话），之后才放行 active，命令都没有启动，审计有 `start_refused_*`；会话退出时入口返回 125 并打印原因。
- 启动预算（合成时钟）：每次读取耗时 9 秒，前三次 unknown、第四次 active，读取只在第 0、10、20 秒发起，不启动；每次读取 12 秒、第三次（第 26 秒发起）返回 active 但已过第 30 秒，也不启动；每次读取的预算都不超过剩余时间。
- 读取预算：服务端 3 秒才应答，预算 1 秒时 2 秒内以错误结束；预算 6 秒时正常得到 active。
- 分段响应（V-3016）：状态行、响应头和两段正文每隔 0.8 秒到达一段，整次约 2.4 秒；预算 1.5 秒时在 1.8 秒内以超时结束，结束后定时器和信号处理都已恢复；预算 6 秒时正常得到 active。端到端：读取上限设为 1.5 秒，复查正在分段接收时结束前台命令，入口在 2.2 秒内返回 143。旧代码在同一分段用例上要等全部响应收完才报错。
- fork 顺序回归：用替身证明 fork 之前没有生命周期查询、建目录和审计。在旧代码上，同一替身记录到的是先查询、后建目录。
- `Confirmation` 遇到 `RuntimeError` 时记为 `unknown`。
