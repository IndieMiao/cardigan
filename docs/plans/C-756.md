# C-756：agent-git 合成 Darwin/Linux 用例在合并检查中超时

用例：`apps/cli/src/agent-git.test.ts` › “synthetic Darwin writer and Linux reviewer clone, build and return deliveries on independent disks”（单用例时限 20 s）。

## 根因

这个用例超时不是偶发等待，而是固定开销太大：每次运行要做约 105 次“远程”调用（clone、worktree、build、upload-pack、receive-pack 等）。每次调用都要串行起三个进程：

1. 测试自带的 `ssh` 替身是 Node 脚本，每次调用都要先起一个 Node 进程（约 20 ms），再由它 `spawnSync` 一个 `sh`；
2. `sh` 再启动 `/usr/bin/python3 -I -B` 跑夹具 helper；
3. helper 加载生产的 `worker-git.py`、`worker-files.py`、`worker-primitives.py`（约 1,800 行）。生产入口带 `-B`，不读也不写 helper 的字节码缓存，所以每次都从源码重新编译，约 25–40 ms。

本机实测（12 核、空闲，仅跑此用例）：用例耗时 10.1–11.5 s，其中 105 次调用的 `sh + python` 部分合计约 6.5 s（`git` 50 次、`exists` 20 次、`validate` 10 次、`receive-pack` 10 次……），每次约 60 ms；另有约 2–3 s 是 Node 版 ssh 替身的启动。

在合并检查里（ubuntu-latest，4 vCPU，`pnpm test --maxWorkers=4`），这个用例和其它也大量起子进程的测试一起抢 CPU，耗时被放大 1.2–2 倍，一直排在最慢测试的前三，离 20 s 时限只差几秒，负载稍高就超时。

## 修复（只改测试夹具，不改生产代码、断言和时限）

1. 本用例的 `ssh` 替身从 Node 脚本改成两行 POSIX `sh`：取最后一个参数交给 `sh -c` 执行（`exec`，退出码原样返回），和原替身以及真实 ssh 执行远程命令的语义一致。每次调用少起一个 Node。
2. `workerGitFixture` 在建夹具时，用 `py_compile` 把三份已安装的 helper 预编译成 **hash 校验型** 字节码，放在受保护磁盘以外的夹具私有目录；包装脚本只把这三份源码的缓存路径指过去（标准库仍用系统自己的缓存）。每次加载都会按源码内容哈希校验，helper 被改过就回到从源码编译；`-B` 照旧，不写任何缓存。受保护目录（`libexec` 等）里不多任何文件，就绪检查的摘要校验不受影响。

   中间试过的 `sys.pycache_prefix` 是全局设置，会让标准库模块也失去系统缓存，用例反而变慢到约 17 s，所以没有采用。

本机同条件对比（空闲、仅跑此用例）：原来 10.1 s；只改 ssh 替身约 7.0 s；两项都改约 5.7 s（−43%）。

用例时限保持 20 s，全局 `testTimeout` 不动。

## 和合并检查相同并发下连续 20 次

条件：`taskset -c 0-3`（模拟 4 vCPU 的 runner），`vitest run apps/cli --maxWorkers=4`（与合并检查的 `--maxWorkers=$(nproc)` 相同，也是主机给员工测试的 worker 上限），整套 apps/cli（71 个文件、929 个用例）一起跑，让同包其它测试真实地抢 CPU。没有人为制造负载。

## 验收第 3 条的去向

“合并检查遇到已知的单用例超时先自动重跑一次”：仓库里已有 C-544 的机制（`packages/host/src/check-flake-cases.ts` 登记表 + 工作流在候选构建前隔离重跑 + 固定名称的 Recovered 回执 + 主机七天台账）。要把这个用例接进去，得改检查工作流、poller 的回执合同、签名匹配（目前只有 5000 ms 超时签名）和对应的策略测试，改动量和 C-544 相当，所以拆到后续卡 C-757（已开卡，见 C-756#4）：签名 `Test timed out in 20000ms`，只在候选差异与本用例输入无关时给一次机会，第二次仍失败照常拦下。
