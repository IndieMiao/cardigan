## 证据和归因

- C-405 / GitHub run `43986622247`：`get_check_log` 对 attempt `527c9033-e5c4-4322-9938-95ab269c8f37` 返回日志已清理或不可读；直接读取该卡系统时间线 C-405#34 保存的失败栈。失败位置为原第 85 行释放旧锁后的 `.resolves.toBe("done")`，实际收到 `runtime_queue_timeout`，栈来自 helper 的回复定时器。未取得该次完整历史日志。
- C-370 / GitHub run `44025885414`：通过 `get_check_log` 连续读取 attempt `59bf9e9f-c2db-4334-a852-c3f24e22a9f5` 的 0–537186 字节直到 EOF，失败断言、错误和栈与上面相同；并非原先 75–300ms 的耗时断言失败。
- 源码显示：排队截止时若 helper 回复仍在途，定时器会将 helper 标记为 broken 并终止；子进程 close 和文件描述符清理由异步生命周期完成，期间重复使用会保守拒绝。原用例只等旧 flock 进程关闭，既没等 helper 清理，也没确认 helper 已启动；随后的成功断言把这一准备过程混在同一个 80ms 排队预算里。日志未记录历史进程调度，不能断言当时分别处于清理或重建的哪一步。

## 实现

保留真实 flock、真实 Python helper 和 governed client。旧进程输出 ready 后，使用真实非阻塞获取操作等待 helper 握手及 busy 回复，明确确认锁仍被旧进程持有，再开始计量 80ms 排队超时。超时后再次要求真实 helper 返回 busy；仅对已超时 helper 尚在自动清理期间的 `runtime_queue_timeout` 等待重试，其它错误和错误获取立即失败。不会主动关闭或修复 helper；自然清理、重建后仍须确认未回收未知占用。最后释放并等待旧进程 close，再断言同一 client 调用成功、底层命令恰好执行一次。

准备操作共用一个绝对截止时间，预算 2000ms，状态采样间隔 10ms；原排队预算 80ms、耗时上下界 75/300ms、超时错误及禁止底层 IO 的断言均保留。准备未就绪在预算内失败，不重试客户端调用、不跳过测试、不改产品锁协议或其它测试文件。
