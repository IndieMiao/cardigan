# C-647 合并检查不再因 main 前进和部署重启反复作废

## 根因

1. **非队列模式重启必然作废**：候选合并提交由 `commit-tree` 现场生成，不固定提交时间。重启后进程内的候选缓存清空，重新准备出的候选 SHA 一定不同，即使基线和树都没变。`queue()` 的 `sameCandidate` 因此判为“候选已改变”，记 `interrupted`（“检查中断或候选已改变，重新排队”），并取消在途 GitHub run。
2. **重启时改了 `max_concurrent` 会让在途 run 以 security 结束**：GitHub 派发身份键（`githubDispatchIdentity`）对整份执行器配置取摘要，包含 `maxConcurrent`。只有“遗弃派发恢复”路径容忍仅 `maxConcurrent` 不同；正常接回路径不容忍，结果是 `executor_unreachable: security`。张良计划在部署时把 `max_concurrent` 从 1 改回 16，正好触发。
3. **名额不按优先级**：`slot()` 只对已经在等名额的任务排序。高优先级任务若在等同卡互斥释放（重启后旧 run 正在取消），`capacity()` 返回 false、让出名额，低优先级任务先拿到 GitHub 容量（11-23 18:04 C-620）。

## 改动

| 位置 | 改动 |
|---|---|
| `apps/server/src/merge-checks.ts` `resumableGithubRun` | 原 `resumableCardCheck`。队列模式行为不变（卡片级检查在任意基线有效）。新增非队列模式：在途检查的基线、树与重建候选相同，日志中仍有同一 attempt、同一 run 的未结束派发，且 run 仍属当前配置的仓库和机器人时，接回原 run，不中断、不取消、不重派。基线前进或树变化仍中断重查。 |
| 同上 `capacity` / `ahead` / `needsSlot` | 准入前统计同一执行器上排名更高（`compare`：优先级 → 批次 → 进入时间）、仍需新名额的任务。GitHub：`在途派发数 + 前面仍在等的任务数 ≥ max_concurrent` 时等待（“等待更高优先级的检查先取得名额”）；SSH：前面有仍在等的任务即等待。“仍在等”指最新检查为 queued / interrupted / executor_unreachable 或已请求重查、当前 attempt 还没有派发意图、不在执行中、没有仓库锁冷却、所在项目执行器不在退避期。暂停、失败、已通过的不占位。 |
| 同上 `reservePrecheck` | 作者预检同样让位给仍在等名额的合并任务（含等互斥的）。 |
| `packages/host/src/github-check-executor.ts` | 正常接回时用日志里本 attempt 已有派发意图的键作为历史键传给 `githubDispatchIdentity`，复用其“只允许 `maxConcurrent` 不同”的证明；工作流、凭据、输入仍须完全一致。 |
| `apps/server/src/merge-batches.ts` | `merge_solo` 成批规则，见下。 |

## merge_solo 语义

- **队列模式**：只决定卡片单独成批。不改变排名，不让卡片插队，也不作废它的卡片级检查（`passedCardCheck` 在任意基线有效，别的批次先合入不影响它）。solo 卡排在队首时单独成批；排在后面时本批跳过它（它本来也不能加入），不再截断其后已通过的卡；它保留排名，除非来了更高排名的卡，否则下一批就是它。
- **非队列模式**：不起作用。每张卡独立检查、独立发布；任何一次合入都会让 main 前进，所有单卡级检查都要按新基线重跑，与是否 solo 无关。只有队列模式能避免这一点。

## 测试

`apps/server/src/merge-checks.test.ts`（C-647 开头的 7 个）：

1. 非队列重启：候选 SHA 重建但基线和树不变，同时 `maxConcurrent` 改变 → 接回原 run，不重派不取消，通过后用重建候选发布。
2. 非队列重启：树改变 → 仍中断重查。
3. 11-23 18:04 复现：两卡在途后重启且 main 前进，低优先级卡的旧 run 先结束 → 低优先级卡等待“更高优先级的检查先取得名额”，不派发；高优先级卡解除互斥后两卡都派发并通过。
4. 作者预检不抢在等互斥的合并检查的名额。
5. 队列模式：3 张卡、批大小 2，两批先后合入、main 前进两次，卡片级检查不重跑（只有最初 3 次卡片级派发），无中断、无取消。
6. 队列模式：批次检查失败按现有规则进入二分（探针只含首个成员），批外卡片的检查、状态不受影响。
7. 队列模式 merge_solo：A(4)、S(3, solo)、B(2) → 第一批 [A, B]，第二批 [S] 单独成批、基于新 main，S 的卡片级检查不重跑。

`packages/host/src/github-check-executor.test.ts`：只改 `maxConcurrent` 的重启接回原键；改工作流仍拒绝。

回退验证：分别撤掉名额保留、非队列接回、solo 跳过、执行器历史键四处改动，对应测试均失败。

## 上线（张良，合并部署后）

按卡片第 3 条：备份 `merge-gate.yaml`，打开 `github-actions.scoped_checks` 和 cardigan 的 `queue`（建议 `max_batch_size: 4`），`max_concurrent` 改回 16，用生产加载器校验，下次部署重启生效。

- 开队列那次重启：在途的单卡级（single）合并检查与新的卡片级不同级，会中断一次并按卡片级重排，属一次性切换。
- 同一次重启若有在途作者预检，`scoped_checks` 改变了派发身份，该预检接回时可能以执行器错误结束（未单独测试），作者重新预检即可。建议在没有在途预检时切换。
- 只改 `max_concurrent` 的重启不再影响在途检查。
