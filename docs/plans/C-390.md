# C-390 人专用维护命令、hc 一键升级与候选版本试跑

## 维护入口

`cardigan maintenance` 和 `cardigan hc upgrade` 只能由人在主机终端执行：命令表登记为人专用，带 Token 或 token 文件时在打开数据库前拒绝，命令模块自身也再拒绝一次。服务和 hc 目标只来自主机私有配置 `~/.config/cardigan/maintenance.yaml`（或 `CARDIGAN_CONFIG_DIR`），要求本账号所有、0600、所在目录不可被他人写，读取规则与 `self-deploy.yaml` 相同；所有命令都是以绝对路径程序开头的参数数组，不经 shell。

```yaml
wait_timeout_minutes: 30        # 等待在跑工作的超时，默认 30
poll_interval_seconds: 10
server:
  stop: [/usr/bin/systemctl, --user, stop, <监督器服务>]
  start: [/usr/bin/systemctl, --user, start, <监督器服务>]
  ports: [<web 端口>, <api 端口>]
  ready_timeout_seconds: 300
hc:
  targets:
    - id: host                  # 本机项目核心
      link: /home/<主机账号>/.local/bin/hc
      install_root: /home/<主机账号>/.local/share/cardigan-hc
      platform: linux-x86_64
      stop: [...]
      start: [...]
      core_version: [...]       # 可选：打印运行中核心的版本
    - id: agent                 # 执行账号
      via: [/usr/bin/sudo, -n, -u, <执行账号>]
      link: ...
      install_root: ...
      platform: linux-x86_64
    - id: mac                   # 已登记 worker
      machine: <机器编号>
      via: [/usr/bin/ssh, <已登记别名>]
      via_shell: true           # ssh 把参数拼成一条命令行，参数按单引号转义
      platform: macos-aarch64
      link: ...
      install_root: ...
```

### 阶段与恢复点

维护状态存于新表 `host_maintenance`（单行），每一步先落库再做下一步。闸门只把“表不存在”（旧库）视为无维护，读库出现其它错误（如数据库忙）时按有维护处理：

`draining → (drain_timeout) → stopping → stopped | operating → starting → completed`，失败走 `rolling_back → starting → rolled_back`，无法自动恢复时停在 `recovery_required`；放弃只允许在停服前（`abandoned`）。`completed / abandoned / rolled_back` 为终态，其余阶段都关闭闸门：

- 派发：server 的 Dispatcher 每轮先读闸门，打开时不投递门铃、不起新 Run（含常驻），排队工作在维护结束后照常发出。
- 检查：`deploymentInProgress` 同时看维护闸门，合并检查与作者预检和部署期间一样保持排队（提示沿用“等待主机部署结束”）。
- 自动部署：部署监督器 `tick` 在闸门打开时不部署；人工 `deploy pin` 不被改动。

维护前记录：软件版本（监督器 `state.json` 的 current SHA 与 server 进程身份）、人工部署固定、各 hc 目标的 CLI 版本。结束时核对 server ready、配置的端口全部监听、软件 SHA 与维护前一致、hc 版本（升级时等于目标版本，回退时等于原版本，人工维护时须兼容），配置了 `core_version` 的再核运行中核心版本；全部通过才把阶段写成终态并解除闸门。闸门是额外的一层，不改动人原有的暂停设置（部署固定、各指派暂停、各项目自动合并暂停），所以结束后不会把原本暂停的项无条件打开；部署固定在维护期间若被改动，结束知会里会写明。

### 等待与超时

等待对象：工作项 Run（dispatched/acked/running/unknown，unknown 也算未结束）、运行中的合并检查与作者预检、检查占用、进行中的自动部署、受管长操作。常驻 PM/host_ops 会话不等待，只列出；停 hc 会结束它们的程序，按 C-313 操作单需要的话先由人暂停。超时（默认 30 分钟，`--timeout-minutes` 或配置可改）后写 `drain_timeout`，列出未结束事项并知会人，系统不取消任何任务：

- `cardigan maintenance continue --wait` 再等一个超时；
- `cardigan maintenance continue --proceed` 不再等，接受的未结束事项写进记录；
- `cardigan maintenance abandon` 放弃，服务未停，闸门解除。

### 命令

- `maintenance begin --reason <说明> [--stop-hc a,b]`：排空后停 server 和指定 hc，停在 `stopped` 等人工操作，完成后 `maintenance end` 启动并核对。
- `maintenance run --reason <说明> [--stop-hc ...] -- <绝对路径命令> [参数]`：停服后执行命令（继承终端），成功后启动并核对；命令失败则重新启动服务并核对后记 `rolled_back`。
- `maintenance status`：阶段、原因、维护前状态、回退范围、未结束事项、错误和恢复说明。
- `maintenance continue`：中断后（例如终端被关）从记录的阶段继续，已完成的停服、切换不会重复。
- `maintenance end`：人工维护结束或 `recovery_required` 人工处理后重新启动/核对。

同一时间只允许一个维护；另一个进程正在推进同一维护时拒绝，进程退出后可由下一条命令接手。

### 回退范围（执行前写入记录并打印）

- 人工维护：只恢复本命令管理的服务启停和闸门；人工改动的回退由操作人负责。
- 指定命令：失败时重新启动服务并核对、解除闸门；命令自身的改动不自动回退，需执行前自备备份。
- hc 升级：每个已切换目标的入口恢复为维护前的软链或文件备份，重启并核对原版本；新版本目录保留。

停服阶段失败（server/hc stop 出错或端口未关）时维护操作尚未执行：重新启动已停的服务，已切换目标按维护前版本、其余目标按兼容性核对，通过记 `rolled_back`。`recovery_required` 后执行 `maintenance end` 沿用同一规则，并保留原错误，不会因人工恢复后核对通过而记成 `completed`。

任何核对失败且无法自动恢复时阶段停在 `recovery_required`，闸门保持关闭，记录写明未通过的核对、server/hc 启动命令和各目标恢复方式，并知会人；人处理后执行 `maintenance end` 重新核对，通过才放行。

### 审计与知会

每次阶段变化在 cardigan 项目写 `host_maintenance_recorded` 审计事件（人发起）；开始、等待超时、完成、放弃、失败回退、需人工恢复另写 `host_maintenance_notice` 系统事件，进入 Needs You 知会（domain 通知列表新增该类型）。

## hc upgrade

`cardigan hc upgrade --version <版本> [--target a,b]`：

1. 版本必须等于 `deploy/hc-version.json` 锁定的版本（不自动选版本，换版本先改清单并合并）。
2. 维护开始前完成所有不影响运行服务的步骤：按平台从官方版本化地址下载、核清单 SHA-256；在每个目标用随包的 `hc-target-helper.py`（经 `via` 到达执行账号或 worker）再核一次摘要，解包到 `<install_root>/<版本>/`，核 `hc --version`，已预置则跳过；核对每个目标的入口存在。`machine` 目标须是已登记且未离线的机器。任一步失败都不暂停、不停服。
3. 经维护入口排空、停 server 和配置了 stop 的目标；逐个目标先把原入口（软链目标或文件备份路径）写进恢复点，再原子替换入口为新版本软链。
4. 启动并核对（hc 版本等于新版本，ready、端口、软件版本）；失败自动按恢复点退回原入口、重启并核对原版本。
5. `maintenance continue / end` 续跑升级时，只有还会走到切换的阶段（排空、超时、停服、执行中）才重新下载和预置（幂等）；已过切换的阶段（启动核对、回退、需人工恢复）只用记录里的恢复点和目标版本，不下载、不调助手预置，外网或 worker 不可达不会挡住恢复。

不扩大账号、凭据或机器登记权限：执行账号和 worker 的访问方式（sudo、已登记的 ssh 别名）由人在私有配置里写明并已有权限。

## 候选版本试跑

`cardigan-check.yml` 新增可选输入 `hc_version`、`hc_sha256`（默认空）。主机派发检查时不传，行为不变；人手动在 GitHub 运行该工作流并填写候选版本及其 linux 归档 SHA-256 时，安装步骤改装该候选版本并照常校验摘要和 `hc --version`，随后跑完整检查。只填其中一个或格式不符时直接失败。通过试跑后，换版本仍需改 `deploy/hc-version.json` 并合并，再由人执行 `cardigan hc upgrade`。
