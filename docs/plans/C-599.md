# C-599 存量 worker 的附件助手迁移与运维待办刷新

承接 C-595 移出的部分（Q-1172、Q-1177）：已登记签名升级的存量 worker 自动补装附件助手、旧 v1 入口的迁移，以及补装命令的生成、刷新和显式检查交互。C-595 的基础分发、固定入口和 `deploy/README.md` 人工补装保持不变。

## 做法

1. **签名自动升级（已登记、v2）**
   - 发布键 `upgradeKey` 纳入两份助手的摘要：只换助手也是新键。
   - 巡检在 helper 一致、没有其他 blocker、本键未尝试过时，以 Run 账号探测助手；缺失、不一致或不可执行（探测失败、控制端发布无法核验都不算）才进入原安装流程，每个键只装一次。停派恢复中换了新键的机器同样按探测结果一并安装。探测结果分“一致 / 缺件 / 未知”：只有一致才在本进程内记住同键不再探测，未知下次巡检重探；外层观察一旦报缺件就忘掉旧的“一致”。
   - 只为助手刷新时，部署切换未完成或无法确认、机器有活跃 Run、认领后在发送前的配置核对失败，或本地签名备包被拒（`worker_upgrade_not_sent`，尚未连接 worker），都撤销认领、跳过本次、不停派；一旦连接发送，失败仍按原规则停派。
   - `installRelease` 的结果带工具条目才算 v2 已装助手；`worker_helper_upgrade_verified` 事件写 `agent_tools`：外层同一观察里助手能力通过为 `verified`，否则 `unverified`；v1 回退为 `entry_v1_needs_migration`。助手不挡派发，复查未通过不报告成功，同键不重装。
2. **v1 入口迁移**：`manual-worker-upgrade.py` 在助手和 helper 都核对一致后，把本项目已登记入口（共享入口和项目专属入口都要求 `project` 文件为 root 所有、非链接且内容是本项目）钉住的三个脚本换成本次已核验发行版的字节（root 0400、独占新建再原子替换、写后复核）；密钥、账号、sudo 规则和防重放状态不动。之后签名升级走 v2。
3. **主机运维待办**（`agent-tools-maintenance.ts`）：观察记录后，若 helper 一致而助手缺失/不一致——
   - 已登记且本键尚未自动尝试：结论 `automatic`，不发命令，等巡检；升级停派中：`held`，按升级待办处理。
   - 已登记且本键已尝试（v1 或复查未通过），或未登记签名升级：暂存当前完整发行材料（`stageWorkerUpgrade`，同 helper 人工升级），按“机器 + 绑定指纹 + 助手摘要 + 暂存命令全文”生成键 `worker-agent-tools:<机器>:<sha256>`，发一条待办；暂存失败时键里命令为空、待办无命令。
   - 新键写入前，系统用领域命令 `retireWorkerMaintenanceActions` 取消同机器该命名空间下其他打开的待办（不记完成）；助手已一致、发行材料或绑定无法核验、本次机器检查未通过（含新发行 helper 不一致、离线、换绑）、或刷新本身出错时全部取消。所以暂存失败后重试成功、换包、换绑都只剩当前一条，新发行只留 helper 升级待办。
   - 暂存后重新核对绑定和登记状态：期间换绑或完成签名登记，本次不发命令并淘汰旧待办。
   - 观察结论（状态、待办编号、键，不含命令）写进本次 machine check 记录（巡检、CLI、Web 发起、后台 helper 恢复复核都写），供加入同一次检查的调用方读取。
   - Needs You 按系统请求事件识别这类待办（`workerAgentToolsAction`）：只在待办命令与当前绑定、当前发行版生成的命令逐字一致时展示原命令，否则隐藏并提示不可用；PM 交接不能改写其命令；当前绑定变化会改变 Needs You 版本号。
4. **显式检查**：`checkRegisteredMachine` 在 `cli` 来源下（独立运行或加入正在进行的巡检）输出 `agent_tools_guidance`。`ready` 时用当前绑定重新生成命令，键与本次观察一致、待办仍打开且命令逐字相同才附命令；否则 `changed`，只给原因和重跑提示。巡检、Web、`machine show` 和检查历史都不含命令。

## 测试

- `packages/domain/src/commands/deployment.contract.test.ts`：只有 system 能淘汰；只限 `worker-agent-tools:<机器>:` 命名空间，不碰其他机器、helper 待办；保留当前键；重复调用无事件；淘汰后同键再来是新待办。
- `packages/host/src/worker-auto-upgrade.test.ts`（C-599 用例）：Linux/macOS 已登记 v2 仅缺助手时装一次并记 `verified`，同键不再探测或安装；v2 复查未通过记 `unverified`、v1 回退记 `entry_v1_needs_migration`，均不停派、不重装并发带命令的待办；无法开始时不停派；认领后失败停派且不发助手命令；未登记机器暂存失败→重试成功→换包→换绑→无法核验→恢复一致的待办刷新与淘汰，历史与检查记录不含命令；已登记未尝试时显式检查不发命令；任一检查未通过即淘汰助手待办、新发行只留 helper 待办；停派恢复换新键时一并安装；发送前失败不停派；一致时同键只探测一次；独立与加入巡检的显式检查得到同一核验命令，检查后换绑则不给命令。
- `packages/host/test-support/worker-upgrade.py`：v1 入口迁移只换本项目入口的三个脚本、权限 0400；项目专属入口写着别的项目时不改、不报迁移；`project` 为链接或目录不安全时拒绝。
- 第二轮（V-3001 及独立复核意见）补测：探测未知不记住、外层报缺件忘掉旧“一致”；本地备包被拒不停派（helper 升级仍停派）；暂存中换绑、暂存中完成登记；`apps/server/src/web/machines.test.ts` Needs You 只显示当前命令、交接不能替换、换绑改版本号；`machine-checks.test.ts` Web 发起与后台恢复复核都保存结论；领域测试识别与改写拒绝。

## 未覆盖

- 未在真实 Linux/macOS worker 上执行签名升级、v1 迁移或补装命令；macOS 仅为同一代码路径的隔离测试。
- 自动安装复查依赖同一次观察的能力探测；若外层观察中断，按原规则停派，由原升级待办恢复。
- 助手不一致期间，每次检查都会对需人工处理的机器重新暂存发行材料（与 helper 人工升级相同），以保证命令对应的暂存文件仍在。
- 同一键的待办文字不随“缺失/不一致”变化而改写；结论以 machine check 输出和审计事件为准。
