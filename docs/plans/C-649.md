# C-649 命令状态热数据集第二阶段

范围按 Q-1292（PM 选 `card_whitelist`）：

- 关闭卡白名单按卡级实现：被引用的关闭卡（C-639 的活跃集）保留整条流；
- 其余关闭卡在去掉遥测之外，再去掉 GitHub 检查分发记录；
- 系统流按类型保留；
- 新行为放在新开关 `lean` 下，默认仍为 `hot`。

“冷卡只留少数几类事实”需要先迁移十几处跨卡读取方，已拆到 C-671。

本卡在合入 C-643（遥测移出命令状态事件流）后的基线上完成，与它的衔接见第 4 节。

## 1. 热路径全表扫描改走事件日志索引（不改语义）

剖析合成库（3 个项目 × 30 万事件，98% 已关闭）时发现：每来一个新快照，下面这些函数都要把整份历史扫一遍，或者每张卡扫一遍。

| 位置 | 原做法 | 现做法 |
|---|---|---|
| `decision-followup.ts` 拍板跟进索引 | 每个快照扫全部事件建 4 个索引 | 从类型索引取 `decision_followup_due`、`decision_resolved` 和进展类型；评论证据按（卡，seq）查 |
| `system-rules.ts` `systemRuleAttention` | 扫全部事件，每条再扫一遍找 `system_wait_closed` | 只取 3 个类型；关闭记录取一次 |
| `provider-start.ts` 供应商熔断 | 扫全部事件 | 只取 2 个类型 |
| `standing-deployment.ts` 部署审计版本 | 每个角色、每轮 `events.find` | 从类型索引取 `host_role_upgraded` |
| `precheck.ts` 预检投影、冲突处理、等待处理 | 全量 filter，或每张卡 `findLast` / `some` | 只取相关类型 |
| `verification-activity.ts` 审核活动 | 每个验证项 `events.find` | 从类型索引取 |
| `review-convergence.ts` 驳回连续段 | 每次把全部事件复制后排序 | 只复制 `review_submitted` 后排序 |
| `merge-batch.ts` 批次、等待、延后 | 全量 filter 或 `findLast` | 批次只读项目流，其余按卡、按类型取 |
| `merge-check-view.ts`、`merge-check-blockers.ts`、`merge-observation.ts` | 全量扫 | 只取相关类型 |

为此 `event-index.ts` 新增三个查找，Store 日志视图上都有索引实现；普通数组按 C-643 的语义，在完整历史（含遥测旁路日志）上过滤：

- `eventsOfTypes(events, types)`：几种类型的事件，按历史顺序排列；
- `streamEvents(events, card)`：一条流；
- `eventsAtSeq(events, card, seq)`：一条流里某个 seq 上的事件。

“按类型子序列做稳定排序”与“先对整体排序再过滤”结果相同。用这个性质的地方都在注释里写明。

## 2. 首次装载流式解码，重启后分段预热

- `command-events.ts`：项目第一次读取时逐行解码，直接追加进新日志，不再先 `all()` 成数组、再按流复制排序。只有出现 seq 倒退时才退回原来的重建。重启后堆峰值下降，RSS 随之下降。
- `Store.warmCommandEvents(project, rows)`：在一个短读事务里最多解码 `rows` 行（默认 5 万），已追上最新行时返回 true。
- `apps/server/src/warm-command-events.ts`：启动后对每个项目分段预热，段与段之间让出主线程。后台循环等预热完成再开始第一轮；Web 不等待，请求先到时由它解码剩余部分。
- 派发器第一次处理某个项目时，先在单独的读事务里预热事件并构建状态，让出一次后再进入写事务。这样重启后的第一个写事务不会把解码和规则计算叠成一次长停顿。

## 3. `lean` 开关

`CARDIGAN_COMMAND_STATE=hot|lean|full`，或 `Store.open({ commandState })`：

- 默认 `hot`，行为与 C-639 相同；
- `full` 为全量；
- 其它值启动时报错。

`lean` 在 `hot` 的基础上增加下面三项。纯函数定义是 `leanCommandEvents(full, extra, protect)`，Store 装载结果必须与它逐条一致。

### 3.1 卡级白名单

- 活跃集规则沿用 C-639 的 `hotCardIds`：未关闭卡、前置卡、父卡、来源拍板卡、活跃指派、未结束 Run 及其触发卡、open 待办和拍板、未结通知、命令目标卡。
- 新增一类：被 `github_run_completed` 等待指向的 GitHub run，其分发记录所在的卡。
  - 由 `waitedGithubRuns(work_items)` 和 `githubRunCards(dispatches, runIds)` 从完整日志的类型索引查出。
- 命令参数里出现像 GitHub run id 的值（例如 `resume_when.target_id`）时，对应的卡同样按命令目标保留整条流。由 `commandRunIds` 查出。

### 3.2 冷卡去掉的类型

`LEAN_COLD_CARD_OMITTED_EVENT_TYPES` 是 C-639 的 8 类遥测，加上 `github_check_dispatch` 和 `github_probe_dispatch`。分发记录在命令状态里只有下面两个读取方，它们要的卡都已按 3.1 保留：

- `work-waits.ts` 的等待目标；
- 等待条件校验。

GitHub 分发日志本身读的是 Store 原始流，不受影响。

### 3.3 系统流按类型保留（`PROJECT_STREAM_RETENTION`）

没列出的类型一律全量保留，包括：

- 合并推送、批次；
- 主机运维；
- 偏好和委托授权；
- 部署；
- 常驻 Run 生命周期。

| 类型 | 规则 | 依据 |
|---|---|---|
| `assignment_branch_backed_up` | 按键只留最新一条，键为（actor 类型，actor 项目，payload 是否数组，assignment_id，machine_id，branch） | 唯一读取方 `worker-backup.ts` 按这些字段取最后一条；键里包含谓词用到的全部字段，所以任何查询的 `findLast` 结果不变 |
| `cross_card_read` | 不装 | 审计读取走 `listAfter`（`support-tools.ts`），项目动态走 SQL；命令状态里没有读取方；payload 不含被索引的字段 |

始终保留的事件：

- 未结束 Run 的触发事件；
- 未结通知的主题事件，由主机提示 `liveNotificationEvents` 查出。

被去掉的事件 id 集合在输入不变时复用同一个对象，所以历史和索引答案在视图之间可以共用；集合变了，缓存键也会变。

## 4. 与 C-643 的衔接

C-643 把遥测移出了 `state.events`，挂在旁路日志里；索引查找仍按完整历史回答。本卡的过滤同样作用到它的三个分区：

- `commandHistory`（业务）；
- `telemetryHistory`（遥测）；
- `history`（完整）。

项目流按 id 去掉事件，会同时作用到这三份。因为分支备份、分发记录都是遥测，所以 `lean` 的效果只体现在旁路日志和完整历史里；业务事件流在 `hot` 和 `lean` 下相同（合成库每项目约 16.6 万条）。

### 后台（`background`，30 s）

有两种口径：

- **首次**：在新生成的库上第一次启动。合成数据在第一轮会补写大量收尾事件。
- **重启**：在同一个库上第二次启动，接近生产重启。

“最长停顿”是事件循环延迟直方图的最大值。

| 指标 | 开工前 hot | 合入后 full | 合入后 hot | 合入后 lean |
|---|---|---|---|---|
| 空闲 CPU（首次 / 重启） | 25.3% / — | 11.8% / 7.3% | 11.3% / 7.1% | 10.4% / 9.0% |
| tick p95（首次 / 重启） | 1018 ms / — | 530 / 69 ms | 538 / 57 ms | 669 / 100 ms |
| 恢复时间（首次 / 重启） | 7.7 s / — | 7.9 / 6.1 s | 7.9 / 7.1 s | 9.5 / 7.3 s |
| 预热期最长停顿（首次 / 重启） | 7.5 s（按 tick 计）/ — | 607 / 392 ms | 786 / 562 ms | 1219 / 446 ms |
| 稳态最长停顿（首次 / 重启） | — | 198 / 26 ms | 168 / 21 ms | 172 / 54 ms |
| RSS（首次 / 重启） | 1108 MB / — | 718 / 706 MB | 744 / 714 MB | 860 / 714 MB |

验收线对照：

- 空闲 CPU < 20%：三种模式都满足。
- RSS < 1 GB：三种模式都满足。
- 重启 30 s 内恢复、无超过 2 s 的停顿：三种模式都满足。

### 怎样归因

- 首次装载流式解码以前，3 个项目装载后的 RSS 约 930 MB；改为流式解码后约 580 MB，堆用量不变。原因是 V8 在装载峰值后不会及时归还内存页。
- 本卡在合入 C-643 之前，hot 模式已经降到：
  - list_needs_you p95 25 ms，project_snapshot p95 52 ms；
  - 后台空闲 CPU 7–12%，RSS 约 680 MB；
  - 重启最长停顿 318 ms。
- 合入 C-643 后，遥测不再进入业务事件流，full 模式也一起变快。
- `lean` 在合成库上没有额外收益：业务事件流两者相同，旁路日志只少了冷卡的分发记录（每项目 20.7 万 → 17.8 万）。它的收益要看生产库里分发记录和分支备份的占比。

## 7. 已知风险与后续

- `lean` 默认关闭。在生产只读副本上回放 `shadow <副本> lean` 一致后再切换；有差异时保持 `hot`，或设 `full` 回退。
- 生产库里分发记录和分支备份的实际占比，以回放输出的事件数为准；合成库里系统流没有这两类事件，`lean` 只体现在冷卡分发记录上。
- “冷卡只留少数事实类型”拆到 C-671（低优先级）。
- `packages/host/src/macos-check-workflow.test.ts` 有一个用例在本机失败：它在临时目录里执行 `git rev-parse HEAD` 失败。该用例和相关工作流文件本卡都没有改动，以远程预检为准。
