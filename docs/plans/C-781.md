# C-781 卡级检查沿用同一提交已通过的作者预检

依据：11-26 架构调研 3-autonomous-flow.md #2；ADR 0004 §1、§2；开发方案 §4.5 不变量 14、21、23。

## 改动

| 位置 | 改动 |

## 沿用条件（domain 在记录事务内逐条重算）

1. 项目启用合并闸门且启用合并队列。未启用队列时单卡检查（`level=single`）是合并依据（不变量 21(a)），一律不沿用。
2. 卡片流程版本 ≥3，未暂停。
3. 卡上只有一个未取消的产出项，合并计划里也只有一份 Git 交付。多产出项的卡不沿用。
4. 当前完成申请还没有任何卡级结果：曾经 passed／failed／timed_out，或被请求过重查，都走真实检查；只有“从未出结果”（queued／running／interrupted／executor_unreachable）才可沿用。失败后的重查不会被沿用短路。
5. 存在 system 记录的 `precheck_finished`：同卡、同产出项、`head_sha` 等于交付提交，`status=passed`，候选／树／基线身份齐全，全部步骤 passed 且退出码 0，并包含主机配置里卡级要跑的每一项检查（按名称）。

主机只提供卡级检查名称（`requestChecks(..., "card")` 去掉 `card_tier` 跳过的 e2e），不提供 SHA、结论或路径。

## 记录形态（不变量 14）

- 一条 system 的 `merge_check_finished`：`level=card`、`status=passed`，`reused_precheck` 写明沿用的预检 attempt、产出项、head、产出交付；候选、树、基线照抄预检自身的值（如实记录实际检查过的东西），逐项结果照抄预检。
- 没有 `merge_check_queued`／`started`，没有 `executor`、`external_run`：预检的 GitHub 运行不会被改绑成卡级检查运行（C-328 精确运行名只对本 attempt 自己的派发成立）。之后对这个 attempt 写 queued／running 会被拒绝。
- 时间线：“合并检查 passed：沿用作者预检 X（提交 S）的通过结果，未重复执行；日志：get_check_log(…预检 attempt…)”。卡级 attempt 的日志只有一行指引，指向预检日志。

## 不变的部分

- 卡级通过（含沿用）仍不能作为 merged 依据；批次检查（全量含 e2e，绑定批次全部完成申请）仍是唯一合并依据（不变量 21(b)）。
- PM 代确认、`auto` 卡视同确认的前置仍是“当前完成申请的卡级检查通过”（不变量 23），沿用记录与真实卡级通过同等对待。
- 代码审核、独立复核不减少。

## 主机配置（张良，合并部署后；本卡不写生产配置）

在 cardigan 的 `merge-gate.yaml` 里给检查条目补齐范围配置（`p2a-13-merge-queue.md` 第 336 行、`scoped-checks-flow5.md` 原定，但生产一直没配）：

```yaml
projects:
  cardigan:
    checks:
      # 其余条目不变
      - name: test
        run: …            # 原值不变
        scope: affected
        skip_docs_only: true
      - name: e2e
        run: …            # 原值不变
        skip_docs_only: true
    queue:
      enabled: true       # 原值不变
      # reuse_precheck: false   # 需要临时关闭沿用时才写；缺省即开启
```

- `affected.extra_dependents` 保留生产现有值，并至少包含 `scoped-checks-flow5.md` 列出的 `apps/web: [apps/server, packages/store]`、`apps/server: [apps/web]`。
- 加了 `scope: affected` 后，卡级 test 只跑受影响包；预检和批次检查不读 `scope`，仍然全量（预检不传缩小参数，批次固定 full），所以“预检 ⊇ 卡级”不被破坏。
- 改完用生产加载器校验再重启。改 `checks` 后在途检查能否全部接回没有单独验证，建议在没有在途检查时切换。

## 风险

- 11-23 以来卡级失败 9 次。沿用后，这类“预检通过、卡级失败”的问题改在批次阶段由同一套全量步骤拦住：批次失败按 ADR 0004 原规则重跑确认、二分定位、退回作者，不会合入。批次检查覆盖卡级全部步骤（还多 e2e），且在更新的基线上跑。代价是此类失败晚一轮暴露，并可能拖累同批其它卡（批次上限 4，二分处理）。
- 预检在旧基线上通过、当前基线上卡级本该失败的情形（基线语义冲突）：与 ADR 0004 §1“基线前进后不重跑”的既有取舍一致，由批次检查兜底。
- 可用 `queue.reuse_precheck: false` 随时关掉，不需要发版。
