# C-688 卡片详情加载提速与服务端减负

作者：赵云。基线 `471d4d742083c5f0860cb75e89fd54940ef17f9f`。只改数据加载和服务端开销，不改详情页布局与交互（C-687 负责）。

## 改前在做什么（热点）

- 每次打开详情（抽屉和整页都发同一个首屏请求 `?limit=20&section=overview`），`scopedCardState` 用 `OR` 和数组成员条件查拍板、人工待办、Assignment、附件。这四条 SQL 无法按卡走索引，只能把整个项目这四张表的文档逐行 `json_extract` 一遍。合成库上它们占首屏 CPU 剖析的约 80%（`all ← readDocs`），且耗时随项目总量和文档大小增长，与卡片大小无关——所以小卡也要 6–7ms，生产文档更大时更慢。
- 故事卡读子卡时同样扫整张 cards 表。
- 抽屉里的详情跟随整个项目的修订号：项目里任何一张卡有事件（100ms 合并一次），打开着的抽屉就重读一次首屏，加上当前标签页再读一次。整页已经只跟随本卡及相关卡。
- 重读一律返回完整 JSON，没有条件请求；响应不压缩。

## 改动

1. **按卡取数，不再整表扫描**（`apps/server/src/web/sql-state.ts`、`timeline-state.ts`）：拍板、人工待办、Assignment、附件、故事子卡改为在当前读事务的集合缓存上按卡/工作项过滤。集合缓存是 C-131 的 Store 快照：按表修订失效，只重新解码变更行，读 worker 常驻。旧附件（没有 `card_id`）先在缓存里挑出，再用 `timeline` 主键 + 卡号确认归属。结果的行与顺序与原 SQL 相同（同一索引顺序）。
2. **条件请求与压缩**（`card-detail-cache.ts`、`read-ops.ts`、`server.ts`）：详情响应带弱 ETag，按请求（项目、卡、规范化查询、合并闸门状态）与去掉 `now` 戳之后的内容计算；`If-None-Match` 命中返回 304、无正文。会话校验仍在比较之前。同一请求在“任何项目都没有实体写入（含回滚；铃声投递记录除外，详情不读它）且不超过 5 秒”时直接复用上次结果，不再计算；5 秒与卡片列表缓存的上限一致，用来约束版本之外的输入（时钟、项目表）。客户端接受 gzip 时，大于 1KB 的正文压缩一次并随缓存复用。
3. **打开着的详情不再跟着全项目重读**（`CardListPage.tsx`、`App.tsx`）：抽屉改用与整页相同的按卡修订号（本卡、拍板涉及卡、依赖卡、引用附件所在卡、项目级事件、重连）。
4. **客户端条件请求**（`api.ts`、`CardDetailPage.tsx`）：详情和标签页读取记住每个 URL 的 ETag 与已整形的结果，重读时带 `If-None-Match`；304 直接交回同一个对象。首屏 304 时保留已加载的较早时间线页，不再合并。退出、401/403、换会话时清掉。
5. 首屏内容不变：标题、状态、等谁、主操作、概览、本卡拍板和最近一页（20 条）时间线；工作项、交付与审核、附件按标签页读取，较早时间线按游标分页（C-507 已有，本卡未改契约）。

依赖合并队列的卡（`awaiting_merge`）仍需全项目合并队列排位：它用 Store 的项目状态缓存（按修订失效），不再重放事件日志；但每次写入后会重建一次状态，见“剩余”。

## 测量方法

`apps/server/benchmarks/card-detail.mjs`：同一脚本分别跑基线树和本次树，`cards` 合成档位（421 卡、11 万事件、2.7 万时间线、4200 附件、800 拍板），开启合并队列与合并闸门。小卡 C-2（1 条时间线）、中卡 C-40（68 条时间线、11 个附件，对应 sensen C-48）、大卡 C-3（300 条、12 个附件，对应 sensen C-43）、待合并卡 C-20。每行 40 次串行读取，每次读取前做一次无关的 Run 写入（模拟后台持续写入，使所有版本变化、缓存不能命中），去掉首样本后取 p50/p95；CPU 为 `process.cpuUsage` 差值；“最长阻塞”为 `monitorEventLoopDelay` 最大值（读取是同步的，等于单次读取阻塞时间）。耗时包含读取、组装和 JSON 序列化，不含网络与浏览器渲染。Node v24.22.1，本机合成数据；未读取生产库，也未人为制造负载。

```sh
pnpm exec tsc -b apps/server
pnpm fixture:generate --profile cards --out <新目录>
node apps/server/benchmarks/card-detail.mjs <源码树> <夹具目录> <输出前缀> 40
```

- 请求数：打开抽屉或整页都是 1 次首屏请求，切到其他标签页各 1 次，较早时间线按页 1 次。打开期间：改前抽屉每个“项目里任意卡有事件”的 100ms 批次重读首屏和当前标签页；改后抽屉与整页一样只在本卡或相关卡变化、项目级事件、重连时重读，并且都是条件请求。
- 全部 421 张卡 × 6 种请求 × 闸门开/关（以及开启合并队列、1/3 附件改为旧格式两种变体）共 3780×3 个响应，与基线逐字节相同（固定 `now`）。

## CPU 剖析（大卡首屏，后台写入间隔，40 次）

改前（`all ← readDocs` 即上面四条整表 SQL）：

| 自身耗时函数 | 位置 | 占比 |
|---|---|---:|
| all ← readDocs | `apps/server/dist/web/sql-state.js:3` | 79.7% |
| prepare ← readDocs | `apps/server/dist/web/sql-state.js:3` | 2.4% |
| all ← (anonymous) | `apps/server/dist/web/timeline-state.js:21` | 2.0% |
| (anonymous) | `apps/server/dist/web/sql-state.js:7` | 1.9% |
| exec ← #writeAndCommit（模拟后台写入） | `packages/store/dist/store.js:461` | 1.3% |

改后没有单一热点：按卡 SQL（约 19%）、JSON 解析、`scopedCardState` 组装、ETag 计算各占 3–10%；占比是各自剖析内的比例，不能跨剖析比较绝对时间。原始 `.cpuprofile` 和 JSON 随交付附件。

## 防回退

- `apps/server/src/web/card-detail-load.test.ts`（随 `pnpm test` 在 CI 运行）：在 `small` 合成夹具上对各状态卡与故事卡的六种请求，各读一遍后插入一次后台写入再读，对执行过的每条语句做 `EXPLAIN QUERY PLAN`，不允许出现对文档表的整表 `SCAN` 或只按 `project_id` 的范围查找（集合缓存自身的增量维护除外）。把 `sql-state.ts` 换回基线时，该测试列出拍板、人工待办、Assignment、附件四条语句并失败。
- 同文件覆盖 ETag/304（弱比较、列表、未登录先 401、各请求各自的验证器、无关写入后仍 304、本卡变化后 200）、gzip、缓存过期与写入失效、条目上限。
- Web：`card-detail-revalidate.test.ts`（带 `If-None-Match`、304 返回同一对象、换会话清空、拿不到验证器时完整重读）、`CardListPage.test.tsx`（抽屉只跟随本卡）、`CardTimelinePaging.test.tsx`（首屏 304 保留已加载的较早页、不重复请求）。

## 剩余

- 待合并卡的排位仍需全项目合并队列：每次写入后重建一次项目状态（合成库约 5ms；主要是变化集合的顺序扫描）。按卡只取排位需要改合并队列计算，本卡不动。
- 数字来自合成库；生产（sensen C-43/C-48、cardigan 最长时间线的卡）的前后对比与 `cardigan cpu-profile` 剖析需合入部署后在主机上采集。
- 首屏仍带最近一页时间线；C-687 定下新布局后，若时间线不在首屏，可再把它挪到按需读取。
