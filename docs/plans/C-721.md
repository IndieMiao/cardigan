# C-721 资源名额按 Run 计算：只做提交/回帖的 follow-up 不被 godot/模拟器名额挡住

来源：C-716 拆卡（Q-1341 选 split）。现象是 sensen C-98 R-2240 只为提交完成申请的 follow-up Run 也按工作项要求占 godot + android.emulator 名额，被两个录屏 Run 挡了 50 多分钟。

## 哪些 Run 不占资源（轻量）

`runResourceKeys`（`packages/host/src/run-resources.ts`）在原来的“工作项 + 角色要求”之外再看 Run 本身。同时满足以下条件才返回空集合，否则仍返回工作项的全部资源：

- 指派是工作项范围的**产出项**（审核、验收等验证项的 follow-up 仍占，审核员要在设备上核对）；
- Run 类型是 `followup`（`initial`、`rework`、`fix`、`decision_resumed` 一律占）；
- 触发事件和本次铃声要带的每一条待读通知都是轻量的；通知类型只能是 `comment`、`completion`、`instruction`，事件必须在已加载的历史里且属于本卡：
  - `comment_posted`：回帖；
  - `review_submitted` / `completion_reviewed`：`verdict=pass`，且没有必改项、不要求返工或复核、没有待补证据、不是并行迟到或等待额度；
  - `delivery_accepted`：交付被接受；
  - 上面两类如果审的是本工作项所依赖的上游工作项（依赖满足后唤醒下游开工），不算轻量；
  - `precheck_finished`：系统发出、`status=passed`、正是本指派和本工作项的作者预检。
- 其它都占：PM 指令（`instruction_issued`）、阻塞恢复（`work_item_resume_requested`）、拍板恢复、驳回、条件通过、合并冲突等。

同一铃声里只要有一条重通知，整个 Run 就按工作项占资源。

## 计算位置

都用同一个函数和同一组“本次可投递通知”（新抽出的 `readyNotes`，与 claim 中原来的过滤完全一致），保证前后一致：

- 派发准入（`claim`）：`resource_keys` 记录本 Run 实际占的键，资源名额、项目资源上限、租约核验都用它；轻量 Run 写入 `resource_keys: []`，名额统计和启动前核验（`startBlocked`、`canPublish`）本来就读 `resource_keys`，不再占名额。
- claim 之前的租约核验（`leases.inspect`）：改为传入同样算出的键，签名与 claim 内一致，不再误报“资源需求已变化”。
- 提前跳过（远程 IO 前的 `availableResources`）：同样用本 Run 的键。
- 前序等待者判断（`hasEarlierCapacityWait`）：新增 `keysFor`，派发器按等待者自己的 Run（触发事件 + 该指派的待读通知）算键，`waitingElsewhere` 与项目上限判断也用这组键；默认（人工 launch 等调用方）仍按工作项算，偏保守。
- 排队巡检诊断（C-714 `capacityBlock`）：只报本 Run 自己要占的资源（按该指派未确认的待读通知算）。
- 人工 `cardigan launch` 路径不变，仍按工作项占资源。

## 隔离

- 轻量 Run 不领 adb 槽位：有 adb 槽位配置的机器上，启动时 `adb_slot` 为 null，环境里 `ADB_SERVER_SOCKET` 指向 `/dev/null`、`ANDROID_SERIAL=cardigan-unassigned`，连不上任何 adb 服务，碰不到持有槽位的录屏 Run 的模拟器；有静态实体绑定的机器上 `resource_bindings` 为空，同样不能操作设备。
- 只按数量计名额、没有槽位和绑定的机器上，轻量 Run 启动时也给空的 `resource_bindings`（`unclaimedResourceKeys` 非空即给），效果同上，并带“没有分配则不得操作设备”的说明。
- 会话不混用：本次 Run 或会话里上一个 Run 少占了工作项资源时，一律换新会话（与 adb 机器原有的 `freshSession` 走同一条替换路径）。轻量 Run 不会继承别的 Run 留下的设备环境，之后按工作项占用的 Run 也不会继承轻量 Run 被封住的环境。
- 少占资源的 Run 每次铃声（包括运行中继续收到的通知）末尾都加一句：本次未占用哪些名额、不要启动或操作；需要它们的工作（包括新收到的通知）用 `report_blocker` 说明并结束本次 Run，恢复后的 Run 属于阻塞恢复，按工作项占名额。运行中的轻量 Run 仍照常接收通知，不扣住通知，避免会话空闲但 Run 未结束时通知一直卡住；需要资源的工作因此走被拒绝、再由恢复 Run 取得名额的路径。
- godot 没有实体隔离（原来也只是计数），靠上面这句约束。

## 不做

不改名额数量、项目上限、C-716 的选机排序与换机，不加门禁，不新增数据库字段或迁移。

## 测试

- `packages/host/src/run-resources.test.ts`：轻量与非轻量判定（各类触发、Run 类型、依赖唤醒、审核员、混合通知、缺事件）；adb 槽位已被录屏 Run 占用时，轻量 Run 核验签名一致、拿不到槽位（启动环境为 null）、需要换新会话，按工作项占用的 Run 未取得槽位时被拒绝启动。
- `apps/server/src/dispatch.test.ts`：godot/模拟器名额占满时，回帖 Run 换新会话直接派发且不占名额；指令、回帖 + 指令、`rework`/`fix`/`decision_resumed` 排队，名额释放后按工作项占用派发；运行中的轻量 Run 收到的每条铃声都带未占名额说明，之后的指令 Run 排队并在新会话里按工作项占用；另一项目预约 godot 时，轻量 Run 按空集合核验并派发。
- 原来用评论触发资源排队的测试改用 PM 指令触发（评论现在属于轻量）。
