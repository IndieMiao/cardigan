# C-546：恢复已结束 Run 的门铃投递

区分两种仍需等终端空闲的情形：向正在执行的 Run 续送；在同一会话中，上一轮由系统代结束，CLI 未必已退出该轮。只有这两种首发继续以 `idle` / `done` 为条件，并在写入前再核对。作者主动 `finish_run` 后的新业务唤醒沿用既有目标、权限、容量和回执检查，不因终端残留状态而滞留。补送不是新业务唤醒，不放宽。

守卫首次拒绝时记录原因、Run、指派、通知与终端状态。复用派发确认窗口（默认 10 分钟）；超时持久移交主机运维，没有可用运维则沿用派发告警收件人。既不强停旧进程，也不替换工作区。用持久化回归测试覆盖主动阻塞、预检恢复、续送、系统代结束与超时交接。

## V-2649 返工：首铃、旧铃与移交后的退役

- 已完成 Run 上的未读提醒继续绑定原 Run，观测和实际写入均须空闲；工作中不打扰、不计为投递。没有可观测会话时不为旧铃启动新会话。对照 C-503：seq 242 给 A-1780 的通知 5 次都指向已完成的 R-9544，没有新 Run；seq 323 最终以 `ack_retry_limit` 记为 `bell_retry_exhausted`，并非无限重投。PM Office 的外接收件行是另一条通知。回执时间及未生效的原因未核。
- 在同一事务保存「发送槽确认未写入」和首次等待事件，不等下一次重试。共享审核返工保留普通失败退避和额度，只取回原触发事件给该指派的通知；超时移交原通知，而不再发空铃。
- 运维移交阻止继续投递，不阻止目标被替代后的退出确认和取消。即使发送槽在写入回调前就拒绝，仍保存该次返工绑定的交付编号和 SHA；不当作已送达，不派后继 Run。

### V-2656 返工：恢复时首次探测已忙

共享返工暂停时可以撤回首发，此时没有已结算的发送尝试。恢复后若首次探测就看到终端忙碌，以这次拒绝作为原通知的等待起点，不等发送槽产生回执。只对能证明尚未写入的补送走这条路径；送达不确定的仍按原确认窗口处理。测试在每次探测前重新打开 SQLite，核对十分钟边界、原通知的发送次数，以及移交后不再补送。
