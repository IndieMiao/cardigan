# C-815 安卓设备任一：模拟器和真机哪个空闲派哪个

来源：C-813#7 所有者追加需求（用平板分担模拟器排队），C-813#21 拆卡。建在 C-813 的通用设备资源框架上。接入和使用说明见 [接入一台安卓真机](../android-device.md) 的“安卓设备任一”一节。

## 能力

- domain `capability-alternatives.ts`：多选一能力 `CAPABILITY_ALTERNATIVES`，目前只有 `android.any` → `[android.emulator, android.device]`（顺序即都空闲时的偏好）。纯规则：机器具备哪些多选一能力、可能占用的全部选项、未选定的多选一、选定规则。
- 机器检查：任一选项验证通过（模拟器工具已验证，或有可用 / 被持有的真机）就登记 `android.any`（无版本，证据指向本次检查）。私有能力目录不能自定义 `android.any`。
- 选机沿用能力匹配，`android.any` 和其它能力一样。

## 派发

- 选定（host `resolveResourceAlternatives`）：对未选定的 `android.any`，按顺序看每个选项：本机当前检查验证过、资源名额和项目额度有空、机器租约（设备租约、adb 槽位、预约）不挡，就是“空闲”；只验证过是“具备”。取第一个空闲的；都不空闲取第一个具备的（排队等它）；都不具备取第一个。
- Run 的 `resource_keys` 记 `android.any` 加选中的选项，所以名额计数、adb 槽位、设备租约、启动环境、释放都按选项走，和直接要求那一类完全相同。
- 调用点：调度器 `runClaim`（检查前的 `admissionKeys`、领取事务内、排在前面的等待者 `waiterKeys`）、主机启动 `launchWithClaim`（检查前、领取事务内、等待者），排队诊断 `queued-run-patrol`。同样的状态得到同样的选择，检查签名与领取一致；状态变化时按既有规则“资源需求已变化”等下一轮。
- 排队中的 Run 每次派发重新选，哪个先空出来用哪个。
- 已写了选项（`android.any` + `android.emulator`，或带编号 / 型号的真机）的不再选；只写 `android.emulator` 或 `android.device` 的工作项不受影响。
- `adbNeeded` / `freshSession`、空闲稀缺会话巡检按“可能占用的全部选项”判断。

## 默认要求

- 默认 PM 角色规则：tester 和取证类工作项需要安卓设备时机器需求默认写 `android.any`；只有明确需要模拟器（快照、冷启动、指定手机分辨率）写 `android.emulator`，明确需要真机写 `android.device`；已写具体类型的不改。
- 默认 tester 角色规则：要求 `android.any` 时看 `ANDROID_SERIAL` 判断分到哪类；需要快照、冷启动、手机分辨率却分到真机时不拿真机结果替代。
- 已有项目自定义角色或模板里写死的 `android.emulator` 不自动改写（属于“写了具体类型”），由该项目 PM 按规则调整。

## 能力说明

- domain `BUILTIN_CAPABILITY_NOTES`：`android.any`、`android.device` 的内置说明，写清真机与模拟器的差异和目前接入的平板参数（HarmonyOS 4.2 / Android 12 / API 31、arm64-v8a、1600x2560、400dpi、没有快照）。
- 只在按能力键读取时生效（启动提示、`get_capability_guide` 指定能力）；项目登记了自己的主说明就用项目的，机器补充照常追加；索引只列项目登记的。`android.emulator` 没有内置说明，只要求模拟器的工作项提示不变。

## 已知未覆盖

- 都空闲时先用模拟器是代码常量，没有按机器配置偏好。
- 现场验证（mac-mini 上 `android.any` 工作项在模拟器满时拿到平板）是合并后跟进，依赖 C-813 的上线配置。
