# C-773 重启后在途的 GitHub 作者预检丢失跟踪

## 根因

作者预检在 server 重启后由 `AuthorPrechecks.execute()` 每轮重新走一遍。对已经绑定 GitHub run 的 attempt，它仍要先通过新派发才需要的全部准入：读分支 HEAD（仓库锁超时就跳过）、GitHub 名额、`reserve()` 预留检查槽位（合并任务在等槽位、执行器容量不可用时返回空）、`acquireMergeCheckCapacity`（部署等待或维护窗口时抛 `DeploymentInProgress`）。这些分支都只是“本轮跳过，下轮再试”，不写事件。只要有一项一直不通过，绑定的 run 就再也没人去读，域状态永远停在 running。

另外，执行器的 `bind()` 对已经绑定、身份齐全的 intent 不追加事件，所以“没有新的 `github_check_dispatch`”只能说明没有走到新绑定，不能说明 `start()` 没跑。主因是上面的准入分支，C-769 当时具体卡在哪一项以生产日志为准，本卡不依赖这一点：所有准入分支都已绕开。

## 改动

1. **重启后重新接上（`apps/server/src/author-prechecks.ts`）**：GitHub 预检的 journal intent 已带 `externalRun`（包括 poller 已确认远端结束、但重启前没来得及记录结果的 finished intent），且候选身份齐全时，`execute()` 走重连路径：不读 HEAD，不判断名额，不预留槽位，不拿容量租约，直接 `runCheckExecutor`。执行器 `start()` 拿到带 `externalRun` 的 intent 只会 `client.run(run_id)`，不会走到 push 或 POST。负责人和 HEAD 在结果出来后照常由 `verify()` 核验。本进程第一次重连时写一条 `github_check_progress`：“主机已重新接上已绑定的 GitHub 检查，正在核对远端状态”。保留的门禁有主机运维交接锁（`CheckHandoffs`）、同一 attempt 存活的容量占用者（防止两个执行者）以及有截止时间的 `GithubRetryLater` 退避。
2. **超时兜底**：已绑定或已在运行的 GitHub 预检，从 `precheck_started`（没有时取 intent 的 `startedAt`）算起超过 `staleAfterMs` 仍未收尾时，系统对绑定的 run 做一次只读 `client.run`（60 秒上限），然后记为 `interrupted`。摘要写明“按核对超时结束”、GitHub 核实到的状态（已结束及结论／仍在某状态／未核实及原因），并注明“结果未经主机完整核验，不作为通过依据，请重新 request_check”。远端 success 也不记为 passed，因为没有经过 poller 的步骤合同核验。随后 journal 把 intent 记为 `attempt_finished`，合并维护照旧取消仍在跑的 run。
   - 默认阈值 `queueWaitMs + 2 × totalTimeoutMs`（默认配置为 3 小时 + 2 × 60 分钟 = 5 小时）：GitHub 排队最长等 `queueWaitMs`，之后最多再跑 `totalTimeoutMs`，另留一个 `totalTimeoutMs` 余量。可通过 `AuthorPrechecks` 的 `staleAfterMs` 选项覆盖。
3. **主机运维入口 `host_ops_recheck_precheck`**（MCP，只对常驻 host_ops 开放）：参数为 `card_id`、`attempt_id`、`action=reinspect|abandon`、`reason`、`idempotency_key`。
   - 领域命令 `hostOpsRecheckPrecheck` 只记录 `precheck_recovery_requested`，同时写 `host_ops_action_taken` 审计。只接受排队中或运行中的 GitHub 预检；已有待处理请求时重复请求不写事件，返回 `already_requested`；不同动作要等前一个处理完。同一幂等键由 `store.runIdempotent` 重放。
   - `reinspect`：清除本地退避，交给上面的重连路径；系统写 `precheck_recovery_handled`（结果为 reattach、active 或 unbound）。
   - `abandon`：同样先做一次只读 GitHub 核对，再以 `interrupted` 收尾，摘要以“主机运维已放弃此次预检查”开头；终态记录和 `precheck_recovery_handled` 在同一事务里写入。
   - host_ops 角色说明补了一条使用规则。
4. **不变量**：上述恢复路径都不会对同一 attempt 发起第二次 `workflow_dispatch`。重连只在 intent 已带 `externalRun` 时启用；超时和放弃只调用 `client.run`。

## 不变

- 同一负责人只能有一个排队中或运行中预检的互斥规则不变；flow≥3 下 submit_delivery 仍要求预检通过。
- 从未派发、没有绑定 run 的排队预检仍走原来的准入和等待逻辑，兜底不会作用于它们。
- C-769 本身由 PM Ops 人工解卡，不在本卡范围。
