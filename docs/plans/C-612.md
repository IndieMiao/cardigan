# C-612 · 受管发布链一次授权

宗旨：打通阻塞，不新增人工确认、拍板、守卫或停摆条件。只有“会丢工作”或“出现两个执行者”才停；其它问题自动修复，或降级为提示后继续。

本卡在 C-607 分支（v3 签名、只读预检、CDN 回读退避、写入后续做）之上实现，C-607 的第 4 条（写入前失败不消耗外发拍板）按张良 C-607#14 的分工改在这里统一实现。

## 1. 发布链拍板

PM 在打包卡发起**一条** `publish` 类拍板，`kind=approve`：

- `target.subject` 为 `artifact_sha256`，值是**未签名包**的完整摘要；
- 选项 `release_chain` 的描述必须恰为 `发布链 <40 位源提交> 发布到 <https APK 地址模板>`；模板可用 `<version>`（versionName）和 `<sha12>`（签后包摘要前 12 位），例如 `发布链 0123…cdef 发布到 https://download.example.invalid/app/test/<version>-<sha12>/app.apk`。

批准方式与逐件外发相同：人在 Needs You 批准，或在“对外发布”授权有效时由 PM Ops 代批（`approvedReleaseChain`，`packages/domain/src/artifact-publication.ts`）。批准后各步都认这一条拍板：

| 步骤 | 依据 | 系统做什么 |
| --- | --- | --- |
| 未签名入库 | `upload_attachment` 的 `basis` 填发布链拍板 | 不变。服务端按收到的字节计算摘要并返回，不需要回读下载 |
| 送签 | 链已批准，且本卡有摘要等于绑定摘要的未签名包 | `request_mobile_signature` 先调 `host.py chain`，为当前 Run 自动登记并批准这份候选，时间线记“已自动登记并批准送签” |
| 签后入库 | 签名回执 | 回执的签后摘要自动绑定到链（`release_chain_signed`，系统事件），服务端直接从控制主机已复核的产物入库为本卡制品（`basis`=发布链），回执带 `release_chain.signed_attachment_id`；不再下载再上传，也不再回读 |
| 外发 | `publish_artifact` 的 `decision_id` 填发布链拍板 | 只认链上绑定的签后摘要；地址必须等于模板代入版本号和签后摘要前 12 位的结果 |
| 版本说明 | — | 按外发结果写，PM Office 按 C-584 发送；不需要拍板 |

不新增守卫：链没批准、找不到未签名包、主机登记失败或本 Run 已有别的授权时，送签照原路径进行（有人工登记的授权就用它，否则主机照旧拒绝）；签后入库失败只在回执里标 `signed_intake: retry`，下次轮询自动重试，不影响签名结果。

## 2. 送签自动登记（`host.py chain`）

- 输入：标准输入两行（本 Run 的签名范围；`commit`、`build`、`sha256`、`size`），候选字节走 fd 3。控制服务从本卡附件读取字节，不接受 Agent 给的路径。
- 只收 Android。路由表里该项目、机器、平台**唯一**的一条路由决定 `app` 和凭据版本；请求号随机生成，有效期 24 小时（`CHAIN_TTL`）。主机按大小和摘要逐字节复核后，在同一事务里写入 `approved` 授权，账本记 `chain_registered`、`chain_approved`。
- 每个 Run 一份候选：本 Run 已有授权时只报告 `existing`（同一摘要、未撤销）或 `other`，从不替换；并发两次调用由写事务内的复查保证只登记一次。
- 签名端检查不变：仍核对项目、机器、Run、摘要和包名，只做 v3 签名。

## 3. 外发：写入前不消耗、写入后续做

- 写入 OSS 之前（configuration、artifact、signature、manifest、immutable_prefix、host_error）失败：不消耗授权，**不限次数**，修好后用同一拍板直接重试。取代 C-607 的“最多两次”。
- 写入之后（upload、download）失败：同一授权再次调用即可续做。主机按目录内容决定：目录为空就正常写；只有本次同大小的 `app.apk` 且本卡有同一地址和摘要的领取记录时跳过上传，回读后补写清单（C-607 的续做路径）；其它情况仍按 `immutable_prefix` 拒绝，从不覆盖。
- 两个执行者才停：同一拍板在本进程里有在途调用时，第二个调用立即报 `in_progress`，不碰主机、不写审计；已经 `verified` 的拍板报 `already_claimed`。

## 4. 打包模板

新增内置模板 `release`（打包发布，流程第五级起可用）：出包 → 送签 → 冒烟 → 外发 → 版本说明，均由 `release_ops` 负责，按顺序自动设置依赖；另有 PM 验收。模板工作项新增 `depends_on`（同模板中排在前面的 key），自定义模板同样可用，校验拒绝自依赖、向后引用、重复和不存在的 key。项目未登记 `release_ops` 时不能用此模板建卡。

## 5. 同机就地交接

- 管理员在 `routes.json` 的路由上加 `"handoff": true`（签名端与 worker 在同一台机器），并在签名端 `identity.json` 加 `handoff_dir`：管理员建的、签名账号所有、权限 `0711` 或 `0751` 的目录（他人可进入但不能列目录或写入）。
- 主机对这类路由请求交接；签名端签完（或 lookup 已签）后把同一份签后包按请求号写成 `<请求号>.apk`（`0644`，先写临时文件，再硬链接，不覆盖已有文件），在回执头里报路径。主机核对路径形状后记入账本 `handoffs` 表，回执带 `local_handoff: {path, sha256}`。同机 worker 直接读取并复核摘要，不再经控制主机下载。
- 任一条件不满足（未配置、目录权限不对、旧版签名端）只是不交接，签名和取回照旧。
- 兼容性：旧签名端忽略请求里的 `handoff`，新签名端在旧主机下不会被请求交接；用 origin/main 的 `worker.py` 和 `host.py` 分别跑新测试套件已核对（见交付测试记录）。交接需要按 README 升级签名端五个文件后才生效。

## 未覆盖

- 没有在真实 OSS、真实签名端和 sensen 链路上实测；合并部署后由打包卡走一次完整链作为现场跟进。
- 未签名包到签名端的输入仍走控制主机（GS66 → mac-mini 的慢方向）；本卡只做签后包的就地交接。
- 未改 sensen 的 `release_ops` 角色说明，也未改 PM 默认角色包；发布链的拍板格式写在 `publish_artifact` 工具说明和本文。
