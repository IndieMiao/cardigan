# C-612 · 受管发布链一次授权

宗旨：打通阻塞，不新增人工确认、拍板、守卫或停摆条件。只有“会丢工作”或“出现两个执行者”才停；其它问题自动修复，或降级为提示后继续。

本卡在 C-607 分支（v3 签名、只读预检、CDN 回读退避、写入后续做）之上实现，C-607 的第 4 条（写入前失败不消耗外发拍板）按张良 C-607#14 的分工改在这里统一实现。

## 1. 发布链拍板

PM 在打包卡发起**一条** `publish` 类拍板，`kind=approve`：

- `target.subject` 为 `artifact_sha256`，值是**未签名包**的完整摘要；
- 选项 `release_chain` 的描述必须恰为 `发布链 <40 位源提交> 发布到 <https APK 地址模板>`；模板可用 `<version>`（versionName）和 `<sha12>`（签后包摘要前 12 位），例如 `发布链 0123…cdef 发布到 https://download.example.invalid/app/test/<version>-<sha12>/app.apk`。

批准方式与逐件外发相同：人在 Needs You 批准，或在“对外发布”授权有效时由 PM Ops 代批（`approvedReleaseChain`，`packages/domain/src/artifact-publication.ts`）。批准后各步都认这一条拍板：

| 步骤 | 依据 | 系统做什么 |
| --- | --- | --- |
| 未签名入库 | `upload_attachment` 的 `basis` 填发布链拍板 | 服务端按收到的字节计算摘要；以链拍板为依据的制品只在链已批准、仍有效、属于本卡，且摘要等于绑定的未签名摘要（或系统绑定的签后摘要）时入库，否则当场拒绝。普通依据的附件不变 |
| 送签 | 链已批准，且本卡有摘要等于绑定摘要的未签名包 | `request_mobile_signature` 先调 `host.py chain`，为当前 Run 自动登记并批准这份候选，时间线记“已自动登记并批准送签” |
| 签后入库 | 签名回执 | 回执的签后摘要自动绑定到链（`release_chain_signed`，系统事件），服务端直接从控制主机已复核的产物入库为本卡制品（`basis`=发布链），回执带 `release_chain.signed_attachment_id`；不再下载再上传，也不再回读 |
| 外发 | `publish_artifact` 的 `decision_id` 填发布链拍板 | 只认链上绑定的签后摘要；卡上有冒烟一项时，只认冒烟已验收、且验收交付的 `artifact_sha256` 正是这份签后包的那一份；冒烟没完成或被取消（例如随卡取消）时在写入前拒绝，不消耗授权。只有从来没有冒烟项的旧卡不受影响；地址必须等于模板代入版本号和签后摘要前 12 位的结果 |
| 版本说明 | — | release_ops 按外发结果写好并交付；交付即通知托管 PM Office 用 C-584 的私聊工具发给所有者，时间线分别记受理和投递。项目没开所有者私聊或没有托管 Office 时，改为提醒 PM Ops 转告。不需要拍板 |

不新增守卫：链没批准、找不到未签名包、主机登记失败或本 Run 已有别的授权时，送签照原路径进行（有人工登记的授权就用它，否则主机照旧拒绝）；签后入库失败只在回执里标 `signed_intake: retry`，下次轮询自动重试，不影响签名结果。

## 2. 送签自动登记（`host.py chain`）

- 输入：标准输入两行（本 Run 的签名范围；`decision`、`commit`、`build`、`sha256`、`size`），候选字节走 fd 3。控制服务从本卡附件读取字节，不接受 Agent 给的路径。
- 只收 Android，只认内部测试签名身份：路由表里该项目、机器、平台下**唯一**一条标了 `"test_identity": true` 的路由决定 `app` 和凭据版本，管理员只给持有内部测试证书的签名身份标这一项。没有标记的路由一律不自动登记，仍按 README 第 2 步逐件批准；请求号随机生成，有效期 7 天（`CHAIN_TTL`，长于任何打包 Run，签后入库和下载不会因过期失败）。主机按大小和摘要逐字节复核后，在同一事务里写入 `approved` 授权，账本记 `chain_registered`、`chain_approved`。
- 授权记下来源：账本 `chain_grants` 表记录链派生授权对应的拍板。
- 每个 Run 一份候选：本 Run 已有授权时只报告，从不替换。只有同一条链、同一源提交、同一摘要、未撤销且处于可用状态（已批准、进行中或已签）的链授权才报 `existing`。人工登记（未批准或已批准）的授权、别的链的授权都报 `other`，控制服务不会把它记成本链的批准。并发两次调用由写事务内的复查保证只登记一次。
- 链失效就停用：链派生的授权只在控制服务声明这条链仍有效、且对应路由仍标着 `test_identity` 时可用（管理员撤掉标记后，旧的链授权在提交签名前被拒，人工授权不受影响）。`request` 和 `check` 的签名范围带 `chain`，主机核对它与登记时的拍板一致，缺少或不符就拒绝，不会退回当作人工授权。控制服务在提交签名前的核验点（fence）再读一次拍板，链被撤销或被替代时拒绝提交。下载（`permit`）不要求声明，仍要求同一个在场的 Run。
- 签名端检查不变：仍核对项目、机器、Run、摘要和包名，只做 v3 签名。

## 3. 外发：写入前不消耗、写入后续做

- 写入 OSS 之前（configuration、artifact、signature、manifest、immutable_prefix、host_error）失败：不消耗授权，**不限次数**，修好后用同一拍板直接重试。取代 C-607 的“最多两次”。
- 写入之后（upload、download）失败：同一授权再次调用即可续做。主机按目录内容决定：目录为空就正常写；目录里只有本次发布会写的文件（`app.apk`、`SHA256SUMS`、`release.json`），大小与本次一致、APK 在其中，且本卡有同一地址和摘要的领取记录时，已有的文件只做公开回读并核对完整 SHA-256，只补写缺的文件；三个都在时只回读核验后补记完成。有陌生对象、大小不符、只有清单没有 APK 或列表被截断时仍按 `immutable_prefix` 拒绝；大小相同但内容不符的文件在回读时失败；从不覆盖。
- 两个执行者才停：同一拍板或同一签后包在本进程里有在途调用时，第二个调用立即报 `in_progress`，不碰主机、不写审计；已经 `verified` 的拍板报 `already_claimed`。
- 一条链只发一处：链领取过某个地址和摘要后，只能续做同一份（换包、换版本号都报 `already_claimed`）；链外发 `verified` 后，后续 Run 不再自动登记送签。

## 4. 打包模板

新增内置模板 `release`（打包发布，流程第五级起可用）：出包 → 送签 → 冒烟 → 外发 → 版本说明，均由 `release_ops` 负责，按顺序自动设置依赖；另有 PM 验收。模板工作项新增 `depends_on`（同模板中排在前面的 key），自定义模板（含 Web 模板入口）同样可用，校验拒绝自依赖、向后引用、重复和不存在的 key。项目未登记 `release_ops` 时不能用此模板建卡。冒烟一项交付时 subject 填签后包的 `artifact_sha256`，外发据此只发冒烟通过的那份。版本说明一项交付后，路由按第 1 节转给托管 PM Office 或提醒 PM Ops。

## 5. 同机就地交接

- 管理员在 `routes.json` 的路由上加 `"handoff": true`（签名端与 worker 在同一台机器），并在签名端 `identity.json` 加 `handoff_dir`：管理员建的、签名账号所有、权限 `0710`（或 `02710`）的目录。目录的组只能含目标 worker 账号，签名账号本身除外；其他账号既不能列目录也不能进入。
- 到期由签名端自己的定时任务保证：管理员以签名账号安装 `worker.py <根目录> prune`（每 5 分钟左右）。它删除超过 1 小时（`HANDOFF_TTL`）的副本和残留临时文件，并刷新 `handoff-pruned`。15 分钟（`PRUNE_FRESH`）内没有刷新就不交接，改为照常下载。所以签名机空闲、撤回又没送达时，副本也会到期删除，不依赖下一次业务请求。
- 只给目标 worker、且在放行之后：签名端每次按账号库核对组成员，恰好只有清单里的 `worker_uid` 才交接。副本用随机文件名（不是请求号）写入，权限 `0640`，组为该目录的组；先写临时文件，再硬链接，不覆盖已有文件。随机名记在签名端账本，回执头只交给控制主机。目录不能列出，主机在最终核验授权并把签名结果和交接记入账本之后才报告路径。在此之前撤销，路径永远不会报告，也就没有人能打开这个副本，它只等到期删除。回执带 `local_handoff: {path, sha256}`，同机 worker 读取并复核摘要；文件不在或摘要不符时照常下载。
- 撤销：`host.py revoke` 顺带请签名端删除副本（`withdraw` 模式，不用密钥、不传字节）。签名端确认之前，账本保留交接记录，重复 `revoke` 会再试；连不上或是旧版签名端时记 `handoff_withdraw_failed`，副本由定时任务到期删除。
- 任一条件不满足（未配置、目录权限或组不对、定时任务没跑、旧版签名端）只是不交接，签名和取回照旧。
- 兼容性：旧签名端忽略请求里的 `handoff`，也不认识 `withdraw`，拒绝后主机只记失败。新签名端在旧主机下不会被请求交接。主机与控制服务同版发布，二者之间的新增字段（`decision`、`chain`）不需要兼容旧版。用 origin/main 的 `worker.py` 和 `host.py` 分别跑新测试套件的结果见交付测试记录。交接需要按 README 升级签名端五个文件后才生效。

## 6. 签后包保留

以发布链拍板为依据入库的制品（未签名包、签后包）在这条链外发核验成功（`artifact_publication_verified`）之前不会被制品清理按时间或容量删除。签后入库的幂等键带本次副本的编号：入库附件过期后重试会重新入库，不会重放旧的附件号。同一签名回执的重叠轮询在进程内共用一次入库，入库提交前再查一次已有附件，只留一份。

## 未覆盖
