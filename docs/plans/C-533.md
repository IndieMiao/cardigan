# C-533：合并检查等待仓库锁

- 只识别候选尚未进入传输的受信锁超时。GitHub 合并检查和作者预检共用 `not_started` 的发布围栏结算；SSH 分发在同一仓库互斥边界区分开始前和开始后的错误。不分析日志或错误字符串。
- 合并检查保留排队身份。把锁等待写入当前尝试的卡片事件和日志，由原调度在前两次超时后分别等待 30、60 秒再重验候选；第三次超时按启动失败处理，不计为执行器失联，不伪造外部运行或测试结果。重启和重复唤醒不重置已记预算。
- 不改审核和发布授权、互斥范围、进行中的远程派发或作者预检的重试策略。用隔离夹具验证锁释放、持续争用、重启、换目标及真假故障分流，运行相关回归、增量构建、domain 测试类型、lint、依赖检查和同 SHA 远程预检。
- 退避表是主机装配参数 `repositoryRetryDelaysMs`，默认 `[30000, 60000]`；不下发给候选，不增加生产开关。预算按完成申请（批次单独计）累计，重新生成候选提交不补发预算，显式重查才重新计数。未开始的尝试仅在重验身份一致后复用；锁释放后、启动工作进程或发送工作流请求前再核对当前基线和申请。
- 同树不等于同一候选。重启后 SHA 变化时，只有原尝试的 GitHub 派发记录证明已越过发送请求的围栏，才恢复对旧运行的查询；仅预约或仍在推送时不能凭同树重发旧 SHA。暂停、容量等排队提示不会成为派发证据。
- 批次或二分探测用完锁重试后保留批次启动失败和日志；该结果不触发确认重跑，也不能用于二分定责。原批次基线或成员失效仍按原流程作废，真实检查失败仍走原定位流程。
- 新工作流请求或启动工作进程前（包括第一次分发）一律重验基线、完成申请及排队尝试。不以曾否超时代替重验；暂停和确证的传输前超时同时发生时，同时保留暂停围栏、预算和退避期限。因暂停拆散的批次以相同基线、完成申请顺序和树重组时，沿用被中断的锁等待。
- 批次或二分探测耗尽预算时，由原队列关闭批次并保留检查日志；并行探测若仍在执行，先等其结束。只为该批次原有的完成申请记录暂不组批，不退回成员、不占用项目队列。仓库恢复后可用 `cardigan merge recheck <卡号>` 显式恢复该卡；恢复不会给其他成员补预算，也不能代替新的批次检查或发布前校验。
- Q-1022：批次检查在调用执行器前登记本次调用；仅受信的传输前锁超时可按调用编号结算一次，退避从结算时起，重复回报不延长。同一项目、基线、批次用途/父探测、有序成员完成申请和树在同一恢复周期内共享预算。中止后的迟到回报只记事实，不复活检查。重新组批时由现有调度执行退避或收尾，显式重查后不继承旧回报。登记未结算不证明传输尚未开始，继续依赖原执行器恢复围栏和真实占用，不用这条登记阻塞其他目标。
- Q-1028：重组后的检查仍在等待仓库锁时，在当前尝试上显示原回执的超时次数和重试时间。所有批次成员共用这条等待说明；说明不新增锁超时记录，不改变调度和发布条件，检查开始后不再作为当前等待展示。
- V-2499：GitHub 合并检查把单次仓库调用的结算权交给实际推送者。监督退出不等于推送结束；只有适配器确证传输前锁超时，才在释放发布围栏前记录原调用的回执。单卡按原完成申请和重查周期、批次按原目标周期沿用预算，发布者不负责改变检查状态。回放单卡和批次第 1、3 次等锁时交接的场景。
- Q-1035：候选发布的本地监督截止与工作流发现窗口分开。发布时固定本次主机监督时限；接手者在 Git 推送未结算时不重发、不扣重试、不判项目断连。超过本地时限或无法确认写者身份时，记录该尝试待恢复，保留互斥。只有原适配器的回执能结算锁超时，重试前仍重验当前目标。用短窗口和默认窗口对照卡片、日志、实际调用时间，再核对超期交接和撤销后的迟到回执。
