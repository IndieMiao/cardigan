# C-671 冷卡只保留少数跨卡事实类型

来源：Q-1292（C-649 拆出的“按类型白名单”）。本卡在 C-649 的 `lean` 之上新增开关 `slim`，默认值不变（仍为 `hot`）：

- 命令状态里冷卡只保留白名单事实类型；
- 跨卡读取方改走事件日志索引（“迁到索引”），不再依赖数组里有关闭卡的全量历史；
- 关闭卡的其它事件在 Store 里不再常驻解码，按需从表里读回（“冷历史按卡按需读取”）。

## 1. 三层做法

### 1.1 命令状态：数组只留白名单，查找照常回答

`slim` 的命令状态数组：

- 热卡（沿用 C-639 / C-649 的活跃集规则）保留整条流；
- 冷卡只保留 `SLIM_COLD_CARD_EVENT_TYPES` 里的 7 类事实，`lean` 已去掉的遥测照旧不要；
- 系统流沿用 `lean` 的按类型保留。

索引查找（`eventsOfType`、`eventsOfTypes`、`cardEventsOfType`、`eventsFor*`、`streamEvents`、`eventsAtSeq`、`eventById`，以及本卡新增的 `eventsWithKey`）不受白名单影响：仍按 `lean` 的范围回答，冷卡上除 `lean` 已去掉的遥测外，其它事件都能查到。实现上，`HistoryFilter` 新增 `keep`：

- 只作用于数组（以及 `fullEventHistory`、遥测日志这类同一过滤的历史）；
- 挂在数组上的索引用去掉 `keep` 的过滤。

`slimCommandEvents(state, extra, protect, keep?)` 是纯函数定义，同样基于事件日志视图构造，Store 装载结果须与它逐条一致。

### 1.2 读取方迁到索引

原则：凡是可能读到冷卡的扫描，改成按类型、按字段、按 id 或按卡的索引查找。

- 结果不变：同一类型在索引里的顺序就是历史顺序。多类型合并后在类型子集上保持相对顺序，与“先过滤整体再取子集”相同。
- 只读需要的类型：不在白名单里的冷卡事件，只在被查找到时才解码。

`flatMapEvents` 派生出的数组（引用读取的项目快照）新增 `MappedIndex`：先在源索引上查找，再经同一映射函数取结果。每个事件只映射一次，因此与派生数组里的对象是同一个。

审计用 8 路并行只读检查完成：先找出所有可能读到冷卡事件的读取方（约 60 处），再逐行分类约 250 处直接扫描。迁移清单如下：

| 读取方 | 原做法 | 现做法 |
|---|---|---|
| `card-dependencies` 完成判断、关键路径 | 按卡分组整份历史 | 只取 6 类完成证据的类型索引 |
| `decisionHistory` 被取代拍板的真实解决 | 全量 `some` | `decision_resolved` 类型索引 |
| `notices` 知会、已读、Office 等待 | 两次全量扫描 | 按知会类型的类型索引（之后按时间排序，不受顺序影响） |

| `stop-state`（人工停止、暂停、停止片段） | 遍历完整历史 | 5 类事件的类型索引；片段起点用事件对象定位，再换算成完整历史下标 |

| `extInteraction` 依据指纹 | 遍历完整历史 | 相关卡的流加拍板 / 待办字段索引，按历史顺序重排 |

| `dispatch-recovery`、`run-recovery`、`preparation-recovery` | 全量 `find/some` | 类型索引 |
| `suggestionProgressEvents` | 全项目建索引 | 按卡的类型索引（决策历史会对已解决拍板调用） |
| `mergeShadowComparisons` | 全量过滤 | 按卡、按类型索引 |
| `latestPrecheckConflict`、`system-review-limit`、`system-rules`、`worker-inspection`、`context-usage`、`role-rule-implementation`、`runtime-incident`、`assignment-role-upgrade`、`delivery-rework`、`pm-recovery`、`queries` 运行时事实 | 全量扫描 | 类型索引或 `eventById` |
| router：`routeRunFinished`、恢复抑制、拍板答复、Office / 系统等待关闭 | 全量扫描 | 类型索引、工作项字段索引、`eventsAtSeq` |

经核对，下面这些扫描不需要改：

- 目标卡、开放卡、未释放指派或未结束 Run 所在卡上的扫描：这些卡都是热卡，数组里有整条流；
- 只读系统流的扫描。

Web 端人工命令（`applyCommand`）比照 MCP 命令，把请求路径段和幂等请求体作为目标，所以命名到的关闭卡保留整条流。

### 1.3 Store：关闭卡的其它事件不常驻解码（`slim` 才启用）

项目第一次被读取时，下面这些行只保留一个轻量占位（`DormantEvent`）：

- 行在这次读取的水位以内；
- 所在卡已关闭；
- 类型不在 `SLIM_RESIDENT_EVENT_TYPES` 里。

占位照常参与以下索引，只是不保留解码后的对象：

- 流、id、类型；
- `decision_id`、`human_action_id`、`completion_id`、`work_item_id`、`resume_work_items`、`batch` 这些字段索引。

占位只保留 id 和 seq，类型和卡号共用同一个字符串。

占位的读取规则：

- 读取方真要用到某条占位时，日志按 `(stream, seq)` 从表里读回并替换。事件只追加、不改不删，读回的内容就是当初的那一行。
- 读回只解码被要到的那几条，每条流读一次表。
- 读回时 id、seq、type 与流任一不符就报错（C-671 前缀），不会静默给出错误答案。
- 按白名单裁掉的占位，在建数组和按过滤查找时都不会读回。
- 读水位以后写入的行，一律照常解码。
- 分段预热（C-649）也走同一规则。

常驻类型 `SLIM_RESIDENT_EVENT_TYPES` 包括：

- 冷卡白名单；
- 命令状态以外按全项目读取的类型：GitHub 分发日志、Office 摘要；
- 项目快照对每张卡、每次都读的类型：合并检查、预检、完成评审证据。

后一类放成常驻，热路径就不必在第一次调用时付解码开销。

## 2. 白名单

`SLIM_COLD_CARD_EVENT_TYPES` 共 7 类：

- `card_merged`
- `card_marked_done`
- `decision_resolved`
- `host_ops_action_finished`
- `context_session_restart_result`
- `remote_worker_lost`
- `remote_worker_released`

上面迁移过的读取方都已经不依赖数组里的冷卡事件；契约测试里白名单为空时结果同样一致（见 4.1）。保留这 7 类是安全余量：一旦缺失会造成永久锁死或等待失效的事实（等待合并、依赖完成、主机运维围栏、远端失联围栏、拍板解决），即使有遗漏的扫描也仍然看得到。它们在关闭卡上量都很小。

## 3. 开关与回退

- `CARDIGAN_COMMAND_STATE=slim`，或 `Store.open({ commandState: "slim" })`；
- 默认仍是 `hot`；
- 可随时切回 `lean`、`hot` 或 `full`：只影响内存里的装载方式，不改写任何数据；
- 非法值在启动时报错。

读取方迁到索引这一层在所有模式下都生效：在 `full`、`hot`、`lean` 下，索引答案与原扫描相同（契约测试和三种模式的影子比对都已覆盖）。

## 4. 验证

### 4.1 契约测试

- `hot-history-slim.contract.test.ts`
  - 场景：只有一张开放卡；其余 8 张关闭卡上放各读取方需要、但不在白名单里的证据，并且确认数组里确实没有这些证据。
  - 覆盖的读取方：拍板历史、知会、主机运维完成和退出确认、人工停止、分发恢复、合并影子、远端失联、建议进展、受限批次遮蔽、预检等待恢复、推送基线。
  - 比对：白名单、空白名单两种情况下，全部 32 项影子比对都与全量一致。
  - 再用 Store 式的占位日志（带读回器）跑一遍：建数组不读回；读取方只读回被要到的事件，冷卡遥测始终不读回；装载结果与定义逐条一致。
- 变异检查：把 11 处迁移逐一改回扫描，10 处会让测试失败。唯一不失败的是 `host_ops_action_taken` 那一处，因为该事件写在系统流上，数组里始终都有。
- `hot-history-scenarios.contract.test.ts`：C-639 的 5 个跨卡场景新增 `slim`。
- `event-log.contract.test.ts`：
  - 占位日志的全部查找与普通日志相同；
  - 按白名单裁掉的占位从不读回，游标读到尾时也不读回；
  - 读回内容不符时报错；
  - `flatMapEvents` 的查找与扫描映射结果相同，白名单历史上也看得到被裁掉的事件。
- `store/command-events.test.ts`：`slim` 的占位数、`listAfter` 与 SQL 一致、新行照常解码、分段预热的占位相同、非法值报错。
- `mcp-server/command-state.test.ts`：Store 装载的 `slim` 与定义逐条一致；冷卡的评论只能通过查找得到，冷卡遥测查不到；命令点名关闭卡时保留整条流。

## 5. 合成基准（C-649 的 3 个项目 × 30 万事件）

测量机器负载很高（load average 18–22），耗时波动大，下面是同一时段交替跑出的范围，属本机自报。内存加了 `--expose-gc` 后、完整回收后的读数，这项最稳定。

### 关闭卡上的事件

| 每项目 | lean | slim |
|---|---|---|
| 关闭卡事件（库中） | 约 26.7 万 | 约 26.7 万 |
| Store 中常驻解码的关闭卡事件 | 约 26.7 万 | 约 10.2 万（工具基准后）/ 约 11.7 万（后台 30 s 后） |
| 命令状态完整历史 | 约 17.8 万 | 约 3.4 万 |
| 命令状态数组（业务事件） | 约 16.6 万 | 约 2.2 万 |

slim 下关闭卡的遥测，以及没有读取方全局查找的类型（合成库里是评论和状态变更），都保持不解码。热卡（被引用的关闭卡）和被命令点名的关闭卡会整条解码，直到下次重启。

### 工具耗时（`bench`，10 轮 × 3 项目，两轮交替）

格式为 p50 / p95，单位 ms。

| 工具 | lean | slim |
|---|---|---|
| post_comment | 2.3–2.5 / 6.7–8.7 | 2.1–2.3 / 6.6–6.8 |
| command_state | 9.7 / 12.0–22.7 | 9.6–9.7 / 15.0–16.3 |
| list_needs_you | 11.0–11.2 / 23.8–24.9 | 10.3 / 18.4–21.7 |
| project_snapshot | 26.9–28.2 / 39.4–41.2 | 25.0–26.8 / 35.4–36.7 |
| get_card | 4.9–5.4 / 7.6–12.6 | 5.0 / 8.3–10.3 |
| get_updates | 3.5–3.6 / 8.7–9.0 | 3.5–3.7 / 7.2–8.1 |

- 单测 command_state（400 次装载，三轮）：p50 lean 9.5–9.8，slim 9.2–9.4。
- p95 两边都在 15–21 ms 波动，未见回退。
- 开发中曾有一版 command_state 慢 25%：每次装载都要逐条核对分发记录是否为占位。现按类型记录占位数，常驻类型直接跳过。

## 6. 已知风险与后续

- 生产只读副本回放未运行。主机侧先执行 `hot-state-bench.mjs shadow <副本> slim`，一致后再切换；有差异时保持现有模式。
- 生产收益取决于实际的类型分布。在合成库上，收益主要来自关闭卡遥测和无人全局查找的业务类型。生产中常被全局查找的业务类型，第一次查找后会解码并常驻，直到重启。
- 关闭卡一旦被命令、通知点名，或被热卡规则拉入，就会整条解码，进程内不再回到占位。
- 仍有少数查找按类型取全项目、再按 run 或指派过滤，例如 `routeRunFinished`、主机运维诊断里的投递失败。它们会让对应类型在第一次调用后常驻。对这些类型可按需再加字段索引，本卡未做。
- `rebuild`（同一流的 seq 倒退时退回的重建路径）会读回全部占位。这是罕见路径，结果正确，只是内存会回到全量。
- 本机 `packages/host`、`apps/server` 的测试受环境影响：依赖 Linux 的 `/proc`、`flock`，以及高负载下的超时。基线提交在本机同样有约 1075 个失败。对比失败集合后，逐个文件单独重跑：本卡与基线的失败数相同，差异只是波动。全量结果以远程预检为准。
