# C-780：CLI 写命令先在读事务里预热命令状态

## 做法

- `apps/cli/src/host.ts` 新增 `warmCommandState(store, project)`：在 `uow.read`（`BEGIN DEFERRED`，不占写锁）里调一次 `loadCommandState`，把命令事件日志、各表行缓存和按项目版本号缓存的命令状态建好。
- `runCommand` 开写事务前先调它。写事务里照旧 `revalidateActor` 重查授权、照旧 `loadCommandState`：状态缓存以项目已提交版本（`command_versions`）为键，版本没变就直接命中；预热之后有别的进程提交了写入，版本变了，就在写锁内按新版本增量重建，reduce 看到的是最新状态，不会拿预热时的旧状态提交。
- 不改 `packages/store`：版本复核是现有 `CommandSnapshots` 的行为，本卡只调整 CLI 调用点的顺序。

## 测量

真实库不在员工机器上，用合成数据（`pnpm fixture:generate`）在本机测写锁持有时间（`StoreObserver.writeLock`），一条 `requestDecision`：

| 数据 | 改前 | 改后 |
|---|---|---|
| `cards`（421 卡、11 万事件），hot | 425～501 ms | 15.5～16.0 ms |
| `production-like`（287 卡、3.3 万事件），hot | 180～545 ms | 19.6～45 ms（本机负载 8.8，抖动大） |
| `cards`，slim | 1303～1340 ms | 37～44 ms |

写锁内缓存命中的 `loadCommandState` 只要 0.1 ms，剩余时间是 reduce、落库和提交本身。

## 未覆盖的风险

- 生产库（cardigan 3.9～4.4 s、sensen-godot 约 1 s）的复测需要在主机侧用报告附录的 `review-b/p5-cold.mjs` 跑；员工机器没有生产快照。
- CLI 进程自身仍要冷建一次状态（耗时和内存不变），只是不再占着写锁。
- 两天量级观察 `database is locked` 是否消失，合并后跟进。
