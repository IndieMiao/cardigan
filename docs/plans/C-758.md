# C-758 候选推送 push_incomplete 归因与分类

## 1. 现象与已有证据

- 11-25 sensen-godot（执行器 `github-actions-sensen`）记了 33 次 `merge_executor_unreachable`，`category=dispatch_unknown`、`stage=push_incomplete`，每次约 1 分钟后同一 attempt 重试成功。
- C-681 保存的 sensen 样本（18:26:16Z）：`http_status=201`。这个 attempt 记下的最近一次 GitHub 请求是**安装令牌的 POST**（`POST /app/installations/{id}/access_tokens` 返回 201）。也就是说，令牌是这次检查当场新换的，紧接着推送就失败了；GitHub API 本身可达。
- cardigan 自己的执行器 `github-actions` 在 C-681 合入后共 3 次 `push_incomplete`（项目事件流）：

| 时间 (UTC) | attempt | 前后情况 |
|---|---|---|
| 11-24 17:23:59 | 73c40f2f（卡级检查） | 附近没有部署；17:23:20 刚组成 MB-53 |
| 11-24 18:30:54 | f1b9a25c（MB-56） | 18:30:40 主机部署完成，重启后 **14 秒** |
| 11-25 18:36:46 | 5e46d041（MB-94） | 18:36:24 主机部署完成，重启后 **22 秒** |

  三次都在约 1 分钟后的第一次重试成功，事件里都没有 `http_status`（令牌由并发检查共用缓存取得，是 C-681 已知缺口）。
- 主机 11-25 共重启（`host_deployment_recorded status=deployed`）**32 次**（统计到 20:03Z），与 sensen 当天 33 次基本一一对应。sensen 和 cardigan 由同一个 server 进程托管，每次重启都会清空各执行器内存里的安装令牌缓存。部署期间排队的合并检查（“等待主机部署结束”）在新进程起来后立即开跑，第一步就是换新令牌，然后马上推送。

## 2. 代码路径：旧的 push_incomplete 混了哪几种原因

`github-check-executor.ts` 中只要 `beginDispatch` 返回 false 就抛 `dispatchUnknown("push_incomplete")`，合并检查再把它记成执行器不可达，并让整台执行器退避 1 分钟起步。命中这个分支的原因有：

| # | 原因 | 旧记录 | 能否区分 |
|---|---|---|---|
| P1 | 推送返回失败：`pushCandidateCommit` 把所有异常都吞成 `failed/other`，包括超时（合并维护里传输上限 180 秒）、认证被拒、引用被拒、GitHub 5xx、网络断开、传输前的本机校验失败 | push_incomplete | 不能，原因被吞掉 |
| P2 | 推送过程中本地中止（检查目标失效，`execution.abort`） | push_incomplete | 不能 |
| P3 | 推送成功后 `beforeDispatch` 期间本地中止 | push_incomplete | 不能 |
| P4 | 推送成功，但发布围栏已被放弃清理收回（被替代 / 已结束） | push_incomplete | 不能 |

## 3. 归因结论（11-25 的 33 次）

| 原因 | 次数 | 依据 |
|---|---|---|
| 重启后第一次推送失败（令牌刚换新，推送失败；P1，传输层具体原因当时没有记录） | 约 32（与 32 次重启对应） | 重启次数与事件数吻合；样本最近一次请求是令牌 POST 201；cardigan 3 次里有 2 次在重启后 14～22 秒；都是同一令牌 1 分钟后重试即成功 |
| 其它（P1 的其它原因或 P2～P4） | 约 1 | cardigan 17:23:59 那次不在重启附近，同期刚组成新批次，可能是本地中止或其它推送失败 |

说明：按 sensen 逐条事件时间和重启时间逐一对齐需要 sensen 项目的事件流，本卡令牌只能读 cardigan 项目，所以 sensen 的“约 32”是按当天总数与重启次数对应得出的，已请 PM 用 sensen 事件流复核。传输层的具体原因（认证被拒还是其它）旧代码根本没有记录，任何保存的证据都无法事后区分；本卡改动后，每次失败都会带上具体原因。

## 4. 改动

1. **传输层分类**（`git-transport`）：`pushCandidateCommit` 返回 `cancelled`（本地中止）、`timeout`（超过传输时限）、`local`（传输前本机校验失败）、`auth`、`rejected`、`github_error`（GitHub 返回 5xx）、`network`（连不上 GitHub）、`other`。只在内存里匹配 Git 输出，原文和令牌不会出传输层。
2. **可修原因**：同一发布围栏内，对 `auth`、`network`、`github_error`、`other` 等 5 秒后**重试一次**（参数 `pushRetryDelayMs`，默认 5000）。重启后新令牌暂不可用这类瞬时失败，在这次检查内就能恢复，不再让整台执行器退避 1 分钟。超时、引用被拒、本地中止不重试。重试时如果拿不到仓库锁，保留第一次的失败结果，不冒称 `not_started`（第一次已经进入过传输）。
3. **分类改正**（host + domain）：
   - `push_cancelled`（P2～P4，以及原有的 `not_sent`）：本地取消，**不记**任何执行器事件，也不触发退避；同一 attempt 下一轮直接重试。
   - `push_timeout`、`push_rejected`（GitHub 拒绝或报错）、`push_failed`（本机失败）：记 `merge_executor_push_failed`，说明写真实原因，**退避节奏与原来相同**；持续 30 分钟后给出针对候选推送的待办，不再写“检查机器、网络和 SSH”；恢复时写“候选推送已恢复”。
   - `push_unreachable`（`network`）以及原有的 `run_not_found`：照旧记 `merge_executor_unreachable` 和“远程检查机不可达”。
   - 事件 `failure` 新增 `push_failure` 字段（固定枚举），主机运维直接看事件就能统计。旧的 `push_incomplete` 仍然接受，以兼容旧记录。
4. 重试与互斥不变：错误类别仍是 `dispatch_unknown`，合并检查仍按原路径保留同一 attempt 等待重试；同卡互斥、发布围栏（`beginPublication` / `beginDispatch`）、C-476 放弃清理、退避计算都没有改动。

## 5. 修复后的对比（合并后跟进）

“修复后 sensen 连续 24 小时的前后对比”只能在合并部署后观测。观测口径：同一 24 小时内 `merge_executor_unreachable` 中 stage 为 push_* 的次数（预期接近 0），加上 `merge_executor_push_failed` 按 `push_failure` 分组的次数，与 11-25 的 33 次对比。
