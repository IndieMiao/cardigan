# C-758 候选推送 push_incomplete 归因与分类

## 1. 现象与已有证据

- 11-25 sensen-godot（执行器 `github-actions-sensen`）记了 33 次（卡片原文；复核后 sensen 为 32 次，见下） `merge_executor_unreachable`，`category=dispatch_unknown`、`stage=push_incomplete`，每次约 1 分钟后同一 attempt 重试成功。
- C-681 保存的 sensen 样本（18:26:16Z）：`http_status=201`。这个 attempt 记下的最近一次 GitHub 请求是**安装令牌的 POST**（`POST /app/installations/{id}/access_tokens` 返回 201）。也就是说，令牌是这次检查当场新换的，紧接着推送就失败了；GitHub API 本身可达。
- cardigan 自己的执行器 `github-actions` 在 C-681 合入后共 3 次 `push_incomplete`（项目事件流）：

| 时间 (UTC) | attempt | 前后情况 |
|---|---|---|
| 11-24 17:23:59 | 73c40f2f（卡级检查） | 附近没有部署；17:23:20 刚组成 MB-53 |
| 11-24 18:30:54 | f1b9a25c（MB-56） | 18:30:40 主机部署完成，重启后 **14 秒** |
| 11-25 18:36:46 | 5e46d041（MB-94） | 18:36:24 主机部署完成，重启后 **22 秒** |

  三次都在约 1 分钟后的第一次重试成功，事件里都没有 `http_status`（令牌由并发检查共用缓存取得，是 C-681 已知缺口）。
- 主机 11-25 共重启（`host_deployment_recorded status=deployed`）32 次（统计到 20:03Z）。PM 用 sensen 事件流复核（C-758#8）：sensen 当天其实是 **32 次**（卡片写的 33 次里，有 1 次是 cardigan 18:36:46Z 那次）；落在某次部署完成后 60 秒内、120 秒内的都是 **0 次**；有 18 次聚集在部署后 13～24 分钟，其余 14 次分散在 128～6312 秒。所以“重启后排队的检查一恢复就失败”**不成立**。

## 2. 代码路径：旧的 push_incomplete 混了哪几种原因

`github-check-executor.ts` 中只要 `beginDispatch` 返回 false 就抛 `dispatchUnknown("push_incomplete")`，合并检查再把它记成执行器不可达，并让整台执行器退避 1 分钟起步。命中这个分支的原因有：

| # | 原因 | 旧记录 | 能否区分 |
|---|---|---|---|
| P1 | 推送返回失败：`pushCandidateCommit` 把所有异常都吞成 `failed/other`，包括超时（合并维护里传输上限 180 秒）、认证被拒、引用被拒、GitHub 5xx、网络断开、传输前的本机校验失败 | push_incomplete | 不能，原因被吞掉 |
| P2 | 推送过程中本地中止（检查目标失效，`execution.abort`） | push_incomplete | 不能 |
| P3 | 推送成功后 `beforeDispatch` 期间本地中止 | push_incomplete | 不能 |
| P4 | 推送成功，但发布围栏已被放弃清理收回（被替代 / 已结束） | push_incomplete | 不能 |

## 3. 归因结论（11-25 sensen 的 32 次）

PM 两轮复核（C-758#8、C-758#10）的数据：

| 维度 | 次数 |
|---|---|
| 部署完成后 60 秒内 / 120 秒内 | 0 / 0 |
| 最近一次请求是换令牌 POST（http_status=201，令牌是当场新换的） | 5（其中 4 次 failure_count=1） |
| 没有任何 HTTP 记录（用缓存令牌，直接推送就失败） | 27 |
| 所在进程（两次部署之间）的第一次失败 / 非第一次 | 18 / 14 |
| 出过失败的进程 | 18 个，其中 4 个进程内有多段互相独立的失败 |

结论：

1. **排除**“重启后排队检查立即失败”：0 次落在部署后 2 分钟内。
2. **排除**“新令牌生效延迟”作为主因：只有 5 次是刚换令牌，27 次用的是缓存令牌；同一进程内会多次失败。
3. GitHub API 并非不可达：失败前后的 API 请求都正常，1 分钟后同一 attempt 重试即成功。32 次都不该记为“远程检查机不可达”。
4. 32 次都落在推送这一步（P1～P4），但旧代码把推送失败的原因吞成 `other`，本地中止和围栏收回也混在同一分类里。因此在 P1 内部（超时、认证、引用被拒、5xx、网络）和 P2～P4 之间，**无法用已保存的证据逐条区分**，这不是统计口径的问题。

可修部分：本卡让每次推送失败都自带原因（固定分类 `push_failure` 和 Git 退出码）、推送次数和总耗时，写进检查诊断和项目事件；本地中止和围栏收回单独分类，并且不再记为执行器故障。在同一围栏内，对瞬时失败依次在 5 秒、15 秒后重试，最多两次，这次检查内就能吸收短暂失败（11-25 的 32 次每次都是约 1 分钟后重试即成功）。合并后第一次再出现时，就能直接看出属于哪一类；若某一类集中出现（例如 `timeout` 对应 180 秒传输上限、或 `auth`），再开后续卡专门修。

不记录 Git 原始 stderr：输出里可能带认证头或令牌，C-349 规定原文不出传输层；固定分类加退出码已经能区分超时、被中止和远端拒绝。

## 4. 改动

1. **传输层分类**（`git-transport`）：`pushCandidateCommit` 返回 `cancelled`（本地中止）、`timeout`（超过传输时限）、`local`（传输前本机校验失败）、`auth`、`rejected`、`github_error`（GitHub 返回 5xx）、`network`（连不上 GitHub）、`other`。只在内存里匹配 Git 输出，原文和令牌不会出传输层。
2. **可修原因**：同一发布围栏内，对 `auth`、`network`、`github_error`、`other` 依次在 5 秒、15 秒后**重试，最多两次**（参数 `pushRetryDelaysMs`，默认 `[5000, 15000]`，围栏内最多多等 20 秒）。短暂的推送失败，在这次检查内就能恢复，不再让整台执行器退避 1 分钟。超时、引用被拒、本地中止不重试。重试时如果拿不到仓库锁，就停止重试并保留上一次的失败结果，不冒称 `not_started`（第一次已经进入过传输）。
3. **分类改正**（host + domain）：
   - `push_cancelled`（P2～P4，以及原有的 `not_sent`）：本地取消，**不记**任何执行器事件，也不触发退避；同一 attempt 下一轮直接重试。
   - `push_timeout`、`push_rejected`（GitHub 拒绝或报错）、`push_failed`（本机失败）：记 `merge_executor_push_failed`，说明写真实原因，**退避节奏与原来相同**；持续 30 分钟后给出针对候选推送的待办，不再写“检查机器、网络和 SSH”；恢复时写“候选推送已恢复”。
   - `push_unreachable`（`network`）以及原有的 `run_not_found`：照旧记 `merge_executor_unreachable` 和“远程检查机不可达”。
   - 事件 `failure` 新增 `push_failure`（固定枚举）、`push_exit_code`、`push_attempts`、`push_duration_ms`，主机运维直接看事件就能统计；检查诊断里写成“推送结果：…，退出码 N；推送 N 次，用时 X 秒”。旧的 `push_incomplete` 仍然接受，以兼容旧记录。
4. 重试与互斥不变：错误类别仍是 `dispatch_unknown`，合并检查仍按原路径保留同一 attempt 等待重试；同卡互斥、发布围栏（`beginPublication` / `beginDispatch`）、C-476 放弃清理、退避计算都没有改动。

## 5. 修复后的对比（合并后跟进）

“修复后 sensen 连续 24 小时的前后对比”只能在合并部署后观测。观测口径（sensen 11-25 基线为 32 次）：同一 24 小时内 `merge_executor_unreachable` 中 stage 为 push_* 的次数（预期接近 0），加上 `merge_executor_push_failed` 按 `push_failure` 分组的次数，与 11-25 的 32 次对比。
