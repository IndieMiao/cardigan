# C-812 受管停止后投递被推迟的通知

## 通知原来卡在哪一步

C-811 现场（A-2497 / R-13211）按代码复盘：

1. 会话仍在运行 R-13211，派发器按 `continuing_turn` 把“预检通过”的门铃推迟（`bell_wake_deferred`）。
2. 推迟超过 `CARDIGAN_DISPATCH_STALL_MS`（默认 10 分钟）后，`recordTurnWait` → `handoffUnread`（`apps/server/src/dispatch-turn-guard.ts`）把原通知行改成 `needs_attention`，同时写 `bell_wake_escalated` 告警主机运维。`needs_attention` 在通知状态机里是终态，只能 `resolve`，派发器永远不会再按这一行（attempts 停在 0）。
3. 主机操作员执行 `cardigan assignment stop A-2497`（受管停止，`hold: false`）。确认退出后的结算步骤（`stopWorkItemAssignment` 的 `released_runtime_ref` 分支）取消 R-13211、清掉终端引用，停止不再拦派发。但结算只重放停止窗口里被推迟的恢复（C-620 `replayStopDeferredResume`），不看被升级的门铃。
4. 派发器只为 `pending` 的通知起会话；此时这位负责人没有任何 `pending` 通知、也没有排队 Run，所以“有新工作时会自动起新会话”永远等不到新工作，直到 PM Ops 发新指令。

结论：卡在第 3 步。不是推迟队列没被重新评估（推迟行早已转成终态），而是受管停止结算时没有任何步骤接手这些已升级、未投递的通知。

## 修法

`packages/domain/src/commands/stop-redelivery.ts` 的 `redeliverEscalatedBells`，在受管停止结算的同一事务里、C-620 重放之后调用：

- 条件：工作项 Assignment 仍有效；工作项在可继续的状态（产出项 ready / in_progress / delivered / accepted / changes_requested，验证项 ready / in_progress）；卡片未关闭、未暂停；有运行目标；没有未结束的 Run（保留的排队 Run 或重放出的 Run 会自己起会话）；且自上次 `run_dispatched` 以来，有系统为这个 Assignment 在本卡写的、带通知的 `bell_wake_escalated`，序号在它的已读游标之后。
- 动作：发一条系统 `work_item_resume_requested`（`stop_redelivery: true`，带原升级事件和通知编号）。路由按现有规则把它投给负责人（新增：系统的 `stop_redelivery` 也可投给 delivered / accepted / changes_requested 的产出项），派发器用当前受信启动配置起新会话；新会话按游标读到原来没投递的更新。
- 同一批升级只请求一次：之后有派发，或已有 `stop_redelivery` 请求，就不再重复。
- 带 `--hold` 的人工暂停不走这一步，仍等人 `cardigan assignment start`。

不改 `continuing_turn` 推迟判定，不改通知状态机（原行保持 `needs_attention` 供运维核查），不扩大重启权限：只在主机已证明旧会话退出、受管停止结算后才请求，同一工作树不会有两个执行者。

## 与 C-570 的关系

不是同一根因。C-570 处理的是会话退役失败（`kept_terminal`、`observation=alive` 一直确认不了退出）时指令被无限挂起：解法是确认归属后直接投进原会话，以及 `bell_turn_recovery_failed` 转为可见、可重试的停滞。那条路径的门铃走 `system_finished_turn` → `bell_turn_recovery_due`，原行保持可派发。

本卡是另一条路径：`continuing_turn` 升级把原行变成终态 `needs_attention`，之后由人执行受管停止并成功结算，会话已经干净退出，但结算没有接手这些通知。C-570 的修复不覆盖这里。

## 测试

- `packages/domain/src/commands/stop-redelivery.contract.test.ts`：受管停止结算后发一次请求；`--hold` 不发；多次升级合并为一次；已派发、已读、已请求、他人的、空通知、非系统、有排队 Run、阻塞、卡片暂停时不发；delivered / accepted / changes_requested 的产出项仍会唤醒。
- `packages/router/src/next-step.contract.test.ts`：系统的 `stop_redelivery` 投给 in_progress / delivered / accepted / changes_requested 的负责人；非系统事件不放宽。
- `apps/server/src/dispatch.test.ts`：用真实派发器复现 C-811（`continuing_turn` 推迟 → 升级为 `needs_attention` → 受管停止结算），断言自动起一个新会话并把请求按到新 Run；`--hold` 时不起会话。去掉修复时该用例失败。
