# C-553：维护循环不逐候选扫项目历史

1. 按不可变事件快照为审核、合并等待和影子观察所需的历史建立键索引。保留原来的匹配条件、事件顺序、状态机与去重键。
2. 在只读事务准备提醒和审计写入；短写事务比较项目版本（清理通知时也比较通知版本），再分配真实编号、追加事件和时间线或更新通知。遇到并发修改留给下轮。Git 取证不占事务，取证后按新鲜状态评估。
3. 用真实临时 SQLite 库和至少 15 万合成事件覆盖三条路径的单轮与最长写事务、重启去重及事务间变化。不修改后台开关或合并授权。

## 逐项复核

| 路径 | 旧成本和锁 | 现在的处理 |
| --- | --- | --- |
| 审核轮数提醒 | 维护写事务中，每个等待项查耗尽事件，或查拍板解决、是否恢复；每条发现再查是否已提醒。历史部分最坏为等待项数 × 项目事件数。 | 在只读快照按工作项、恢复项、拍板编号找相关历史。只收集一次已提醒的「拍板＋工作项」，额度耗尽仍由原命令通知。 |
| PM 合并停滞提醒 | 同一写事务中，每个有效确认分别筛选并排序检查事件、确认变更事件，再全表查重。旧通知按事件编号定位原本已有快照索引。 | 按完成申请、确认编号取各自的历史，仍按流内最大序号确定等待起点；仅在停滞事件中匹配旧通知，以「拍板＋等待起点」去重。 |
| 合并影子记录 | 对已关闭拍板在锁外逐个查历史；每候选另开写事务读全状态，查检查、暂缓、分类、旧预测和评论。前一候选的写入还可能使后一候选重载历史。 | 先筛选候选、在事务外取 Git 路径，整组取证结束核对基线；再从新鲜快照评估原 16 条及 PM 门禁。按完成申请、拍板、事件类型与卡定位历史；源拍板仍可跨卡；按卡索引最近非系统评论。仅不同预测追加审计和时间线。 |

仅一处逐候选的全量查找，16.5 万事件 × 128 个候选就要检查约 2,112 万行。新实现每个所需索引在不可变快照上至多建一次，之后仅遍历相关桶；这不是说所有业务计算都是常数时间，交付、审核、依赖、工作项和真实 Git IO 的成本仍随项目变化。

### C-552 清单的其余路径（不改行为）

- `Dispatcher.claim`：仅需要新建 Run 时，在领取写事务里按这一次的 `cause.event_id` 找触发事件。每次 O(E)，不是一次持锁做所有候选的乘积。单独用 16.5 万已解码合成事件测尾部 ID 的一次 `find` 为 4.5 ms，不含读库、排队或 Run 创建。
- `DispatchMonitor.reconcile`：先读快照，随后逐 Assignment 计算，不持写锁。丢失记录本身按快照缓存；A 个 Assignment 查 L 条 loss，再对命中的 K 个查是否已有退出观察，最坏 O(E + A×L + K×E)。同规模合成数组，首次筛丢失约 1.0 ms，查一次不存在的退出观察约 1.0 ms；128 次未命中可达百毫秒量级，是后台 CPU 风险，不是本卡的写锁路径。
- `FeishuApp.execute`：是一次点击的领取、授权与执行，不是定时循环。原基线在写事务做全体事项投影、再取当前事项，来源匹配最坏 O((D+H)×E)，1093 个拍板和 186 个事项约 2.1 亿次比较。按上述 16.5 万行一次简单筛选约 1 ms 粗估，**仅旧来源查找**即可到秒级；不是飞书实测。C-552 的发送器已改为锁外准备；其共享投影也索引来源，但点击仍须事务内复核。C-552 在 151,200 事件下的首轮只读投影约 198 ms，可作规模参照，不代表点击持锁时长。

## 性能回归与并发语义

`pnpm exec vitest run --reporter=verbose apps/server/src/maintenance-history.test.ts`：三个独立临时 SQLite 库，每库先放 150,000 条无关历史，再放 128 个真实候选。测每条维护路径的完整调用（含装载、判定和落库，不含造数或其它调度任务）。冷轮实际产生 128 条提醒或影子记录；后续轮读取含新增事件的版本，无重复写入。无 Git 远程或消息网络等待。

| 毫秒：只读事务累计 / 完整调用 / 最长写事务 | 冷轮实测 | 重放实测 |
| --- | ---: | ---: |
| 审核轮数 | 203.3 / 274.0 / 14.4 | 19.2 / 19.2 / 0 |
| 合并停滞 | 199.4 / 268.0 / 12.4 | 21.5 / 21.5 / 0 |
| 合并影子 | 191.6 / 248.1 / 10.8 | 32.3 / 36.8 / 0 |
| 各路径回归上限 | 2,000 / 2,500 / 75 | 500 / 600 / **不打开写事务** |

写事务计时包含申请写锁到提交返回，是持锁时间的保守上界。每批最多 16 条；只在自己的前一批提交之后推进期望版本。抢先写入、处理通知或并发停用影子开关会使相关计划失效，未写的部分下轮重算。停滞通知清理还核对独立于业务快照的收件箱版本，不能覆盖并发 ACK。未改表结构、生产配置、提醒阈值或合并授权；数据库持续变化时可能延后一个或多个 tick。

增量复核证据的撤销不会改变数据库版本。只在预测实际依赖主机证据时，单条使用 `BEGIN DEFERRED`：先固定数据库快照并核对业务版本，再用当前信任源核对该条预测用到的证据。这样即使同一条预测需要多份证据，策略文件读取和同步 Git 查询也全在取得写锁之前。结果改变或信任源更换时不分配编号、不写事件或时间线；下轮重新计算。核对通过后，在同一同步调用中立即将同一快照升级为写事务并追加；不释放事务重开，不等待写锁。若另一个写者仍在写或已经提交，升级失败，余下计划留到下轮。普通记录仍可每 16 条一起写入。

`apps/server/src/merge-shadow-host-evidence.test.ts` 复用真实主机信任源、受保护的临时策略文件和本地 Git，覆盖一个已通过增量复核的完成申请及其 16 个待记录的合并确认。每次同步查询基线时，另一 SQLite 连接都必须能取得写锁；另断言实际追加 16 条、最长写锁仍低于 75 毫秒、重放不打开写事务，以及库外撤销后旧预测不写事件或时间线。实测整轮 277.9 毫秒，128 次 Git 调用均在写锁外，最长写事务 5.6 毫秒。持锁计时从尝试升级到提交返回，只读取证另计；整轮计时包含两者。
