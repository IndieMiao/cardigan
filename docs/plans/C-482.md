# C-482 连续驳回后的处理

- 同一验证项的第 3 次及以后的连续驳回进入现有审核上限拍板；通过或 conditional 重置，继续处理仍绑定最新驳回。列出最近三次的审核编号、必改原因摘要、类别；优先采用审核员标注，未标注时按必改内容归类。未知原因不因都未归类就视作同类。
- 最近两次连续同类时推荐换做法或收窄，也提供拆卡。收窄由 PM 写明移出本轮的范围；拆卡先以本拍板为来源建真实后续卡，再确认转移。原卡不删除必需审核、独立复核或验收条件，不把这些选择当审核通过。
- 换做法后向产出负责人发卡内指令；作者用结构化评论提交方案，当前验证项审核员明确回复该方案确认方向。只在已确认后通知作者改代码；交付准备和事务结算均检查此门禁。方案确认不是正式审核，不能给交付记通过。
- 更新默认角色包与已存在的界面文案。沿用部署时的角色指纹比对、自动升级和知会，不改生产配置。以领域契约、路由、工具及角色测试核对，运行增量构建、domain 测试类型、lint 和依赖检查。
- 方案门禁按产出项汇总：局部确认记入对应决定，最后一项确认才通知作者开工。已确认的方案及确认评论不能用普通评论替换，可回复补充；确认前作者可重新提案。
- 替换验证项不改原决定及审核记录。后继项接手待确认方案；即使旧交付已撤回，也能启动处理方案，但不能据此提交正式审核。契约覆盖提案前后替换、普通评论替换和并行确认。
- Git 卡仅确认方案时，主机启动、唤醒和 CLI 走同一目标选择：在原只读工作目录检出卡片基线，不生成交付构建目录，也不把基线或旧提交当成审核目标。确认后恢复等待真实交付；新交付到达后按其确切提交正常准备审核目录。
