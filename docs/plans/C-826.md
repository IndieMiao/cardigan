# C-826 排队中的 Run 按实时可用资源重选机器

来源：所有者 11-27“排队机制进行动态检查”；现场 SEN-C-212 在 cardigan-ci 等 godot 名额两个多小时，而 mac-mini 有空。

## 行为

- 排队巡检（`QueuedRunPatrol`，调度器每轮）对因名额排队（`queue_reason=concurrency_limit`）满阈值的 Run，用调度器自己的准入规则（解析后的资源键、机器租约与预约、项目额度、资源名额、排在前面的等待者、整机 Run 上限）逐台核对“现在能不能开工”。
- 原机器现在能开工就不动，交给正常派发；没有别的机器能开工也不动，沿用原有的 PM Ops 排队提醒。
- 有别的机器能开工时调用 domain `migrateQueuedRun`（仅 system）。同一事务内：取消原排队 Run、释放原指派（与 C-716 首发前改派相同的 prelaunch 释放证明）、在目标机器建后继指派（沿用员工、角色版本、恢复来源，`recovery.previous_assignment_id` 指向原指派），记 `work_item_assigned`、`machine_selected`、`queued_run_migrated` 事件，时间线一行：“R-n 在 原机器 排队 N 分钟（原因），已自动改到 新机器：A-旧 → A-新”。不交人，不通知 PM Ops。
- 后继指派的分配事件（system）照常唤醒它；原指派未读的门铃由调度器按 C-527 的交接规则转给后继。

## 只迁移从没开工过的指派

- 指派仍是 `not_provisioned`，没有会话、终端、工作区、分支、基线，没有派发记录（`neverDispatchedQueue`），没有启动预留或资源租约核验、待处理主机操作、角色升级或人工停止。
- 已开工的指派（有作者提交、工作区、会话）一律留在原机器继续等。跨机按备份重建要先确认旧会话退出、证明原工作区干净且 HEAD 等于中心仓库备份，C-588 还没有方案，主机也没有这类可信观测；这部分记为已知缺口，待 C-588 出方案后另开卡。
- 原机器由人或 PM 显式指定、或者是 C-826 之前的指派（`machine_selected` 没有 `requested` 字段）不自动迁移：`requested` 记录指派时调用方额外要求的 os、arch、标签，迁移按“工作项 + 角色 + requested”重新选机，现有筛选规则（状态、os/arch/标签、能力与版本、启动器、远程绑定、工作树准备、健康、冷却、容量配置）全部照旧，并且目标在实时占用下必须有余量。

## 防抖

- 排队满 `queued_migrate_after_minutes`（默认 5）才考虑；同一 Run 每分钟最多核对一次。
- 同一工作项迁移后 `queued_migration_cooldown_minutes`（默认 30）内不再迁移；冷却期过后任何机器（包括迁出的那台）都可以再作为候选，避免新机器满、原机器空时死等（PM 意见，C-826#12）。
- 每轮巡检最多迁移一个 Run。
- 优先选已有同卡产出项工作区的机器（沿用选机的 affinity 排序）。

两项都写在可信 `run-capacity.yaml` 顶层，正整数分钟；配置无效时用默认值，并照旧暂停普通派发。

## 指派时选机

- 选机读取的机器资源名额改为“实际占用 + 已指派但还没占位的指派将要占用的名额”（与整机并发数的预测口径一致），所以有排队者在等的资源不会再被当作空闲。
- 其它项目对某项资源的独占预约（日历预约，当前生效）在选机时算“现在不能开工”：该机器剩余比例记 0、`full` 写明“被其它项目预约独占”，并且排在单纯名额已满的机器之后（`not_reserved` 排序键），所以不会因为名额空着就把需要它的工作派过去。安卓设备任一只有在机器已验证的选项全部被预约时才算被挡。
- 排队重选的准入核对直接用调度器的机器租约判断（含预约、设备租约、adb 槽位），口径与 C-815 一致：先按目标机器选定多选一选项，再判断。
- 其余排序（有余量优先、控制机、同卡工作区、剩余比例、偏好、编号）不变。

## 已知未覆盖

- 已开工指派的跨机迁移（见上）。
- 安卓设备任一（`android.any`）在选机排名时不按名额区分模拟器和真机哪个有空（预约已区分）；迁移时的准入核对已按实际选项计算。
- 指派时选机只看整项资源的预约；按单台设备（`<类型>:<编号>`）的预约只在派发和排队重选时由设备租约判断。
