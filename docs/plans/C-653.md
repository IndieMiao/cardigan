# C-653 extMessageItems 改用按编号和按拍板/待办的索引

来源：C-640 计划“留给后续卡”一节；生产剖析里 ext-message 占后台 5.0%。

## 改动

- `packages/domain/src/ext-message.ts`：删掉对 `state.events` 的两次全量遍历（先建“事件编号 → 时间”映射，再逐条扫 `decision_id` / `human_action_id`）。改为每个拍板用 `eventsForDecision`、每个人工待办用 `eventsForHumanAction` 取点名它的事件；`source_event_id` 的时间用 `eventById` 取。
- `packages/domain/src/event-log.ts`、`event-index.ts`：新增 `human_action_id` 字段索引（Store 日志追加维护，普通数组懒建），和 `decision_id` 同一套。

## 不变

- 投递条目逐字段不变：来源事件仍是历史顺序里第一条点名事件（含同时带两种编号的旧事件），`activity_at` 的内容和顺序、`undated_ready` 判定、敏感、已处理、就绪都不变。
- 拍板编号是 `Q-`、人工待办是 `H-`（旧写法 `q(n)` / `h(n)`），两类编号不会互相撞上，所以按各自字段查和原来“任一字段等于该编号”结果相同。事件编号按项目唯一（主键），`eventById` 取第一条和原来映射取最后一条相同。
- 不改外部消息渠道、频率、内容格式，也不改其他读事件的调用方。

## 测试

`ext-message-index.contract.test.ts`：

- 原实现原样冻结为对照，随机生成 300 组拍板、待办和事件（含双编号旧事件、缺失或存在的来源事件、匹配与不匹配的就绪条件、非对象负载），普通数组和 Store 日志历史两种形态下输出完全相等；并断言样本确实覆盖了多次触达、有日期放行和无日期放行。
- C-643 合入后，命令态事件流不再含遥测事件（运行开始、结束等），对照实现随基线改为遍历 `fullEventHistory`。按编号、按拍板和按待办的查找本身就覆盖完整历史（Store 历史带完整历史的索引，其它数组查遥测日志），所以新实现不需要额外处理。随机样本加入了带拍板或待办编号的遥测事件，并加测两种命令态形态（普通数组拆分、Store 命令流），断言有足够多条目的来源事件只在遥测日志里。
- 在 Store 历史上给每个事件槽位计数：本函数的读取次数等于它调用的其余部分（Needs You 查询、就绪判定、知会）的读取次数，原实现多出正好两遍历史。

## 基准（合成数据，19.4 万事件、630 卡、400 拍板、200 待办，Store 日志历史，每次先追加一条事件再建新视图，25 次取中位数）

| | 每次调用 |
|---|---|
| 改前 | 40–42 ms |
| 改后 | 10–11 ms |
| 其中仍由知会和 Needs You 查询占用（未改） | 9–10 ms |

本函数自身的部分从约 31 ms 降到 1 ms 以内。

## 留给后续
