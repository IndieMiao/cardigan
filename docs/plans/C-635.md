# C-635 工具调用前的同步写去重和节流

## 问题

每次 Card MCP 工具调用在 handler 前同步执行握手（C-600）、活动时间、Run 确认三类写入。活动时间每次都写；任何一次写遇到其它进程持有写锁时，node:sqlite 会同步等待最长 5 s，整个 web 事件循环随之冻结。

## 做法

新增 `packages/mcp-server/src/tool-call-bookkeeping.ts`，由 `startMcpServer` 为每个进程创建一份。

1. **热路径不等锁**：握手、活动、Run 确认的写入都通过 `Store.withoutLockWait`（busy_timeout=0）执行。遇到 SQLITE_BUSY 时本次调用先按已算出的结果继续（握手的 listed/missing 照常决定是否拒绝），写入留在内存，由定时器退避重试（50 ms 起，翻倍，上限 1 s）。同一会话延后的握手先于它解锁的 Run 确认写入。
2. **活动时间延后、搭车**：调用只把活动时间交给 `Store.deferAssignmentActivity`。本进程下一个写事务（多为本次调用自己的 handler：游标、心跳、评论、交付、结束 Run，或 Run 确认）在 COMMIT 前顺带写入。到期仍没有写事务时才单独写一次，一次写入带上所有待写会话。到期时间：
   - 已记录的活动距今不足间隔（默认 30 s）：已记录时间 + 间隔；
   - 否则（会话刚醒来）：1 s 内。
3. **Run 确认按索引查询**：`Store.dispatchedRunIds` 替代每次解析全项目 Run（cardigan 已有上万条）。
4. **规则不变**：延后的写入在自己的事务里重新检查“指派仍 active、Token 是该会话的 Token、握手仍 pending、时间不倒退”，换会话后旧会话的迟到调用仍然不算数。

## 为什么失活判定不变

所有读取 `last_mcp_activity_at` 的判定阈值都不小于 60 s（断流恢复 60 s，失活提醒、停止期限、空闲回收以分钟计）。滞后的记录最迟在“已记录时间 + 间隔”写入，所以记录滞后期间它距今总小于一个间隔，“已静默至少 T”在 T ≥ 间隔时结论与实时记录完全一致。唯一的新窗口是醒来后的第一条调用最多晚 1 s 落库；改动前这次写入本身就可能等锁数秒。

## 观测

- 工具日志新增 `ack_writes`：本次调用在 handler 前尝试的写事务数。
- 新增 `event=tool_bookkeeping` 日志：定时补写的写事务数 `writes`、仍待写 `pending`。
- 每次调用的写事务 = (Σ`ack_writes` + Σ`tool_bookkeeping.writes`) / 工具调用数；`phases_ms.acknowledge` 对应验收的 ack 阶段耗时。
