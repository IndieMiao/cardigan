# C-639 命令状态“活跃集”第一阶段

范围按 Q-1230（PM 选 phase1）：本卡只做活跃集装载、影子比对、如实基准和跨卡场景契约测试。跨卡事实迁移、系统流按类型保留、关闭卡白名单，以及原定的 2 倍 / 1 GB 目标，转到 C-649。

## 1. 审计结论（只读）

逐个检查了 domain 112 个文件，以及 host、apps、mcp-server、router 共 93 个文件中读取 `state.events` 的位置，结论如下。

- 关闭卡的历史被约 40 处跨卡或全项目逻辑读取，例如：
  - 前置卡完成判断和关键路径；
  - 等待某张卡合并；
  - host-ops 围栏（taken 在系统流，finished 在卡流）；
  - 远端失联；
  - 只能由人处理的待办；
  - 受限批次时间线遮蔽；
  - 来源拍板的 basis；
  - 知会；
  - Run 触发链；
  - 常驻 PM 停滞。
- 系统流里大部分类型要么需要全量，要么需要“每个键最新一条”。

因此第一阶段：

- 系统流保持全量；
- 关闭卡只有在“没有任何活跃引用”时才算冷卡；
- 冷卡也只去掉经过核实、没有跨卡读取的执行遥测。

## 2. 规则

定义在 `packages/domain/src/hot-history.ts`。

**热卡**（保留整条流）包括：

- 未关闭的卡；
- 未关闭卡的前置卡、父卡、来源拍板所在卡和受影响卡；
- 有未释放 Assignment 的卡；
- 有未结束 Run 的卡（包括 `recovery_policy.card_id` 和 `bell_delivery.card_id`）；
- 未结束 Run 的触发事件所在卡，由主机按事件 id 查出；
- 有 open 待办的卡（包括 `ready_when` 指向的卡）；
- open、snoozed 或 provisional 拍板的 `card_id`、`affected_cards`、`affected_work_items` 所在卡，以及其 `ready_when` 指向的卡；
- 有未结收件箱通知（pending、belled、delivery_failed、needs_attention）的卡；
- 命令目标卡：从参数中的卡、工作项、指派、交付、审核、拍板、待办、Run 编号逐层解析得出。

**冷卡**：其余已关闭的卡。冷卡去掉下列类型，其它事件全部保留：

- `run_queued`
- `run_dispatched`
- `run_started`
- `run_finished`
- `bell_wake_deferred`
- `session_maintenance_changed`
- `machine_selected`
- `github_check_progress`

`github_check_dispatch` 保留，因为 `github_run_completed` 等待可能指向任意卡的 Run。

热数据集是全量状态的纯函数：`hotCommandEvents(full, extra)`。Store 加载器的结果必须与它逐条一致，这一点由测试和比对工具共同核对。

## 3. 实现

### Store（`command-events.ts`）

- 事件流按流惰性解码，追加时只解码已加载流的新行。
- 写入方 seq 交错时才排序。
- 64 代未读的流从缓存中淘汰。
- `ofTypes(types, exclude)` 提供按类型的增量子集。冷卡视图走这里，被省略类型的行不再解码。
- `listStreams` 对外语义不变：`get` 返回整条流，迭代顺序仍为首次追加顺序。

### 开关

- `Store.open({ commandState })` 或环境变量 `CARDIGAN_COMMAND_STATE=hot|full`。
- **默认 `hot`**；设为 `full` 即恢复原来的全量状态。
- 其它值在启动时直接报错。

### 命令状态（`mcp-server/commands/execute.ts`）

- `loadCommandState(tx, project, settings?, { targets })`。
- hot 模式下先按规则得到热卡，再用通知卡和目标卡扩展，扩展时只重建事件序列。
- 被目标或通知点名过的冷卡会“粘”进基础热集 512 代，使重复目标共用同一份历史和索引。这只会扩大热集，不会改变结果。

### 其它调用方

- `executeCommand` 和预备命令把参数和调用者指派作为目标。
- Workbench 卡片详情以卡号为目标。
- 路由以被路由流的卡为目标，派发器的 `StateLoader` 透传该选项。
- `run-capacity` 在 hot 模式下复用热历史。
- GitHub 分发日志只读 `github_check_dispatch` 子集，不再解码整条流。

## 4. 影子比对

- `compareHotState(full, hot, { now })` 在全量和热两份状态上运行同一组规则与投影，比较结果，只报告第一处差异的 JSON 路径，不输出值。覆盖：
  - 依赖刷新、合并检查阻塞、自动合并等待、PM 协调、拍板跟进、取消待办、等待恢复等系统命令；
  - `project_snapshot`、Needs You、知会、外部消息、拍板历史、关键路径；
  - host-ops 待办和每个指派的围栏。
- 回放工具：`node apps/server/test-support/hot-state-bench.mjs shadow <库副本>`。它按项目同时用 full 和 hot 两种 Store 读取，核对两件事：加载器结果与定义逐条一致；所有比对项一致。不一致时退出码为 1。生产回放需由主机侧在**只读副本**上运行，本卡**未运行**。

## 5. 合成基准

### 数据与方法

- 数据：`hot-state-bench.mjs generate`，3 个项目，每个 30 万事件。
  - 98% 的卡历史已关闭；每个项目留 24 张未关闭卡。
  - 系统流约 9%。
  - 卡上事件一半是遥测，一半是业务事实。
- 每个项目约有 21 张卡是热卡。热状态的事件数从 300,000 降到约 207,400（−31%）。
- 测量机器同时在跑其它员工任务，数值有波动。每项都在同一时段交替测量，下面给出代表值。

### 工具耗时（`bench`，10 轮 × 3 项目）

单位为毫秒，格式为 p50 / p95。

| 指标 | full | hot |
|---|---|---|
| post_comment（写命令全路径） | 9.3 / 15.4 | 9.9 / 17.1 |
| command_state（每次有新事件） | 16.9 / 20.5 | 15.2 / 20.9 |
| list_needs_you | 179 / 233 | 109 / 153 |
| project_snapshot | 163 / 221 | 144 / 164 |
| 冷启动单项目状态构建 | 1.01–1.07 s | 0.96–1.08 s |
| RSS / 堆 | 1401 / 922 MB | 1097 / 455 MB |

### 后台空闲（`background`，30 s）

派发器和合并循环按生产节奏运行，无外部 IO；共三次交替测量，数值为三次的范围。

| 指标 | full | hot |
|---|---|---|
| 空闲 CPU | 9.3–15.3% | 15.3–16.6% |
| tick p95 | 460–846 ms | 842–884 ms |
| tick max | 887–1365 ms | 1432–1540 ms |
| 重启恢复（首轮派发加合并） | 5.2–7.6 s | 9.0–9.3 s |
| RSS | 777–794 MB | 920–929 MB |

hot 的重启首轮更慢，原因在合成数据：首轮系统规则会在大量关闭卡上补写收尾事件，路由逐卡把它们作为目标扩展，每次都重建一份历史。生产库已经过了这个稳态，影响有待生产回放确认。

### 对照今天的 sensen

数据来自调研报告 1.5 节，单位为毫秒，格式为 p50 / p90。

| 工具 | sensen | 本卡 hot（合成） |
|---|---|---|
| list_needs_you | 22 / 35 | p95 153，约为 4–7 倍 |
| project_snapshot | 61 / 90 | p95 164，约为 1.8 倍 |

合成数据没有复现 cardigan 生产中 O(卡×事件) 的爆炸，所以全量模式在合成数据上也没有生产那么慢；收益要以生产回放为准。原定“每个工具不超过 sensen 2 倍、RSS < 1 GB、重启 30 s 内无 2 s 停顿”在本阶段**未达到**，转 C-649。

## 6. 已知风险与后续（C-649）

- 系统流未裁剪。cardigan 生产系统流约 6.3 万条，热状态规模仍随它增长。
- 冷卡仍保留业务事实；要做到 1/20，需要先把 host-ops finished、远端失联、常驻 PM 停滞、依赖完成等跨卡事实迁到系统流或实体。
- hot 是按审计结论选的默认值，生产只读副本回放**未运行**。如发现差异，设置 `CARDIGAN_COMMAND_STATE=full` 即可回退。
- 合成后台测量中 hot 没有带来 CPU 收益，重启首轮更慢（见上文原因）。生产收益未知，以回放和部署后的 tick_profile 为准。
