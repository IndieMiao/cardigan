# C-609 自动部署不打断在途工作

## 现场数据（部署前基线，2026-11-22 UTC 全天）

来源：本项目 50 张 11-21～11-23 建的卡的时间线，以及项目流里的 `host_deployment_recorded` 事件（只读，未触碰生产目录）。

- 自动部署 46 次，其中 1 次回滚（12:06）。
- 合并检查排队 103 次，其中 52 次以 `interrupted` 结束（约 50%），30 张卡有 50 次通过或失败。
- 52 次中断都发生在某次部署 `stopping` 之后 9～154 秒，摘要都是“检查中断或候选已改变，重新排队”。其中 47 次已经在 GitHub 上运行，5 次还在排队。
- C-587 被中断 10 次，C-589 被中断 5 次。检查要跑 15～20 分钟，而部署大约每 16 分钟一次，所以这两张卡长时间合不进去。

根因：每次部署都由一次合并触发，中心 main 因此前进。旧服务端在检查运行期间不会重新准备候选。新服务端启动后会重新准备候选，发现基线变了（`base_sha` 不同），于是调用 `interrupt()` 并重排。在当前的单级合并检查模式下，`passed()` 要求候选的树和基线都与当前 main 一致，所以旧基线上的结果本来就不能用于合并。也就是说，即使不重启，这次检查也必须在新基线上重跑。重启只决定了这件事在什么时候被发现。

## 改动

1. **受管长操作登记**（`packages/host/src/long-operations.ts`，新表 `host_long_operations`）：
   - 服务端在以下操作期间登记一行：受管送签（每个签名进程从启动到结束）、测试包外发（整个上传过程）、worker helper 自动升级（领用安装起，到机器检查日志写入最终结果为止）。行里记录拥有者进程的身份（PID、启动时间、机器）。
   - 拥有者进程已经退出的行，读取时直接删除，不会拖住部署。拥有者身份无法确认的行，按“仍在运行”处理。
   - 登记失败或表还不存在时，操作照常进行，读取时视为空列表。只会缩短等待，不会把部署卡住。
   - 合并检查和作者预检查不进这张表：它们已经有检查容量表管理。GitHub 上的运行一旦绑定，重启后可以重新接上。
2. **部署前等待**（`DeploymentController`）：
   - 部署前如果还有登记的操作在进行，本轮不占检查容量、不构建，只记录一次 `waiting_for_operations`（列出在等哪些操作），下一轮再看。这段时间新的检查照常准入。
   - 构建完成、停服之前再看一次。如果构建期间新起了操作，每 5 秒检查一次，和构建前的等待共用同一个截止时间。
   - 截止时间默认 15 分钟（`operation_wait_timeout_ms`，设为 0 关闭），按当前运行的版本计时，main 继续前进不会把截止时间往后推。
   - **停服栅栏**（新表 `host_long_operation_fence`）：决定停服时，监督器在同一个事务里立起栅栏并读取仍在进行的操作。此后申请的送签、外发和 worker 升级，在登记前等待栅栏撤除：送签任务保持 `queued`、不领用签名授权；外发在领用批准之前等待；worker 升级在领用安装之前等待。旧服务端停掉后，这些请求由新服务端执行。因此每个操作要么在停服决定之前已经开始（被等待，或到截止时间记为打断），要么在新服务端上开始，不存在“最后一次读取后才开始、随即被切断、也没记下来”的空档。栅栏读到构建后新开始的操作而截止时间未到时，撤下栅栏继续等。
   - 栅栏在本次部署结束时撤除，包括部署成功、失败和回滚。监督器进程已退出，或栅栏存在超过 30 分钟（`LONG_OPERATION_FENCE_MAX_MS`）时，栅栏不再生效，不会让操作永久停住。
   - 到截止时间照常停服，并在停服记录里写 `interrupted_operations`。每张受影响的卡在自己的项目里收到一条时间线：“…仍在进行，重启后续跑或重排”。
   - 打断后的接续方式：
     - 送签：按原请求号续做（C-601）。
     - 外发：同一个发布批准已经领用、但还没有成功记录，并且本进程里没有在途的同一外发时，可以再次调用接着传。只接受同一地址和同一包的摘要；前缀里只能有本次发布的三个文件。已有文件不重写，按公网回读校验字节和摘要；缺的文件仍然禁止覆盖写入；时间线记 `resumed`。没有领用记录时，非空前缀照旧拒绝。
     - worker 升级：同一绑定、同一发行版、状态仍为 `installing` 的升级，重启后续跑一次（`worker_helper_upgrades.resumes`）。先按当前检查结果判断：helper 已是本发行版的，只重新做 worker check 和 machine check；检查仍显示过期的，才再装一次。登记缺失、有其它阻塞或第二次中断时，按原来的失败流程处理并通知运维。
3. **部署合批**：
   - 两次重启之间至少隔开合批窗口，默认 5 分钟（`batch_window_ms`，设为 0 关闭）。
   - 窗口内新进的合并只记录一次 `waiting_for_batch`。窗口到了，部署届时最新的 main。
   - 监督器启动后的第一次部署，以及人工固定版本，不合批。
4. **合并检查接续**（`apps/server/src/merge-checks.ts`）：
   - 合并队列模式下，卡级检查只要完成项曾经通过一次就算数，与基线无关（`passedCardCheck`）。所以服务端重启后，如果 GitHub 上已绑定的卡级运行仍属于未结束、未放弃的派发记录，就直接接上并读取结果，不再中断重跑。
   - 单级模式下，基线前进后必须在新基线上重新检查。为了和真正的中断区分开，这种情况改记固定摘要“中心 main 已前进，候选已改变，按新基线重新检查”，状态仍是 `interrupted`（不改领域状态机）。
5. **记录**：
   - `DeploymentRecord` 新增 `waiting_for_batch`、`waiting_for_operations` 两个状态，以及 `deferred_operations`、`interrupted_operations`、`batch_window_ms` 字段，均有格式校验。
   - 部署项目的记录只写各类操作的数量（`{kind, count}`，按类别汇总，计数不截断），等待、停服和最终记录一致，不出现其它项目、卡号或标签。领域校验拒绝带明细的条目。
   - 逐项明细写在来源卡自己的时间线上，只有能读这张卡的人看得到：部署开始等待某个操作时记一条 `host_deployment_operation_deferred`（每个操作只记一次），到截止时间仍在进行的记一条 `host_deployment_operation_interrupted`。
   - 等待记录同一情况只写一次，不发通知，也不开人工待办。

## 约束与风险

- 没有新增人工确认、拍板或会停住的守卫。所有等待都有上限，到期一定部署。
- 部署监督器不会自我升级（见 cardigan-deploy README「升级监督器本身」）。合批和等待要在管理员按既有流程升级监督器之后才生效。服务端的登记和合并检查接续，会随正常的自动部署生效。系统会按既有逻辑自动提醒监督器需要升级。
- 外发续传需要由原来的执行者再次调用外发工具：服务端不会在后台自行续传。批准、地址和包摘要的绑定不变，也不会覆盖已有文件。
- 构建后的等待期间持有部署容量，新的检查准入会等待，最长到截止时间。

## 部署后回填

部署后 24 小时内，按同样的方法统计合并检查的排队次数、`interrupted` 次数，以及其中“检查中断或候选已改变”和“按新基线重新检查”各占多少，再统计部署次数和 `waiting_for_*` 记录，与上面的基线对比，回填到卡上。对比按实际重查次数和原因分别计数（原候选仍有效、重启后接回已绑定检查的次数；基线前进、候选失效后按新基线重查的次数；真正中断的次数），不能只靠摘要改名算作减少中断。原候选仍有效时重启接回已绑定检查，由既有 C-316 用例覆盖；本卡不启用生产合并队列。这一步要等合并并升级监督器之后才能做。
