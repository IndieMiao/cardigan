# C-600 受管 worker 上 Codex 会话连不上 Card MCP

本卡的设计说明。开发方案正文留待里程碑收尾时由规划角色统一同步。

## 现场证据（摘自卡片，地址已换成占位）

- 受管 macOS worker 开着系统代理：本机代理软件监听 `127.0.0.1:<port>`，例外列表含 `*.<tailnet>.ts.net`。
- Codex 会话启动时 Card MCP 的 `initialize` 失败：请求被交给本机代理，代理连不到 tailnet 地址；直连则返回 401，属于正常。
- 启动环境里没有任何 `*_PROXY` / `NO_PROXY`。
- MCP 初始化失败后，Run 照常启动，Agent 只能靠命令行包装发评论，原生工具缺失却没有任何告警。

## 1. 启动材料：Card MCP 主机不走代理

`packages/roles/src/mcp-proxy.ts` 由启动编译和机器检查共用。

**逐层叠加。** 每种拼写（`NO_PROXY`、`no_proxy`）的原值按从低到高的顺序取：账号继承的环境 < 启动配置的 env < Claude 的 `--settings`（它在 Claude 进程内覆盖进程环境）。

各客户端读取这两个变量的方式不同，对空值的解释也不同：

| 客户端 | 读取方式 |
|---|---|
| Python urllib、Node undici | `no_proxy` 已设置就用它（空值表示没有例外），否则用 `NO_PROXY` |
| curl、Go | 取第一个非空的（curl 先小写，Go 先大写） |
| reqwest（Codex） | `NO_PROXY` 已设置就用它（空值表示没有例外），否则用 `no_proxy` |

合并规则：

- 非空的拼写：原值恰好是 `*` 时保持不变；否则在原值前面加上 Card 主机名（小写，不带端口和括号）。
- 某一拼写在各层都没有设置时，沿用另一拼写的原值再加 Card 主机，这正是各客户端在该拼写缺失时实际采用的名单。
- 显式为空的拼写：另一拼写也为空或未设置时，所有客户端原本都没有例外，改为只含 Card 主机；另一拼写是非空名单时保持为空。此时各客户端原本就不一致（urllib、reqwest 读到“没有例外”，curl、Go 回退到另一名单），任何取值都无法同时给两类客户端加上 Card 主机而不改动其中一类的其它路由（V-2999:2 与 V-3013:1 正是这两个方向的反例）。保持为空后，读这个空值的客户端仍让 Card 走代理；若这是 Harness（例如 `NO_PROXY=""` 且 `no_proxy` 非空时的 Codex），会话核验会在期限内报出“MCP 初始化失败”，机器检查也按同一取值走系统代理并报出。
- TS 侧用 `??` 与空串判断，shell 合并块按 `${VAR+set}` 判断是否设置。

所以注入前后，任何客户端访问非 Card 地址的路由都不变。

**运行时合并。** 账号继承的值只有在 Harness 启动时才知道，所以合并都在那里做：

- **本机**：`launch.sh` 在导出之后执行 `cardigan_bypass` 合并块。编译期已知的层（profile、Claude 设置）写成字面量，继承值在运行时读取。
- **远程 worker**：helper 用 `launch.json` 的 env 覆盖继承环境，所以 `launch.json` 里不放这两个变量；`command` 改为 `/bin/sh -c '<合并块>; exec "$0" "$@"' <原 CLI> <原参数…>`，合并后原地 exec 原 CLI（同一进程）。helper、发布文件清单和协议都不变。
- **Claude**：`--settings` 里若设置了这两个变量，就在设置文件里写入合并后的值，否则 Claude 会在进程内把 Card 例外覆盖掉。设置文件在编译期写出，看不到账号继承的值：其中显式为空的拼写，只有在另一拼写由启动配置固定为空时才改为 Card 主机，否则保持为空（不改动任何非 Card 路由）。

**其它。**

- `NO_PROXY` / `no_proxy` 若被声明为 provider 的 `secret_env`（包括 Claude 设置文件里的 secret），在产出任何启动材料之前直接拒绝。
- 模型接口仍按原有系统代理或环境代理走，不另设 `HTTPS_PROXY`。

**测试。** `mcp-proxy.test.ts` 用 Python urllib 和 curl 的真实判定，以及 reqwest、Go 的规则，对比注入前后非 Card 地址的路由，要求四者都不变；Card 主机除上述保持为空的情形外都直连。它在 sh 中实际执行本机 `launch.sh` 的合并块和远程 `launch.json` 的命令。覆盖的组合：

- 单层的各种取值：只有大写、只有小写、两者都有、`*`、` * `、`localhost, * `；
- 跨层：profile 设一种拼写、账号继承另一种，以及两层都设；
- Claude 设置层与继承层叠加；
- 显式为空的拼写：单层各自为空、`*` 加空、名单加空，以及空值出现在 profile 层或账号继承层（V-2999:2、V-3013:1）。

## 2. 会话核验：只认本次启动的 Harness

开关：

- server 由 `CARDIGAN_MCP_SESSION_CHECK` 控制，默认开，设为 `0` 关闭，其它值拒绝启动。
- CLI 手动启动（`assignment start` / `pm start`）只在该变量为 `1` 时核验。

适用范围：只用于启动时必定先 `tools/list` 的 Harness，即 Codex 和 Claude Code（适配器属性 `listsMcpToolsAtStartup`）。Pi 的 MCP 适配器可能凭缓存的元数据延迟连接，不纳入。

核验流程：

- **会话密钥**：每次新建会话，主机生成一个随机会话密钥，只写进该 Harness 自己的 MCP 配置，作为请求头 `X-Cardigan-Session`：Codex 写在 `config.toml` 的 `http_headers`，Claude Code 写在 `mcp.json` 的 `headers`。密钥不进环境变量，也不进 `launch.sh`。dispatch 时，域命令在 Assignment 上记录 `mcp_handshake=pending`、密钥的 SHA-256，以及本次启动签发的 Token 编号。
- **只认本次 Token**：上一次启动的 Token 发来的请求（例如被替换会话的迟到调用）不改变新会话的握手状态，也不能确认新会话的 Run，也不刷新新会话的活动时间。确认 Run 的域命令 `acknowledgeRun` 带上请求已鉴权的 Token 编号，在同一写事务内与 Assignment 记录的本次启动 Token 比较，不符（含未带编号）时不做任何改动、不报错；`touchAssignmentActivity` 也在写事务内比较。只对记录了启动 Token 的核验会话生效，未核验的启动不变。同理，带着别次启动密钥的请求只来自那次启动的 Harness，同样不算新会话失败的证据。只有完全不带密钥的工具调用（命令行包装等）才会把 pending 记为 missing。
- **原生判定**：MCP 端点只认带本次密钥的请求，它的 `tools/list` 或工具调用会把状态改为 listed。同一 Token 的其它客户端（不带密钥或密钥不符）列出工具不算数；仍是 pending 时，不带密钥的工具调用会把状态改为 missing。
- **期限**：派发后在期限内（默认 180 秒，`CARDIGAN_MCP_HANDSHAKE_TIMEOUT_MS` 可调；如果普通派发超时更短，就以派发超时为准，以免会话先被当作派发超时重建）一直没有带本次密钥的列出，主机按同一个密钥把状态改为 missing。这覆盖了“原生 `initialize` 失败，服务端一个请求也收不到”的情况，不需要失联的会话先发一个工具调用。
- **missing 是终态**：之后该会话的所有工具调用都被拒，正文为“MCP 初始化失败：会话没有原生 Card 工具……”；不确认 Run，也不记活动。`acknowledgeRun` 在域层同样拒绝 pending 和 missing。
- **恢复**：Dispatcher 看到 missing 立即走停止流程，原因为 `mcp_unavailable`，不等派发超时。领取和开始停止时都重核证据；会话在此期间列出了工具，就撤回停止，原因记 `mcp_evidence_changed`。
  - 首次：确认终端退出后，取消原 Run，记 `failure_reason=mcp_unavailable`，重排一次（新会话）。
  - 恢复机会已用，或重建后的会话仍失败：同样先停止，确认终端退出后把该 Run 记为启动失败（`failure_reason=mcp_unavailable`），并释放会话引用。随后发 `run_dispatch_stalled`；没有 PM Ops 时另建人工待办；再写 `mcp_session_failed`，作为 Needs You 知会，显示“会话 MCP 初始化失败”。不重排第三次。
  - 停止未获确认：保留停止围栏、Run 和会话引用，按原规则上报“无法确认旧终端已停止”，不重排。之后确认退出时，照常把该 Run 结算为启动失败，但不重复上报。
  - `mcp_unavailable` 只能经停止围栏结算，不会在不停终端的情况下上报。

## 3. 机器检查：按 Harness 的实际网络路径探测

- `checkWorkerMcpReachability`（机器检查）和 `checkWorkerMcp`（远程启动预检）共用同一个 Python 探测。
- 探测在 worker 账号下读取 `_scproxy` 给出的 https 系统代理，并且不用系统例外列表，与 Codex 一致。
- 套用的 NO_PROXY 由启动编译用的同一个 `launchProxyBypass`，对该 worker 配置的启动环境计算得出，再按 Harness 的读取顺序（大写优先）取值。取值与 Harness 读到的相同：通常含 Card 主机（或原值为 `*`）；`NO_PROXY` 显式为空而 `no_proxy` 非空时保持为空，探测与 Codex 一样走系统代理并报出 `mcp_harness_proxy_failed`。
- 选中代理后，关闭 urllib 自身对系统例外的二次判断。
- 应走代理而代理不通时，报 `mcp_harness_proxy_failed`，界面文字“Agent 经系统代理连不上 Card MCP”。
- 启动材料若不再写入 Card 主机，这项检查会走系统代理路径并报出失败。测试通过生产入口模拟这一点，而不是给探测传测试专用参数。macOS 下 urllib 对默认端口的例外匹配也在测试中重现。

## 已知边界与未核事项

- 现场：Codex 在系统代理下是否套用环境里的 NO_PROXY，本卡没有在 mac-mini 实测，由 H-207 在部署后核验。若不生效，第 2 层会在期限内以“MCP 初始化失败”停止并上报，不会空转。
- 机器检查不运行真实的 Harness，只能证明“启动材料 + 系统代理”这条路径能通；Harness 是否采纳由第 2 层在每次会话启动时核验。
- 正在运行的会话不热更新，下次新建会话才带上新的环境和会话密钥。
- Linux worker 的探测运行在 `env -i` 下，看不到 sshd 登录环境里的代理变量。启动时的合并会保留这些变量，并加入 Card 主机。
- 会话密钥写在运行目录的 Harness 配置中（0600）。Agent 若刻意读取它冒充握手，只能证明自己拿得到工具清单，不扩大任何权限。
