# C-600 受管 worker 上 Codex 会话连不上 Card MCP

本卡的设计说明。开发方案正文留待里程碑收尾时由规划角色统一同步。

## 现场证据（摘自卡片，地址已换成占位）

- 受管 macOS worker 开着系统代理：本机代理软件监听 `127.0.0.1:<port>`，例外列表含 `*.<tailnet>.ts.net`。
- Codex 会话启动时 Card MCP 的 `initialize` 失败：请求被交给本机代理，代理连不到 tailnet 地址；直连则返回 401，属于正常。
- 启动环境里没有任何 `*_PROXY` / `NO_PROXY`。
- MCP 初始化失败后，Run 照常启动，Agent 只能靠命令行包装发评论，原生工具缺失却没有任何告警。

## 1. Codex 的 Card 连接：经 stdio 桥直连（C-600#111，Q-1189 确认）

**为什么不改代理变量。** `NO_PROXY`/`no_proxy` 由会话里所有进程继承，各客户端对空值的读法不同：urllib、undici 认小写的空值，curl、Go 跳过空值读另一拼写，reqwest（Codex）认大写的空值。小写显式为空、大写是名单时，urllib 和 curl 读同一个小写变量；大写显式为空、小写是名单时，reqwest 和 Go 读同一个大写变量。只要把 Card 主机写进这个变量，就会改掉其中一类客户端的其它路由；不写，Card 又会走代理（D-2307、D-2316 正是这两个方向的失败）。所以 Card 直连只作用于 Card 这一条连接。

**做法。**

- Codex 的 `config.toml` 里，Card MCP 不再是 HTTP 地址，而是一个 stdio 服务器：`command` 是 Python 解释器，`args` 是 `-I -B -c <桥脚本> bridge <Card 地址>`（`packages/roles/src/mcp-bridge.ts`）。写法与现有浏览器 MCP 的 stdio 配置相同。
- 桥从 stdin 逐行读 JSON-RPC 消息，用 `card_post` 发到配置的 Card 地址，把 JSON 或 SSE 回复逐行写回 stdout；通知（202、无正文）不回写；并发请求各自一个线程。
- `card_post` 用 `http.client` 直接连接：它没有任何代理支持，环境变量和系统代理都无法改变路由；重定向从不跟随，按错误回给 Codex。远端必须 HTTPS，用默认证书与主机名校验；明文 HTTP 只接受本机回环（127.0.0.0/8、::1、localhost）；地址里不能带用户名口令。启动编译在产出材料之前就拒绝桥不接受的地址。
- Token 不进文件：Codex 用 `env_vars = ["MCP_TOKEN"]` 只把它转给桥。会话密钥写在该服务器自己的 `env` 表（`CARDIGAN_MCP_SESSION`），只进桥进程的环境，不进 Codex 会话环境、`launch.sh` 或进程参数。桥不写 stderr，错误回复只含分类码（如 `mcp_tls_failed`）或 HTTP 状态，不含 Token 和密钥。
- 解释器：本机为 `/usr/bin/python3`；远程 worker 用该 worker 的 MCP 预检和机器检查所用的同一个解释器（`workerMcpPython`，即 `fileHelper.python`，其次 `gitHelper.python`，再次 `python3`）。
- 生命周期：桥是 Codex 为本会话拉起的子进程，随会话退出或重建结束；没有常驻中继、端口或后台进程。重建会话时会拉起新的桥，带上新的 Token 和会话密钥。
- 撤掉全部代理变量改写：`launch.sh` 合并块、`launch.json` 的 sh 包装、Claude 设置文件改写、`secret_env` 中 `NO_PROXY` 的拒绝都去掉。启动环境与本卡之前相同，任何客户端访问其它目标的路由都不变。
- Claude Code 和 Pi 不读系统代理，保持原生 HTTP 连接（Claude Code 仍带会话密钥头）。

**远程 worker。** 桥只是 `config.toml` 里的参数，`config.toml` 本来就是 helper 原样复制的启动文件（`deploy/worker-files.py` 只复制 Codex 的 `config.toml`）。worker helper、发布文件清单和协议都不变，不需要提高协议版本，旧 worker 不会被跳过；前置条件只有 worker 本来就有的 Python 3（3.8 及以上；macOS Command Line Tools 自带 3.9）。

## 2. 会话核验：只认本次启动的 Harness

开关：

- server 由 `CARDIGAN_MCP_SESSION_CHECK` 控制，默认开，设为 `0` 关闭，其它值拒绝启动。
- CLI 手动启动（`assignment start` / `pm start`）只在该变量为 `1` 时核验。

适用范围：只用于启动时必定先 `tools/list` 的 Harness，即 Codex 和 Claude Code（适配器属性 `listsMcpToolsAtStartup`）。Pi 的 MCP 适配器可能凭缓存的元数据延迟连接，不纳入。

核验流程：

- **会话密钥**：每次新建会话，主机生成一个随机会话密钥，只写进该 Harness 自己的 MCP 配置，作为请求头 `X-Cardigan-Session`：Codex 写在 `config.toml` 中 Card 桥自己的 `env` 表，由桥加在每个请求上；Claude Code 写在 `mcp.json` 的 `headers`。密钥不进会话环境，也不进 `launch.sh` 或进程参数。dispatch 时，域命令在 Assignment 上记录 `mcp_handshake=pending`、密钥的 SHA-256，以及本次启动签发的 Token 编号。
- **只认本次 Token**：上一次启动的 Token 发来的请求（例如被替换会话的迟到调用）不改变新会话的握手状态，也不能确认新会话的 Run，也不刷新新会话的活动时间。确认 Run 的域命令 `acknowledgeRun` 带上请求已鉴权的 Token 编号，在同一写事务内与 Assignment 记录的本次启动 Token 比较，不符（含未带编号）时不做任何改动、不报错；`touchAssignmentActivity` 也在写事务内比较。只对记录了启动 Token 的核验会话生效，未核验的启动不变。同理，带着别次启动密钥的请求只来自那次启动的 Harness，同样不算新会话失败的证据。只有完全不带密钥的工具调用（命令行包装等）才会把 pending 记为 missing。
- **原生判定**：MCP 端点只认带本次密钥的请求，它的 `tools/list` 或工具调用会把状态改为 listed。同一 Token 的其它客户端（不带密钥或密钥不符）列出工具不算数；仍是 pending 时，不带密钥的工具调用会把状态改为 missing。
- **期限**：派发后在期限内（默认 180 秒，`CARDIGAN_MCP_HANDSHAKE_TIMEOUT_MS` 可调；如果普通派发超时更短，就以派发超时为准，以免会话先被当作派发超时重建）一直没有带本次密钥的列出，主机按同一个密钥把状态改为 missing。这覆盖了“原生 `initialize` 失败，服务端一个请求也收不到”的情况，不需要失联的会话先发一个工具调用。
- **missing 是终态**：之后该会话的所有工具调用都被拒，正文为“MCP 初始化失败：会话没有原生 Card 工具……”；不确认 Run，也不记活动。`acknowledgeRun` 在域层同样拒绝 pending 和 missing。
- **恢复**：Dispatcher 看到 missing 立即走停止流程，原因为 `mcp_unavailable`，不等派发超时。领取和开始停止时都重核证据；会话在此期间列出了工具，就撤回停止，原因记 `mcp_evidence_changed`。
  - 首次：确认终端退出后，取消原 Run，记 `failure_reason=mcp_unavailable`，重排一次（新会话）。
  - 恢复机会已用，或重建后的会话仍失败：同样先停止，确认终端退出后把该 Run 记为启动失败（`failure_reason=mcp_unavailable`），并释放会话引用。随后发 `run_dispatch_stalled`；没有 PM Ops 时另建人工待办；再写 `mcp_session_failed`，作为 Needs You 知会，显示“会话 MCP 初始化失败”。不重排第三次。
  - 停止未获确认：保留停止围栏、Run 和会话引用，按原规则上报“无法确认旧终端已停止”，不重排。之后确认退出时，照常把该 Run 结算为启动失败，但不重复上报。
  - `mcp_unavailable` 只能经停止围栏结算，不会在不停终端的情况下上报。

## 3. 机器检查与启动预检：执行桥的同一个连接函数

- `checkWorkerMcpReachability`（机器检查）和 `checkWorkerMcp`（远程启动预检）在 worker 上以 `probe` 模式运行同一段桥源码，调用同一个 `card_post` 发 `initialize`，与 Codex 会话的实际连接逐字相同：直连、不经任何代理、不跟随重定向。URL 和 Token 只经 stdin 传入。
- 失败按原有分类报出：`mcp_tls_failed`、`mcp_unreachable`、`mcp_timeout`、`mcp_redirect`、`mcp_gateway_error`、`mcp_auth_failed`、`mcp_protocol_error`。上一版的 `mcp_harness_proxy_failed`（走系统代理）不再出现，界面文字一并去掉。
- 解释器与 Codex 的桥相同（`workerMcpPython`），所以探测也核验了桥在该 worker 上能否运行。

## 4. 测试与实测

- `packages/host/src/mcp-bridge-launch.test.ts`：用真实的主机启动流程（`launchRun`）生成 Codex 的 `config.toml`，按其中的命令、参数、`env_vars` 和 `env` 拉起桥，按 Codex 的方式经 stdio 对话；Card 服务是真实的 MCP 端点，前面套一个带 tailnet 名字的 TLS 前端。所有代理变量（大小写各一份，含 `NO_PROXY=''`+`no_proxy=<名单>` 及反过来）和模拟的 macOS 系统代理都指向一个能转发到 Card 的记录代理。判定以收件记录为准：Card 收到带 Token 和密钥的 `initialize → notifications/initialized → tools/list → tools/call`，代理收到 0 个请求；握手为 listed，只列工具不启动 Run，首个工具调用才启动。另测缺会话密钥按原规则拒绝、证书不可信时 Token 不外发且不改走代理。
- `packages/roles/src/mcp-bridge.test.ts`：配置形态（无 Token、密钥不在参数里）；地址规则；桥对 JSON、SSE、202 通知、重定向、401 和并发请求的处理；以及真实 curl、urllib 在九种大小写/空值/分层组合下，本机 `launch.sh` 和 worker `launch.json` 启动前后命中的端点（目标站或代理各自记录）完全一致，代理变量逐字不变。
- `packages/host/src/worker-mcp.test.ts`：原有探测分类全部保留；新增账号配了代理（环境变量和系统代理）时探测仍直连、代理零连接，以及直连不通时不会被可用的代理“救活”。
- 本机实测（交付附件）：真实 Codex 0.161 用生成的配置拉起桥，对真实 Card 服务完成 initialize、tools/list 和原生 whoami 调用，Run 由 dispatched 变为 running；两种冲突组合下记录代理都没有收到 Card 请求，Codex 自己的模型和其它请求照常走代理。

## 已知边界与未核事项

- 现场：mac-mini 上 Codex 经桥初始化成功并能调用原生 Card 工具，由 H-207 在部署后核验。桥在 worker 上用 Python 的默认证书库校验 TLS；机器检查用同一解释器和同一函数，部署前即可看出该 worker 能否校验 Card 的证书。
- 真实 Codex 无法在 CI 运行；CI 以按配置拉起的桥加真实 Card 端点覆盖，真实 Codex 的本机实测见交付附件。
- 正在运行的会话不热更新，下次新建会话才用上桥和新的会话密钥。
- 会话密钥写在运行目录的 Codex 配置中（0600），也在桥进程的环境里。Agent 若刻意读取它冒充握手，只能证明自己拿得到工具清单，不扩大任何权限。
