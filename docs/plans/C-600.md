# C-600 受管 worker 上 Codex 会话连不上 Card MCP

## 现场证据（卡片目标）

- mac-mini 开着系统代理（FlClash 127.0.0.1:7890，例外列表含 `*.taildf0ff5.ts.net`）。
- Codex 会话的 `initialize` 失败，经 FlClash 无法连到 tailnet 地址；直连返回 401，正常。
- 启动环境里没有任何 `*_PROXY` / `NO_PROXY`。
- MCP 初始化失败后 Run 照常启动，Agent 只能靠命令行包装发评论，原生专用工具悄悄缺失。

## 方案

### 1. 启动编译：Card MCP 主机不走代理

- 实现：`packages/roles/src/mcp-proxy.ts`，由 `compileAssignmentLaunch` 调用。
- 三种 Harness 的启动环境都在 `NO_PROXY` 和 `no_proxy` 首位写入 Card MCP 主机名（小写，不带端口、不带括号）。
- 启动配置 env 里已有的条目保留在后面。本机 `launch.sh` 用 `"${NO_PROXY:+,$NO_PROXY}"` 接上账号原有的值。
- 远程 worker 走 `launch.json` 下发同样的值。macOS core 的启动环境本来就由 `env -i` 清空，不会丢失原值。
- 模型接口仍走原来的系统代理或环境代理，所以不额外设置 `HTTPS_PROXY`。

### 2. 会话核验：没有原生工具的会话不许继续

- 开关：主机配置 `LaunchHost.verifyMcpSession`。
  - server 在 `resolveServerConfig` 读取 `CARDIGAN_MCP_SESSION_CHECK`，默认 `1`，`0` 关闭，其它值拒绝启动。
  - CLI 的 `assignment start` / `pm start` 只在该变量显式为 `1` 时核验（手动启动默认不核验，免得现有用 SDK 直连的模拟 Agent 和人工调试受影响）。
  - 测试和直接构造的主机默认不开。
- 核验只用于启动时必定先 `tools/list` 的 Harness，即 Codex 和 Claude Code（适配器属性 `listsMcpToolsAtStartup`）。Pi 的 MCP 适配器可能凭磁盘上缓存的工具元数据延迟连接，为免误判不纳入核验。
- 新建会话（dispatch 带新 `runtime_ref`）时，域命令把 Assignment 记为 `mcp_handshake=pending`。
  - 复用会话保持原状态。
  - 不开核验的新会话清掉旧状态。
- MCP 端点（`advanceMcpHandshake` 推进状态）：
  - Codex 和 Claude Code 启动时必然先 `tools/list`，收到后 pending → listed。
  - 仍是 pending 时就来的 `tools/call`，必然不是原生工具发出的，pending → missing。
  - missing 是终态：之后再 `tools/list` 也不会恢复。
  - 处于 missing 的会话，所有工具调用一律被拒，错误码 `illegal_transition`，正文“MCP 初始化失败：会话没有原生 Card 工具……”。被拒的调用不确认 Run、不记活动。
  - `acknowledgeRun` 在域层也拒绝 pending 和 missing。
- Dispatcher（`retryDispatchedRuns`）看到 dispatched Run 的 Assignment 为 missing 时，立即处理，不等派发超时：
  - 自动恢复机会未用：按 `mcp_unavailable` 停止旧终端，确认退出后取消旧 Run，重排一次（新会话）。说明里写“MCP 初始化失败”。
  - 恢复机会已用，或重建后的会话仍失败：发 `run_dispatch_stalled`，reason=`mcp_unavailable`，正文带“MCP 初始化失败”和机器检查提示。没有 PM Ops 时另建人工待办。
  - 同时写系统事件 `mcp_session_failed`，作为 Needs You 知会显示为“会话 MCP 初始化失败”。
- 停止的领取和开始都重核证据：会话在此期间列出了工具（listed）就撤回停止，原因记 `mcp_evidence_changed`。

### 3. 机器检查：按 Harness 的实际网络路径探测

- `checkWorkerMcpReachability`（机器检查）和 `checkWorkerMcp`（远程启动预检）共用同一个 Python 探测。
- 探测在 worker 账号下读取 `_scproxy` 的 https 系统代理（macOS），并且故意忽略例外列表，与 Codex 一致。
- 然后套用启动会注入的 NO_PROXY（与编译共用 `mcpProxyBypassHost`），按以下规则匹配：
  - 完全相同的主机名；
  - 后缀匹配；
  - `*`。
- 应走代理时经 CONNECT 隧道探测。失败报 `mcp_harness_proxy_failed`，界面文字“Agent 经系统代理连不上 Card MCP”。
- 修复生效后路线就是直连，不增加 SSH 往返。将来注入一旦回退，这项检查会先报出来。

## 测试

- roles：`mcp-proxy.test.ts`（三种 Harness、本机与远程、保留原有条目、在 shell 中实际展开）。快照只新增 NO_PROXY 相关行。
- domain：`mcp-session.contract.test.ts`，覆盖：
  - pending、listed、missing 的状态与会话归属；
  - 拒绝确认 Run；
  - 停止证据的重核与撤回；
  - 重建一次后上报、知会，不重复上报。
- store：`activity.test.ts` 中 `advanceMcpHandshake` 的状态迁移，以及第二个连接能读到。
- mcp-server：`acknowledge.test.ts`，用真实 SDK 客户端走 HTTP，覆盖三种情况：先列工具再调用、未列工具就调用、未开核验。
- host：`worker-mcp.test.ts`，覆盖：
  - 系统代理不可用但 NO_PROXY 覆盖时直连；
  - NO_PROXY 未覆盖、代理不通时报 `mcp_harness_proxy_failed`；
  - 经 CONNECT 代理成功；
  - 无系统代理时直连。
- host：`mcp-session-launch.test.ts`，覆盖主机启动时写入 pending（Codex、Claude Code；Pi 和未开核验的不写入）和 launch.sh 中的 NO_PROXY。
- server：`dispatch-mcp-session.test.ts`（经 Dispatcher 跑完整流程）和 `config.test.ts`。
- e2e 的模拟 Agent 改为连接后先 `listTools()`，与原生 Harness 的行为一致。

## 已知边界与未核事项

- 现场：mac-mini 上 Codex 的 reqwest 对系统代理是否套用环境变量 NO_PROXY，本卡没有在现场实测。上线后按验收标准第 5 条验证。
  - 万一不生效，第 2 层会让会话直接以“MCP 初始化失败”停止并上报，不会空转。
  - 第 3 层的机器检查只能证明这条网络路径本身能通。
- 已在运行的会话：环境不会热更新，下次新建会话时才带上 NO_PROXY。
- Linux worker：Harness 只读环境变量里的代理。sshd 登录环境中若有代理变量，本探测（`env -i`）看不到。不过启动时注入的 NO_PROXY 同样覆盖这种情况。
- 包装器识别：如果包装器也先调 `tools/list`，就会被当成原生会话。这只说明那个会话确实能拿到工具清单，不再按本卡的问题处理。
