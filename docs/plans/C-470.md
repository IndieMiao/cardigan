# C-470：后台分支备份分段发布（Q-899）

1. 保留原有来源解析和同一个中心仓库锁。每次先读取目的引用旧值，再从授权来源抓取到本次独占的临时 bare 仓库；抓取、提交类型检查、对象导入均不持共享锁、不直接写备份引用。
2. 发布时在共享锁内重新核对项目、指派、来源，按抓取前旧值原子更新引用。未登记的本地分支仍可备份，但不能越过新指派。登记分支保留成功事件，证据事务失败按旧值恢复；抓取失败不发布。不修改清理流程或其它网络操作。
3. 临时 Git/SQLite 夹具覆盖延迟传输与交互读 HEAD、并行发布和故障；记录同条件前后观测。构建、lint、依赖及相关测试在本地，完整检查以同提交预检和最终合并检查为准。

## 验证记录

- 测量方法：`apps/server/src/git-worker.test.ts` 的 `interactive HEAD` 用例；真实临时 Git 仓库、SQLite 和项目锁；只把工作机的 SSH 入口替换成临时目录的 upload-pack。在第一次备份传输入口写标记、固定等待 1.5 秒，观察到标记后发起同项目、同指派的真实读 HEAD。`performance.now()` 度量备份各次锁回调中最长的一次，以及 HEAD 请求锁到进入回调的等待；不包含 HEAD 自身的 Git 耗时。

| --- | ---: | ---: |
| 改前（`c6ef534c`，只加观测夹具） | 1624 ms | 1540 ms |

- 复测命令：`CARDIGAN_TEST_BACKUP_SAMPLE=1 pnpm exec vitest run --silent=false apps/server/src/git-worker.test.ts -t 'interactive HEAD finishes'`。常规回归改由 HEAD 完成后才放行备份，而不是对毫秒数做断言。单次合成延迟、小仓库，不是生产分位数或吞吐结论；C-468 的现场样本仅为立项背景。
- 发布同时比较旧 SHA 和逐分支代次：即使后来一次成功轮询仍指向原 SHA，也能拒绝迟到结果。代次只引用小型随机标记，不让临时抓取的提交变成恢复点。正常返回/异常均回收临时仓库；进程被强杀可能留下私有临时目录。本卡不更改清理、外部推送或通用锁策略。
