# C-805 独立复核的版本范围与等合并时的出口

## 问题

SEN-C-175：独立复核通过代码产出后，卡上又加了签名产出并交付签名包。合并闸门把“卡上全部产出的最新交付”当作复核版本，判复核过期；完成申请按验证项目标判断复核仍有效，不把复核项列入；等合并时又拒收审核。三处定义不一致，卡死在合并前。

## 统一定义

`independentReviewVersions`（`pre-merge-check-view.ts`）决定独立复核结论覆盖哪些版本：

- 独立复核项（未取消、未替换）的目标产出：始终计入；
- 其它产出：只有当前交付是 Git 提交、且不是目标产出已有的同一提交时才计入（带来了新代码）；签名包、制品、文档版本等非代码产出不计入；
- 卡上没有独立复核项时，沿用原来的全部版本。

闸门（`effectivePreMergeChecks`）对“独立复核”只比较这个范围内的版本；其它核对项不变。

## 出口

`independentReviewRechecks`（`independent-review-recheck.ts`）：闸门读到“独立复核”为待核（过期或被重置），而独立复核项仍是已通过、目标产出的当前交付已接受时，列出需要重新复核的项。

- 完成申请绑定（`completionSources`）在有这类项时不成立：不生成完成申请，已生成的由现有失效机制作废。
- 系统完成规则（`systemCompleteCard`，主机定期扫描）先重新打开：目标交付回到待审，产出项回到已交付，复核项回到就绪，作废当前完成申请（原因 `independent_review_recheck`），并发 `delivery_verifier_added` 通知复核员。合并检查运行中、批次发布中、已合并或暂停的卡不动。
- 复核员对当前交付提交通过后，结论按当前版本写入，系统重新汇总完成申请，按原流程合并。

已经卡住的卡（如 SEN-C-175）：签名包不改代码，部署后闸门直接认原复核；如果签名产出是另一条新提交，下一次扫描会重新打开复核项。

## 不在范围

- 截图核对（开启“截图核对计入代确认”时）仍按全部版本判断。
- 跨提交的等价沿用（合入基线等）不改写独立复核的核对版本，闸门会判待核，现在会走上面的出口由复核员重核。
