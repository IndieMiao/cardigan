# C-511 设置页“机器”交互：检查、排空与容量保存、新建 worker 向导

在 C-512 的只读机器页上接入 C-509 的机器操作和 C-510 的向导后端。不改服务端接口和权限，不改真实机器、账号或生产配置。

## 机器详情

- 抽屉标题行操作：`排空`（在线时）/`恢复`（排空时）、`立即检查`（本项目有绑定时，主操作在最右）。只在人类登录会话（`CapacityProvider canEdit`）且客户端提供对应方法时显示；离线/降级机器没有排空/恢复。服务端仍按当前所有者授权，拒绝时原位显示原因。
- 立即检查：`POST …/check {}` 后每秒读 `GET …/checks/:id`，进度写在抽屉反馈区（“正在检查：SSH…”），按钮变为“检查中…”并 `aria-disabled`，重复点击不发请求。打开详情时若本项目绑定记录着进行中的检查，直接跟随它，不再发起。结束后提示“检查通过”或“检查未通过：失败步骤”，并重读列表、详情和共享容量。
- 排空/恢复点击即提交。服务端不按键去重检查和排空（检查只合并正在运行的同机作业），所以这两个请求每次点击带一个操作键作为标识，但不交给传输层自动重发（`resend: false`，V-2540）。服务端明确拒绝（4xx）时原位显示原因并重读。回包丢失或 5xx 时结果未知（Q-1048）：前端无法证明这一次请求是否被受理，所以之后的读取只说明这台机器在做什么，不归因到这次请求。未知标记按项目和机器存放在本标签页的会话存储中，关闭重开抽屉、切换机器、重新读取、刷新页面都保留，不会借此重发。读回就是抽屉的详情读取：读回完成前两个操作都不可点；读回被拒（401/403/404）时立即撤下详情和写控件，重试仍被拒时继续撤下，直到之后的读取获准；普通读回失败保留上次详情，只提供重读。检查：任一绑定有进行中的显式检查（可能记在另一项目，V-2549）就跟随，显示“这台机器正在检查”；只有健康/接入记录显示“检查中”时保持不可点并定时再读；只有未知之后见过运行中的作业结束，才显示“这台机器最近一次检查：…”并解除未知。其他来源的记录变化不作结论。读取已成功、未见检查运行时，提供“仍要重新检查”，二次确认后作为一次新的检查发送。排空/恢复：读回到目标状态则显示“当前已排空/已恢复”；仍是原状态时显示结果未知，只允许同方向再执行；其他状态只提供重读。状态归属（Q-1074）：检查和排空的在途写入、未知标记、正在跟随的作业和反馈按“项目+机器”保存在页面级状态（`views/machine-actions.ts`），抽屉只订阅；请求由这份状态发出，回包也写回这里，所以关闭重开抽屉、旧请求晚到的回包都作用在同一份状态上。在途写入和未知标记同时写入本标签页的会话存储，请求在途时刷新页面，重新载入后按未知处理。读回是否“新鲜”按页面时钟判断：只有未知之后才发起、且获准的详情读取才算。进度读取带作业号和令牌，只采用当前作业的回包；详情和进度共用一个结束入口，按作业号核对，只清理该作业的进度错误和重试，较早作业的结束不影响正在跟随的新作业。同一台机器同时只有一个进度读取。未知提示只写“上次检查请求结果未知”，不带传输层原因；确认框关闭后焦点回到打开它的按钮，按钮已不在时回到“立即检查”。检查和排空各自显示反馈，排空不会清掉检查进度的“重试”；本页已看到结束的检查不会因较旧的读数再次跟随。
- 跟随哪个检查（Q-1076）：不比较主机给出的开始时间，只看证据的发出时刻（页面时钟）。页面在跟随对象变更、跟随的检查结束或开始核对时，把当时的页面时钟记为栅栏。只有晚于栅栏发出的详情读取或启动请求，才能开始跟随或换成另一个作业；服务端同一台机器同时只运行一个检查，所以这类证据显示运行中的作业就是当时唯一在跑的。早于栅栏的证据只能更新同一作业的步骤，或提供终态（终态不论新旧都成立）。若它声称另一作业在运行，就不切换，“立即检查”保持锁定，并只读重读详情；只有晚于这次核对标记发出、且获准的详情读取能解除锁定。核对期间跟随的检查结束时，标记随之前移。读取失败或被拒时，检查一行只写“未能确认正在进行的检查”，重读用详情读取自带的“重试”（只读，与 Q-1048 读回失败一致，不另设第二个重读按钮）。本页见过结束的作业永不再跟随。作业事实与界面反馈分开（Q-1083）：任何来源见到的终态（详情记录、进度读取、启动回包）都先记入本页的事实表，不论是否正跟随该作业，记录本身不改按钮和反馈；表中的作业不再跟随、也不再读进度。启动回包报“运行中”而编号已在表中时，直接以表中结果作为本次请求的结果。开始跟随新作业时清掉上一作业的结果和错误，上一作业的结果只留在“最近检查”历史中。进度回包与本次请求（Q-1085）：进度回包的编号等于所请求的编号且为终态时，先记入事实表，再由轮询代次决定能否改按钮、反馈和定时器。“立即检查”的启动回包给出的编号即本次请求对应的作业；本次请求的反馈只能是它的结果：已知且未跟随其他作业时立即显示；正在跟随别的作业时，那个作业在途只显示其进度，结束后显示本次请求作业的已知结果，未知则不显示任何结果，不以其他作业的结果代替。
- Agent 并发上限从原“并发与容量”分栏移到详情“资源上限”，沿用 `useSettingWrite` 即时保存（失焦/回车、保存中只读、失败留草稿、离页失败在反馈栈提示“回到设置”到 `?tab=machines`）。值取自详情自身的机器读数（Q-1013：抽屉只显示一个上限），该读数登记为设置读数以确认写入；共享容量读数仍确认离页后的写入。本项目没有绑定的机器只显示上限事实；只读会话的“仅人类登录会话可修改”放在行的悬停说明里。
- 原“并发与容量”导航项保留，点击进入“机器”；旧链接 `?tab=capacity` 以替换历史的方式落到 `?tab=machines`。合并检查目标以只读分组列在机器列表下方，与机器列表同样遵循共享容量的 stale 状态：读取失败后运行中/排队/上限显示“—”，直到之后的读取成功。

## 新建 worker 向导

- 面板标题行“添加 worker”打开抽屉。表单在本地按服务端同样的规则先校验（机器编号、`cg_` 账号、UID/GID ≥ 501、端口），macOS 固定 arm64。
- 预览：显示服务端返回的脱敏差异（私有值为“已隐藏”）和有效期；只有“确认写入配置”才调用 `confirm`。
- 检查：显示全部步骤记录（配置核对、九步 1～9、能力刷新）及耗时；受阻步骤原位显示原因码、修复建议，有对应命令时可直接复制。“目标机命令”列出账号、目录、工具、helper 四条命令，可复制，人工执行后点“继续检查”/“复查”。运行中每秒读取进度。
- 远程派发：通过后在“需谨慎”分组里先“预览开启”，勾选“我确认开启远程派发”后“开启远程派发”才可用；勾选只属于当时那一份预览（按预览编号），换成新预览须重新勾选。预览过期，或被服务端判为失效（`worker_preview_stale`，即使未到期、编号未变）后不再可提交，改为“重新预览”；配置预览被判失效时“确认写入配置”不可用，只能“返回修改”后重新预览。可直接“完成”不开启。
- 续办：浏览器只按项目在 `localStorage` 记住向导编号，服务端接受预览即记录（与抽屉是否仍打开无关）；关闭抽屉提示“已保留添加 worker 的进度，可稍后继续”，按钮变为“继续添加 worker”。会话不在了（404：重启、超时）时提示重新填写并清除记录。已记住的会话暂时读不到时不显示空白表单，只给“重试”或明确的“放弃并重新填写”。服务端拒绝读取（401/403）时撤下向导内容、命令和操作，重试获准后恢复。任何一次成功读取都会继续进行中的轮询（含手动重试）。每次读取只对发起时仍是当前会话的编号生效：放弃、取消或新建会话后，旧会话迟到的成功或 404 都被丢弃，不会清除或替换新会话。步骤提交中关闭/Escape 不关抽屉。向导请求不自动重试；失败后重读会话以显示真实状态，并保留该操作的错误说明。
- 文档：`docs/linux-worker.md`、`docs/macos-worker.md` 新增“5a. 用 Workbench 向导接入”。

## Q-1088 事件矩阵：启动回包与 A/B 终态

沿用 Q-1085 已确认的行为，不改服务端协议和权限，不推断请求是否被受理，不比较主机时间。

**共同前提（步 1～3）**：点“立即检查”，启动请求 P 挂起；详情读到 A 在运行，页面跟随 A 并读 A 的进度（该读取挂起）；较新的详情读到 B 在运行，页面改为跟随 B 并读 B 的进度。此后到达的事件：

- **P**：启动回包，`running`，编号为 A、B 或 C（见下）。
- **EA**：A 的进度回包（迟到，终态通过或失败）；A 也可能始终没有回包。
- **EB**：B 的进度回包（终态通过或失败），同时详情记录 B 已结束。
- **EC**：C 的进度回包（终态）。只有页面跟随 C 后才会读 C 的进度，所以 EC 一定在 P 之后。

**结论：给定各作业的终态，页面状态只取决于已到达了哪些事件，与到达顺序无关。** 所以矩阵按“已到达事件的集合”列出，测试生成全部顺序，每到一个事件都按下表断言。

### P 的编号为 A 或 B

| 已到达 | 跟随 | 反馈 | 按钮 |
|---|---|---|---|
| 无 / EA | B | 正在检查：MCP… | 锁（检查中…） |
| EB / EA+EB | 无 | 正在开始检查… | 锁 |
| P / P+EA | B | 正在检查：MCP… | 锁（检查中…） |
| P+EB | 无 | P=A：不显示结果；P=B：B 的结果 | 可用 |
| P+EA+EB | 无 | P=A：A 的结果；P=B：B 的结果 | 可用 |

- 结果文案：A 失败“检查未通过：SSH”，B 失败“检查未通过：MCP”，通过“检查通过”。P=A 时任何一格都不出现 B 的结果，P=B 时不出现 A 的结果。
- P=A、A 尚无回包时，P 到达会触发一次只读核对；核对读回前反馈可短暂为“正在读回机器状态…”，表中写的是读回后的状态。之后 EA 到达（P+EB 后再来），就补上 A 的结果，按钮保持可用。
- 每一格：启动请求恰好 1 次；进度读取最终为 [A, B]，已结束的作业不再读进度。

### P 的编号为 C（主机在 B 结束后才处理这次请求）

| 已到达 | 跟随 | 反馈 | 按钮 |
|---|---|---|---|
| 不含 P | 同上表前两行 | | |
| 含 P、不含 EC | C | 正在检查：工具… | 锁（检查中…） |
| 含 P 和 EC | 无 | C 的结果 | 可用 |

P 早于栅栏，先只读核对，核对读到 C 正在运行（晚于栅栏），才改为跟随 C；迟到的 EA、EB 只记事实。启动请求 1 次，进度读取 [A, B, C]。

### 不可达或不展开的组合

- **P=C 却早于 B 结束**：主机同一台机器同时只运行一个检查，B 运行时到达的请求会合并到 B，不会另开 C。
- **EC 早于 P**：页面没有跟随 C 就不会读 C 的进度。
- **P=C 且 A 通过**：与 A 失败相同（A 的结果在 P=C 时不作答复），只展开 A 失败与无回包两种。
- **A 在页面切到 B 之前就结束**：此时 A 是正在跟随的作业，按常规结束，B 由之后的详情读取接手，不属于“切换后迟到”。
- **P 本身就是终态**：等同于 P 和被点名作业的结束同时到达，已有回归覆盖。
- **进度读取出错**：B 的进度读取失败时照旧显示“未能读取检查进度…”和“重试”，保持锁定（已有回归），不在本矩阵展开。

### 现状与改法

- 当前提交 799fd558 上，116 格中 25 格不符，全是同一种：**B 失败、且 EB 早于 P**。启动回包未到时 `end()` 还不知道本次请求对应哪个作业（`asked` 为空），就把 B 的失败当作结果写进反馈；反馈区错误优先显示，盖住了“正在开始检查…”。B 通过时文案被发送中状态盖住，所以不暴露。attachment-8273 的第二条也属于这一类。
- 改法：启动请求未回包期间，作业结束照常记入事实表、停止跟随、前移栅栏、重读，但不给出任何结果，反馈保持“正在开始检查…”。P 到达后，由已记下的事实答复本次请求（Q-1085 原路径）。只改 `machine-actions.ts`，进度读取错误的重试、按钮锁、防重复提交不变。
