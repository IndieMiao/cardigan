# P2-V V1 员工实体

- 对应：`docs/plans/phase-2.md` §3.1 V1；产品方向见开发方案 §1.4"人只提需求"。
- 前提：P2a-6 已确认 Assignment 级的"审核者不是作者"（开发方案 §4.5 第 15 条）。
- 开发方案要改的章节：§4（新增 Employee 实体）、§4.4（员工状态）、§4.5（员工级不变量）、§9（`whoami`）、§10（启动配置的选择顺序）、§13.1（CLI）、§20.2（如有新的包内模块）。

## 1. 目标

1. 新增员工（Employee）：有名字、职位、简介、头像引用，担任一个角色，可以单独配启动配置（Agent CLI + 网关 + 模型）。
2. 指派时可以点名员工；只给角色时，系统从该角色的在职员工里挑一个。
3. 时间线、交付、审核、评论里能查到"是哪个员工做的"；Agent 用 `whoami` 能知道自己是谁。
4. 没有员工的老数据和老用法完全不变。

## 2. 关键设计

### 2.1 员工是全局的

- 员工不属于某个项目：一支团队服务所有项目，团队页（V6）按人展示。编号全局分配，形如 `E-1`。
- 员工担任的是角色编号（例如 `coder`）。指派到某个项目时，该项目必须登记了这个角色，否则拒绝并说明。
- 数据库新增全局表 `employees`（不带 `project_id`）。员工的增删改走 domain 命令，事件写入一个全局事件流；项目内的事件只引用员工编号。如果现有事件和存储全按项目组织、做全局流代价太大，可以退一步：员工命令的事件记在"创建员工时指定的主项目"下，但员工记录本身仍是全局的。实现时在 PR 里说明选了哪种。

### 2.2 字段

| 字段 | 说明 |
|---|---|
| `id` | `E-n`，全局唯一，不复用 |
| `name` | 显示名，例如"诸葛亮"；在职员工之间不能重名（不区分全半角空格差异，去掉首尾空白） |
| `title` | 职位，例如"产品经理" |
| `bio` | 一两句简介，可空 |
| `avatar` | 头像素材引用（V4 之前可空，只存引用字符串，不存图片） |
| `role_id` | 担任的角色 |
| `launch_profile_ref` | 可空；为空时用角色的启动配置 |
| `status` | `active` / `inactive` |
| `created_at`、`updated_at` | 审计 |

- 名字、职位、简介有长度上限（例如 40 / 40 / 200 字），不能含控制字符。
- 停用（`inactive`）不影响已有 Assignment 继续完成手上的工作，只是不再被分配新工作；不提供删除，历史记录要能一直显示名字。

### 2.3 指派

- `assign` 新增可选参数 `employee_id`（CLI `--employee <E-n 或名字>`，MCP `assign` 同样）。
- 指定员工时：员工必须在职，`role_id` 必须等于工作项要求的角色，且通过 §2.5 的不变量。
- 只指定角色时：在该角色的在职员工里挑一个——先排除违反 §2.5 的，再优先选当前没有未结束 Run 的，再按最近一次被指派的时间最早者。没有任何在职员工时，沿用现在的行为（不带员工），保证老项目不受影响。
- 一个员工可以同时有多个 Assignment（员工是身份，不是单个进程）。
- Assignment 记录 `employee_id`（可空），创建后不能修改。

### 2.4 启动配置

- 编译启动配置时，选择顺序：员工的 `launch_profile_ref` → 角色的 `launch_profile_ref`。
- Run 已经记录了模型和 CLI 版本；再记录本次用的 `employee_id` 和 `launch_profile_ref`，保证可复现。
- 员工改了启动配置，只影响之后新开的 Run，进行中的不变。

### 2.5 不变量（开发方案 §4.5 新增）

- 员工级的"审核者不是作者"：验证工作项的 Assignment 所属员工，不能是其目标产出项任何一个（当前或曾经的）Assignment 的员工；完成申请的验收项同理，不能是主产出项的员工。双方都没有员工时不检查（沿用 Assignment 级规则）。
- 停用的员工不能被指派。
- 员工的 `role_id` 必须与工作项要求的角色一致。

### 2.6 显示和查询

- 时间线、交付、审核、评论、附件的 `author` 字段保持现状（`assignment:A-n`），读取视图里补上 `employee`（编号、名字、职位、头像引用）。没有员工的显示为"未命名的 <角色>"。
- MCP `whoami` 返回员工的编号、名字、职位（没有员工时这些字段为空）。
- Workbench 本次只在已有显示作者的地方带出员工名字（文字即可）；头像、团队页、筛选等是 V4–V6，不在本任务。

### 2.7 CLI

- `cardigan employee add --name <名字> --title <职位> --role <角色> [--bio <简介>] [--launch-profile <名字>] [--avatar <引用>]`
- `cardigan employee list [--role <角色>] [--all]`（默认只列在职）
- `cardigan employee update <E-n> [--name] [--title] [--bio] [--launch-profile] [--avatar]`
- `cardigan employee deactivate <E-n>` / `activate <E-n>`
- `cardigan assign <W-n> --role <角色> [--employee <E-n 或名字>] ...`
- `--launch-profile` 必须是 `launch.yaml` 里存在的名字，否则拒绝；不能借此改角色。
- 中文输出、非零退出码，沿用现有 CLI 风格（含 C-18 的中文错误说明）。

## 4. 测试

- domain 契约测试：员工的创建、更新、停用和恢复；重名拒绝；字段校验；停用员工不能指派；角色不匹配拒绝；员工级"审核者不是作者"的每种拒绝和放行；没有员工时的老行为。
- 指派选择：指定员工、只给角色时的挑选顺序（排除作者、优先空闲、最早被指派）、没有在职员工时退回老行为。
- 启动配置：员工配置优先，为空时用角色的；Run 记录员工和配置。
- 存储迁移：老数据库升级后老数据可读、Assignment 没有员工字段时正常。
- CLI：每个命令的成功和错误输出。
- 实现方只跑改动所在包的测试和 `pnpm lint`、`pnpm check:deps`；全量和 e2e 由主机侧检查负责。

## 5. 不做

- 头像素材导入（V4）、员工出现在所有界面（V5）、团队页（V6）、网关和接入点管理界面（V2）、Agent 侧按员工身份发言和 `@员工名`（V3）。
- 员工之间的权限差异（权限仍由角色决定）。
- 删除员工。
