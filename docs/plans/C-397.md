# C-397：检查排队统一由 Cardigan 管理

## 任务与实现选择

按 C-397 / W-1365 的最终验收口径，移除 `.github/workflows/cardigan-check.yml`
的 `concurrency` 段。GitHub 同组只保留一个 running 和一个 pending，后续派发会
取代旧 pending；按卡分组使不同预检和合并检查相互影响。

本卡选择完全移除重复分组：Cardigan journal 已在持久事务中管理执行器容量和
同卡互斥，不需要 GitHub 再维护另一份队列，也不需要引入新的组名和输入。
`check-workflow.test.ts` 断言工作流及所有 job 均无 `concurrency`，避免在 job 层
重新引入相同问题。检查步骤、输入、权限、hc 安装及主机配置均保持原样。

本说明取代 `flow-v2.md` §4.2 / D2 中的“同卡 concurrency 组兜底”约定，其余
可信工作流和主机调度约束继续适用。前置 C-396 已按本卡记录随基线
`dbc0516b971b995704ea79401133d17c2c52acfc` 部署。

## 主机正确性依据

| 约束 | 现有实现及回归 |
| --- | --- |
| 容量、同卡互斥 | `GithubDispatchJournal.claim` 在同一事务内拒绝未结束的同卡检查，并按执行器统计占位；executor 测试覆盖跨卡容量、同 attempt 幂等和不同 attempt 等待 |
| 可信身份及结果 | `GithubCheckExecutor.bind/validateRun` 核六字段运行名、工作流路径、基线历史、触发身份和首次运行；poller 按已绑定 run id 复核身份及步骤合同，不读取并发组 |
| 未知状态保守占位 | 丢失派发响应或本地不可达不释放 journal；重启按原标识恢复，不重复 POST；journal 和 executor 测试覆盖 SQLite 重开及未决派发 |
| 取消与恢复 | lifecycle 按绑定 run id 取消；poller 取得可信远端终态后才回收占位；取消失败继续观察，过期和被取代的派发保留原恢复边界 |

核对后未发现依赖 GitHub 并发组保证正确性的主机逻辑，本卡无需修改执行器、
journal 或取消实现。实际检查、发布门禁与自动重跑策略沿用既有行为。

attempt、检查类型、GitHub run id、工作流来源版本、状态及排队/取消原因；

同时核对 Cardigan 仍按既有执行器容量调度，同卡未结束或状态未知时仍占位，
只在远端可信终态后接续下次检查；被取代检查仍由主机按原身份取消。

不伪造卡片或 attempt，不取消无关运行，不改变并发上限或同卡互斥。

runner 可用性仍可能造成平台排队，移除组不承诺消除所有 queued。
