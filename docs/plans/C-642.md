# C-642 读交付源两阶段与机器探测短缓存

## 读交付源（`apps/server/src/git.ts` `withAssignmentSource`）

submit_delivery、request_recheck 的交付校验和 request_check 的 HEAD 读取原来整段持有项目仓库锁：锁内解析运行目标、经 worker upload-pack 远程取对象、计算证据、写 ref。现在分两段：

1. 锁外：解析运行目标；`GitDeliveryVerifier.prepareVerify` / `prepareHead` 完成校验和全部 Git 读取。远程取对象改用 `GitCentralPort.fetchBranchTip`：与分支备份同样的私有 stage（`central/.incoming-*`，借中心对象协商），只把分支 tip 的对象导入中心仓库，不写任何 ref（含 FETCH_HEAD），stage 用完即删。
2. 锁内：先复核运行目标未变，再只写本地 ref：`refs/cardigan/incoming/...`（按读到的旧值 CAS）、`refs/cardigan/candidates/<A>/<sha>` 或 `refs/cardigan/prechecks/<A>/<head>`（只建不改）。

行为保持：被拒的交付仍记录本次读到的 incoming tip；格式错误等不需要取对象的拒绝不进锁。锁等待超时仍按 C-628 分类为“仓库忙”，运行目标错误带原因码，其它只给错误类别。

观测：每次进入锁写一行 `{"event":"delivery_source_lock", project_id, assignment_id, operation: "verify"|"head", wait_ms, held_ms}` 到 server 标准输出，用于部署后核对“持锁 p95 < 2 s”。

## 机器探测短缓存（`packages/host/src/runtime-targets.ts`）

探测指 `rawMachineCheck` 里的实时观察：`git --version`（本地为 hc 健康）加 worker 就绪和 MCP 可达性。按 (项目, 机器, 执行模式, 目标绑定指纹) 合并：

- 同时进行的探测共用一次（single-flight）。
- 启动、唤醒前准备等 launch 路径（`forLaunch`、`forSession`、`captureFor`）复用 5 s 内结束的干净结果。
- 显式检查（`check`、CLI/Workbench 检查、巡检 `refreshMachine`）始终重新探测，结果覆盖缓存；失败或有阻塞项的结果不缓存。
- 机器状态、远程启动开关、升级保留和绑定是否变化仍每次实时读取；绑定变化即换新键。

配置：`CARDIGAN_MACHINE_PROBE_CACHE_MS`，默认 5000，取值 0–60000 的整数，0 关闭复用（仍合并并发探测），非法值使运行时目标创建失败。

## 说明

现有 worker（带 git helper）路径的读交付源本身不调用上述活体探测；锁内耗时主要来自远程 upload-pack 和锁内 Git 读取。探测合并作用于启动和唤醒路径，与读交付源的两阶段独立。
