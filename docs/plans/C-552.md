# C-552：外部提醒不占用后台写锁重算

1. 一次索引事项的首个来源事件；复用工作台的拍板筛选，不为推送构造完整页面。已处理、已读事项不新建发送记录，仍复查已有待发记录。
2. 从一致的只读快照准备投影和发送；短写事务核对项目版本、绑定和租约。版本冲突留给下一轮，不用旧快照发送。不改变去重、退避、免打扰汇总及敏感信息规则。
3. 用合成生产规模数据计时，覆盖首次启用、事务间变化及重启；在飞书文档说明启用行为，记录后台其它相似路径，不顺带修改。

## 性能验收

真实临时 SQLite 库：151,200 个事件（来源放在十五万条无关事件后）、1,000 个未决拍板、200 个未办事项。首次与下一轮各新增并发送 32 条。用模拟渠道排除网络等待，Store 观察器记录完整只读投影和最长写事务（包括提交）；另计整个 tick 的墙钟时间。

| 毫秒 | 冷启动实测 / 上限 | 后续版本实测 / 上限 |
| --- | ---: | ---: |
| 读快照与计算 | 181.7 / 2,000 | 27.4 / 200 |
| 单次最长写事务 | 9.2 / 50 | 10.0 / 50 |
| 整轮（含 32 次领取和结果提交） | 449.0 / 3,000 | 297.2 / 750 |

冷启动包含首次 SQLite 读取与 JSON 解码；不是对生产时延或网络的承诺。上线后由负责人恢复总开关，观察后台 tick 和 Web 数据库超时，再安排绑定。

## 同类路径排查（仅记录）

- `apps/server/src/dispatch.ts` 的 maintenance 写事务调用 `escalateReviewLimitWaits` 和 `escalatePmMergeStalls`：`review-limit-attention.ts`、`pm-merge-stall-attention.ts` 均为每个 finding 在全项目 `events.some` 查是否已提醒。
- `apps/server/src/merge-shadow.ts`：外层逐拍板筛选的 `events.some` 在写锁外，但每个候选的 `recordMergeShadow` 在写事务内重新计算，还会全量过滤 `system_merge_shadow_recorded` 查上一条。
- `apps/server/src/dispatch.ts` 的派发领取事务按本次 `cause.event_id` 调用 `state.events.find`；一次领取一次扫描，不是单事务内对所有事项做笛卡尔遍历。`dispatch-monitor.ts` 中 `reconcile()` 逐 Assignment 查 remote loss 的扫描则在只读快照之后，不在写事务内。
- 飞书点击回调的 `FeishuApp.execute` 也需要新鲜状态，仍在用户操作写事务中重核授权，并非轮询发送；本卡不拆该事务或放宽交互校验。

## 返工回归（V-2716）

- 逐渠道区分「本轮待发写入已达上限」与「仍有可发送的免打扰事项未入队」。仅后者推迟尚未冻结的汇总，已冻结的重试、普通提醒继续使用原有规则。测试覆盖 33 个免打扰事项、1 个普通事项、两批之间关闭并重开 SQLite：普通事项独立送达，最终只有一条总数 33、展示 20 项的汇总。
- 同一份不可变事件快照中，按卡片和完成交付索引最新合并检查；可选树版本取对应树的最新 seq，排队原因只取本尝试在排队之后的最新系统事件。契约测试比较同一规模历史中 1 个与 8 个「人已确认、当前检查失败」的拍板：都在外部投影可见，访问无关事件的次数不随拍板数增长。未修改合并权限或失败接管规则。

## 返工回归（V-2722）

- 22:00 创建的 33 个就绪事项，直到次日 07:59:59 才首次扫描；首批只建 32 行且不发送，08:00:00 没有任何业务变更也应只发一条 33 项的汇总。不能单靠来源时间判断，也不能将醒后新增事项算入。
- 每个项目和渠道（含应用绑定代次）只在有需要时保留一份未入队成员清单，只含事项类型和编号。成员判定、编码在只读快照内完成；清单和本轮最多 32 条入队记录一起提交。写入前核对快照版本、绑定和清单版本，首次领取汇总时也复核清单版本。清单排空后删除，不改原发件箱、重试预算或权限。
- 另测跨三批重开数据库，未入队先办结者不补行，醒后普通事项不等汇总；两发送器交错扫描时旧快照不能覆盖已提交的静默资格。生产规模用例同时覆盖静默扫描和醒后继续入队，沿用相同的只读投影、整轮及写锁阈值。
