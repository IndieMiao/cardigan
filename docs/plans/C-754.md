# C-754 外发拍板发起时校验格式和主机发布配置

## 背景

SEN-C-127（0.4.4 对外发布）：所有者批准后连续失败两次。一次是拍板为 `kind=choose`、没有 target（`approval`），一次是凭据文件被写进 6 个 profile（`configuration`），另有包名配置过期险些在 manifest 失败。错误只有一个词，PM 看不懂。

## 改动

1. **发起时校验格式**（domain `requestDecision`）：`category=publish` 且带 `publish` 选项的拍板，要求 `kind=approve`、带 `card_id`、`attachment_ids` 恰好一个且在本卡、target 为该附件完整 SHA-256 的 `artifact_sha256`、`publish` 选项说明为“发布到 <HTTPS 地址>”。缺 target 而附件唯一时自动补齐；其余不合格项一次列全并附正确格式。不带 `publish` 选项的 publish 类拍板沿用原规则。
2. **发起时主机预检**（mcp-server `request_decision` 改为预备命令）：格式合格后调用主机注入的 `precheckPublication(project, 附件, URL)`。主机实现（`apps/server/src/publish-precheck.ts` 的 `approvalPrecheck`）复用 C-607 的只读预检，并增加：URL 是否符合 `origin/前缀模板/app.apk`（版本取自 URL、`<sha12>` 须为附件前 12 位）、附件按登记 SHA-256 取出、签名证书、包名、版本名、该版本发布目录为空。任一失败：拍板不创建、不进 Needs You，PM 收到逐条原因；同时给主机操作员建一条 `executor=operator` 待办（同卡同内容只保留一条未结）。本主机未开启外发时预检直接报“本主机未开启测试包外发”。预检本身不写 OSS，不动卡片。
3. **失败子原因**：`PublicationError` 增加固定文案 `reason`，返回和审计写作 `类别（子原因）`。approval 子原因由 domain `publicationApprovalProblem` 给出（kind、target、附件、未批准、代批授权等）；configuration 子原因区分配置不可读、项目缺失、字段不合格（只列字段名）、credential_file 不符、凭据 profile 数量、名称、模式、地域、缺 AK；signature、manifest、immutable_prefix 也给出子原因。均不含路径以外的配置值和凭据。
4. **工具说明**：`request_decision`、`publish_artifact` 描述写明外发拍板正确格式（共用 `PUBLISH_APPROVAL_FORMAT`）。不改角色包正文。
5. **主机命令**：`publish-precheck-main.js <项目> [<APK> <版本名>]`，用法写在 `deploy/README.md`。

## 默认值

- URL 中版本名格式沿用 `publish_artifact` 的 version 规则（字母数字开头，`._-`，最长 80）。
- 发起时无法得知 versionCode，预检只核对版本名；versionCode 仍在外发时核对。
