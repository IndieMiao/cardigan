# C-492：用 Markdown 导入一组角色配置

1. 在 roles 包解析严格的 YAML 页首与正文，不把文件路径或主机配置交给客户端。`based_on` 创建时优先取本项目同名角色，其次取默认包；`default:<编号>` 指定默认包。创建后以目标自身为底稿，继承不是动态引用。正文是完整 instructions；导出旧角色时以 `prompt_format: legacy` 标识 core_prompt。`tools.add/remove` 是增删，`tools.set` 是导出时用的完整集合，两种写法互斥。
2. 在 host 组合既有领域命令。`template.id` 是目标，`from` 是底稿（已有目标可省略）；`replace_role` 把底稿中指定角色改为本角色，或 `add_work_item` 在底稿上增加一项（角色隐含为本角色）。内置模板只可复制。员工按在职规范名比对；完全相同跳过，不覆盖不同资料，头像仅支持人物库。
3. 项目 API：`POST /role-document/preview` 接受 `{markdown}`；`POST /role-document/apply` 接受 `{markdown,snapshot}` 和 `Idempotency-Key`；`GET /roles/<id>/export` 返回 `{markdown}`。快照绑定输入、项目、所依赖的版本与启动配置。预览使用只读事务；应用在幂等事务内读取最新状态、检查快照、重算并写入角色、模板、员工及事件。无新版本时不写事件。沿用人类角色管理和员工所有者边界，不增加 MCP 工具。
4. CLI 使用同一主机服务；`role apply 文件` 只打印预览，`--yes` 才执行，`role export 编号` 的标准输出只含文件内容。测试覆盖整体回滚、冲突、幂等、权限和导出往返，不改设置页和默认角色包。

## 文件示例

```markdown
---
role_id: proofreader
display_name: 校对员
based_on: reviewer
launch_profile: review-profile
tools: {remove: [project_snapshot]}
template: {id: proofread, from: dev, replace_role: reviewer}
employees:
  - {name: 小林, title: 校对员}
---
对照验收标准检查稿件，逐条列出需修改的地方。
```

`review-profile` 须替换为本机已有的启动配置。预览和应用都返回 `role`（动作、目标版本、字段差异、放宽项）、`template`（动作与前后内容，未指定为 `null`）、`employees`（动作与资料）和不透明的 `snapshot`。员工新编号仅在实际应用后返回。重复发送同一应用请求沿用原幂等键；收到 `409 stale_target` 时重新预览并为新请求生成新键。
