# C-616 附件大小上限改为主机配置

## 配置

- `CARDIGAN_ATTACHMENT_MAX_MIB`：整数 MiB，1–64，未设或空白取默认 10；其它写法（小数、带单位、超出范围）在进程启动加载附件模块时报错，错误信息带变量名和范围。
- 上限 64 MiB 是作者选定的可配置天花板：base64 请求体整体进内存，再大应走制品流式上传（C-496）或 C-614 的 OSS 通道。

## 推导关系（`packages/mcp-server/src/attachment-limits.ts`）

| 项 | 来源 |
|---|---|
| 解码后字节上限 | `mib × 1 MiB` |
| base64 长度上限 | `4 × ⌈bytes / 3⌉`（MCP `upload_attachment.file.maxLength`、Workbench 上传 schema） |
| 请求体上限 | base64 + 1 MiB（MCP `maxRequestBodySize`、Workbench 附件接口 `readJsonBody`） |
| 已存附件读取上限 | 固定 64 MiB（`MAX_STORED_ATTACHMENT_BYTES`），保证日后调低上限后旧附件仍可读取、预览和下载 |

## 各层

- MCP：工具描述和 schema 随配置；超限报 `Attachment exceeds N MiB`。
- Workbench 接口：base64 超长直接 413 并写明上限；解码超限 400，同一文案。`/api/session` 登录后返回 `attachment_max_bytes`。
- Workbench 前端：评论框在发表评论前检查粘贴图片大小，超限提示“附件不能超过 N MiB。”，不先建评论；服务端英文报错翻译成“附件超过 N MiB”。
- CLI：本地预检和帮助文字随配置；服务端报错按同一键翻译。
- worker 助手：upload-evidence 连接后 `tools/list` 读取 `upload_attachment.file.maxLength` 换算上限（取整到 MiB，最多 64 MiB；旧服务端或读不到时按 10 MiB）；download-attachment 普通附件按 64 MiB 天花板校验，仍以 SHA-256 绑定全部字节。旧版助手继续按 10 MiB 工作，不影响 10 MiB 以内的上传下载；新版随部署发布的 agent-tools 更新，发布清单和协议不变。

## 部署后跟进

- 在 GS66 的 server 运行环境（selfdeploy 单元或 runtime.env，CLI 也需同值）设 `CARDIGAN_ATTACHMENT_MAX_MIB=30`，重启。
- 反向代理（若有）请求体上限 ≥ 41 MiB。
- Workbench 与 mac-mini 各用约 20 MB 文件验证上传、下载 SHA-256 一致，并回填内存与响应时间实测。
