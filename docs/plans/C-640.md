# C-640 事件索引改为 Store 追加维护

对应 C-633 扩展性评估第 3.1 节 A2（P1-2）。

## 改动

- `packages/domain/src/event-log.ts`（新）：
  - `EventLog`：按项目只追加的事件日志，就地维护按流（卡）、按类型、按字段（`decision_id`、`completion_id`、`work_item_id`、`resume_work_items`）、按 id 的索引。每条事件 O(Δ)，不复制、不重排任何流。
  - `EventLogView`：用序号水位（`baseEnd`/`end`）限定的只读视图，实现 `listStreams` 返回的 `ReadonlyMap`。之后的追加不改变已有视图、它物化的数组和索引答案。
  - `history(order)`：按“项目流 → 各卡流（卡片顺序）→ 流内 seq”的既有契约一次拼出 `state.events`，并挂上索引。
- `packages/domain/src/event-index.ts`：`eventsOfType` 等查找先用挂在数组上的索引，没有时保持原来的按数组懒索引，结果完全一致。新增 `appendEvents(base, tail)`：`[...base, ...tail]` 复用 base 的索引，只索引 tail。命令里把草稿历史传给查找函数的位置改用它。
- `packages/store/src/command-events.ts`：事务内新读到的行进事务私有的 overlay；COMMIT 时并入共享日志，ROLLBACK 直接丢弃 overlay。共享日志与它缓存的答案只含已提交事件，所以未提交的索引不会泄露。流内 seq 倒退（仅测试夹具）时走重建，重建出的新日志在提交前同样私有。
- `packages/mcp-server/src/commands/execute.ts`：`eventHistory` 改用 `streamHistory`。
- 事务内的 `events.listAfter`（`Store.uow.run` / `read`）改由同一视图回答：同一条流，seq 升序，含本事务未提交的写入，每次返回新数组。不再执行 SQL 扫描，也不再逐行 JSON.parse。事务外的 `getUpdates` 仍走 SQL。

## 不变

- `CommandState.events` 的顺序、内容和不可变语义不变；没有批量端口的后端仍走原路径，结果一致。
- 依赖方向不变：日志是 domain 内的纯内存结构，没有 IO。

## listAfter 调用方评估（张良 11-23 剖析）

- 本卡已处理：生产剖析第一热点是 `listAfter` 自身（SQL 全量扫描加逐行解析，后台 self 21.7%）。事务内的约 45 处调用现在全部由日志回答，调用方不用改。
- 留给后续卡：
  - 调用方拿到整条流后再按类型过滤，仍是 O(流长度) 的数组遍历，但不再有 IO 和解析。这类调用包括 merge-push-loop、web card-state 与 merge-queue-state、get-check-log、deployment-roles、reconcile-helper-actions、support-tools、publish-artifact。可以改用按类型索引，或者 since_seq 游标。
  - web `stream.ts:122` 逐卡 `.at(-1)` 只为取最大 seq，属于 C-633 P0-2 的范围。
  - `extMessageItems`（ext-message 5.0%）对 `state.events` 做两次全量遍历（建 id 到时间的映射，再扫字段）。可以改用 `eventById` 加按 decision 和 human_action 的索引，要动 domain 语义，单独拆卡。

## 已知限制

- `state.events` 仍是普通数组，每个新快照要做一次按精确长度的指针拷贝（不排序、不逐条处理、不重建索引）。要彻底去掉，得靠 P1-1 热数据集，或者改 domain 的数组契约。
- 日志常驻内存：19.3 万事件约 31 MB。旧路径每个快照都重建约 14 MB 的索引再丢掉；新路径常驻多出约 17 MB，换来每次追加不再产生这部分垃圾。
- “GC 占比小于 5%”是生产剖析指标，要部署后用剖析复核；微基准分母太小，不能用来判断这一项。
