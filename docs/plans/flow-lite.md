# Flow Lite：按“个人/小团队本地工具”定位精简开发流程（计划）

日期：2026-11-16。依据：张良整合的流程评审（Opus 176 卡、Codex 225 卡两份独立报告，`~/.cache/cardigan-host-checks/zl/flow-review/`）和用户当天的拍板。

## 用户拍板（2026-11-16）

1. 提高“交人”的门槛，减少需要人亲自处理的卡。（补充：这几类只是**默认**交人，不是强制；人可以对任何一类开启授权，由 PM 或系统自动拍板。）
2. 提供一个开关，打开后由系统直接自动合并（类似 Claude 的 bypass、Codex 的 yolo）。
3. 只有高危改动才需要独立复核。
4. 卡片不再逐张修改开发方案，优先以卡片信息为准。
5. 评审给出的五个优化方向都要做，尤其是方向 5：后续多机（Mac、Linux）、飞书消息、多 Agent、更多模型、配置等都会涉及大量集成测试。

定位：Cardigan 是面向个人和小团队的本地开发 Agent，不是多租户平台。默认值按这个风险级别来设。

## 批次与范围

### 批次 A：规则、提示词、文档（不改领域逻辑）

A1. AGENTS.md
- “独立复核”一节改为：只有命中高危路径（见 B3）或人标记为高危的卡，才必须配独立复核。`permission`、`numeric_rule` 等标签只作分类和知会，不强制独立复核。
- 第 5 条改为：实现卡不修改 `docs/development-plan.md` 正文。设计说明写在卡片目标、PR 描述或 `docs/plans/<卡号>.md` 里；开发方案由 Claude 在里程碑收尾时统一同步。
- 合并规则改为：开启自动合并时，由系统合并；强制交人的只剩 B1 列出的几类。

A2. 角色包（packages/roles）
- PM：
  - 数值、阈值、重试间隔这类细节，由作者或 PM 选一个可配置的默认值，在卡上知会，不交人拍板。
  - “是否分阶段交付”由 PM 自己决定。
  - 验收标准不超过 5 条、写结果不写实现合同。
  - 不把已授权的事项再升级给人。
- reviewer、independent_reviewer、design_director：只有正确性缺陷、安全漏洞、缺测试可以列为 must_fix。其它意见写成建议，不挡合并。一次收齐问题，不追加新范围。
- coder：交付前必须跑 lint（biome）、受影响包的测试（含快照）、`check:deps`；有预检工具时，首次交付前先跑一次预检。
- 同步更新 `packages/roles` 的测试，以及 AGENTS.md 和角色正文的一致性测试（pm-lessons）。

### 批次 B：系统机制（领域与服务端）

B1. 缩小默认交人的范围（用户第 1 点）
- **默认**由人确认的，只保留下面几类。用户补充：这些不是强制交人，人可以在偏好里逐类开启授权，由 PM 或系统自动拍板（包括合并确认）；人标记的敏感卡同样可以通过授权放开。系统里不再有“永远只认人”的硬编码类别，包括原来的 permission：
  - 花钱（spending）；
  - 凭据和账号（account/credential）；
  - 删除真实数据（data_deletion）；
  - 对外发布（publish）；
  - 人手动标记为敏感的卡（sensitive）。
- `permission`、`scope_change`、角色规则改动（Q-279）、`human_required_reason` 里的一般情形，改为“PM 或系统处理，并知会人，人可以撤销”。
- 已验收产出的正式返工：如果卡的范围是人亲自拍板改的（来源拍板），PM 可以直接执行返工，不再逐次交人。
- 修复返工依据失效的缺陷：同一张卡上的加轮、指派等无关变动，不应让已经发出的返工确认（例如 Q-749）永久失效。依据只绑定目标交付、目标提交和撤回的审核。

B2. 自动合并开关（用户第 2 点）
- 新增项目偏好 `auto_merge`，取值 `off | on`，默认 `off`，只有人能改。
- 开启后：卡片满足以下条件，系统就直接合并并自动部署，不生成合并确认：
  - 必需的验证项全部通过；
  - 合并检查通过；
  - 没有未处理的 must_fix；
  - 不属于 B1 的强制交人类别。
- 同时在时间线和 Needs You 里给人发一条知会。
- 保留现有的暂停开关 `auto_merge_paused`、部署失败自动回滚、发布前的身份核对（CAS）。
- 尽量复用 Flow v2 A3 的系统合并实现：这个开关开启时，不受 `flow_version` 和 `FLOW_VERSION_MAX` 限制，对在途的旧卡也生效。

B3. 高危路径才独立复核（用户第 3 点）
- 新增项目偏好 `high_risk_paths`（JSON 路径数组）。默认包括：
  - `packages/store/migrations/**`、`packages/store/src/**` 里的迁移相关文件；
  - 部署：`packages/host/src/deployment*`、`apps/cli/src/self-deploy.ts`；
  - 凭据、令牌、密钥处理；
  - Agent 隔离、运行时、账号边界（agent-ssh、runtime-herdr 的隔离部分）；
  - 执行器身份绑定；
  - `.github/**`。
  具体列表由实现方按代码核对后给出，在 PR 里写清楚。
- 只有交付差异命中高危路径，或人手动给卡打了高危标签，完成申请才要求同卡配必需的独立复核。其它卡只需代码审核。
- 现有的 `risk_tags` 保留，用于分类和统计，不再单独触发独立复核硬门。
- 独立复核轮数用完时，按 B2 的系统加轮规则自动加轮；超过上限才发异常给 PM。

B4. 审核结论跟着代码树走（方向 2）
- 重新交付时，如果相对上一份已审版本只有以下变化，原有的审核结论保留，审核员只看增量，或者直接沿用：
  - 合入了新的 main；
  - 只解决了合并冲突；
  - 只改了格式（lint 自动修复）；
  - 只更新了快照。
- 判断依据是 range-diff 和树比较。
- 审核轮数只计驳回（reject），通过和沿用不计。

B5. 冲突源（用户第 4 点的系统部分）
- 合并冲突如果只出在 `docs/development-plan.md`：由系统按“两边都保留”自动解决，或直接提示作者，不计入审核轮数。
- 在批次 A 生效以后，这种情况会越来越少。

### 批次 C：集成探针模式（方向 5，用户重点）

目标：对接真实外部环境的工作，例如 GitHub Actions、多机（Mac、Linux）、飞书消息、多 Agent 和多模型、各类配置，允许负责的 Agent 在受控的沙箱目标上直接、反复验证，跑通端到端冒烟后，再交一张带证据的卡做事后审核。

C1. 探针档案（主机私有配置 `probes.yaml`，不进仓库）
- 每种集成定义一个沙箱目标，以及允许的操作：
  - **github**：只能推 `ci/probe/*` 分支、只能用 `kind=precheck` 派发、只能取消自己派发的 run；用 GitHub App 身份；有 REST 配额上限。
  - **machine**：Mac mini、Linux 测试机上的专用测试账号（不是生产 agent 账号），通过 SSH 跑命令；只能使用测试目录。
  - **feishu**：测试群的机器人 webhook 或应用凭据，只能发到测试群。
  - **model**：各模型提供方的测试密钥，有每日花费上限。
  - **config**：在临时数据目录里启动一个隔离的 Cardigan 实例（临时 SQLite、临时端口），做配置和启动验证。
- 凭据只放在主机侧，Agent 拿不到原值，由主机代为执行，或者注入到临时子进程。

C2. 探针工具
- 给 coder（或新增的 integrator 角色）一个 `run_probe` 工具：传入探针名、操作和参数，由主机在沙箱里执行，返回去敏后的结果和日志。
- 所有调用都写审计，产生的资源（分支、run、消息）由系统清理。

C3. 流程
- 卡片模板 `integration@1`：开发（可以调用探针）→ 端到端冒烟证据 → 代码审核 → 合并。冒烟证据作为必需附件。
- 探针目标出错时，只影响沙箱，不影响生产。

C4. 需要人准备或拍板的
- 各个沙箱目标：Mac 测试账号、飞书测试群和机器人、模型测试密钥及花费上限。花钱的部分要拍板。
- 探针允许的操作清单。

## 落地方式（这次的教训）

- 每个批次由一个 Agent（Codex 或 Opus）在临时克隆里一次做完：实现、本地全量测试、必要时在 GitHub 上跑预检。然后只开一张卡，附上补丁和证据，走代码审核和合并检查，由人确认合并。
- 批次 A、B 可以并行：A 只动文档和提示词，B 动领域和服务端，二者的冲突面很小。
- 批次 C 先出设计，用户确认沙箱资源后再实现。

## 不在本计划内

- 合并队列、批量合并（评审方向里优先级较低的一项）。
- 删除现有的硬安全保护：发布前的 CAS 身份核对、凭据隔离、防重复派发。

### 批次 B 补充（2026-11-16，用户要求“找出导致频繁拍板和阻塞的约束，简化或移除”）

B6. 审核轮数
- 轮数只计驳回。
- 轮数用完时，由系统自动加轮，独立复核同样适用（取消“独立复核永不自动加轮”）。
- 同一个验证项连续驳回超过 3 次，才升级给 PM；PM 处理不了再交人。

B7. 员工隔离
- 独立复核员只要求不是本次交付的作者，不再核对“当前及历史 Assignment（含已释放）”。

B8. 人工待办
- 现场验证、实测类人工待办默认不挡合并，改为合并后跟进。
- 只有需要提供凭据或外部账号这类前置操作的，才设 blocks_merge。

B9. 角色升级
- 默认角色包变化如果来自已合并的卡（代码已经审过），部署时自动升级，并知会人；只有手改过的角色出现冲突时才交人。
- 常驻会话由系统在空闲时自动轮换。

B10. 新角色、新模板
- PM 可以创建为草稿并知会人，人可以否决，不再走 permission 拍板。（可选，视实现成本决定。）
