## 1. 是否仍有用途

Flow v2 实现卡已完成。C-341#53 记录 GitHub 排队异常期间实际回退 SSH，随后切回 GitHub；#55 记录人结束逐次观察，#56 由人取消观察卡。SSH 仍是已有回退路径，不能据此认定已经退役并自动取消本卡。

当前源码的 `CheckRecovery.sweep` 在没有执行器或执行器为 GitHub 时直接返回。因而 SSH 恢复锁调整对当前 GitHub 检查没有即时收益；收益限于后续使用 SSH 时的恢复诊断与已经正常清理资源的登记核销。未读取实时生产配置、部署目录或远端锁属性，以上现场事实仅引用卡片记录，不声称是当前现场快照。

## 2. 同版路径与安全意图

| 入口 | 调用条件与锁 | 安全意图及属性 |
| --- | --- | --- |
| `prepareCheckLock` | `temporary-checkout.ts` 中没有远端 `prepared` 结果时；local 或不带 host 的同机隔离账号 | 主机准备自己的持久锁，要求本进程属主，0600/0660；不是远端恢复使用的锁 |

| `recoverCheckDirectory` | 要求 host；`CheckRecovery.sweep` 跳过 GitHub | 非 root worker，逐槽位打开原锁；要求非自身属主、单链接、空普通文件、无任何写位、无 POSIX ACL，并成功排他取锁；后续仍校验资源身份、挂载与退出/缺失证据 |
| GitHub | 独立执行器 | 不使用上述 SSH 恢复 worker，不调整其路径 |

`deploy/install-agent.py` 不预置检查锁。现有书面预置要求位于 `docs/plans/p2a-12-remote-merge-check-host.md`：root 所有、0644 空文件。恢复程序的 `st_mode & 0o222` 会拒绝其中的属主写位。这并不说明 root/0644 授予执行账号写权限，也不说明本地准备与远端恢复互相冲突。

### 证据与限制

本次新增隔离回归在同一锁 inode 上分别设置属主、组、其它写位：均在 `stage=lock` 返回 `manual_attention/unverified`，尚未扫描进程。仅去掉写位后，完整存在的资源仍返回 `exclusion_unproven` 并保留；只有夹具模拟正常清理、完整身份条件仍成立、资源全缺失且再次确认后才返回 `cleaned/complete`。

夹具沿用既有测试边界：管理员属主与保护目录链被虚拟化，挂载和进程扫描由假数据替代；模式位、文件描述符、Git 登记和 flock 使用真实临时文件。该测试证明写位拒绝及后续合同，不证明真实 root 账号隔离、远端 ACL、当前占用或生产核销成功。

历史 H-68/attachment-2754 仅由 C-329#230 的更正说明及本卡验收引用，本次未重读原附件，不将其计作新的现场证据。没有逐次归因全部历史 `unverified`。

## 3. 可选方案

| 方案 | 具体改动 | 安全与收益 |
| --- | --- | --- |
| A：统一远端预置为 root/0444（建议） | 选择后修订远端预置文档；原授权操作员在批准窗口内仅对通过核验的原锁去掉写位，保留 inode；主机私有脚本由其另行维护 | 保留现有恢复校验；0444 可供执行账号只读打开并 flock。仅解除锁阶段的模式位拒绝，不保证核销，不改变移交围栏 |
| B：允许 root/0644 | 另行设计并审核“执行账号实际不可写”的判断，涵盖属主、组、补充组、ACL、目录替换能力与并发身份稳定性 | 放宽恢复信任规则；不能只删除 `0o222` 条件。按本卡要求先由 PM 汇总交人审，再实现和独立复核 |
| C：保留现状 | 不改文档默认值、恢复程序或现场锁；保留拒绝结论 | GitHub 路径无影响；回退 SSH 后该模式仍阻止恢复。若人决定 SSH 完全退役，再由 PM 提议取消本卡 |

本次只交诊断、回归与可审方案，未应用 A/B。A 不需要修改 `prepareCheckLock`、空闲探针或恢复 worker。不能为了让恢复通过而调整本地锁模式，不能以无占用替代完整缺失合同。

## 4. 方案 A 操作单草案（选择并获现场批准后，由原授权操作员执行）

1. 固定实际控制器与执行版本、执行目标、已有槽位数及需要处理的登记；读取生产版本对应源码，确认与本文合同一致。目标或版本无法绑定则停止，不把本地基线当作已部署版本。
2. 使用已有移交流程阻止所有相关生产者准入；等待在途检查正常退出并完成原有清理。未知、占用、不可读、无法取得完整围栏时保持现场，不发信号、不强制退出、不替换锁。
3. 对每个**已存在**的原槽位锁逐级核对父目录、符号链接、属主、有效访问权限、ACL、挂载和替换能力；锁须 root 所有、空普通文件、单链接、当前模式为已批准的 0644，并记录 device/inode/uid/gid/mode。检查所有槽位，不创建缺失锁，不自动修其它异常。
4. 使用经审核的操作入口按目录描述符和 `O_NOFOLLOW` 打开原锁，核对 fd 与路径仍指向记录的同一文件；持有原锁的排他互斥及已有移交围栏，对该 fd 去掉写位为 0444。复核路径与 fd 的 device/inode/uid/gid 不变、size=0、nlink=1、无 ACL；任一漂移即停止并保留围栏。不得使用重建、复制覆盖、删除再创建或宽泛 chmod 命令。
5. 保持移交围栏，先显式释放第 4 步取得的临时排他锁并关闭本次持有的 fd；不删除、替换原锁。然后在同一批准窗口核对执行账号能只读打开与取原锁、有效权限仍不允许写入或替换，验证完成后同样解锁并关闭验证用的全部 fd。出现异常也收尾本次临时 fd，保留原围栏和未核状态，停止后续步骤；不能让本次持锁阻断后续空闲探针。
6. 临时锁均已释放后，通过原移交流程验证目标就绪并恢复准入：由现有控制器执行 `checkTargetIdle` 等完整检查，再按原 generation/binding 和容量等条件解除围栏为 `open`。此步不调用恢复 worker，也不以 `cleaned` 为解除围栏的前置条件。若仍有残留目录、Git 登记、占用、不可读或退出证据不足，原就绪检查会拒绝；保留围栏及资源，停止操作，另按获准处置处理，不绕过探针、强行开围栏或为解除围栏先运行恢复。
7. **只有第 6 步成功且相关围栏均已开放后**，才把精确登记的显式重查/正常恢复作为单独受控步骤，仍由现有入口校验当前执行器、登记身份、原锁和准入。保持 GitHub 执行器时原恢复巡检仍跳过 SSH，不为核销切换目标或直调 worker。SSH 路径可能遇到新检查持锁或新围栏，按现有 busy/未知/准入拒绝处理并保留未核结果；不承诺解除围栏到恢复之间持续空闲。只接受完整身份、挂载和缺失二次确认后的 `cleaned`；存在、局部缺失、身份不符、未知或占用都保留原资源与拒绝状态，不手改登记、不删除目录、不增加围栏内恢复授权入口。
8. 回传实际版本、目标、原锁身份前后对照、临时 fd 释放、就绪验证、围栏解除及随后恢复各阶段的独立结果。围栏解除前异常继续保留围栏，不执行第 7 步；解除后恢复失败不冒称已核销，也不撤销后来建立的围栏。是否恢复原模式另按批准的回退操作处理，禁止重建 inode；未执行或未取得证据的阶段明确记“未核”。

空闲探针会取锁，恢复会写审计事件；这些步骤都须在相应批准范围内执行，不能当作无副作用读取。

顺序依据：`CheckRecovery.sweep` 在认领、IO 和缺失确认时无 grant 调用 `assertCheckAdmission`，非 `open` 的同目标或同项目围栏会拒绝恢复；现有入口不支持围栏内核销。V-1916 指出的旧第 6/7 步顺序已据此修正。既有 `host/check-recovery.test.ts` 的 `the original handoff fence blocks recovery IO` 用例覆盖围栏阻止 IO 和 IO 中新增围栏禁止发布 `cleaned`；移交控制器的就绪/解除合同见 `apps/server/src/check-handoff.ts` 及其测试。

不新增轮询/退避数值，不改并发容量。现场确认是后续工作，不以凭据或外部账号前置为名阻挡软件合并；本次方案选择本身须先完成。
