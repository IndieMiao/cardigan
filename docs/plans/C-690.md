# C-690：mac-mini 上的 claude 作者会话收到通知后不续起（sensen A-100）

## 结论

A-100 停工的根因是**回收交接（handoff）把仍在的会话一直挡在派发外**，与 Agent 是否退出无关。共有两种情况：

1. **旧会话留下的交接（本卡主因，对应 retirement_handoff_changed）**
   - 空闲回收在 mac-mini 上连续 3 次无法确认空闲后，会转成交接，诊断显示为 `retained_for_dispatch`。实例：04:56Z 三次撤回。
   - 人工 `stop --hold` 释放终端时只清空 `runtime_ref`，`start` 用 `dispatchRun` 绑定新终端，两步都不处理 `idle_retirement`。旧会话的交接因此留在新会话上，`runtime_ref` 仍指向已关闭的旧终端。
   - 这条旧交接会挡住新会话的所有后续动作：
     - **派发**：`busy()` 只要看到 `handoff` 就返回 `idle_retirement`，门铃和排队 Run 都不投递。R-1836 一直排队、10:05Z 的提醒没有 `run_queued`，都是这个原因。
     - **停滞诊断**：有排队 Run 时，交接不属于当前会话，诊断报 `retirement_wait` 且 `restart_blocked=retirement_handoff_changed`；只有通知时，因为存在 `idle_retirement`，诊断报 `session_maintenance`。
     - **主机运维**：`host_ops_restart_assignment` 拒绝带交接的指派。
     - **会话维护**：交接不属于当前会话，维护不按 `retained_for_dispatch` 处理，而是等 60 分钟空闲后重新回收。这期间一直被挡。
   - 每次人工重启都把交接带到下一个会话，所以 A-100 一天要人工处理 5～6 次。诊断里那种“退役交接状态反复变化”也是这个原因。
2. **当前会话的交接，只有通知**
   - 交接属于当前会话、处于 `waiting`（没发过信号），之后只来了通知、没有排队 Run。
   - C-575（Q-1133）的运维接手只处理带排队 Run 的交接；派发器又把交接当作忙碌。所以这种情况没有任何路径能续起。
   - 实例：04:56Z 交接后，07:04Z 张良 @A-100，等了 5 分钟仍没有 `run_queued`。

### 为什么诊断写 agent_exited=false

诊断与实际一致：Agent 并没有退出。

- C-602 之后，mac-mini 上终端的主程序是空闲 owner（外层 Python），claude 是它的子进程，与它同属一个进程组。
- hc 报告的 `pid` 和 `foreground.pid` 都是 owner，不是 claude。本机用真实 hc 0.1.21 复现过：父进程等待子进程 `sleep` 时，`foreground.pid` 仍是父进程。
- 主机运维的 worker 巡检（`inspect-worker.py` 的 `terminals()`）只列 hc 报告的这两个 PID。所以无论 claude 在不在，看到的都是“只剩外层 PID”。
- C-672 的探针按 claude 的出生身份判断，给出的“未退出”是对的。C-672 的自动续起一直没有触发，也是因为 claude 本来就在。

### A-100 与 A-182 的差别（按代码路径推断，生产库未核）

| | A-100（coder） | A-182（tester） |
|---|---|---|
| 会话启动方式 | 当天多次人工 `stop --hold` → `start` | 系统派发 |
| 回收交接 | 04:56Z 交接，被人工重启带到之后每个新会话（不属于当前会话） | 无遗留交接 |
| 终端状态 | 两者相同：owner 是终端主程序，claude 是子进程，巡检只能看到外层 PID | 同左 |
| 结果 | `busy()` 一直判忙，诊断报 `retirement_handoff_changed` / `session_maintenance`，运维无权重启 | 积压走普通路径（C-680、C-669），系统自动换会话 |

差别不在角色（coder 还是 tester），也不在 claude 的退出方式，而在于有没有回收交接，以及交接是否属于当前会话。

## 改动

1. **新会话取代旧交接**（领域 `dispatchRun`）
   - 绑定新终端时，旧会话处于 `waiting` 的回收记录直接删除，记 `idle_session_retirement_superseded`。
   - `stopping`（可能已发出信号）仍由原来的 `target()` 拒绝启动。
2. **清理存量**（会话维护，每 60 秒）
   - `clearSupersededRetirements`：指派已绑定新会话、遗留的是旧会话 `waiting` 回收记录的，直接清除。没有 IO，不发信号。
   - 还没绑定新会话（`runtime_ref` 为空）的保持不动，只有人工 `start` 或主机运维能取代，与 Q-1133“人工停止后不清旧栅栏”一致。
3. **派发不再被旧交接挡住**（`busy()`）
   - 只有属于当前会话（或尚未换绑）的交接，以及 `stopping`，才判忙。
   - 维护清理之前，派发就已经能投递到新会话。
4. **只有通知的交接让出给派发**（会话维护 `releaseRetainedForWork`，领域 `releaseRetainedRetirement`）
   - 条件：交接属于当前会话、`waiting`、有待投递通知，并且没有排队、在跑、在停或在投递的 Run，没有人工停止、主机运维操作或角色升级。
   - 处理：持两把主机运维锁、重核后撤回回收，记 `idle_session_retirement_released(reason=business_work)`。之后派发器按普通受守卫路径唤醒会话（空闲守卫、C-672 的 Agent 退出检查都照常）。
   - 有排队 Run 的交接仍归 C-575 运维接手，不变。
5. **诊断**：Agent 已被证实退出时，`retirement_handoff_changed` 和 `retirement_exit_unconfirmed` 的停滞行与 `session_maintenance` 一样不再报阻塞，`can_restart=true`，由受守卫的 `releaseExitedAgent` 续起。

## 不变量

- **不会出现两个执行者**
  - 只删除 `waiting` 状态的回收记录，没有发出或在途的信号。
  - 被取代的记录指向的终端已经由人工停止释放，新会话也已由人工 `start` 启动；保留旧栅栏挡不住任何旧执行者，只会挡住新会话。
  - `stopping` 回收、人工停止、在跑或在停的 Run、主机运维操作、角色升级都保持原状。
- 工作区、分支、排队 Run 和 Token 都不变，不关闭、不替换终端。
- 只有带排队 Run 的交接归 C-575 运维接手（Q-1133）。只有通知的交接原来没有任何接手方，本卡让它回到派发器。
