# C-680 空闲常驻会话有积压通知却不派 Run；自动换会话被误报“上游未恢复”撤回

## 原因核查

事实（sensen-godot 主机运维 A-61，pi-deepseek，local）：R-1788 在 06:52:19Z 正常结束；07:01:36Z 出现 `standing_backlog`（cause 通知，age 约 10 分钟，`runtime_state=idle`，`restart_blocked=null`）；之间没有任何 `run_queued`。

按 `dispatchStallCauses` 的算法，常驻积压的起算点是“通知创建时间”和“最近一次 Run 开始时间”中较晚的一个。07:01:36Z 年龄约 10 分钟，说明这条通知在 06:51:3x 创建，**比 R-1788 结束早约 40 秒**，也就是 R-1788 还在跑的时候来的。

后面发生了这几件事（已用测试按同样步骤复现，见 `apps/server/src/standing-idle-backlog.test.ts`）：

1. **门铃投递**：R-1788 运行中，派发器按 `continue` 模式把门铃打进正在运行的轮次。通知变成 `belled`，`run_id=R-1788`。
2. **项目流门铃没有重试时间**：送达结算只给卡片流门铃写 `next_attempt_at`（`sent && n.card_id`），项目流门铃没有。
3. **维护重试跳过项目流**：`maintenance` 的未读重试明确跳过 `!n.card_id && status === "belled"`。
4. **派发只看 `pending`**：候选索引只读 `pending` 通知。Agent 在 06:52:19Z 结束 R-1788，没有 ACK 项目流，这条项目流通知就永远停在 `belled`。没有任何路径会再排 Run。
5. **停滞巡检**：10 分钟后，`belled` 被算作 `standing_backlog`，巡检自动换会话。

所以没排 Run 的原因在**门铃投递之后的重试条件**：“项目流门铃不重试”是 C-475 之前的遗留规则。当时 `covered()` 判断不了项目流有没有 ACK，现在已经可以按 `PROJECT_EVENT_STREAM` 游标判断，这条跳过规则就没有必要了。空闲判定和派发条件本身没有问题：结束后才到的新通知照常在第一轮派发里排 Run，测试也覆盖了这种情况。

同日 05:38Z 那次（撤回原因是 `identity_changed`）约 10 分钟后自己消掉。这与同一模式相符：后来有别的门铃另起了 Run，Agent 在那个 Run 里 ACK 了项目流。但现有登记不足以单独证实。

### “上游未恢复”的误报

`host-ops.ts` 的 `mayStop` 只要 `checkUpstream` 抛错，一律写 `upstream_recovery_not_ready`。但抛错的条件包括很多与线路无关的诊断：

- `agent_busy`：hc 报终端在工作；
- 交互状态读不准（`unknown`/`wait`）；
- 多个会话同时失活需要排查；
- `provider_not_resolved` 或 `classification_failed`：诊断本身不可用。

撤回时没有记录诊断。这次具体是哪一种，现有登记里查不到；今天没有任何 `upstream_incident`，所以不是线路故障。人工 `assignment start` 能成功，是因为 CLI 直接排 Run 并在原会话启动，不经过这道上游检查。

## 改动

1. **派发**（`apps/server/src/dispatch.ts`、`packages/store/src/inbox.ts`）：
   - 项目流门铃与卡片流门铃一样，送达后写 `next_attempt_at`，维护按 1/2/4/8 分钟退避重试，次数用完后照旧转 `needs_attention`。ACK 仍按项目流游标判断，不伪造 ACK。
   - 常驻指派的未读门铃在原轮次结束后重试时，解除与已结束轮次的绑定（`unbind_continuation` 现在也作用于 `retry`），作为新的收件箱工作。派发器为它排一个新 Run（`run_queued`，trigger 为该通知），在原会话唤起，不停止、不替换会话。
   - 时限：第一次重试在门铃送达后 60 秒到期。轮次结束时如果已过期，下一轮派发就处理。所以从会话空闲到排 Run 不超过 1 分钟，不依赖停滞诊断或换会话。
   - 原轮次还没结束时不重发，与原规则一致。
2. **撤回原因与事实一致**（`packages/host/src/upstream-health.ts` 的 `upstreamHoldReason`，`host-ops.ts`）：

   | 诊断 | 撤回原因 |
   |---|---|
   | 有 `incident_id`，或 cause 为 `upstream_unreachable`、`upstream_suspected` | `upstream_recovery_not_ready` |
   | 诊断不可用（`classification_failed`、`provider_not_resolved`） | `upstream_diagnosis_unavailable` |
   | cause 为 `unknown` | `session_state_unconfirmed` |
   | 其它 | 直接用 cause，例如 `agent_busy`、`waiting_interaction` |

   积压撤回事件新增 `blocked_by: { cause, action, evidence }`，例如 `agent_busy` 的依据 `harness_working`。派发停滞诊断行新增 `withdrawn_blocked_by`，`next_step` 里带上依据。
3. **撤回后的轻量恢复**（`packages/host/src/stall-patrol.ts`，领域命令 `nudgeStalledPatrol`）：
   - 巡检自己的积压，在系统换会话被撤回、积压仍在、旧会话仍在时，改用最轻的方式恢复：等价于 `assignment start`，在原会话排一个 Run（system，kind=initial）。之后由派发器按常规检查唤起。
   - 条件：
     - 不停止、不释放终端；
     - 只在 `runtime.status` 确认终端 live（非 `--keep` 外壳）时才排，终端不再列出时不排，避免出现两个执行者；
     - 人工停止、主机运维操作、未结束的 Run 都不排。
   - 每次记 `dispatch_stall_nudged`（assignment、cause、run、attempt）。
   - 同一 cause 最多 `CARDIGAN_PATROL_RESTART_RETRIES` 次（默认 3），间隔不少于 `CARDIGAN_PATROL_RESTART_RETRY_MS`（默认 60 秒）。
   - 诊断行新增 `light_recovery: { attempts, limit, last_at }`，`next_step` 显示“已在原会话续排 Run n/3 次”。
   - 旧会话已经确认退出的，仍按 C-669 自动续起。

## 不变量

- 不会出现两个执行者：轻量恢复只给确认 live 的原会话排 Run，不起新会话，不发信号；派发器仍按原有检查唤起。
- 人工停止（含 `--hold`）不续排、不重发。
- 不伪造 ACK；Agent 已经 ACK 的项目流门铃不会重发。

## 测试

- `apps/server/src/standing-idle-backlog.test.ts`：
  - pi 和 claude-code 常驻会话，项目流和卡片流各一组：运行中送达、结束时未读的门铃，在 60 秒内排出新 Run，并在原会话唤起；
  - 轮次结束远晚于门铃时，下一轮就跟进；
  - 结束后才到的通知，第一轮就排 Run；
  - 已 ACK 的项目流门铃不重发；
  - 无上游故障时撤回原因为 `agent_busy`（不是 `upstream_recovery_not_ready`），并带 `blocked_by`；
  - 撤回后在原会话续排 Run，最多 3 次，诊断可见；
  - 人工停止不续排。
- 领域契约测试（`host-ops-context-restart.contract.test.ts`）：`blocked_by` 的记录；`nudgeStalledPatrol` 仅限 system，不能与未结束 Run、人工停止、主机运维操作并存，没有终端时拒绝。
- `upstream-health.test.ts`：撤回原因映射。
- 既有用例更新：
  - C-669 的“旧会话仍在”现在会续排 Run，仍不停止会话；
  - C-248 的分类失败改报 `upstream_diagnosis_unavailable`；
  - 常驻 PM 交互读不准的情况改报 `session_state_unconfirmed`。

## 已知未覆盖

- 这次 `mayStop` 抛错时的具体诊断没有历史记录，无法回溯；上线后由 `blocked_by` 记录。
- `assignment stop --hold` 对常驻主机运维被拒（`illegal_transition`）：领域命令 `stopWorkItemAssignment` 只接受 `scope=work_item`，常驻 PM 另有入口，常驻主机运维没有。这不在本卡范围，可另开卡。
