# ADR 0004：合并检查可以绑定合并批次 MB-n

- 状态：已采纳（用户 2026-11-11 拍板），实现见 `docs/plans/p2a-13-merge-queue.md` B 组
- 依据：开发方案 §3.5、§4.4、§4.5 不变量 20／21／23／27、§7.4、§8.2、§12.5；P2a-1 计划 §2.1、§2.2、§2.5；P2a-12 计划
- 卡片：C-143（接替 C-124）

## 背景

P2a-1 合并闸门让每份完成申请在“当前基线 + 本卡交付”的候选 tree 上跑一次全量检查（install／build／test／lint／deps／e2e），通过记录绑定 `(completion_id, tree_sha)`。2026-11-11 张良的调研（149 次 `merge_check_finished`）：

- 通过的检查平均 207 秒（140–386 秒），其中 test 平均 127 秒，e2e 约 63 秒且只能串行；
- 结果 passed 87、failed 40、interrupted 22；
- 主要放大因素：main 每前进一次，所有排队卡的候选 tree 都变了，全部重跑。k 张卡排队时，一次合并让其余 k−1 张卡的检查作废（`apps/server/src/merge-checks.ts` 中 `prepare` 的候选缓存键含基线，见不变量 21 和 P2a-1 §2.1）；
- 近 40 次合并里只改文档的有 3 次，60% 同时改了 apps 和 packages。

只做分层检查（计划 A+C 组）能缩短单次检查，但改变不了“每张卡都要在最新 main 上单独全量通过”这个前提，排队越长浪费越多。要消除这部分重跑，只能让一次全量检查同时为多张卡作证，这就必须改写不变量 21。

## 用户拍板（2026-11-11，邵杰在与张良的对话中确认）

以下四条引自 C-143 卡片原文，未改写：

1. 同意改写不变量 21：检查通过记录可以绑定一个合并批次（批次最终 tree 必须有绑定本批全部完成申请的通过记录；批次中间的 tree 不要求单独检查）。走 ADR 0004。
2. 合并确认的含义改为“同意合并，以批次全量检查通过为准”（确认在前，全量检查在后）。
3. 卡级检查不跑 e2e，e2e 只在批次检查里跑。
4. 合并批次 ID 使用 MB-n（M-n 已被成员占用），与其他项目内 ID 一样递增不复用。

用户对前端的原话：“同意,此外多卡合到一个合并在前端需要如何区分级表现, 例如卡片状态等”；“同意用MB-n”。前端方案见计划 B 组 B4。

## 决定

### 1. 两级检查

- **卡级快速检查**：卡片进入 `awaiting_merge` 后，在“当前基线 + 本卡”的候选上跑 build、lint、deps 和受影响包的测试，不跑 e2e；只改 `docs/` 的卡跳过 test。记录仍绑定 `(completion_id, tree_sha)`，标记 `level=card`。它是合并确认的前置信息和 PM 代确认的前置条件，**不能作为合并依据**。基线前进后不重跑：卡级结果只说明“这张卡本身没问题”，基线前进不改变这一点。
- **批次全量检查**：已确认的卡进入项目合并队列，按顺序叠加成批次 MB-n，在批次最终 tree 上跑一次全部检查（含 e2e），记录绑定 `(batch_id, tree_sha)` 和本批全部 `completion_id`，标记 `level=batch`。

### 2. 不变量 21 的新旧表述

**旧（P2a-1）**：

> 项目启用合并闸门时，记录 merged 的 tree 必须有同一完成申请的 passed 检查记录。主机负责从实际候选提交读取 tree 并验证其 Git 身份，domain 校验记录绑定；不同候选提交可复用同树的通过记录，不同 tree／完成申请不可复用。唯一例外是主机已证明所有计划交付均为当前基线祖先的 noop，结果必须显式标记 noop，且 merge_sha == previous_sha；不需要也不伪造检查通过。

**新（P2a-13 B 组合入后生效）**：

> 项目启用合并闸门时，记录 merged 必须满足下面两种之一：
> （a）**单卡合并**（项目未启用合并队列，或队列关闭期间的旧路径）：沿用旧表述，合并 tree 有同一完成申请的单卡检查（`level=single`，旧事件没有 level 字段，视同 single）passed 记录；单卡检查跑全部步骤。
> （b）**批次合并**：本卡属于批次 MB-n；MB-n 的最终 tree 有一条 passed 记录，其绑定的完成申请集合与 MB-n 的成员集合**完全相等**，且每个成员都是各自卡片的当前完成申请；本卡的合并提交在 MB-n 的叠加链上（是最终提交的祖先或就是最终提交）；同一事务内本批全部成员一起记录 merged，基线由一次比较更新从 MB-n 的 `base_sha` 前进到 `final_sha`。批次中间的 tree 不要求单独检查记录。
> 两种情况下 `level=card` 的通过记录都不能作为 merged 的依据；不同 tree、不同批次、不同完成申请集合的通过记录不能复用（同一批次重组后 tree 不变时可以复用）。noop 例外不变。主机负责读取实际 tree、验证叠加链和祖先关系，domain 只校验记录绑定和集合相等。

### 3. 合并确认的含义

确认从“这棵树已经检查通过，同意合并”改为“同意合并，以批次全量检查通过为准”。顺序变成：卡级快速检查 → 确认 → 进入队列 → 批次全量检查 → 合并。

- Needs You 的确认按钮写“确认合并（批次检查通过后生效）”，卡片附卡级快速检查结果；C-115 的“等检查通过才进人的 Needs You”改为等**卡级**检查通过（或主机验证 noop）。
- PM 代确认（不变量 23）的前置条件从“当前完成申请的合并检查已通过”改为“当前完成申请的卡级快速检查已通过”，其他条件（验证项全部通过、无未处理 must_fix、知会必填）不变。
- C-29 超时代批：同样以卡级检查通过为前提，代批只是让卡进入队列，合并仍等批次检查。
- `merge_policy=auto` 的卡：卡级检查通过即视为确认，进入队列。
- 确认之后，批次失败并定位到本卡时，确认不撤销，卡片按“检查失败”在 Needs You／PM 队列重新出现，处理方式沿用 C-66／C-79（退回修改或重新检查）。

### 4. 对敏感卡的影响

- 敏感卡（D12 四类、需求范围变化、卡片来源拍板、人标记的敏感卡）仍只接受 human 确认，PM 不能代确认、不适用超时自动合并，这些都不变。
- 人确认的含义同样变为“以批次检查通过为准”。人确认后，敏感卡可能和别的卡同批合并，**本卡的合并提交不单独检查**；这一点在确认按钮旁和卡片详情如实写明。
- 批次失败定位到敏感卡时，按现有规则交人：PM 不能退回或代确认，只能按 §4.4 的结构化超时规则重新检查。
- 人或 PM Ops 可以给卡打“单独跑”标记（计划 B 组），敏感卡要不要默认单独跑**不在本 ADR 内决定**，见“待定”。

## 风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| 中间 tree 未检查 | main 的历史上会出现没有单独检查过的提交（批次内除最后一张卡以外的合并提交）。`git bisect` 或回滚到中间提交时，可能拿到一个过不了检查的版本 | 只能快进到批次最终提交，main 的分支指针从不停在中间提交；回滚以批次为单位（时间线写清同批成员）；卡片详情和批次详情如实写明“本卡合并提交未单独检查，检查覆盖的是批次最终 tree” |
| 互相抵消 | 卡 A 引入的问题被同批卡 B 掩盖（例如 B 删掉了 A 改坏的测试），批次通过但 A 单独看是坏的 | 卡级快速检查仍单独跑每张卡的受影响测试，能挡住大部分单卡问题；PM Ops 可给高风险卡打“单独跑”；批次大小有上限（默认 4） |
| 二分误判 | 不稳定测试让二分定位到无辜的卡 | 定位结论至少要两次失败证据（见计划 B2 的二分规则）；超时类失败先按 C-116 重跑一次；D 组识别不稳定用例 |
| 一张坏卡拖慢同批 | 批次失败要额外跑二分探测 | 卡级检查先挡掉大部分问题；二分探测用空闲槽位并行；同批其余卡自动重新入队，不需要重新确认 |
| 确认和合并之间的时间差变长 | 人确认时看到的是卡级结果，不是最终合并结果 | 按钮文案和 Needs You 说明写明“批次检查通过后生效”；批次失败定位到本卡时重新出现在 Needs You |
| 外部推送 | 批次合并一次前进多个提交 | §12.7 推送队列不变，每张卡仍各自 `merge_push_queued`；推送循环已支持把积压合并为最新提交（须验证祖先关系），批次只是让积压更常见 |

## 不变的部分

- Card 状态机：卡片仍是 `awaiting_merge → done`，不新增状态。排队、批次检查、二分、定位失败都只是从批次数据派生的“合并阶段”子标签。
- 每张卡仍各自一个合并提交，`card_merged` 的 `merge_sha` 指向本卡的合并提交，便于按卡追溯。
- 不变量 20（超时自动合并要人授权）、23 中“敏感卡只由人确认”的部分、27（检查运行中禁止撤回审核，扩展到“本卡所在批次检查运行中”）。
- 所有 Git 操作仍由主机在中心 bare 仓库内完成（§12.1），domain 不做 IO。

## 待定（不在本 ADR 内决定）

- 敏感卡是否默认“单独跑”：计划不预设，B 组上线前由 PM 提给人拍板。
- 批次上限默认 4，上线后按实测（失败率、二分耗时）调整。
