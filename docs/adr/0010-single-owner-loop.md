# ADR 0010：单负责人闭环（GitHub Actions 检查、失败直退、作者预检、系统合并）

- 状态：**已接受**（用户 2026-11-15 拍板；同日补充拍板：GitHub Actions 为首选执行器、D 先做；两层测试；凭据、默认数值、自动标签路径等六条细节，见文末）。
- 实现计划：[`docs/plans/flow-v2.md`](../plans/flow-v2.md)。
- 依据：开发方案 §1.5、§3.5、§4.4、§4.5（不变量 13、15、16、20、21、23、27、29）、§6.4、§7.1、§7.4、§12.1、§12.5、§12.9、§13.4、§14、§15 D15、§20.2。
- 与其它 ADR 的关系：
  - ADR 0002（账号隔离）、0003（持久化边界）不变。
  - ADR 0004（合并队列）：推迟，本 ADR 落地后按数据再定。
  - ADR 0006（独立复核与风险标签代确认）：独立复核、三方隔离、风险标签和完成申请硬门全部保留；“PM Ops 代确认”在新版卡上由“系统合并”取代，条件不变。
  - ADR 0007（Gitea Actions，待决）：未采纳，被本 ADR 取代，其状态随计划文档卡一起改；§15 D15 以本 ADR 结案；C-78、C-224 取消。
  - ADR 0008（系统规则）：决定 1（自动指派）、决定 3（催办）、决定 4a（自动加轮）保留并扩展；决定 2 的“合并前分类确认”（条件 16）和 Q-397（排除 `numeric_rule` 卡）在新版卡上不再适用，风险分类前移到建卡和交付时（见决定 4）。

## 背景

2026-11-15 的三份只读评审（两份流程评审、一份耗时统计；窗口 11-12 至 11-15 的 72 小时，约 165 张已合并卡）给出的主要事实：

1. 新发起的拍板里合并确认占约 68%，开发流程类合计 81.5%～86.5%；人 3 天点了约 204 次，产品层面的约 35 次。
2. 58 次合并检查失败。失败后先由 PM Ops 或人在合并确认上选“退回”，作者才收到通知；失败到重新入队平均 43 分钟，其中约 29 分钟没有任何活动；失败到合并中位 70 分钟、平均 121 分钟；每个失败回路多跑约 15 个 Run。
3. 失败多在 test 步骤（48/58），常见原因是别的包的测试断言了旧行为，作者本地只跑受影响测试，完整反馈来得太晚。检查本身不慢：通过的检查中位约 3.7 分钟，全量 test 在 12 worker 上约 168 秒、7,485 个用例，e2e 约 67 秒。
4. PM Ops 约占全部 Run 的 41%，选审核员、叫作者修、合并确认都要等它串行处理。
5. 独立审核有实效：代码审核退回率约 24%，独立复核约 8%；PM 验收约 1.6%。
6. Agent 已是 `bypassPermissions` / `--yolo`，阻断来自流程和架构，不来自工具审批。现有 SSH 检查机并发上限为 3。

用户的判断：单对话闭环（自测 → 推 CI → 失败自己修 → 绿了合并）比现在的多层流程快。约束：保留任务卡；拍板只留产品层面；Agent 权限不变。仓库将以 Apache-2.0 公开，可以用 GitHub 免费托管 runner。

## 决策

### 决定 0：流程版本固定在卡片上

卡片建卡时固定 `flow_version`，项目偏好决定新卡版本，只有人能改；旧卡只能由人在安全边界（无未作废完成申请、无运行中检查、不在待合并）升级。同一张卡任何时刻只适用一个版本的规则。各决定按级别逐步开放（计划 §4.1），每一级在其全部任务合并后才允许启用。

### 决定 1：GitHub Actions 为首选检查执行器，先做

- 合并检查和预检抽象为同一个执行器接口，SSH 执行器（现有检查机）与 GitHub 执行器并列，按项目配置选择；cardigan 项目默认 GitHub，SSH 留给私有项目和 GitHub 不可用时由人切回。同一 attempt 只用一个执行器，不自动切换。
- 主机把候选提交推到 `ci/<card>/<delivery 或 assignment>/<attempt>` 分支，用 `workflow_dispatch` 触发**基线分支（main）上**的可信 workflow，inputs 为候选 SHA、tree、卡号、交付号、attempt、类型，run-name 写同样的标识。
- 主机按 run-name 和绑定条件找到 run 并把 `run_id` 记到 attempt 上。只认同时满足以下条件的 run：workflow 路径为配置值、`event=workflow_dispatch`、分支为基线分支、`head_sha` 在中心仓库基线历史里、触发者是主机 GitHub App 的机器人身份（`<app-slug>[bot]`，由配置提供）、`run_attempt=1`、run-name 完全一致。不满足按 `executor_unreachable` 处理，不记通过。tree 仍由主机从候选提交读取，最终合并依据仍要求候选树匹配（不变量 21 不变）。
- 主机凭据用 GitHub App：只装在本仓库，权限 `actions:write`、`contents:write`、`metadata:read`，无 webhook；主机私有配置提供 App 编号、安装编号和私钥文件，主机用 JWT 换 installation token，令牌只在内存中使用、不落盘。
- 主机统一轮询（默认每 20 秒，配置项；Workbench 只监听本机，不开公网 webhook），用 ETag 和退避控制 REST 用量；失败时取失败 job 日志，经现有脱敏器写入主机私有日志，截取首个 FAIL 回给作者（决定 2）。
- workflow：只读 `contents` 权限，不用 secret，不用 `pull_request_target`，检出时不留凭据，先核对 HEAD 和 tree；候选 job 的依赖缓存只恢复不保存，缓存由 main 上的独立 workflow 生成；同卡一个 concurrency 组，`cancel-in-progress: false`，主机保证同卡最多一个 run 在途。
- 候选对 `.github/` 的改动只在合并后生效；这类交付由系统自动加 `security` 标签，走独立复核。
- `hc`（herdr-core，版本以 `deploy/install-agent.py` 为准，公开下载带 sha256）缺失或版本不符时判失败，不能让 e2e 被 `skipIf` 整组跳过而显示绿。test 的 `--maxWorkers` 适配 runner 的 4 vCPU。
- 容量按 GitHub 账号的并发 job 上限配置（以官方文档为准，配置项 `max_concurrent`，不写死）；每次检查 1 个 job，第一版不分片。
- 合并、作废或超期后主机删除 `ci/` 分支。外部贡献者 PR 需审批才能运行 workflow，其结果不作为合并依据。
- 前置：仓库转公开（C-321 公开前清理合并后由主机侧转公开）。转公开前可以先做执行器抽象、追踪数据模型、workflow 文件本身；真正接通要等公开。切换前先双跑，SSH 为权威、GitHub 为影子，默认 20 次结果一致后再切权威（配置项）。

### 决定 2：检查失败直接退回作者（A1）

当前完成申请的合并检查以 `failed`/`timed_out` 结束时，system 在同一事务走现有退回迁移，给原产出 Assignment 排 `fix` Run（复用原会话），原因带失败步骤、首个 FAIL 和脱敏日志摘要（GitHub 执行器取自失败 job）；不再在合并确认上生成人工选择。

- 基础设施类偶发失败（超时、已知 runner/进程特征，由主机按完整日志判定）自动重跑一次，与 C-116 共用每份完成申请一次的额度。
- 作者判断失败与本卡无关时，每组产出 SHA 可调用一次受限的 `request_recheck`：以原 SHA 重新交付，沿用对同 SHA、同树的审核，在当前基线上重跑完整检查。
- 失败的申请在新交付前不随基线前进反复重跑。
- 本卡产出方和验证方经受控只读工具 `get_check_log` 读取本卡 attempt 的脱敏日志，有长度上限。
- 敏感卡和 D12 卡也由 system 退回（退回不扩大权限），合并仍交人。

### 决定 3：作者自助预检与两层测试（A2）

- 产出方调用 `request_check`，主机在“当前基线 + 该 Assignment 分支 HEAD”上构造候选，用与合并检查完全相同的执行器和配置跑一次（cardigan 项目即一次 GitHub run），结果和日志回到产出方会话。同一 Assignment 同时只允许一个预检；合并检查优先于预检，非抢占（Q-486）。
- `submit_delivery` 要求该 SHA 已有通过的预检。审核员只看已过完整检查的代码。
- 最终合并检查仍在最新基线的候选树上跑，预检通过不能替代。
- 两层测试：所有角色（coder、reviewer、独立复核员、PM 等）在本地会话只跑与改动相关的非全量检查（增量构建、lint、deps、相关单测，改 `packages/domain` 加 `test:types`），不跑全量测试和 e2e（e2e 会在本机起 herdr-core，与生产 hc 同机）。全量测试和 e2e 只在远程预检和合并检查里跑。本地结果是 Agent 自报，不能作为审核或合并依据；可信依据是绑定 `run_id`、SHA、候选树的远程 run。本地测试 worker 上限从 2 提到 4，仍是主机配置项。
- 由在途卡 C-298（原为风险卡独立复核前预检）改范围实现。

### 决定 4：系统合并（A3）

- `pmMergeBlockers` 全部清空（当前完成申请检查通过、所有未取消验证项通过、无未处理 must_fix、风险卡独立复核 Review 绑定当前交付编号和 SHA、截图核对规则）时由 system 直接合并，事后在 Needs You 知会区发通知；`merge_confirmation` 不再作为拍板出现。
- 仍交人：与本卡合并内容相关的 D12 四类（花钱、账号、权限、删除数据）或 `scope_change` 拍板（含来源拍板）、人标的敏感卡、对外发布、角色规则改动（Q-279，由主机的角色规则清单识别）。
- 项目级“暂停自动合并”开关，只有人能改；暂停时系统不合并、已由系统确认但未发布的合并在发布前被挡住。
- 自举项目合并即自动部署生产（C-201）：改部署监督器或数据库迁移的卡在建卡时标敏感或打 `security`（写进 PM 规则）；系统按路径清单自动加 `security`：`.github/**` 固定，数据库迁移目录（`packages/store/migrations/**`）和部署监督器相关代码（`packages/host/src/deployment*`、`apps/cli/src/self-deploy.ts`）为默认，人可增删。产品拍板前移到建卡或开工时。
- 由在途卡 C-320（PM Ops 减负，ADR 0008 决定 2）扩大范围实现。

### 决定 5：审核精简（B）

- 保留一位独立代码审核员，不用作者会话的 subagent 代替（不变量 15、16）；subagent 自检只作为作者的建议。
- 审核只针对已有通过预检的 SHA。
- 同一目标上并行验证方的问题一次收齐：一方 reject 后，另一方仍能对同一交付提交。
- 增量复核由 C-308 实现，不在本 ADR 重复。
- 普通审核达到轮次上限时由系统自动加轮（像 C-301 对独立复核的授权那样不再交人），`review_limit` 不再生成拍板；独立复核规则不变。
- 完成申请由系统汇总生成。PM 验收改为模板可选：新内置模板 `dev@2`（工程卡）不含 PM 验收，验收标准对照并入代码审核；`product@1`（产品卡、界面卡）保留 PM 验收。模板版本不可变，旧卡不自动变。

### 决定 6：PM Ops 退出机械调度（C）

选审核员、叫作者修复、检查通过后发布都由 system 执行；PM Ops 只负责规划、建卡、产品拍板提问和异常（没有合格员工、执行器不可达、加轮达上限、加标签后缺复核项、产出方失活）。角色包改动按 Q-279 交人确认。

### 顺序

D（决定 1）优先；A1 → A2 → A3；B、C 跟在 A3 后面。ADR 0004 的合并队列不在本次范围，A3 之后再看数据。

## 备选方案及否决理由

| 方案 | 结论 | 理由 |
|---|---|---|
| 维持现状，只调参数 | 否决 | 失败回路和合并确认是结构性的：作者收不到失败、每次失败重走全链、68% 的拍板是机械确认。调参数改不了这些 |
| 单会话 + 作者自己的 subagent 审核，取消独立审核员 | 否决 | subagent 继承父会话的 Token 和身份，无法证明独立（不变量 15、16）；独立审核实测退回率 24%，在挡真实问题；单会话也撑不住现在的并行吞吐 |
| 只换 CI 平台，不改流程 | 否决 | 慢在流转不在执行：失败要等 PM/人退回、退回后重走审核和确认。换平台只解决容量 |
| 自建 SSH 执行器继续作为主路径 | 不作主路径，保留为备用 | 已有 nonce/HMAC、隔离账号等安全设计，适合私有项目；但并发上限 3，扩容要加机器和维护；公开仓库后 GitHub 托管 runner 免费、每个 job 是一次性虚拟机，容量和隔离都更合适 |
| 本地 Gitea + act_runner（ADR 0007 方案②） | 否决 | 要新增一个需备份、升级、保管凭据的服务；ADR 0007 列出的 job token、runner 凭据隔离等安全待实测项尚未验证；GitHub 托管 runner 用一次性虚拟机，同类问题天然不存在 |
| GitHub 自建 runner（ADR 0007 方案③） | 否决 | 候选代码与 runner 控制凭据同机，需要另做隔离；公开仓库上自建 runner 风险更高 |
| 用 `push` 或 `pull_request` 事件触发、读候选里的 workflow | 否决 | 候选可以改 workflow 删步骤或伪造通过；只用 main 上的 workflow 经 `workflow_dispatch` 触发 |
| `pull_request_target` | 否决 | 以基线权限运行候选代码，是公开仓库的常见攻击面 |
| 主机用细粒度 PAT | 否决 | 令牌长期有效、需人定期续期，权限按用户而非按安装；App 令牌一小时自动过期、只装本仓库 |
| 给 Agent GitHub 凭据，让 Agent 自己推分支、开 PR、看 CI | 否决 | 违反 §12.1“Agent 不持有 Git 凭据”；开了 yolo 后隔离账号和凭据是防提示注入的主要边界；主机代推、代查即可达到同样效果 |
| 只有 PM Ops 代确认、系统做影子记录（ADR 0008 决定 2 原样） | 否决 | 每张卡仍要 PM Ops 做一次分类确认，串行瓶颈不变；风险分类前移到建卡、交付时的路径规则，覆盖面与它相当 |
| 转公开前重写 Git 历史或另开新仓库 | 否决 | 当前树没有真实密钥；重写会改变全部提交 SHA，数据库里交付、审核和合并记录都绑定 SHA，需要大规模数据迁移，也丢掉自举开发的完整历史 |

## 后果

正面：

- 检查失败到作者开始修复从“等 PM/人”变成同一事务内排 `fix` Run；作者在原会话里拿到失败步骤和日志。
- 大部分失败在审核之前由预检暴露，审核员只看已过完整检查的代码，失败回路不再重走审核、验收、确认。
- 合并确认、审核加轮这两类流程拍板从人的 Needs You 和 PM Ops 队列里消失；人只处理产品层面事项和强制交人的卡。
- 检查容量从固定的 3 个提升到 GitHub 账号的并发上限，可支撑更多员工并行。

负面和需要接受的代价：

- **自动合并即自动部署**：自举项目每次系统合并都会经 C-201 部署到生产。缓解：暂停开关、部署监督器和迁移卡的标记规则、风险卡独立复核、最终候选树检查、§12.9 备份与回滚。
- **合并前公开候选**：未审核的候选代码在 `ci/` 分支上公开，CI 日志也公开。仓库本来公开；CI 无 secret、测试只用合成数据、开启 secret 推送保护；Agent 已有出网能力，不新增外传通道。§12.1“合并前不推外部平台”对使用 GitHub 执行器的项目改写。
- **依赖 GitHub 可用性和限额**：不可用时检查记为 `executor_unreachable`，不退回作者；由人或主机运维切回 SSH 执行器。
- **4 vCPU 上检查变慢**：全量 test 在 12 worker 上约 168 秒，4 vCPU 上会更久；双跑期测量，必要时分片。
- **不再逐卡做合并前分类确认**：漏标风险的兜底从“PM 合并前再看一遍”变为“建卡时标记 + 交付路径自动标记 + 主机角色规则清单 + 抽查”。`numeric_rule` 卡在独立复核通过后也由系统合并（Q-397 在新版卡上不再适用）；新数值本身仍须在建卡时由人拍板。
- 人在时间线评论里写“先别合”不会阻止系统合并（用户 2026-11-15 已接受）；要阻止须用暂停开关、对系统持有的确认选 hold，或给卡片标敏感。
- PM Ops 的职责明显收窄；PM 角色包、AGENTS.md、CLAUDE.md 中关于合并规则、独立复核代确认、Claude 合并职责的文字需要改写（建议改法见计划 §8，角色规则和 AGENTS 改动由人确认）。

## 保留的安全边界

| 边界 | 本 ADR 后的状态 |
|---|---|
| Agent 不持有 Git/GitHub 凭据、不能 push（§12.1、§14） | 不变；推候选、dispatch、查询、取日志、删分支都由主机代办，主机凭据只在主机私有配置 |
| Agent 隔离账号、没有 sudo、读不到数据目录和主机日志目录（ADR 0002） | 不变；日志只经受控工具按卡、按 attempt、限长提供 |
| 检查命令由主机可信配置决定 | 不变；GitHub 执行器的命令在 main 上的 workflow 里，候选不能改它；Agent 发起预检不能传命令、路径或执行器 |
| 合并依据是当前完成申请 + 实际候选树的通过记录（不变量 21） | 不变；预检、本地自测、未通过绑定校验的外部 run 都不能作为依据 |
| 审核者不能是作者（不变量 15、16）、审核绑定版本（不变量 14）、撤回审计（不变量 26、27） | 不变 |
| 风险标签卡必须有必需的独立复核且对当前交付编号和 SHA 通过（ADR 0006、不变量 29） | 不变；系统只能加标签，不能删 |
| D12 四类、`scope_change`、敏感卡、对外发布、角色规则改动只由人确认 | 不变；系统合并对这些卡一律交人 |
| 自动合并需要人的授权（不变量 20） | 扩展：系统合并的授权来自人设置的项目流程版本，人可随时暂停 |
| 部署只由 C-201 监督器执行 | 不变；不迁到 GitHub job |
| 持久事件、Run 幂等、worktree 单写者（不变量 4、7，ADR 0003） | 不变；系统退回、系统合并、外部 run 追踪都在写事务内重查并落事件 |

## 回滚

- 暂停自动合并开关：立即停止系统合并和未发布的系统确认。
- 项目 `flow_version` 改回低一级：只影响之后新建的卡，在途卡按自己的版本走完。
- 执行器配置改回 SSH：下一个 attempt 起生效。
- 系统退回、系统合并、自动加标签、预检和外部 run 记录都是普通事件，回滚不需要数据迁移；已发布的问题按“已完成卡不能取消”的规则开回滚卡。
