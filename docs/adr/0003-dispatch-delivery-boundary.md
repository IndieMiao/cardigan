# ADR 0003：Dispatcher 的持久化边界

- 状态：M3.4 分批实现，待审核
- 依据：开发方案 §6.1、§6.8、§13.9；M3 计划 §3.2、§3.3、M3.4

## 按流消费

复用 M3.3 的 `(project_id, stream)` 游标。卡片流的 stream 是卡片 ID；项目级流使用 PROJECT_EVENT_STREAM。每条流只读取 seq 大于自身游标的事件，按 seq 顺序路由，在同一事务内写入通知并推进该流游标。

同一卡片内部串行，不同流互不借用游标，也不要求项目内所有卡片有一个总顺序。没有全局事件位置表、触发器、回填或额外的游标迁移；迁移 0005 只存投递意图。事件和通知继续使用其原有流内 seq。

## 数据库提交与外部调用

SQLite 事务不能原子包含 Runtime.wake / 新终端启动。调用失败、进程退出或 SSH 中断，都不能证明门铃没送达；不能通过新建第二个 Run 来重试。

1. 在写事务中准备/复用 Run、写入收件箱事实，再写一条投递意图（接收 Assignment、Run、通知编号、开始时间和租期截止）。提交后才做外部 IO。
2. 同一 Assignment 只能有一个未结束意图，由数据库唯一约束保证。调用成功或失败后，在另一个事务中结算意图和通知状态。已结算的意图不被迟到结果覆盖。
3. 重启后读取未结束意图：未过租期的不抢占；已过租期的发送结果不确定，按 delivery_failed 交给 PM Ops，保留原 Run，不静默重复调用。之后 Agent 的真实 ACK 仍可将 delivery_failed 确认为 acked。
4. 正常发送成功但尚无 ACK 的退避重发继续按 M3 计划处理：有未结束 Run 时不重发；重发也复用原触发记录，不创建重复 Run。

这保证的是持久事件/Run 的幂等与不重复的自动投递意图，不宣称外部消息恰好送达一次。崩溃发生在提交意图之后、实际调用之前时，也可能被保守升级为失败；这是 §6.8 下为避免不确定副作用重复执行所采用的处理方式。

## 分批交付

先交付投递意图的最小 store API，再用 M3.3 的按流游标接入 Router 消费/投递、ACK/退避与看门狗/运行时事件。store 层不做 Runtime IO，也不自行决定重发、取消 Run 或接管机器。server 的组装与 PM 常驻启动仍归 M3.5。

## 进程中断与关闭验证

真实子进程在持久化意图后进入 Runtime.wake，父进程确认已到达外部调用再发送 SIGKILL。接着分别启动新进程验证：租期内不抢占；租期过后按 delivery_failed 升级且 Run 编号不变；再次重启无第二次 wake、无第二个 Run、无重复失败事件。进程间只共享 SQLite，不沿用 Dispatcher 的内存状态。测试用假 Runtime 表达调用结果不确定，不依赖真实 Agent。

正常关闭通过 startDispatchLoop.stop() 停止调度并等待当前 tick 结算，再 abort／清理订阅。M3.5 的 SIGTERM 处理必须等待该 Promise 后才关闭 Store。没有强制超时后再重发的路径；外部调用的截止时间仍由 Runtime／主机启动适配器负责。
