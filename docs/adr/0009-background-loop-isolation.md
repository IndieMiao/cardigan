## 问题与代码事实

HTTP、SSE、MCP 和 `assembly.ts` 装配的后台循环共用 Node 事件循环。Store 使用同步 `node:sqlite`，连接设置 WAL 和 `busy_timeout=5000`；WAL 允许读写并行，但同一时刻仍只有一个写事务。同步查询、JSON 解码、领域计算和写锁等待都能阻挡当前线程处理请求。

卡片记录的生产现象是 reconcile 平均 6.8 秒、backup 平均 6.3 秒，首次首页请求约 5.8 秒；重启后曾有 reconcile 27 秒、backup 12 秒。这些是立项证据，不是本次独立复测。`reconcile.git` 包含目录扫描及其后的 `reconcile.checks`；它的墙钟耗时不能直接等同于主线程被阻塞的时间。

现有 `LocalGitTransport` 和 `CentralGitTransport` 已通过异步 `execFile` 执行 Git，工作区命令在隔离模式下经 Agent 专用入口执行。问题包括重复传输、重复历史解码和同步数据库工作，并非把 `*Sync` 改名就能解决。Git 子进程仍会消耗整机 CPU，搬出线程也不会消除整机资源竞争。

## 本卡先落地的优化

1. Reconcile 按项目、卡片保存已读取 seq 和各检查 attempt 的最新事实。只解码新增事件；非 system 事件仍推进读取位置但不改变检查所有权。快照在读事务成功结束后才发布，异常丢弃临时快照；重启从零重建。保留旧 attempt，关闭卡片、结束时间和原宽限期的判定不变。目录扫描后才读取检查状态，扫描期间新增检查仍受保护。这不是 Router 或 Agent ACK 游标。
2. 登记源对账和同用户模式备份先通过 `ls-remote --refs` 读取实际源 refs，再与中心实际 refs 比较；只对不同步的对象执行 fetch，登记源祖先分类只在基线／源 SHA 对变化时重算。同轮中心仓库校验复用一次，下一轮仍重新校验。绑定 upload-pack 的 Agent 传输沿用每轮一次流式 fetch，不做 refs 预检（Q-412 退回要求）：额外探测会增加 SSH 调用，并引入查询超时和文本缓冲上限，不能改变原传输序列。源、基线、固定交付 refs、worktree 登记和目录仍会观察，数据库未变化不能证明磁盘未变化。
3. 备份对象是默认执行目标的每项目基础 clone 中全部 `refs/heads/agent/*`，目标仍为中心 `refs/cardigan/backups/local/agent/*`；沿用当前仅支持 local 机器编号的规则，不增加对独立检查执行机的备份。启动及默认每 10 分钟轮询、清理前备份入口均不变。不是只备份当前活跃 Assignment，也不以数据库事件推断是否有未交付 commit。
4. 比较双方实际 refs，不以“上次尝试成功”的内存标记跳过。新增分支、前进、强制回退和目标 ref 丢失都会重新传输；失败保留原备份，下轮重试；源分支删除不 prune 旧备份。单分支源消失仍报错。探测之后新到达的提交由后续轮询发现，与原 fetch 的瞬时快照一样，不承诺备份扫描结束瞬间的全部并发提交。
5. 探测和传输均通过现有异步 Git、安全 argv 和受管中心目录。Agent 仓库仅通过主机绑定的 upload-pack 执行 fetch；缺少入口时仍拒绝，不在 Agent 仓库以内执行主机 Git。数据库只在 IO 前后开启同步短事务，不跨 await 持有；无新凭据、权限、配置、周期或状态机变更。

冷启动仍须重放历史，目录和 refs 轮询也不是零成本。本卡不优化 dispatcher 或列表分页，不引入迁移，不改变业务语义。

## 三个方案

| 维度 | ① 单进程增量优化 | ② 后台 worker_threads | ③ Web／MCP 与后台两个进程 |
|---|---|---|---|
| CPU 与故障隔离 | 同一事件循环；减少冗余，后台同步长任务仍影响请求 | 各线程独立 V8 与事件循环；进程退出、内存总量和部分系统资源仍共享 | 独立堆和事件循环，可分别诊断退出；仍共享整机 CPU、磁盘和 SQLite |
| SQLite 连接 | 当前 server 连接；CLI、监督器仍可能与之竞争 | 每线程独立 Store／SQLite 连接，不能传递 DatabaseSync 句柄 | 每进程独立连接，数据库文件和 WAL 共用；不复制数据库 |
| 写锁与 busy_timeout | 现有 5000ms；同步等待会阻塞请求线程 | WAL 不提供多写者；后台与主线程竞争时，Web 写命令仍可能同步等锁至现有超时 | 同样只有一个写者；Web 写事务仍可能被后台写事务阻塞，进程拆分不保证所有请求即时响应 |
| 事务边界 | 本卡消除重复读取，所有 Git 等待在事务外 | 保持“短事务领取／记录 → 外部 IO → 短事务重查结算”；不能在消息往返中悬挂写事务 | 同一模式；继续用持久租约、唯一约束、Git CAS／跨进程 flock，而不是进程内 Map 保证唯一执行 |
| 通知与 SSE | 沿用按流 seq、先提交后通知 | MessagePort 只传“有更新”提示，接收方回库按游标补读；丢提示不丢事实 | IPC 同样仅作唤醒提示，可先沿用数据库轮询；断线重连按流补读，不能只依赖 IPC |
| 缓存 | 当前缓存按提交发布 | 各连接独立缓存，以事务内修订核验跨连接可见性；不共享可变对象 | 同左；内存缓存不充当持久事实，重启后重建 |
| C-201 部署／回滚 | 一个 server 的 ready、端口及身份校验保持原样；本卡无迁移 | 监督器仍管理一个子进程，但 server ready 必须覆盖 worker 初始化；worker 退出须转为明确健康故障；回滚同版本整体重启 | 监督器必须登记并管理两个精确进程身份；两个角色同一 release，任一未 ready 都不能发布；失败停止候选双方、恢复上一版本双方 |
| 实现工作量 | 小：本卡的事件增量、差异传输及回归 | 中：初步估计 4–7 个工程日，含组装拆分、消息协议、连接一致性和故障测试 | 较大：初步估计 6–10 个工程日，另需主机演练；主要增量是双进程监督、部署恢复、健康与诊断 |

工作量是设计估计，不含排队、生产观察和新的业务需求，不是工期承诺；实现前需由 PM 制定任务计划。

## 已采纳的方向与拆分边界

Q-410 已决定先合入①并复测；如仍需结构隔离，选择③，以同机两个受监督进程为后续实现方向。②节省一个操作系统进程，但仍需拆连接、通知和退出处理；对 C-201 的生命周期工作也不能省略，因此不额外实现一次线程中间形态。本卡交付增量优化及本评估，完成审核后沿现有门禁合并部署；张良在主机侧完成下节的生产复测，PM 再依据复测结果另开双进程实现卡并制定任务计划。本次拍板不改变部署入口或默认启动行为，也不跳过后续卡的审核和部署门禁。

建议边界是 Web／MCP 进程负责请求、认证、命令入口和 SSE；后台进程唯一拥有 dispatcher／RuntimeMonitor、merge／merge-check／merge-push、cleanup、reconcile、backup 和附件清理循环。HTTP 请求涉及的交付校验等异步操作仍在请求所属进程，通过同样端口执行。二者依赖 `host` 及以下包，领域规则继续在 domain 内；不新增 Agent 启动后台进程或修改主机配置的权限。

现有 SSE（`apps/server/src/web/stream.ts`）已经按各流 seq 周期性读库，而非只靠进程内广播。新线程或进程提交的事件可被下一次读取看到；保持重连补读、流内顺序和去重。容量队列 revision 已有读库路径；上下文采样等由组装层提供的内存投影必须逐项梳理，改为读取持久采样或通过明确的只读消息投影，不能把旧进程的对象引用当跨进程通知。Router、门铃和 ACK 仍以持久记录为准，消息总线不承担“恰好一次”。

双进程实现必须解决以下部署细节，不能仅追加一次 spawn：

- 用主机监督器拥有的运行互斥及既有领取事务，禁止旧、新后台同时执行；可用健康握手传递角色和部署代次，但不能由 Agent 自报 ready。
- 优雅停止先停止后台领取，等待或按原协议结算在途 IO，再关闭连接；确认双方的 PID、boot ID、start ticks、UID 和 release 后才切换。无法确认旧后台退出时不得启动替代执行者。
- 数据迁移前停止两个旧角色；C-201 的数据库备份覆盖 WAL，沿用部署与合并检查容量互斥。候选双方使用同一构建及 schema；不以“Web 已 ready”提前发布。
- 保存双方身份和就绪状态，监督器崩溃重启要重查双方；任何一方异常退出需要可观测的失败与受控恢复，避免后台已死但端口仍通。日志按角色和代次区分，保持主机私有及脱敏边界。
- 回滚停止候选双方，恢复上一构建双方；数据库仍不自动覆盖。旧构建不兼容新 schema 时按 C-201 交人处理，不丢弃上线后写入的数据。

单独拆进程只能隔离后台 JavaScript 执行，无法消除 Web 同步 SQL 和写锁等待。优先压缩写事务、避免长读快照阻碍 WAL 检查点；若复测仍被同步查询／锁等待卡住，另行评估数据库调用线程化或异步请求代理。不能偷偷降低 busy_timeout、放宽事务内权限重查或引入未拍板的超时／重试数值。

## C-248：双进程实现

生产入口拆为 `apps/server/dist/bin.js`（Web/MCP）与 `background-bin.js`（后台），由 C-201 主机监督器从**同一个**已核验 release 启动。直接执行前者现在只启动请求端；生产应使用监督器管理整组。嵌入式 `startCardiganServer` 未传角色时保留旧装配兼容，仍与独立后台共用文件互斥，不作为新生产部署方式。

| 唯一归属 | 工作与写入 | 另一进程如何观察 |
|---|---|---|
| Web/MCP | HTTP 认证、领域命令、交付校验及固定引用、请求触发的 HostOps 意图；运行时登记仅在监听成功后写入 | 命令提交后，后台原有 dispatcher 轮询读取事件、通知和意图 |
| 后台 | Dispatcher/RuntimeMonitor、HostOps 巡检/意图消费/自动上下文恢复、merge/check/push/shadow、cleanup、reconcile、backup、附件 GC、外部通知 | 原事务提交；MCP 按游标读库，SSE 按原 500ms 节奏补读并保持流内 seq 去重 |
| 后台采样、Web 只读 | 迁移 0029 `context_samples` 每项目原子替换最近完成的上下文观察，包括空样本；失败或停机后的迟到样本不发布 | Web 每次读持久投影，继续按原新鲜度过滤及现有执行视图的会话代次规则；Dispatcher 的活动样本仍由后台自身消费 |

上游连接探测由后台唯一采样，迁移 0030 `upstream_probe_samples` 持久化每个 provider 最近完成的状态、检查时间、失败类别及最近失败时间。样本绑定 provider、线路分组、显式探测目标和原探测参数的配置摘要；库中不存探测 URL、请求内容或凭据。采样 IO 完成后以单条原子写发布，Web/MCP 的 HostOps 诊断、恢复预检和后台执行前重查读取同一事实。相同状态的再次完成也刷新样本，不依赖是否新增 `upstream_probe_changed` 事件；独立连接和重启均可见。沿用原 `stale_after_ms`，过期或来自未来的时间仍为 unknown，目标/配置不匹配不复用；恢复后的样本保留最近失败时间，不改变原故障恢复或权限规则。

V-1322 发布失败边界：后台在探测 IO 前，先在原 JSON 投影内以独立发布身份标记本轮未完成；短事务中无网络等待。只有标记成功才开始网络探测，写标记失败时不做新探测，后台通过既有 classification_failed 关闭恢复资格。完成的结果先留在内存，再按同一发布身份提交；发布失败经现有主机观察错误回调报告固定诊断，不回显SQLite异常或私有内容，且不会丢已知不可达及最近失败时间，下一轮原周期完成的可达样本也携带这段失败历史。未完成标记在数据库中保留，所以可读该库的 Web/后台均不会将旧成功样本当成完整新事实：诊断标为分类不可用、相关线路恢复等待，reconcile 不产生假恢复事件，后台停止前的真实预检同样拒绝执行。数据库若不可读，读取失败也不能返回可恢复结论；标记尚未建立时独立读者仍可能看到原有效样本，但没有新探测结果，后台本地失败关闭仍阻止实际恢复。

发布身份只用于技术提交归属，过期提交和取消不能覆盖另一轮，既不进入领域探测/事件内容，也不对 Agent 返回。正常关闭取消尚未完成且此前干净的本轮 IO 时，只撤销自己拥有的标记，恢复原已完成样本，不捏造一次失败；已经有未发布结果的标记不能借关闭清掉。若进程重启失去这段未发布结果，保守保持分类不可用，下一次可达不能证明被遗失的故障不存在；之后新确认的不可达提供真实的较新失败界限，才可按原规则继续发布/恢复。这里不增加自动清除时长、探测/重试周期或权限，也不伪造失败时间。持久标记沿用原 JSON 表，无新增迁移编号。


两个进程各自打开同一 SQLite/WAL，保留 `busy_timeout=5000`，每次写事务仍只允许一个写者。既有 `command_versions` / 事件增量缓存在事务快照内核验跨连接修订，不依赖进程内提交通知；不增加 IPC 业务事件总线。所有外部 IO 仍在事务外，原循环间隔、容量、租约、退出与重试规则不变。进程拆分没有消除同步 SQL 或写锁等待，也不是账号权限隔离。

后台及兼容的单进程装配在启动循环前持有 `<dataDir>/locks/background.lock`，直到所有循环和采样任务排空；使用既有 flock 获取方式及监督器相同的 1ms 获取预算，不重试启动另一执行者。进程异常退出由内核释放描述符，未知退出仍不能凭锁可获得而跳过监督器身份核验。原仓库锁、检查领取、树与原锁绑定不变。

监督器状态保留 Web 的 `process` 和后台的 `background` 两份 boot ID/PID/start ticks，公共 `running` 绑定同一 SHA/release。启动通过继承的专用 IPC 通道握手：先保存子进程身份，才允许入口打开数据库、迁移或启动循环；握手前失去父通道立即退出。业务提交不走该通道。双方 ready 必须声明各自角色和 `deployment_fence=2`，Web 另外核对两个固定回环端口。监督器先放行 Web，只有该精确进程的 ready 与两监听端口核验通过，才派生并放行后台；两阶段共用原一次 `ready_timeout_ms` 预算，Web 重试/失败期间不启动后台循环。监督器核对双方 UID、Node 可执行文件、release cwd 及指定入口 argv；按持久身份查 `/proc`，不扫描进程命令行寻找目标。

任一角色退出，即使 Web 端口仍通也记失败并交原主机恢复策略；持久状态保留另一方身份。恢复不完整候选或半组进程时先验证存活方，再停止整组，确认双方退出后才启动已部署版本整组。监督器 CLI 用 `Store.open({ migrate: false })` 只打开既有 schema，不在接管时抢先应用新 release 的迁移；保留正常 WAL/超时配置及缓存修订核验。数据库备份仍在旧双方停止后、新双方启动前，迁移由候选角色启动时执行。候选后台未 ready 也必须停止候选双方并整体回滚；回滚不覆盖数据库。旧 release 没有后台入口时，监督器只接受原 `deployment_fence=1` 单进程握手，用于既有构建接管/回滚，不能把新入口的缺失误当作双进程就绪。

Web 在 HTTP/认证日志路径同步人设置的 tick-profile 开关，后台继续在原 tick 边界同步；无需重启，也不增加轮询数值。

日志继续使用原每代串行轮转 sink，两个角色共用现有单文件/总份数/待写预算，源输出行增加固定 `[web]` / `[background]` 标识（跨块行不插入额外标记，处理计时 JSON 前先去掉行首标记），不增加日志容量。原始内容仍仅在主机私有目录；公开失败诊断只含原白名单代码和各角色退出状态。
