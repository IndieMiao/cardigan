## 默认信息层级

1. 来源人员、拍板与卡片编号、问题标题。
2. 标题下一个状态条：是否阻塞后续、暂缓至何时、当前等谁、合并检查结果。只有实际暂缓时出现到期标签。390px 按信息组换行，仍是同一容器，不拆成独立面板。
3. C-202 概述，固定顺序为“改了什么 / 对你的影响 / 风险”。这是第一个正文区块。三个字段不做行数裁剪；`risk` 非“无”时加粗并使用警示色。“未提供”与“无”必须区分。
4. 影响判断的例外事项、建议及操作。Q-337 保留“合并后：升级 PM、独立复核员两个角色”，步骤入口展开交付说明；这是额外的实际工作，不能跟标准四步一起藏掉。
5. 补充说明、交付详情、审核与验收、上下文原文、操作说明默认折叠。已知遗留仅在明确为 0 项时默认折叠；非空或资料未知时默认展开，规则见下表。桌面证据入口两列，窄屏单列；展开后占整行。

“建议”默认只显示选项与一句依据，不重复三段概述。有效建议按钮直接标动作“按建议：确认合并 / 退回修改”，直接“确认合并”降为次按钮；无建议时“确认合并”为主按钮。四种操作的记录方式、原话和服务端校验沿用原逻辑，不把两种确认合成同一提交。“操作说明”内补一句：两种确认都会记录人的合并决定，前者另记为采纳建议。

## 状态条和异常组合

以下用 `｜` 仅表示并列的视觉分组，界面不显示该字符。状态配合图形与中文，不只用颜色。阻塞后续与非阻塞均用中性色加 ◇，表示拍板属性；待处理/暂缓用等待色；运行用进度色；通过用完成色；失败用危险色。不得用编号类型色表示状态。

| 情境 | 标题下的短标签 | 默认保留的关键内容或动作 |
|---|---|---|
| 人确认、检查通过 | 阻塞后续｜等你确认｜合并检查：已通过 | 概述、风险、建议、按钮 |
| 非阻塞拍板 | 非阻塞｜等你确认｜合并检查：已通过 | 不因为检查通过而改变是否阻塞的标签 |
| PM 持有 | 阻塞后续｜PM 代确认中｜你可直接处理｜合并检查：已通过 | 保留人的处理按钮；不计入人的待办数量 |
| PM 暂缓 | 阻塞后续｜已暂缓至 MM-DD HH:mm｜PM 暂缓中｜你可直接处理｜合并检查结果 | 原始暂缓原因；不另写一段 PM 接管教程 |
| 人暂缓 | 阻塞后续｜已暂缓至 MM-DD HH:mm｜等你确认｜合并检查结果 | 原始暂缓原因；检查仍运行时也按现有规则可见 |
| 暂缓到期 | 阻塞后续｜暂缓已到期｜等你确认｜合并检查结果 | 原暂缓原因；到期事实来自服务端，不由前端改变状态 |
| 排队 / 运行 | 阻塞后续｜等你确认｜合并检查：排队中 / 运行中 | 人的普通确认在 Needs You 只进等待检查汇总；详情仍有原操作 |
| 核对未完成或旧版失效 | 阻塞后续｜等你确认｜可提前确认｜合并检查结果 | 具体缺项、失效原因展开；人的确认入口及原二次确认保留 |
| 检查失败 / 超时 | 阻塞后续｜等你处理｜合并检查：未通过 / 超时 | 必须修复问题、失败摘要展开；重新检查、退回等按原条件显示 |
| 已确认后失败 | 阻塞后续｜等你处理｜合并检查：超时｜已确认合并 | 不重复确认或暂缓；保留重查、退回入口 |
| 中断 / 主机不可达 | 阻塞后续｜等主机恢复｜合并检查：已中断 / 执行主机不可达 | 短句“等主机恢复后自动重新排队”；不冒充代码失败 |
| 配置无效 | 阻塞后续｜等主机处理｜合并检查：配置无效 | 原固定错误提示；没有重查入口，不显示“排队” |
| 主机验证 noop | 阻塞后续｜等你确认｜合并检查：无需检查 | “交付均在基线中”必须由主机事实支持，不伪装为通过 |
| 项目未启用检查 | 阻塞后续｜等你确认｜合并检查：未启用 | 不显示“检查通过后才会合并”；不假造通过结果 |
| 卡级检查通过 | 阻塞后续｜等你确认｜合并检查：卡级检查已通过 | “卡级检查不含端到端检查”；保留“确认合并（批次检查通过后生效）” |
| 建议过期 | 状态条按当前真实状态 | 标“已过期”，隐藏按建议处理，保留直接操作；不自动套用旧建议 |

“阻塞后续”只转述拍板的 `blocking`（并沿用 `followup_notice` 的原展示排除），不是前端计算出来的合并许可。“核对已完成”只代表前置核对，不替代合并检查或合并成功。状态条、按钮可用性、PM/人归属、Needs You 分组都使用原有领域读模型；排队、失败、暂缓等展示时机沿用 §8.2，不因原型有切换器而把所有情境塞进人的待办。

暂缓时间按浏览器本地时区显示日期与时分；完整年份与时区保留在 `time` 的可读描述中。跨日不只写“到 10:30”。原型 Q-332 的 `10:21 UTC` 在本次截图时区显示为 `11-13 18:21`（UTC+08:00）。缺失到期时间显示“暂缓中（到期时间未知）”，不造倒计时。原有自动合并时间如果存在，仍在状态区可见，不能折入教程；它与暂缓时间使用不同标签。

Q-332 专门处理文案与归属不一致：状态条写“PM 暂缓中 / 你可直接处理”，检查仍写“已通过”，暂缓原因原样保留。用户可在“暂缓原说明”查看 PM 的“等截图核对通过后交人确认，不由我代确认”。不从这段自由文本推断 `decider=human`、不显示“等你必须确认”、不自动转交；是否已转交由结构化事实决定。原型的 Q-332 区块仅证明层级与状态文案，缺失的业务概述不用于模拟一个完整可决策案例。

## 哪些内容不能因折叠而消失

| 内容 | 默认处理 |
|---|---|
| 风险字段、必须修复问题、强制交人原因 | 概述或异常短块完整显示，正文不截断 |
| 未完成 / 失败 / 过期的合并前核对 | 显示具体项和原因；完整核对列表仍可展开 |
| 检查失败摘要、无效配置、自动合并时刻 | 状态条或邻近异常区可见，日志正文折叠 |
| 阻塞合并的人工事项、遗留的前置条件 | 将必要原文提到风险区，链接回完整事项；不以折叠的“遗留 N 项”代替 |
| 已知遗留明确为 `[]` | 默认折叠，摘要显示“已知遗留 0 项” |
| 已知遗留非空（含与 `risk` 相同的内容） | 默认展开全部原文，摘要显示“已知遗留 N 项”；不去重、不截断、不解析重要性 |
| 已知遗留字段缺失、`null` 或资料未取得 | 默认展开“遗留资料未提供，不能视为无遗留”，摘要显示“资料未提供”；不得当作 0 项 |
| 决策引用的关键截图 / 附件 | 在概述之后、按钮之前保留原缩略图与打开入口；其余附件归入详情 |
| 概述缺失的旧记录 | 显示“尚未提供改动概述 / 风险尚未说明”，交付原文自动展开；不从通过状态推断无风险 |
| 标准四步操作 | 一个“操作说明”折叠行；默认没有编号教程 |
| 非标准动作，如合并后的角色升级 | 展开一句动作及步骤入口；实际命令在原交付中，本例不补造 |

遗留仅按数据是否完整与数组长度判断；本版不采用“非关键遗留”或“可靠概述”等无法机械判定的分支，也不因 `risk` 相似而收起。用户可以手动收起；此时仍显示项数，独立的关键风险与阻塞事项仍留在顶部。原型 `noGaps`、`differentGaps`、`handoff` 分别覆盖明确 0 项、与风险不同的两项原文和资料未知。实际产品按接口的完整性契约区分缺失与空列表，不从未摘录资料推断不存在。

上述升格内容应使用已有字段与原文；本卡不新增业务分类器或要求解析自由文本。C-202 的 `changed/impact/risk` 若尚未集成，开发先等待依赖合并，再对齐实际接口，不以本原型对象名代替接口设计。

## 卡片详情与交互

卡片页头固定为“卡片编号 + 完整标题 → 同一个状态条 → 关键风险”。标题不省略；状态条每组为短标签，390px 按组换行。关键风险紧随状态条全文显示；有合并确认时，将其 `risk` 提到这里，后面的概述保留“改了什么 / 对你的影响”，不重复同一风险。

| 详情情境 / 原型参数 | 页头状态条 | 关键内容与入口 |
|---|---|---|
| 有合并确认 `ready` | 待合并｜阻塞后续｜等你确认｜下一步：确认合并｜合并检查：已通过 | C-199 编号和真实完整标题；Q-337 的风险、概述、建议及操作 |
| 等审核 `cardReview` | 审核中｜等妙玉审核｜下一步：完成设计审核 | 风险“窄屏与暗色布局尚待设计审核”；“查看待审交付”展开当前交付入口，无合并区 |
| 人工待办阻塞 `cardBlocked` | 进行中｜人工待办阻塞｜等你处理｜下一步：补齐截图 | 风险“缺少窄屏截图，设计审核暂不能继续”；“查看人工待办”展开事项，无合并区 |

后两例使用 C-205 的真实编号、标题和工作项，但状态、人工待办与风险均为**假设数据**，页头及页尾明确标为状态示意，不冒充当前或历史事实。`cardBlocked` 的卡片状态仍是 `in_progress`，没有新增 `blocked` 卡片状态。Q-332 的 C-197 标题未摘录，原型明确标明，产品始终使用真实 `card.title`。

开发映射：卡片状态用 `card.status` 的现有中文映射；“等谁”读取 `waiting_on` 与 `next_owners` 的结构化对象，人员按现有引用解析名称，未指派显示岗位；下一步使用同一对象类型及既有状态的展示短标签（审核 → 完成审核、人工待办 → 处理事项、待合并 → 处理合并确认），本例“补齐截图”取自示意人工事项标题。只有自由文本 `why` 时保持原文在邻近说明中，不从正文猜负责人、权限或新的状态；缺少可信来源显示“待明确”。多个并列等待项逐组显示，不任意择一。

有合并确认时只渲染一个合并后的状态条：在卡片状态与下一步旁加入确认的阻塞属性、暂缓和检查结果；处理方只显示一次。随后是拍板问题、概述及原有操作，不在拍板正文再渲染第二条状态。没有确认时也保留完整页头，不产生合并按钮。目标与逐条验收、工作项/关联/附件可展开；时间线仍是正文，执行视图在其后默认折叠。导航和“查看”入口先展开目标再定位。编辑、敏感标记、取消等既有控制由开发保留原入口与权限。

- 使用原生 `details/summary`：Tab 可达，Enter/空格切换，读屏可获知展开状态。关键动态变化通过既有反馈播报；整张卡不做持续 `aria-live` 播报。
- 只在现有规则要求时二次确认。未完成核对的弹窗默认焦点落在取消按钮，Escape 关闭并还给触发按钮；原型没有给普通确认增加新弹窗。
- 暂缓、退回原因必填，空白不能提交；暂缓时间可选，默认值、上限和错误仍由原服务端处理。折叠或取消保留同页草稿；失败不清空内容、不换目标版本。原型只模拟同页草稿，不声称验证了真实刷新或服务端拒绝。
- 建议退回时预填原因，用户修改后不被新到的建议覆盖；建议过期无一键按钮。请求中沿用原 busy 状态及防重复提交。已确认后失败仍使用原操作条件。
- 窄屏按钮最小高 44px，按原顺序换行，不横向滚动，不固定悬浮挡住风险。正文不通过缩小字体换取高度。
